## 4. 고정 인증 아키텍처

기본 구현안은 기존 PostgreSQL이 위치한 Supabase의 **Supabase Auth**를 신원 공급자로 사용한다. 비밀번호 해시를 애플리케이션 DB에 직접 저장하거나 자체 비밀번호 인증 체계를 새로 만들지 않는다.

### 4.1 인증 흐름

1. Web은 `POST /backend-api/auth/login`으로 이메일과 비밀번호를 보낸다.
2. NestJS의 `AuthService`가 서버 환경에서 Supabase Auth의 password sign-in을 호출한다.
3. 성공 시 Supabase access token과 refresh token을 브라우저 JavaScript에 반환하지 않고 API가 쿠키로 설정한다. 별도로 임의성이 충분한 `AppAuthSession.id`를 HMAC 서명한 opaque HttpOnly session-handle cookie를 발급한다. raw provider token이나 provider session_id를 handle에 넣지 않는다.
4. 쿠키는 운영에서 `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, `Domain` 미지정으로 설정한다. `/backend-api` 프록시를 사용하므로 `Path=/api`를 사용하면 안 된다.
5. 모든 API 요청에서 `AuthGuard`가 access JWT의 서명, issuer, audience, expiry, `sub`, `session_id`를 검증한다. 검증은 직접 암호 구현을 하지 않고 검증된 라이브러리와 Supabase JWKS를 사용한다.
6. JWT의 `sub`를 `AppUser.authUserId`와 연결하고, 매 요청마다 DB의 `isActive`, onboarding 상태, 현재 역할을 확인한다. JWT 안의 애플리케이션 역할을 권한의 최종 근거로 사용하지 않는다.
7. raw token이 아닌 provider `session_id`만 저장하는 `AppAuthSession`을 두고 매 요청 활성 상태를 확인한다. login/refresh 시 session row를 만들거나 갱신하고 logout·비활성화 시 `revokedAt`을 기록한다. Supabase refresh token 폐기 뒤에도 만료 전 access JWT가 재사용되는 문제를 앱에서 즉시 차단한다.
8. access token 만료를 나타내는 안정된 `ACCESS_TOKEN_EXPIRED` 코드에서만 Web이 `POST /auth/refresh`를 한 번 호출하고 원 요청을 한 번만 재시도한다. refresh token 회전 결과를 새 쿠키로 교체한다.
9. refresh/logout은 access cookie가 없거나 만료돼도 서명된 session handle로 AppAuthSession을 식별·lock·폐기한다. 로그아웃은 현재 AppAuthSession을 먼저 폐기하고 Supabase 세션 폐기를 시도한 뒤, 성공 여부와 무관하게 모든 인증 cookie를 삭제하며 Web의 React Query 캐시도 전부 비운다.

Supabase는 JWKS 기반 JWT 검증 방법과 서버 측 초대 API를 공식 제공한다. 구현 세션은 당시 최신 공식 문서를 다시 확인해야 한다.

- [Supabase JWT 공식 문서](https://supabase.com/docs/guides/auth/jwts)
- [Supabase 사용자 초대 공식 문서](https://supabase.com/docs/reference/javascript/auth-admin-inviteuserbyemail)
- [Supabase 사용자 관리 공식 문서](https://supabase.com/docs/guides/auth/users)
- [Supabase 이메일 템플릿 공식 문서](https://supabase.com/docs/guides/auth/auth-email-templates)

### 4.2 계정 정책

- 공개 회원가입은 만들지 않는다.
- 게스트도 익명 방문자가 아니라 총관리자가 초대한 로그인 계정이다.
- 일반 로그인은 이메일과 비밀번호만 사용한다. OTP, passwordless 로그인, MFA/2차 인증은 이 계획 범위에 포함하지 않는다.
- Supabase JWT가 유효해도 대응하는 활성 `AppUser`가 없으면 `403 ACCOUNT_NOT_PROVISIONED`로 거부한다.
- 초대 중인 사용자는 `InviteStatus.ACTIVE`가 되기 전까지 일반 업무 API를 사용할 수 없고 초대 확인·비밀번호 설정·로그아웃·최소 `/auth/me`만 사용할 수 있다.
- `InviteStatus`는 `PENDING_PROVIDER → INVITED → VERIFIED_PENDING_PASSWORD → ACTIVE` 정상 경로와 `RECONCILE_REQUIRED`, `CANCELLED` 예외 상태로 고정한다. email/authUserId는 DB unique constraint로 보호한다.
- 초대는 Supabase의 서버 전용 `inviteUserByEmail`과 이메일의 일회용 초대 링크를 사용한다. email template은 `/invite/accept#token_hash={{ .TokenHash }}` 형태의 앱 링크를 사용해 token hash가 서버 query log에 들어가지 않게 한다. 사용자는 OTP를 입력하지 않으며 링크를 명시적으로 수락한 뒤 최초 비밀번호를 설정한다. 초대 링크의 일회용 token hash는 초대 승인 값일 뿐 일반 로그인이나 2차 인증에 사용하지 않는다.
- 초대 링크는 앱 landing page에 도착한 것만으로 소비하지 않고 사용자의 명시적 수락 POST에서 서버가 검증한다. token hash는 즉시 URL에서 제거하고 localStorage, analytics, logger, audit에 저장하지 않는다.
- v1에는 공개 signup, password reset을 만들지 않는다. 만료·실패 초대는 provider identity와 로컬 상태를 재검증한 뒤 총관리자가 재초대 또는 취소한다.
- `SUPER_ADMIN`만 사용자 초대, 역할 변경, 활성/비활성 변경을 할 수 있다.
- 사용자는 hard delete하지 않고 `isActive=false`로 비활성화한다.
- 마지막 활성 총관리자는 강등하거나 비활성화할 수 없다.
- 자기 자신을 실수로 잠그는 작업도 서버에서 보호한다.
- Supabase secret key는 API의 secret 저장소에만 두고 Web, `NEXT_PUBLIC_*`, 응답, 로그에 절대 노출하지 않는다.
- 로그인 실패 메시지는 계정 존재 여부, 비활성 여부, 비밀번호 오류를 외부에 세분화해 알려주지 않는다.
- access JWT 만료는 `ACCESS_TOKEN_EXPIRED`, 폐기/무효 session은 `SESSION_REVOKED` 또는 `SESSION_INVALID`, 비활성 계정은 `ACCOUNT_INACTIVE`, onboarding은 `ACCOUNT_ONBOARDING_REQUIRED`, 일반 권한 부족은 `PERMISSION_DENIED`로 구분한다. 프런트는 만료만 refresh하고, session/계정 오류는 캐시를 제거하며, 일반 403은 `/auth/me`를 한 번 갱신한 뒤 권한 UI를 다시 계산한다.

### 4.3 CSRF와 캐시

쿠키 인증을 사용하므로 상태 변경 요청은 `SameSite`만 믿지 않고 허용 Origin 검증과 CSRF 방어를 적용한다. 인증/쿠키를 설정하는 응답은 `Cache-Control: private, no-store`로 처리한다. 사용자별 응답이나 `Set-Cookie` 응답을 CDN이 공유 캐시하지 않게 한다.

| `/uploads/*` 업로드 POST와 DELETE | `imports.manage` |
| `/sales/cafe24/uploads` POST와 DELETE | `imports.manage` |
| `/coupang/uploads/*` POST와 DELETE | `imports.manage` |
| `/mappings/product-rules`, `/mappings/product/manual`, `/mappings/stage/manual`, `/mappings/rematch` POST | `mappings.manage` |
| `/sales/cafe24/rules` POST/PATCH/DELETE와 `/sales/cafe24/rematch` | `mappings.manage` |
| `/coupang/mapping-rules` POST/PATCH/DELETE와 `/coupang/rematch` | `mappings.manage` |
| `POST /decisions/run` | `operations.run` |
| `/coupang/manual-purchases` PUT/DELETE | `operations.run` |
| 전역 `PATCH /settings/:key` | `settings.manage`; ADMIN에게 동적 key endpoint를 열지 않음 |
| `PATCH /settings/products/coupang-manual-purchase-vendor-fee` | `products.manage`; server가 고정 key만 갱신하는 제품 도메인 endpoint |

모든 활성 handler는 `@Public`, `@InternalProbe`, `@Authenticated`, `@RequirePermissions(...)` 중 하나가 명시되어야 한다. `@InternalProbe`는 readiness처럼 hosting 내부 probe만 위한 별도 분류이며 일반 인증/public 우회로 재사용하지 않는다. 어떤 metadata도 없는 handler는 전역 Guard가 거부하고 자동 테스트도 실패해야 한다. 이는 OWASP의 기본 거부 및 매 요청 권한 검증 원칙을 따른다: [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).

## 7. 중복 구현 방지와 재사용 원칙

### 7.1 API

- 역할→권한 매핑, 권한 검사, JWT 검증, 현재 사용자 추출은 각각 한 군데만 둔다.
- 각 컨트롤러에서 역할 문자열을 비교하지 않는다.
- `createdBy`, `updatedBy`를 body에서 받지 않고 `@CurrentUser()`가 제공한 `AppUser.id`를 서비스에 전달한다.
- 인증/role/session/onboarding 판단은 `AppUser`와 `AppAuthSession` 중앙 조회에서 수행한다. 각 Guard나 서비스가 서로 다른 상태 판정을 만들지 않는다.
- 서비스의 기존 날짜·enum·업무 의미 검증은 DTO 도입 뒤에도 방어 계층으로 유지한다.
- 활성 `/settings` 구현은 `apps/api/src/products/settings.controller.ts`다. `apps/api/src/settings/*`는 현재 AppModule에 등록되지 않은 중복이므로 새 세 번째 구현을 만들지 않는다.
- Coupang 기본 업체 수수료는 동적 `PATCH /settings/:key`를 재사용해 ADMIN에게 열지 않는다. 같은 활성 SettingsController에 명시적 `PATCH /settings/products/coupang-manual-purchase-vendor-fee` handler를 두고, 기존 ProductsService/AppSetting 저장 함수를 fixed key로 호출한다. Web도 이 새 경로만 사용한다.
- 기존 `UploadStorageService`의 파일명 정규화와 저장 루트 이탈 방지 로직을 공통 Storage 구현으로 승격한다.
- `ApiExceptionFilter`의 안정적 오류 payload 형태는 유지하되 내부 오류 메시지와 Prisma meta 노출은 제거한다.

### 7.2 Web

- 실제 layout은 `apps/web/src/app/providers.tsx`와 소문자 `apps/web/src/components/app-shell.tsx`를 사용한다.
- 대문자 `components/Providers.tsx`, `components/AppShell.tsx` 등의 중복 파일을 잘못 수정하거나 세 번째 Provider/AppShell을 만들지 않는다.
- `api.ts` 내부에 단일 `apiRequest`를 만들고 JSON, FormData, 다운로드, 204, 401, 403, CSRF 처리를 중앙화한다. 기존 `apiGet/apiPost/apiPatch/apiPut/apiDelete` 공개 함수는 가능한 유지한다.
- API 계층은 auth lifecycle event만 발행하고 AuthProvider가 QueryClient clear/refetch와 redirect를 소유한다. `ACCESS_TOKEN_EXPIRED`만 refresh하며 session invalid/revoked/inactive는 전체 cache 제거, onboarding은 전용 화면, permission denied는 `/auth/me` 1회 갱신으로 처리한다.
- 한 탭의 Promise single-flight뿐 아니라 `BroadcastChannel`/Web Locks와 서버 AppAuthSession DB lock을 함께 사용해 여러 탭의 refresh 회전을 조정한다.
- `/auth/me`의 opaque `authorizationVersion`을 focus/reconnect/보호 route 재진입/짧은 visible refetch에서 확인하고, 변경 시 모든 탭의 사용자 cache와 권한 UI를 재동기화한다. 서버 권한 차단은 이 주기와 무관하게 매 요청 즉시 적용된다.
- `/auth/me` 한 번으로 사용자와 계산된 permissions를 얻고 `useCan(permission)`과 `PermissionGate`를 재사용한다.
- 로그아웃·계정 전환 시 QueryClient 전체 캐시를 비운다.
- 조회와 편집이 결합된 화면은 페이지 전체를 숨기지 말고 `readOnly`/`canManage`로 쓰기 폼과 action 열만 제거한다.

### 7.3 감사·파일·운영 공통 계약

- 사용자/역할/상태와 중요 제품 삭제·비활성화, 설정, upload 삭제, mapping 변경은 모두 append-only 보안 감사 대상이다. 로컬 mutation과 SUCCESS audit는 같은 DB transaction으로 처리한다.
- Meta에서 현재 보존하던 원본 외에 Cafe24/Coupang 원본 파일을 보안 작업을 이유로 새로 영구 저장하지 않는다. 별도 보존은 개인정보·retention·비용 승인 뒤에만 한다.
- 다중 API instance의 rate limit은 atomic distributed store를 사용한다. memory store라면 단일 instance 고정과 우회 불가를 증명한다.
- staging에서 DB restore뿐 아니라 object 삭제·복원/hash 검증, maintenance edge rollback, release artifact/runtime proxy 구성을 실제로 연습한다.
- 운영은 RPO/RTO와 PITR 또는 snapshot 이후 write ledger/reconciliation이 없으면 쓰기를 재개하지 않는다.

### 7.4 공유 계약

서버가 permissions 배열을 반환하므로 프런트에서 역할→권한 매핑을 복제하지 않는다. `packages/shared`를 실제 양쪽 런타임 의존성으로 바꾸려면 CommonJS/ESM 및 build 경로를 먼저 해결해야 하므로, 그 작업만을 위해 빌드 구조를 무리하게 변경하지 않는다. 공통 응답 타입을 공유할 때는 기존 build가 깨지지 않는지 먼저 확인한다.

### 7.5 계획서 실행 원본

1단계 전에는 원본 폴더의 계획서가 bootstrap 원본이다. 1단계가 계획 bundle을 보안 worktree에 복사하고 bundle hash/버전을 기록한 뒤부터는 **보안 worktree 안의 계획서와 진행상태가 단일 실행 원본**이다. 2단계 이후 세션은 원본 폴더의 복사본이 아니라 worktree 안의 문서를 읽는다. 계획 변경이 필요하면 보안 branch의 문서를 commit하고 진행상태에 이유를 남긴다.

## 9. 세션 공통 완료 조건

각 단계 종료 전에 최소한 다음을 수행한다.

```powershell
npm.cmd run prisma:validate
npm.cmd run lint
npm.cmd run test
npm.cmd run build
git diff --check
git status --short --branch
```

- 단계가 건드린 기능에 대한 신규 테스트가 있어야 한다.
- 기존 전체 테스트·lint·build가 통과해야 한다.
- 실패를 “기존 문제”라고 주장하려면 1단계 기준선 기록으로 증명해야 한다.
- 평가자 발견사항은 식별자, 심각도, 파일/경로, 재현 절차, 기대/실제 결과를 포함한다.
- 개발자는 발견사항을 수정하고 평가자는 같은 항목과 전체 회귀를 다시 검증한다.
- P0/P1/P2 열린 결함이 0개가 될 때까지 완료로 처리하지 않는다. P3도 계획 범위 내 결함이면 수정하고, 범위 밖이면 잔여 위험에 명시한다.
- 메인 에이전트만 Git index와 commit을 조작한다. 하위 에이전트는 commit하지 않는다.
- 사용자가 단계 실행 프롬프트에서 commit을 명시적으로 허용한 경우에만 commit을 만든다.
- commit SHA는 자기 자신을 포함하는 같은 commit에 기록할 수 없으므로 단계마다 두 commit을 사용한다. 먼저 구현 commit을 만들고, 그 SHA·검증 결과를 `진행상태.md`에 기록한 뒤 handoff 문서 commit을 만든다. handoff commit은 자신의 SHA를 문서 안에 쓰지 않으며 다음 단계가 시작 HEAD로 기록한다.
- `보안단계별적용/진행상태.md`에 단계, 시작 commit, 구현 commit, migration 이름, 변경 파일, 실행 명령과 결과, 평가 루프 횟수, 남은 위험, 다음 단계 전제조건을 기록한다.
- 최종 handoff commit 뒤 worktree가 clean이어야 단계가 완료된다.

## 10. 아직 외부 승인이 필요한 결정

아래 항목은 계획에서 임의 확정하지 않는다.

- 실제 도메인과 DNS 변경
- 운영/스테이징 호스팅 사업자와 과금 리소스 생성
- 운영 객체 저장소 사업자와 bucket 생성
- Supabase Auth 운영 설정, secret key 등록, 초대 메일 SMTP/템플릿
- 2단계 착수 전 Supabase Auth를 신원 공급자로 사용하는 것 자체에 대한 사용자 승인
- 사용자가 직접 언급하지 않은 upload/import, mapping/rematch, decision/manual-purchase, 새 server report 생성의 역할 배정은 현재 권한표의 제안대로 ADMIN/USER에 줄지 1단계에서 최종 승인
- 운영 비밀값 회전
- 운영 유지보수 시간과 배포 승인
- 운영 DB backup/snapshot 또는 dump 실행
- 운영 RPO/RTO, PITR 또는 snapshot 이후 write reconciliation 정책
- release tag와 private remote push/encrypted git bundle 등 외부 source backup
- DNS TTL/TLS 전환·rollback rehearsal

7~9단계에서 이런 결정이 필요하면 세션은 코드로 우회하지 말고 정확한 선택지와 영향을 사용자에게 보고하고 승인을 기다린다.

# 새 세션 실행 프롬프트

아래 프롬프트는 사용자가 제안한 방식을 보완한 것이다. 핵심 개선점은 실제 작업 경로를 원본이 아닌 보안 worktree로 고정하고, 하위 에이전트의 파일 소유와 평가 루프, Git/DB 금지사항, 단계 완료 증거를 명시한 점이다.

## 1. 1단계 전용 프롬프트

```text
다음 두 파일을 처음부터 끝까지 읽어라.

C:\Users\seong\Desktop\workspace\Meta-Ads-Performance\보안단계별적용\00_전체요구사항과실행순서.md
C:\Users\seong\Desktop\workspace\Meta-Ads-Performance\보안단계별적용\0811작업단계1.md

현재 업무용 원본 경로는 C:\Users\seong\Desktop\workspace\Meta-Ads-Performance 이다. 이 폴더의 main 브랜치, 소스, .env, 실행 중인 업무 프로그램은 절대로 전환·수정·중단하지 마라. 계획서에 따라 별도 Git worktree와 codex/security-rbac 브랜치를 만들고, 이후 변경과 명령은 오직 계획서가 지정한 보안 worktree에서 수행하라. 운영 DB, 운영 schema, 운영 업로드·보고서 폴더, 원본 .env를 개발이나 테스트에 사용하지 마라.

먼저 저장소 구조와 현재 Git 상태를 직접 확인하고 계획을 갱신하라. 그런 다음 서브에이전트를 최소 2개 사용하라. 사용 가능한 가장 높은 reasoning_effort를 사용하고, reasoning override 때문에 필요하면 fork_turns="none"으로 생성한 뒤 읽어야 할 절대경로를 메시지에 전달하라.

최소 역할은 다음과 같다.
1) 개발/환경 담당: 계획서 범위의 구현과 테스트
2) 독립 평가 담당: 구현 전에는 평가표와 공격·회귀 테스트를 준비하고, 구현 후 diff와 실제 테스트 결과를 검토

파일 소유가 겹치지 않게 배정하라. 하위 에이전트는 Git commit, push, merge, reset, clean을 하지 못하게 하고 메인 에이전트만 통합하라. 평가자는 기존 기능, 데이터 흐름, 권한 우회, DB 격리, migration 안전, 중복 API/함수, 기존 스타일, 유지보수성, 테스트 누락을 검토한다. 발견사항마다 심각도·재현 절차·기대 결과를 적어 개발자에게 전달하라. 개발자가 수정한 뒤 평가자가 같은 항목과 전체 회귀를 다시 검증한다. 계획 범위의 열린 결함이 없어질 때까지 반복하라.

destructive Git 명령, 운영 DB 명령, main 병합, push, 외부 배포, DNS 변경, 비밀값 출력은 금지한다. 계획서의 완료 조건을 모두 충족하고 전체 prisma:validate, lint, test, build, git diff --check를 통과시켜라. 사용자는 이 단계 변경의 로컬 commit 생성을 허용한다. 메인 에이전트는 먼저 단계 번호가 포함된 구현 commit을 만들고, 그 구현 SHA와 변경 파일·환경 격리 증거·테스트·평가 루프·남은 위험을 진행상태.md에 기록한 뒤 별도 handoff 문서 commit을 만들어라. handoff commit 자신의 SHA를 같은 문서에 쓰려고 하지 마라. 마지막에는 clean worktree여야 한다.
```

## 2. 2~8단계 공통 프롬프트

`<N>`을 단계 번호로 바꿔 사용한다.

```text
다음 파일을 처음부터 끝까지 읽어라.

C:\Users\seong\Desktop\workspace\Meta-Ads-Performance-security-rbac\보안단계별적용\00_전체요구사항과실행순서.md
C:\Users\seong\Desktop\workspace\Meta-Ads-Performance-security-rbac\보안단계별적용\0811작업단계<N>.md
C:\Users\seong\Desktop\workspace\Meta-Ads-Performance-security-rbac\보안단계별적용\진행상태.md

실제 코드 작업 경로는 C:\Users\seong\Desktop\workspace\Meta-Ads-Performance-security-rbac 이다. 반드시 이 worktree의 codex/security-rbac 브랜치에서만 수정하라. 원본 업무용 C:\Users\seong\Desktop\workspace\Meta-Ads-Performance 폴더의 파일, 브랜치, .env, 실행 프로세스와 운영 DB·운영 파일 저장소는 건드리지 마라.

먼저 Git 상태, worktree 목록, 현재 branch, 이전 단계 commit, 진행상태, 전체 코드 구조와 해당 단계 관련 흐름을 직접 검증하라. 이전 단계가 계획서의 선행 조건을 충족하지 않았거나 미커밋 변경이 있으면 reset/checkout/clean/stash하지 말고 상태를 분석해 사용자에게 보고하라.

서브에이전트를 최소 2개 사용하라. 가능한 가장 높은 reasoning_effort를 사용하고 필요하면 fork_turns="none"으로 생성한 뒤 계획서와 worktree 절대경로를 메시지에 제공하라. 개발 담당의 파일 소유를 겹치지 않게 나누고, 독립 평가 담당은 개발 완료 전에는 파일을 수정하지 말고 평가표와 테스트를 준비하게 하라.

개발 완료 후 평가자는 diff와 실제 실행 결과를 바탕으로 다음을 검토한다: 기존 기능과 집계 회귀, 데이터 흐름 단절, 권한 우회와 직접 API 호출, 인증/세션/CSRF, migration 및 기존 데이터 호환, 중복 API·함수·역할 비교, 코드 스타일과 유지보수성, 불필요한 리팩터링, 테스트 누락. 발견사항마다 ID, 심각도, 파일/경로, 재현 절차, 기대/실제 결과를 기록해 개발자에게 전달하라. 개발자가 수정하고 평가자가 재검증하는 루프를 계획 범위의 열린 결함이 0개가 될 때까지 반복하라. 메인 에이전트도 하위 에이전트의 결론을 그대로 믿지 말고 최종 diff와 테스트를 직접 확인하라.

선행 단계의 AuthService, Guard, permission map, CurrentUser, apiRequest, AuthProvider, PermissionGate, Storage abstraction을 재사용하고 역할 비교나 fetch/검증 로직을 새로 중복 작성하지 마라. 계획 범위를 벗어난 대규모 정리나 미사용 중복 파일 삭제는 하지 마라.

destructive Git 명령, 임의 pull/rebase, main 병합, push, 운영 migration, 외부 배포, DNS 변경, 비밀값 출력은 금지한다. 단 8단계의 최신 main 통합과 스테이징 작업은 해당 계획서와 사용자 승인 범위에서만 수행한다.

종료 전에 prisma:validate, lint, 전체 test, 전체 build, git diff --check를 실행하라. 사용자는 이 단계 변경의 로컬 commit 생성을 허용한다. 메인 에이전트만 단계 번호가 포함된 구현 commit을 만들고, 그 구현 SHA와 migration·변경 파일·테스트·평가 루프·해결 결함·남은 위험·다음 단계 조건을 진행상태.md에 기록한 뒤 별도 handoff 문서 commit을 만들어라. handoff commit 자신의 SHA는 다음 단계가 시작 HEAD로 기록한다. 최종 worktree는 clean이어야 한다.
```

## 3. 9단계 운영 전환 프롬프트

9단계는 실제 운영 쓰기·외부 변경이 있으므로 승인 경계를 더 엄격하게 둔다.

```text
다음 파일을 처음부터 끝까지 읽어라.

C:\Users\seong\Desktop\workspace\Meta-Ads-Performance-security-rbac\보안단계별적용\00_전체요구사항과실행순서.md
C:\Users\seong\Desktop\workspace\Meta-Ads-Performance-security-rbac\보안단계별적용\0811작업단계9.md
C:\Users\seong\Desktop\workspace\Meta-Ads-Performance-security-rbac\보안단계별적용\진행상태.md

실제 작업 경로는 C:\Users\seong\Desktop\workspace\Meta-Ads-Performance-security-rbac 이다. 우선 읽기 전용 사전점검과 배포 체크리스트 작성만 수행하라. 운영 DB migration, 운영 backup/snapshot, 운영 secret 변경, 외부 호스팅 배포, DNS 전환, main 병합, push처럼 외부 상태를 바꾸는 각 작업은 계획서의 승인 게이트에 도달하면 정확한 대상·명령·영향·롤백 방법을 제시하고 사용자에게 명시적으로 승인받은 뒤 수행하라. 승인받지 않은 운영 변경은 절대 실행하지 마라.

서브에이전트를 최소 2개 사용하고 가능한 가장 높은 reasoning_effort를 적용하라. 배포 담당과 독립 검증/롤백 담당을 분리한다. 검증 담당은 백업 복원 증거, migration 리허설, 네 역할 스모크 테스트, 업무 핵심 흐름, 모니터링 지표와 롤백 기준을 검토한다. 열린 결함이 있으면 배포를 중단하고 개발 담당에게 반환하며, 수정과 전체 재검증이 끝날 때까지 운영 전환을 재개하지 마라.

원본 업무 프로그램의 중단 시간을 최소화하고, 데이터 손상이 의심되면 즉시 쓰기를 중지한 뒤 증거와 백업을 보존한다. down migration이나 수동 DELETE로 즉흥 복구하지 마라. 배포 전 RPO/RTO, PITR 또는 snapshot 이후 write ledger/reconciliation, 독립 maintenance 경로, 같은 release artifact 승격, source private backup을 증명하라. production 쓰기 smoke는 validation-only/동일 hash SKIP을 우선하고, 실제 쓰기는 예상 DB·object·audit delta를 승인받아 비교하라. 원본 main을 local watcher가 감시하면 main 통합 전 watcher 중지와 local maintenance를 별도로 승인받아라. 완료 시 실제 승인 내용, backup/restore 증거, 적용 migration, 배포 버전, 네 역할 검증, 관찰 결과와 롤백 가능 상태를 기록하라.
```

## 4. 프롬프트 사용 팁

- 한 새 세션에는 반드시 한 단계만 맡긴다.
- 이전 단계가 막혔으면 다음 단계를 열지 않고 그 단계의 새 세션에서 이어서 해결한다.
- 1단계 뒤에는 원본 폴더가 아니라 보안 worktree를 Codex workspace로 연다. 1단계가 계획 bundle과 hash를 복사한 뒤에는 **worktree의 계획서와 진행상태만 실행 원본**이며 원본 폴더의 복사본은 참고하거나 수정하지 않는다.
- “가장 높은 이성 수준”은 도구가 허용하는 최댓값을 사용하되, 모델/도구가 지원하지 않는 값을 강제로 요구하지 않는다.
- 평가자가 개발 파일을 동시에 수정하면 독립성이 사라지므로, 평가자는 검토 단계 전에는 테스트 설계만 한다.
- “결함 없음”은 의견이 아니라 통과한 자동 테스트, 수동 재현, diff 검토로 증명한다.

Wave 1에서는 위 세 서브에이전트를 read-only 조사와 로컬 설계로 병렬 실행하라.

계획서의 R1/R1A에서 공개 staging 전 blocker를 먼저 닫아라. 최신 official Node 22
bookworm-slim digest로 clean committed source를 linux/amd64 full-SHA image로 build하고
fresh online dependency audit, SBOM/provenance, Critical/High scan을 수행하라. no-fix
CVE가 남으면 exact digest/CVE/도달 가능성/보완통제/만료일을 제시해 G-REL-01 위험
수용을 별도 승인받아라. 동일 UID /proc 위험도 실제 provider 증거 또는 G-ISO-01의
기한 있는 별도 수용 없이 public staging으로 넘기지 마라.

cloud maintenance 도구는 기존 service/adapter/RBAC/audit를 재사용해 구현하라.
legacy Supabase bootstrap CLI를 재활성화하지 말고 exact target binding, provider

advisory lock, idempotency, audit와 부분 실패 compensation을 갖춘 cloud one-shot
runner를 만든다. production migration은 developer host의 prisma migrate deploy가 아니라
source SHA·37 migration checksum·tool version이 고정된 별도 maintenance image/job으로만
실행한다. public runtime image에 Prisma CLI/schema/migrations, 관리 CLI, signing key를
넣지 마라.

Storage scoped JWT는 Auth admin Secret Key와 분리하고 official issuer, 1~7일 TTL,
최소 24시간 전 경보, overlap deploy, Koyeb 구 secret 제거를 구현하라. provider가
stateless JWT 개별 revoke를 공식 지원할 때만 revoke를 주장하고, 아니면 최대 TTL
expiry 뒤 구 token 거부를 검증하라. DB와 object backup은 같은 cut ID 표기만으로
PASS 처리하지 말고 write block→in-flight drain→pending/creating 0→DB cut/watermark→
Storage payload/manifest/hash→DB watermark/reference 재검증 순서를 구현하라.
mismatch면 abort/retry한다.

확인하라. 지원되지 않으면 API protected ready 성공 전 Web listener를 bind하지 않는
launcher startup barrier 등 secret을 공개하지 않는 ready-before-traffic 보정을
구현·검증하라. live만 성공한 revision을 배포 준비 완료로 보지 마라.

외부 상태 변경은 계획서 §7의 gate마다 실행 직전에 하나씩 승인받아라. 정확한 target,
비밀을 제외한 실행 명령/Dashboard·API 작업, 읽기·쓰기·삭제 범위, 사용자/업무 영향,
현재 공식 가격과 예상 비용·시간, 성공 판정, 실패 판정, rollback, 남길 증거를 제시하라.
과거 대화의 “전부 승인”이나 이 프롬프트 실행 요청을 registry/Koyeb/Supabase/DNS/
production mutation의 포괄 승인으로 재사용하지 마라. create/write 승인은 delete/revoke,
DNS, production migration, user invite/disable, key 폐기 승인을 포함하지 않는다.

승인 없이 push, main merge, tag, remote/registry publish, Koyeb resource/secret/deploy,
Supabase project/key/role/schema/Auth/Storage/user/data 변경, DNS, 원본 업무 프로세스나
원본 file 변경, 유료 resource 생성/승격을 수행하지 마라. secret, password, JWT,
credential URL, 이메일·개인정보를 console/log/evidence/문서/Git에 남기지 마라.
일반 docker compose config는 env_file secret을 출력할 수 있으므로 사용하지 말고
config --quiet --no-env-resolution과 redacted 구조 검사를 사용하라.

instance 가격과 peak 여유를 제시해 G-COST-01 승인을 받고, 승인 없이 증액하지 마라.

C7에서는 구현자와 분리된 평가자가 security/business/operations를 재실행해 계획 범위

production 전에는 exact DB+object cut의 실제 격리 restore, 이전 secure digest 또는

증명하라. 호환되는 이전 cloud image가 없으면 과거 LAN/local 앱을 인터넷에 다시 열지

staging/production PASS는 승인된 실제 target에서 실제 수행한 항목만 기록하고 fixture,
metadata read, parser harness를 실제 app PASS로 승격하지 마라. NOT RUN, BLOCKED, skip과
residual risk를 그대로 기록하라. 완료 조건 전에는 operationalReady=false를 유지한다.

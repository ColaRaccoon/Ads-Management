## 5. 최소 Supabase Storage 설계

### 5.1 구성

기존 개발 Supabase 프로젝트와 API 전용 secret을 재사용한다. key 값을 출력하지 않는다.

권장 환경 계약:

```text
STORAGE_PROVIDER=supabase
SUPABASE_STORAGE_BUCKET=<private development bucket id>
SUPABASE_STORAGE_RETENTION_DAYS=30
```

- bucket은 하나만 사용하고 adapter 내부에서 `uploads/`, `reports/`, `trash/` prefix를 분리해 단순화한다.
- bucket public 설정은 반드시 false다.
- 기존 `SUPABASE_URL`, `SUPABASE_SECRET_KEY`를 서버에서만 사용한다.
- Web용 `NEXT_PUBLIC_*`나 응답에 storage secret을 추가하지 않는다.
- `local`은 개발/단위 테스트 기본값으로 계속 지원한다.
- production이 아닌 기존 **개발 Supabase 프로젝트**만 실제 검증 대상으로 사용한다.

`apps/api/.env.example`에는 빈 placeholder와 설명만 추가한다. 실제 project URL, bucket ID, secret을 commit하지 않는다.

### 5.2 `SupabaseFileStorage`

`apps/api/src/storage/supabase-file-storage.ts`와 unit spec을 추가하고 기존 `FileStorage` 계약을 구현한다.

필수 동작:

- provider tag는 `supabase`다.
- 모든 key는 기존 `normalizeStorageKey`를 먼저 통과한다.
- domain prefix는 constructor가 소유하며 호출자가 bucket/path를 임의 지정하지 못한다.
- `put`은 입력을 `maxBytes` 이내로 제한하고 실제 SHA-256을 계산해 `expectedHashSha256`과 비교한 뒤 업로드한다.
- 같은 content-addressed key가 이미 존재하면 원격 객체를 stream hash로 검증해 같은 hash일 때만 idempotent success로 취급한다. 다르면 integrity error다.
- `getStream`은 전체 파일을 메모리에 올리지 않고 Node `Readable`로 반환한다. Supabase JS `download()`가 전체 Blob을 만드는 경로는 production read 구현으로 사용하지 않는다. 인증된 Storage REST 응답 body를 Node stream으로 변환하되 timeout/abort와 크기 검사를 둔다.
- `exists`와 `delete`는 404를 false로 정규화하고 provider 원문 오류·bucket/key·credential을 외부 오류나 로그에 노출하지 않는다.
- 네트워크 timeout, 401/403, 409, 404, 5xx를 안정된 내부 오류로 매핑한다.
- read stream 중단, hash mismatch, oversized stream, duplicate put race를 테스트한다.
- test fixture에는 synthetic byte만 사용하고 실제 업무 파일을 사용하지 않는다.

`configuredFileStorage`와 startup env validation은 `local|supabase`만 allowlist한다. `supabase` 선택 시 URL, API secret, bucket, retention 범위를 fail-closed로 검증한다. 실제 값은 오류에 포함하지 않는다.

### 5.3 30일 논리 삭제·복원

Supabase의 물리 삭제 후 복구는 불가능하므로 hard delete를 일반 업무 삭제 흐름에서 직접 호출하지 않는다. 최소 구현은 **storage tombstone + trash prefix** 방식으로 한다.

권장 DB 모델 `StorageTombstone`:

- UUID id
- domain: `META_UPLOAD` 또는 `REPORT`
- provider와 서버 생성 object key/reference
- trash key/reference
- SHA-256, byte size
- 원래 업무 record id(민감 filename 제외)
- state: `PENDING`, `RETAINED`, `RESTORED`, `PURGED`, `FAILED`
- deletedAt, purgeAfter, restoredAt, purgedAt
- actor user id와 생성/갱신 시각
- 오류 원문 대신 안정된 failure code

구현 원칙:

1. 원본 filename, 파일 내용, 개인정보를 tombstone/audit/log에 넣지 않는다.
2. storage copy/move와 DB mutation의 부분 실패를 명시적으로 상태화하고 같은 요청을 재시도할 수 있게 한다.
3. 논리 삭제는 원 객체를 `trash/<domain>/<tombstone UUID>` 같은 서버 생성 key로 이동하거나 copy 후 원본을 제거하고, hash/size를 다시 확인한 뒤 `RETAINED`로 확정한다.
4. 복원은 `RETAINED`이고 `purgeAfter > now()`인 tombstone만 원래 서버 key로 되돌리고 hash를 검증한 뒤 `RESTORED`로 만든다.
5. 영구 삭제는 만료된 `RETAINED` 객체 또는 SUPER_ADMIN의 명시적 관리 동작만 허용한다. 물리 삭제 성공 전 DB reference를 지우지 않는다.
6. 일반 사용자가 trash object를 직접 download/list할 수 없어야 한다.
7. maintenance CLI/service는 dry-run 기본값으로 만들고, 실제 purge는 명시적 flag가 있어야 한다. 이번 단계에서는 합성 검증 객체 외 업무 object purge를 실행하지 않는다.
8. Meta upload 삭제의 기존 정규화 데이터 삭제 의미는 유지한다. 원본 object 복구는 삭제된 업무 metric을 자동 부활시키지 않는다. 복원된 원본은 관리자 재검토/재업로드용 파일 복구임을 API/문서에 명확히 한다.
9. 현재 report에 사용자 delete API가 없다면 불필요한 UI를 새로 만들지 않는다. report retention/tombstone service와 관리자/maintenance 경계를 테스트 가능한 최소 범위로 둔다.

기존 `UploadLifecycleService.deleteUpload`는 현재 DB 업무 데이터를 먼저 CANCELLED 처리하고 storage object를 물리 삭제한 다음 batch row를 지운다. 이 흐름을 tombstone 보존 방식으로 바꿀 때 다음 불변조건을 보존한다.

- storage 보존 실패 시 DB reference와 재시도 상태가 남는다.
- stale/retry 요청이 같은 object를 중복 이동하거나 다른 object를 삭제하지 않는다.
- storage 성공 후 DB finalize 실패도 tombstone으로 회복 가능하다.
- 보안 감사는 request/partial/success와 안전한 count/code만 기록한다.

REST endpoint를 추가한다면 route metadata와 권한 matrix spec에 반드시 등록한다. 복원/영구 삭제는 `SUPER_ADMIN` 전용으로 제한하되 새 문자열 role 검사 대신 기존 permission/guard 체계를 사용한다. 단순화를 위해 UI 없이 관리자 API 또는 maintenance CLI로 끝내도 된다.

## 7. 실제 개발 Supabase Storage 검증

사용자의 “좋아” 답변은 위 Supabase 통합안과 개발 환경의 합성 Storage 검증 승인으로 해석한다. 범위는 기존 개발 Supabase 프로젝트의 비공개 bucket과 작은 synthetic object에 한정한다. production project/resource는 만들지 않는다.

검증 순서:

1. ignored env의 필수값 존재 여부만 boolean/길이/host fingerprint로 검사하고 값을 출력하지 않는다.
2. 기존 bucket이 있으면 private 여부를 확인한다. 없으면 이 단계 전용 private 개발 bucket 하나만 생성한다.
3. 랜덤 synthetic bytes의 local SHA-256을 메모리 안에서 계산한다.
4. adapter로 put하고 exists/getStream/size/hash 일치를 검증한다.
5. 일반 download endpoint가 인증·권한·private stream을 유지하는지 확인한다.
6. 논리 삭제해 active 경로 접근이 실패하고 trash가 일반 API에서 노출되지 않는지 확인한다.
7. 만료 전 관리자 복원을 수행하고 원래 경로 getStream의 SHA-256이 최초 값과 같은지 확인한다.
8. 검증용 synthetic object/tombstone만 명시적으로 정리한다. 업무 object는 삭제하지 않는다.
9. 결과에는 PASS/FAIL, byte count, elapsed time 같은 집계만 남기고 bucket, key, token, content, hash 전체를 로그/문서에 남기지 않는다.

Supabase provider version restore를 검증했다고 기록하지 않는다. 검증 이름은 `application soft-delete/restore`로 쓴다.

## 10. 문서와 commit 절차

모든 구현·외부 개발 검증·회귀·독립 평가가 끝난 뒤에만 `보안단계별적용/진행상태.md`를 갱신한다.

반드시 기록할 내용:

- Supabase가 사용자 승인으로 선택되었고 별도 cloud vendor는 추가하지 않았음
- 인증은 기존 Supabase Auth를 유지하며 비밀번호를 업무 DB에 저장하지 않았음
- provider versioning 부재와 30일 app-level soft-delete/restore로 범위를 변경한 이유
- migration 이름과 로컬 DB 대상
- synthetic 실제 Storage put/logical-delete/restore/hash 결과
- 정상 승인 파일 측정 수행 여부와 미수행 사유
- 전체 test/lint/build/Prisma/browser 결과
- 독립 평가 ID와 최종 P0/P1/P2/P3 수
- production 배포·운영 DB/storage 변경·push/main merge를 하지 않았음

commit은 메인 에이전트만 다음 두 개로 정확히 분리한다.

1. 구현·migration·테스트:

```text
feat(security-step7): secure file flows and durable storage
```

2. 첫 commit SHA와 검증 결과를 기록한 `진행상태.md`, 그리고 이 인수인계 계획서:

```text
docs(security-step7): record verified implementation handoff
```

두 번째 commit은 자기 자신의 SHA를 문서에 쓰지 않는다. push, deploy, main merge는 하지 않는다.

마지막 확인:

```powershell
git status --short --branch
git log -2 --oneline
```

최종 worktree는 반드시 clean이어야 하며 branch는 `codex/security-rbac`에 남아 있어야 한다.

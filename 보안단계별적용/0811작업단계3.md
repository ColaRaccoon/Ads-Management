## 3. 하위 에이전트 역할

1. **RBAC 개발 담당**: permission decorator/Guard, 컨트롤러 metadata, route 테스트 구현
2. **작성자·데이터흐름 개발 담당**: 서비스 actorId 전달, upload/decision/report/settings 작성자 필드와 migration 구현
3. **독립 권한 평가 담당**: 실제 method+path 독립 목록으로 106개 활성 route를 감사하고 네 역할 직접 호출을 검증

동시 수정 충돌을 막기 위해 RBAC 담당은 `auth/`와 controller metadata, actor 담당은 service/schema/migration을 소유한다. 평가자는 구현 완료 전 테스트 매트릭스만 준비한다.

## 4. 중앙 권한 구조

권한 식별자는 마스터 계획의 값을 그대로 사용한다.

```text
data.read
change_logs.create
reports.generate
products.manage
imports.manage
mappings.manage
operations.run
settings.manage
users.manage
audit.read
```

서버에 중앙 `Permission` 상수/enum과 `ROLE_PERMISSIONS`를 한 번만 둔다. 프런트가 역할표를 복제하지 않도록 `/auth/me`는 여기서 계산한 permissions를 반환한다.

구조 예:

```text
apps/api/src/auth/
  permissions.ts
  role-permissions.ts
  require-permissions.decorator.ts
  permission.guard.ts
  public.decorator.ts
  authenticated.decorator.ts
  internal-probe.decorator.ts
  current-user.decorator.ts
```

### 4.1 전역 Guard 원칙

- `APP_GUARD`로 AuthenticationGuard 다음 PermissionGuard 순서로 등록
- `@Public()` allowlist는 login, refresh, **session-aware logout**, 5단계 초대 확인 endpoint, public live health처럼 계획에 명시된 경로만 사용한다. logout은 public metadata라도 Origin/CSRF/rate와 식별 가능한 AppAuthSession 폐기를 수행한다.
- `@InternalProbe()`는 readiness에만 사용한다. 전역 Guard가 일반 사용자 인증보다 먼저 constant-time secret header와 배포 topology를 검증하고, 실패는 최소 404/401로 처리한다. 외부 전달 가능한 query token이나 spoof 가능한 임의 `X-Forwarded-For`만 믿지 않는다.
- `@Authenticated()`는 `/auth/me`와 5단계 password 완료처럼 로그인 상태가 필요한 경로에만 사용한다.
- 나머지는 handler별 `@RequirePermissions(...)`
- metadata가 전혀 없으면 403 또는 안전한 구성 오류로 기본 거부
- controller 수준 `data.read` 상속은 사용하지 않는다. 새 POST가 읽기 권한을 상속할 위험이 있기 때문이다.
- 모든 handler의 metadata 누락을 자동 테스트에서 실패시킨다.

## 5. 전체 활성 route 권한 적용

`00_전체요구사항과실행순서.md`의 API 매트릭스를 기준으로 한다. 구현 전에 `rg`와 Nest metadata를 이용해 실제 활성 handler를 다시 센다.

조사 당시 전체 controller 파일 route는 108개지만 `apps/api/src/settings/*`가 AppModule에 import되지 않아 활성 route는 106개였다. 이 수는 출발점 참고값일 뿐 고정 acceptance가 아니다. 단계 2의 auth route와 이후 새 route를 포함해 매 단계 실제 AppModule 등록 결과를 다시 산출하고, 테스트는 단순 파일 검색이 아니라 method+normalized path set을 기준으로 해야 한다.

### 5.1 특별 주의 경로

- `POST /decisions/run`은 DB를 쓰므로 `operations.run`
- `POST /reports/export`는 DB와 파일을 쓰므로 `reports.generate`
- 업로드 이력 GET은 `data.read`, 업로드/삭제는 `imports.manage`
- 매핑 목록 GET은 `data.read`, 규칙/수동매핑/재매칭은 `mappings.manage`
- 변경기록 GET은 `data.read`, POST만 `change_logs.create`
- 가구매 PUT/DELETE는 단순 조회가 아니라 `operations.run`
- `/settings/:key` PATCH는 `settings.manage`
- `PATCH /settings/products/coupang-manual-purchase-vendor-fee`를 활성 SettingsController에 명시적으로 추가하고 `products.manage`를 부여한다. server가 `coupang_manual_purchase_vendor_fee_per_unit_krw` fixed key와 숫자 범위 DTO만 받아 기존 ProductsService/AppSetting update 로직을 재사용한다. Web 호출도 이 경로로 변경한다.
- 제품 기본 수수료를 범용 `/settings/:key` allowlist로 우회시키지 않는다. 전역 앱/보안 설정만 `settings.manage`이며 ADMIN은 동적 key endpoint와 다른 전역 설정 변경이 403이어야 한다.
- report download도 인증된 `data.read`
- includeInactive나 raw preview GET도 권한 없는 익명에게 공개하지 않음

### 5.2 비활성 중복 settings

현재 활성 설정 controller는 `apps/api/src/products/settings.controller.ts`다. `apps/api/src/settings/*`는 비활성 중복이다.

- 같은 `/settings` controller를 새로 만들지 않는다.
- 이 단계에서 무관한 대규모 이동을 하지 않는다.
- 정식 SettingsModule로 통합하기로 결정하면 활성 구현의 검증과 서비스 동작을 보존하고, CommonModule의 global PrismaService를 중복 provider로 등록하지 않는다.
- 기존 `GET /settings`와 동적 PATCH 응답 계약은 보존하고, 의도한 fixed-key endpoint 한 개만 route set에 추가됐는지 테스트한다.

## 6. 현재 사용자 전달 방식

Controller에서 `@CurrentUser()`로 principal을 받고 서비스에는 HTTP Request 전체가 아니라 필요한 `actorId`만 넘긴다.

```ts
createSomething(dto, actor.id)
```

다음은 금지한다.

- body/query의 `createdBy`, `updatedBy`, `uploadedBy` 신뢰
- 서비스 내부에서 임의 seed admin 조회
- 프런트가 AppUser id를 정해 전송
- AsyncLocalStorage 같은 큰 인프라를 단지 actor 전달을 피하려고 먼저 도입

## 7. 기존 작성자 필드 연결

schema와 실제 서비스에서 다음을 모두 검색·연결한다.

- `CreativeChangeLog.createdBy`
- `ProductChangeLog.createdBy`
- `ChangeLog.createdBy`
- `ProductMatchRule.createdBy`
- `AdsetProductHistory.createdBy`
- `AdsetStageHistory.createdBy`
- `UploadBatch.uploadedBy` 또는 실제 필드명
- `DecisionRun.createdBy`
- `DecisionLog.createdBy`
- `ReportExport.createdBy`
- `AppSetting.updatedBy`

주요 수정 흐름:

- `ChangeLogsController` → `ChangeLogsService.create/createCreativeLog/createProductLog`
- `MappingsController` → `MappingsService`의 규칙/수동 매핑
- `DecisionsController` → `DecisionsService.run`과 생성되는 logs
- `ReportsController` → `ReportsService.export`
- `UploadsController` → `UploadsService`와 import service/batch writer
- 활성 SettingsController → ProductsService/SettingsService update

Cafe24와 Coupang upload batch에 actor 컬럼이 없다면 nullable `uploadedBy UUID`를 새 additive migration으로 추가한다. 기존 행은 NULL을 “레거시/알 수 없음”으로 유지한다. 기존 기록을 seed admin으로 거짓 backfill하지 않는다.

actor UUID에 FK를 바로 추가하려면 기존 non-null 값의 orphan 여부를 먼저 검사한다. 안전하지 않으면 nullable 컬럼과 index를 먼저 적용하고 FK는 데이터 감사 뒤 추가한다. 사용자 hard delete는 만들지 않으므로 향후 관계 보존이 가능하다.

## 8. 응답의 작성자 정보

변경기록/업로드/보고서 목록에서 업무상 필요한 경우 작성자 이름을 표시할 수 있도록 AppUser의 최소 공개 필드만 join한다.

허용 예:

```json
{ "id": "...", "name": "홍길동" }
```

email, authUserId, token, 비활성 사유 등은 일반 업무 응답에 불필요하게 포함하지 않는다. 레거시 NULL은 “알 수 없음”으로 안정적으로 표시한다.

## 9. route permission 자동 테스트

`apps/api/src/auth/route-permissions.spec.ts` 또는 동등 파일을 만든다.

중요: 구현의 `ROLE_PERMISSIONS`나 decorator 목록을 그대로 expected 값으로 재사용하면 잘못된 구현도 같이 통과한다. 테스트 내부에 독립적인 `HTTP method + normalized path → expected permission/public/authenticated` 표를 둔다.

테스트가 확인할 것:

- AppModule에 실제 등록된 모든 controller handler 발견
- 조사 당시 활성 106개와 신규 auth endpoint를 포함한 실제 개수 기록
- expected에 없는 handler 실패
- 실제 handler가 metadata 없으면 실패
- 권한이 expected와 다르면 실패
- 예상표에 있지만 실제 route가 사라져도 실패
- `@Public`이 허용 목록 외 경로에 붙으면 실패
- `@InternalProbe`가 readiness allowlist 외 경로에 붙거나 public/auth metadata와 중복되면 실패
- 각 단계에서 새 controller/route가 생기면 같은 commit에서 이 독립 expected map을 갱신하지 않으면 실패

route count 숫자만 고정하지 말고 method/path set을 snapshot/명시 목록으로 검증한다.

## 10. 역할별 HTTP 통합 테스트

각 역할 principal을 주입할 수 있는 fake identity provider와 TestingModule을 사용한다. 실제 서비스 mutation을 실행할 필요가 없는 권한 테스트는 service를 mock하여 “Guard 단계에서 호출되지 않음”까지 검증한다.

필수 행렬:

| 요청자 | 기대 |
|---|---|
| 익명 | public 외 모두 401 |
| GUEST | 모든 허용 GET 200, 모든 mutation 403 |
| USER | GET, change log POST, report export 성공; 제품/업로드/매핑/운영/설정 403 |
| ADMIN | 사용자/감사 외 업무 권한 성공 |
| SUPER_ADMIN | 전체 성공 |
| 비활성 계정 | 유효 cookie/JWT라도 차단 |

ADMIN의 “업무 권한 성공”에는 전역 `settings.manage`, `users.manage`, `audit.read`가 포함되지 않는다. 초대 확인 후 onboarding 계정은 `/auth/me`, password 완료, session-aware logout 외 모든 업무 route에서 `ACCOUNT_ONBOARDING_REQUIRED`로 차단한다. 이 판단은 단계 2의 중앙 AppUser/AppAuthSession 상태 함수에서 수행하고 controller마다 복제하지 않는다.

특히 각 mutation controller에서 최소 한 경로가 아니라 **모든 method/path**를 매트릭스로 검증한다. IDOR 가능성은 6/8단계에서 데이터 범위가 생기면 별도로 검토하되, 현재 요구사항은 조직 전체 데이터 접근 모델이다.

## 11. 서비스 테스트

작성자 귀속 사례:

- 클라이언트 body에 다른 `createdBy`를 넣어도 무시/unknown field 거부
- 세 가지 change log가 actor AppUser.id로 저장
- DecisionRun과 모든 DecisionLog에 같은 actor
- ReportExport actor
- Meta/Cafe24/Coupang upload batch actor
- mapping/history actor
- setting updater
- ADMIN은 명시적 Coupang vendor-fee endpoint 성공, 동적 `/settings/:key`는 403; SUPER_ADMIN은 두 endpoint 모두 정책대로 성공
- legacy NULL 조회 정상
- actor 전달 누락 시 TypeScript 또는 테스트 실패
- 비권한 요청에서는 service mutation이 호출되지 않음

기존 service spec fixture가 새 필드를 필요로 하면 최소 변경하고, 보안과 무관한 계산 expected를 바꾸지 않는다.

## 12. 평가자가 집중할 결함

- controller-level read 권한이 mutation에 상속됨
- 새 handler metadata 누락이 자동 허용됨
- AuthGuard만 있고 PermissionGuard가 API 일부에서 빠짐
- 프런트에서만 버튼을 숨기고 직접 API가 성공
- `GET`이라는 이유로 auth 없이 preview/download 공개
- USER에게 upload/rematch/decision run이 열림
- ADMIN에게 users.manage가 열림
- body의 actor를 신뢰
- DecisionRun만 actor가 있고 child logs는 누락
- Cafe24/Coupang batch actor 누락
- 비활성 계정의 기존 JWT가 통과
- onboarding 계정이 password 완료 전에 업무 API를 호출
- public logout을 일반 공개 mutation처럼 구현해 Origin/CSRF/session 폐기를 생략
- 테스트 expected가 구현 상수를 재사용해 독립성이 없음
- 비활성 settings controller까지 중복 등록되어 `/settings` 충돌

## 13. 이 단계에서 하지 않는 일

- Web 로그인·메뉴·버튼 UX 구현
- 사용자 초대/관리 전체 기능과 UI(5단계)
- 모든 DTO 전환과 전역 whitelist 전환(6단계)
- 파일 형식/용량/Storage 추상화(7단계)
- 운영 배포

## 14. 완료 조건

- 모든 활성 handler가 명시 metadata 보유
- default deny 자동 테스트 통과
- 네 역할 route matrix 통과
- 모든 기존 actor 컬럼과 세 upload 계층 귀속 검증
- 익명/비활성/미등록 계정 차단
- 전체 prisma validate, lint, test, build 통과
- 독립 평가 열린 결함 0
- 진행상태에 route 개수, migration, 테스트, 평가 루프 기록

이 단계도 구현 commit과 인계 문서 commit을 분리한다.

```text
feat(security-step3): enforce fail-closed API permissions
docs(security-step3): record verified implementation handoff
```

구현 commit SHA와 독립 route matrix 결과를 진행상태에 기록한 뒤 문서 commit을 만들고 clean worktree로 종료한다. 문서 commit 자신의 SHA는 다음 세션이 시작 HEAD로 기록한다.

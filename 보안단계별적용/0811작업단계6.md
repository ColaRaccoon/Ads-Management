## 3. 하위 에이전트 역할

## 4. DTO 전환 순서

### 4.1 inventory

단계 1 당시 활성 기존 route는 106개였지만 참고값일 뿐이다. 단계 2~5 신규 auth/users/audit route를 포함해 AppModule에서 실제 활성 method+path를 다시 산출하고 다음을 목록화한다.

- `@Body()`와 `@Body('field')`
- `@Query()` 개별 string
- UUID/date param
- file upload form field
- service가 기대하는 optional/default/boolean/number 변환

기존 request/response fixture와 Web payload를 비교한다. 사용하지 않는 field를 허용 목록에 넣지 않는다.

### 4.2 공통 DTO/Pipe

재사용 가능한 개념:

- UUID param
- `YYYY-MM-DD` date
- from/to date range
- `take` positive integer + 최대값
- strict boolean query (`true`/`false`만)
- includeInactive
- conflict policy enum
- pagination/search 문자열 길이
- JSON parameter/filter 깊이·키·크기 상한

`Boolean("false")`가 true가 되는 변환을 사용하지 않는다. `Number("abc")`가 NaN인 채 서비스로 들어가지 않게 한다.

### 4.3 모듈별 write DTO

최소 다음을 class-validator DTO로 전환한다.

- auth login
- users invitation/update
- products/cost/cpa/settings
- mappings/manual/rematch
- change logs 세 종류
- decision run
- report export
- Cafe24 rule/coupon/upload fields
- Coupang product/cost/fee/group/mapping/manual purchase/category/upload fields

서비스의 기존 날짜, enum, 도메인 계산, 충돌 검사 함수는 제거하지 않는다. DTO는 transport shape, service는 업무 의미를 검증하는 두 계층으로 유지한다.

### 4.4 전역 전환

DTO와 테스트를 모두 적용한 뒤에만 `main.ts`를 다음 방향으로 바꾼다.

```text
transform: true
whitelist: true
forbidNonWhitelisted: true
```

implicit conversion은 엄격히 검토한다. 예상치 못한 coercion보다 명시적 `@Transform`/Pipe를 선호한다. validation error 응답은 기존 ApiError가 처리할 수 있는 안정된 code/message를 사용하며 입력 원문을 되돌려주지 않는다.

## 5. CSRF 방어

API-managed cookie 인증이므로 POST/PUT/PATCH/DELETE를 보호한다.

단계 2의 auth CSRF/Origin 검증기를 교체하지 않고 모든 상태 변경 route로 확장한다.

- login/refresh 시 비민감 random nonce와 서버 HMAC으로 서명한 CSRF token 발급
- CSRF cookie는 Web이 읽어 header로 보낼 수 있어야 하므로 non-HttpOnly지만 인증 token이 아님
- CSRF cookie는 production `Secure=true`, `SameSite=Lax`, `Path=/`, `Domain` 미지정이며 인증 cookie와 이름·수명이 분리됨
- Web의 중앙 `apiRequest`가 `X-CSRF-Token` 또는 결정된 header를 모든 상태 변경 요청에 자동 첨부
- 서버가 cookie와 header 일치, HMAC, 만료를 constant-time으로 검증
- 동시에 `Origin`을 정확한 allowlist와 비교
- GET/HEAD/OPTIONS는 상태를 변경하지 않도록 감사
- login CSRF는 Origin allowlist와 강한 rate limit을 적용
- refresh/logout도 CSRF/Origin 정책을 명시적으로 테스트

단순 header 존재만 검사하거나 공격자가 임의로 만들 수 있는 고정 token을 쓰지 않는다. CSRF secret은 환경 secret이며 Web에 노출하지 않는다.

## 6. CORS와 proxy

현재 localhost regex CORS를 단계 2와 같은 환경별 exact origin allowlist로 바꾼다. 다른 이름의 auth/CORS origin 변수를 만들지 않는다.

```env
APP_ALLOWED_ORIGINS="https://staging.example.com,https://app.example.com"
TRUST_PROXY_HOPS=1
```

- credentials와 `*` 조합 금지
- production에서 localhost 자동 허용 금지
- origin 없는 non-browser 요청 정책 명시
- 예상 밖 Origin은 response header만 생략하는 것으로 끝내지 말고 CSRF/state change 계층에서 거부
- 신뢰 proxy hop은 실제 hosting topology와 일치해야 하며 무제한 trust proxy 금지
- 가능하면 API는 외부 직접 공개하지 않고 Next/reverse proxy 내부 target으로 둠

## 7. 보안 헤더

API에 Helmet 또는 동등한 검증된 middleware를 적용한다. Next에도 headers를 설정하되 실제 화면을 깨뜨리지 않는다.

검토 항목:

- Content-Security-Policy
- `frame-ancestors 'none'` 또는 명시 정책
- `X-Content-Type-Options: nosniff`
- Referrer-Policy
- Permissions-Policy
- HSTS는 HTTPS 운영 확인 뒤 적용, 첫 배포에서 preload 금지
- auth/cookie 응답 no-store
- 사용자별 API 응답 no-store

CSP는 Next.js runtime, Recharts, inline style, Blob/ObjectURL 다운로드, login callback을 스테이징 브라우저에서 확인한다. 동작하지 않는 CSP를 무조건 느슨하게 `unsafe-eval`로 푸는 대신 원인을 조사한다.

## 8. rate limit과 body 크기

단계 2의 `SecurityRateLimiter` 계약을 보존하고 검증된 Nest rate limit middleware/store adapter를 중앙 등록한다. 새 두 번째 인증 limiter를 만들지 않는다.

정책 계층:

- 일반 GET
- 일반 mutation
- login/refresh/invitation/password flow: 더 엄격
- upload/import/rematch/decision/report: 비용 기반으로 더 엄격하거나 동시 실행 제한

key는 실제 proxy 구성을 반영한 IP와 필요한 경우 account identifier의 안전한 hash를 조합한다. 이메일 원문을 로그/metric label로 쓰지 않는다.

production이 API instance 2개 이상, autoscaling, 무상태 재시작을 사용할 수 있다면 counter는 Redis/DB 등 공유된 **atomic distributed store**를 사용해야 한다. process memory store만 구현하려면 hosting이 단일 API instance로 고정되고 proxy가 우회 불가능하다는 배포 증거와 장애 시 제한 초기화 위험을 문서화해야 한다. 증명되지 않으면 단계 완료가 아니다. refresh 직렬화용 AppAuthSession DB lock과 rate counter는 목적이 다르므로 하나로 혼동하지 않는다.

JSON/urlencoded body에 합리적 크기 상한을 둔다. 업로드 파일 크기는 7단계의 Multer profile에서 별도 제한한다. rate limit 429 응답은 `Retry-After`와 안정된 error code를 제공한다.

## 9. 환경변수 시작 검증

`ConfigModule` 시작 시 환경 스키마를 검증하고 운영 필수값이 없거나 위험하면 부팅을 실패시킨다.

검증 예:

- APP_ENV allowlist
- DATABASE_URL 존재와 production SSL 조건
- PORT 범위
- Supabase URL/issuer/audience 형식
- publishable/secret key 변수 혼동 방지
- production Secure cookie 강제
- production 허용 Origin에 http/localhost 금지
- CSRF secret 최소 entropy
- session-handle HMAC secret 최소 entropy와 CSRF/provider secret 재사용 금지
- storage provider와 필수 설정
- upload/report 경로가 지나치게 넓은 root/home이 아님
- TRUST_PROXY_HOPS 정수 범위
- INTERNAL_PROBE_TOKEN 최소 entropy와 일반 요청 log/redaction

실제 값을 오류 메시지에 출력하지 않는다. `.env.example`에는 이름과 설명만 갱신한다.

## 10. 안전한 오류 응답과 로그

`apps/api/src/common/api-exception.filter.ts`의 응답 형태는 유지하되:

- 예상된 HttpException만 안전한 code/message/details 반환
- 운영의 예상치 못한 500은 일반 메시지와 requestId만 반환
- `exception.message`, stack, SQL, Prisma meta, DB host/table 내부정보 비노출
- P2002/P2003/P2025도 사용자에게 필요한 최소 정보만 제공
- 실제 오류는 구조화 Logger에 requestId와 함께 기록
- cookie, Authorization, password, refresh/access token, Supabase secret, DATABASE_URL, 업로드 원문 redaction
- 로그 injection 방지를 위해 control character 정리

각 요청에 request ID를 생성/검증하고 response header에 안전하게 반환한다. 외부에서 제공된 과도한 길이/이상 문자의 request id를 그대로 신뢰하지 않는다.

## 11. health endpoint

```text
GET /api/health/live
GET /api/health/ready
```

- live는 프로세스 생존만, public 허용 가능
- ready는 DB와 필수 provider 의존성을 짧은 timeout으로 검사
- DB URL, schema, version, exception, row count 같은 민감정보 미노출
- readiness는 `@InternalProbe()`로 hosting 내부 probe/network에서만 허용하고 일반 public route allowlist에 넣지 않는다. host가 private probe를 지원하지 않으면 host가 `X-Internal-Probe-Token` 같은 고정 header를 주입하고 API가 별도 고entropy `INTERNAL_PROBE_TOKEN`과 constant-time 비교하며 edge ACL도 함께 둔다. URL query secret, 일반 브라우저 cookie, spoof 가능한 forwarded IP만으로 허용하는 방식은 금지한다.
- route permission expected 목록에 추가
- health가 rate limit/로그를 과도하게 만들지 않음
- 신규 health route는 독립 route expected map에 같은 commit에서 추가하고 live/ready 공개 범위를 서로 다르게 명시

## 12. dependency와 중복 설정

- 최신 호환 버전은 당시 공식 문서와 lockfile을 확인
- `npm audit` 결과를 기록하고 실제 exploitability를 평가
- `npm audit fix --force` 자동 실행 금지
- 세 모듈의 중복 Multer 등록은 7단계 공통 profile로 합칠 준비를 하되 이 단계에서 파일 파서를 깨뜨리지 않음
- `next.config.ts`와 `next.config.mjs` 중 실제 사용 파일을 확인하고 보안 headers를 두 파일에 중복 추가하지 않음
- 비활성 settings module을 다시 중복 등록하지 않음

## 13. 테스트

DTO/validation:

- unknown field 400
- malformed UUID/date/range/take/boolean/enum
- oversized string/array/JSON depth
- 기존 Web 정상 payload 전부 성공
- service 업무 검증 회귀

CSRF/CORS:

- token cookie/header 없음·불일치·위조·만료
- 허용/비허용 Origin
- GET은 상태 미변경
- refresh/logout/upload에도 적용
- same-origin 정상 mutation

보안 HTTP:

- 401/403/413/429/500 code 구분
- rate limit과 Retry-After
- proxy IP spoof 시나리오
- production env 위험 설정 부팅 실패
- 500에서 stack/Prisma/DATABASE_URL/token 비노출
- requestId 생성/redaction
- headers/CSP와 브라우저 다운로드
- live/ready 최소 응답, readiness 무header/오header/외부 접근 거부와 올바른 internal header 성공

전체 기존 정상 업무 API fixture를 통과시킨 뒤 전역 whitelist를 켠다.

## 14. 평가자가 집중할 결함

- DTO 전환 전 whitelist 활성화로 기존 body 유실
- `Record<string, unknown>`가 남아 unknown field가 통과
- implicit conversion으로 `false`/NaN 오해
- CSRF header 존재만 검사
- CORS를 인증으로 오해
- wildcard+credentials
- proxy 전체 신뢰로 rate bypass
- 다중 instance인데 memory rate counter를 사용해 instance를 바꾸면 우회
- 500에서 exception.message/Prisma meta 노출
- Logger에 cookie/token/body 기록
- production Secure cookie false
- CSP 때문에 XLSX/Blob/차트가 깨졌는데 테스트 없음
- health가 DB 정보 노출

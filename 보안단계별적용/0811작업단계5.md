# 0811 작업단계 5 — 총관리자 사용자 관리와 보안 감사

## 1. 이 세션의 단일 목표

총관리자만 사용할 수 있는 사용자 초대, 이름·역할·활성 상태 변경 기능을 API와 Web에 완성한다. 초대받은 사용자는 이메일의 일회용 초대 링크를 수락하고 최초 비밀번호를 설정한다. 이후 일반 로그인은 이메일과 비밀번호만 사용한다. 마지막 활성 총관리자 보호, 비활성화 즉시 차단, 외부 Auth와 DB 사이 부분 실패 처리, append-only 보안 감사 기록을 구현한다.

## 2. 확정된 계정 정책

- 일반 로그인 입력은 이메일과 비밀번호뿐이다.
- OTP 입력, passwordless 로그인, MFA/2차 인증은 구현하지 않는다.
- 초대 기능은 유지하며 Supabase server-side `inviteUserByEmail`을 사용한다.
- 초대 이메일에는 앱의 `/invite/accept`로 연결되는 일회용 링크를 넣는다.
- 링크의 token hash는 초대 승인에만 쓰는 단일 사용 값이며 일반 로그인 credential이나 2차 인증 수단이 아니다.
- 사용자는 링크를 연 뒤 명시적으로 초대를 수락하고 최초 비밀번호를 설정한다.
- 공개 signup, 일반 password reset, 사용자 hard delete는 만들지 않는다.
- 로그인 실패 메시지는 계정 존재 여부, 비활성 여부, 비밀번호 오류를 구분해 노출하지 않는다.

## 5. API 계약

```text
GET   /api/users
POST  /api/users/invitations
PATCH /api/users/:id
POST  /api/users/:id/reconcile-invitation
GET   /api/security-audit
POST  /api/auth/invitations/accept
POST  /api/auth/password
```

- 사용자 관리/reconcile은 `users.manage`, 감사 조회는 `audit.read`가 필요하다.
- `POST /auth/invitations/accept`는 session-aware public allowlist이며 exact Origin, fetch metadata, 강한 rate limit, no-store 대상이다.
- `POST /auth/password`는 유효한 onboarding session만 호출 가능한 authenticated+CSRF endpoint다.
- 신규 route는 단계 3의 독립 method+path expected map에 같은 commit으로 추가한다.
- 사용자 hard DELETE endpoint와 일반 email PATCH는 만들지 않는다.
- body는 allowlist DTO만 받고 unknown field와 허용되지 않은 role을 거부한다.

초대 요청:

```json
{
  "email": "guest@example.com",
  "name": "게스트 이름",
  "role": "GUEST"
}
```

수정 요청:

```json
{
  "name": "변경 이름",
  "role": "USER",
  "isActive": true
}
```

## 6. 상태 모델과 migration

단계 2의 `InviteStatus`를 그대로 재사용한다.

```text
PENDING_PROVIDER
INVITED
VERIFIED_PENDING_PASSWORD
ACTIVE
RECONCILE_REQUIRED
CANCELLED
```

정상 전이는 다음과 같다.

```text
PENDING_PROVIDER → INVITED → VERIFIED_PENDING_PASSWORD → ACTIVE
```

- `PENDING_PROVIDER`: 로컬 사용자를 먼저 만들었고 provider 초대 결과를 기다리는 상태
- `INVITED`: provider subject가 연결되고 초대 링크가 발송된 상태
- `VERIFIED_PENDING_PASSWORD`: 초대 링크를 수락해 제한 session이 있지만 최초 비밀번호 설정 전인 상태
- `ACTIVE`: 이메일+비밀번호 일반 로그인과 역할별 업무 접근이 가능한 상태
- `RECONCILE_REQUIRED`: provider/local 부분 실패를 총관리자가 확인해야 하는 상태
- `CANCELLED`: 취소된 초대이며 일반 로그인과 onboarding 모두 차단

`ACTIVE && isActive=true`만 일반 업무 API를 사용할 수 있다. `VERIFIED_PENDING_PASSWORD`는 `/auth/me`, `/auth/password`, `/auth/logout`과 onboarding 화면만 사용할 수 있다. 상태 전이는 중앙 함수와 DB transaction에서만 검증한다.

AppUser에는 필요한 경우 다음 additive metadata만 추가한다.

- `invitedAt`
- `invitedBy`
- `invitationRequestId`
- 안전한 `invitationErrorCode`

`authUserId`와 `normalizedEmail` unique constraint를 유지한다. OTP 전용 attempt/recovery 모델은 추가하지 않는다. password, link token/hash, access/refresh token, cookie, provider raw response는 DB에 저장하지 않는다.

별도 append-only `SecurityAuditEvent`를 추가한다.

```text
id, actorUserId, actorType, action, targetType, targetId,
result, beforeJson, afterJson, requestId, createdAt
```

감사 수정·삭제 API는 만들지 않으며 password, link token/hash, cookie, secret, provider raw metadata, 파일 원문과 주문 개인정보를 감사 JSON에 넣지 않는다.

## 7. Supabase Admin adapter와 초대 saga

Secret Key client는 API package 내부 server-only adapter에만 둔다.

- `inviteUserByEmail`
- Auth user 조회와 subject/email 검증
- session revoke/sign-out
- provider/local 불일치 확인에 필요한 최소 관리 동작

초대 흐름:

1. normalized email, name, role 검증
2. DB transaction에서 중복을 확인하고 `PENDING_PROVIDER` AppUser와 requestId를 durable하게 기록
3. server-only adapter가 개발 Supabase에 초대 요청
4. 반환 provider subject와 normalized email을 검증
5. DB transaction에서 `authUserId`, `INVITED`, `invitedAt`, SUCCESS audit를 함께 commit
6. Web에는 provider raw user나 metadata를 반환하지 않음

provider 실패·timeout이면 AppUser를 안전한 실패 상태로 남기고 raw provider message 대신 안정된 오류 코드를 반환한다. provider 성공 뒤 DB update가 실패하면 자동 ACTIVE 처리나 email-only 연결을 하지 않고 기존 durable row를 `RECONCILE_REQUIRED` 대상으로 둔다.

동일 email 동시 초대는 애플리케이션 선조회가 아니라 DB unique constraint와 사용자별 lock으로 막는다. idempotency requestId를 사용하며 무한 자동 retry는 하지 않는다.

`POST /users/:id/reconcile-invitation`은 다음 allowlist action만 받는다.

- `RETRY_INVITATION`: provider subject/email과 local target을 다시 확인한 뒤 당시 공식 provider 계약이 허용하는 경우에만 새 초대 링크 발송
- `CANCEL`: local 초대를 취소하고 이미 생긴 provider identity는 exact subject/email/request ownership을 확인한 경우에만 안전한 보상 처리

email만 같다는 이유로 provider identity를 연결하거나 삭제하지 않는다.

## 8. 초대 링크 수락과 최초 비밀번호 설정

1. invite email template은 `/invite/accept#token_hash={{ .TokenHash }}` 형태의 앱 링크를 사용한다. fragment는 서버 query log로 전송되지 않는다.
2. landing page는 링크를 연 것만으로 초대를 소비하지 않는다. Web은 fragment의 token hash를 메모리에만 두고 즉시 `history.replaceState`로 주소에서 제거한다.
3. 사용자가 수락 버튼을 누르면 Web이 `POST /api/auth/invitations/accept`에 token hash를 한 번 제출한다.
4. API는 exact Origin/fetch metadata, 중앙 rate limiter, DTO 길이·형식, no-store를 적용한다.
5. server-only adapter가 초대 링크를 검증하고 반환된 provider subject/email을 사전 연결된 AppUser와 대조한다.
6. 일치할 때만 DB transaction에서 `VERIFIED_PENDING_PASSWORD`, 제한 AppAuthSession, SUCCESS audit를 commit한다.
7. DB commit 뒤에만 HttpOnly cookie를 설정하고 Web은 전체 사용자 cache clear와 account-changed broadcast 후 `/auth/me`를 갱신한다.
8. provider 검증 성공 뒤 DB commit이 실패하면 cookie를 발급하지 않고 provider session을 best-effort revoke하며 총관리자 reconcile 대상으로 남긴다.
9. 사용자가 `/complete-invitation`에서 최초 비밀번호를 제출하면 server-only adapter가 비밀번호를 설정하고 DB transaction에서 `ACTIVE`, authzVersion 증가, SUCCESS audit를 commit한다.
10. 비밀번호 provider 성공 뒤 local commit이 실패하면 업무 접근은 계속 닫힌다. 같은 onboarding session의 idempotent 재시도 또는 총관리자 reconcile만 허용한다.

이미 ACTIVE session이 있는 브라우저에서는 초대 수락을 `409 ACTIVE_SESSION_PRESENT`로 거부하고 기존 cookie/cache를 교체하지 않는다. 사용자가 명시적으로 logout하거나 private browser를 사용하도록 안내한다.

만료·잘못된·이미 사용된 링크, subject/email 불일치와 replay는 계정 존재를 과도하게 드러내지 않는 `INVITATION_INVALID_OR_EXPIRED`로 처리한다. 성공/실패 모두 no-store이며 link token/hash, password, token, cookie를 URL 정리 후 logger, analytics, localStorage, audit, snapshot에 남기지 않는다.

초대 링크는 로그인 2차 인증이 아니다. 초대가 완료된 뒤 모든 일반 로그인은 기존 `/auth/login`의 이메일+비밀번호 한 단계로만 수행한다.

## 9. 역할·비활성 invariant

서버 transaction에서 다음을 보장한다.

- 마지막 활성 `SUPER_ADMIN` 강등·비활성화 금지
- 자기 자신 비활성화와 최종 관리자 권한 제거 차단
- 동시 두 총관리자 강등 경쟁조건 차단
- role allowlist와 상태 전이 검증
- role/isActive/inviteStatus 변경과 같은 transaction에서 `authzVersion +1`
- 비활성화 또는 민감 역할 변경 transaction에서 대상의 활성 AppAuthSession을 먼저 revoke
- provider revoke 실패와 무관하게 다음 요청부터 DB 상태로 즉시 차단
- revoke 부분 실패는 재시도 가능한 안전한 audit/log로 기록

마지막 총관리자 검사는 transaction isolation, row/advisory lock 또는 동등 방식으로 동시 경쟁을 막는다.

## 10. 보안 감사 범위

최소 기록:

- bootstrap super admin의 idempotent imported event
- 민감정보 없는 login success/failure 운영 기록
- invitation, provider 결과, reconcile/cancel
- role change, activate/deactivate, session revoke 결과
- 중요 제품 삭제·비활성화
- 전역/제품 setting 변경
- upload 삭제
- mapping 생성·변경·비활성화

순수 DB mutation의 상태 변경과 SUCCESS audit는 같은 Prisma transaction에 둔다. provider/filesystem 작업은 REQUESTED, PROVIDER_SUCCEEDED, COMPLETED 또는 동등한 saga 결과를 구분하고 provider 실패를 SUCCESS로 기록하지 않는다. upload 삭제 실패는 DB reference와 PARTIAL/retry 정보를 보존한다.

actor가 없는 bootstrap은 SYSTEM, 익명 login 실패는 ANONYMOUS, 일반 mutation은 USER와 actorUserId를 사용한다.

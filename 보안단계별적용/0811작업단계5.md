## 4. API 계약

권장 endpoint:

```text
GET   /api/users
POST  /api/users/invitations
PATCH /api/users/:id
POST  /api/users/:id/reconcile-invitation
GET   /api/security-audit
POST  /api/auth/invitations/confirm
POST  /api/auth/password
```

사용자 관리/reconcile endpoint는 `users.manage`, 감사 조회는 `audit.read`가 필요하다. `POST /auth/invitations/confirm`은 session-aware public allowlist이지만 exact Origin, CSRF/fetch metadata, 강한 rate limit, no-store 대상이다. `POST /auth/password`는 유효한 onboarding session만 호출 가능한 authenticated endpoint이고 CSRF 대상이다. 일반 `data.read`로 사용자 목록/감사 로그를 열지 않는다. 이 신규 route도 단계 3의 독립 method+path expected map에 같은 commit에서 추가한다.

사용자 hard DELETE endpoint는 만들지 않는다.

초대 요청 예:

```json
{
  "email": "guest@example.com",
  "name": "게스트 이름",
  "role": "GUEST"
}
```

수정 요청은 allowlist field만 허용한다.

```json
{
  "name": "변경 이름",
  "role": "USER",
  "isActive": true
}
```

email 변경은 Auth 신원과 연결되므로 이 단계에서 일반 PATCH로 허용하지 않는다. provider identity 재검증·session 폐기·감사·충돌 처리를 갖춘 별도 email 변경 절차가 생기기 전에는 immutable로 취급한다.

## 5. Prisma 모델

단계 2에서 만든 InviteStatus와 중앙 상태 판정을 그대로 사용하고, AppUser에 아직 없는 초대 metadata만 additive migration으로 추가한다.

- `invitedAt`
- `invitedBy`
- 아래 고정 `InviteStatus`가 단계 2와 정확히 일치하는지 확인
- `deactivatedAt`
- 필요하면 `lastLoginAt`

```text
PENDING_PROVIDER
INVITED
VERIFIED_PENDING_PASSWORD
ACTIVE
RECONCILE_REQUIRED
CANCELLED
```

허용 조합을 중앙 상태 머신으로 고정한다.

- `PENDING_PROVIDER`, `INVITED`, `VERIFIED_PENDING_PASSWORD`는 onboarding 진행을 뜻하므로 `isActive=true`를 유지할 수 있지만 업무 API 사용은 불가다. 상태 검사는 단순 isActive 검사보다 먼저 invitation 상태를 구분한다.
- `VERIFIED_PENDING_PASSWORD`만 `/auth/me`, `/auth/password`, `/auth/logout`을 사용할 수 있다.
- `ACTIVE && isActive=true`만 역할에 따른 업무 API를 사용할 수 있다.
- `RECONCILE_REQUIRED`, `CANCELLED`는 `isActive=false`이며 관리자가 상태를 해결하기 전 일반 로그인/onboarding을 모두 막는다. 단, 총관리자가 발급한 유효 `RECOVERY_OTP` attempt가 있는 RECONCILE_REQUIRED만 public confirm에서 한시적으로 허용한다. `CANCELLED` 또는 `isActive=false`의 기존 AppAuthSession은 즉시 폐기 대상이다.
- 상태 전이는 controller마다 문자열 비교로 복제하지 않고 중앙 함수와 DB transaction에서 검증한다.

`authUserId`와 `normalizedEmail`은 DB unique constraint로 강제한다. 단계 2의 정규화 함수를 그대로 재사용하고, 동시 초대에서 애플리케이션 선조회만 믿지 않는다.

provider 호출 전 durable 상태를 남기기 위한 모델을 추가한다.

```text
AuthOnboardingAttempt
- id UUID
- appUserId UUID FK
- purpose INVITE_VERIFY/PASSWORD_SET/RECOVERY_OTP
- status STARTED/COMPLETED/FAILED/RECONCILE_REQUIRED
- requestId nullable
- safeErrorCode nullable
- startedAt/completedAt/expiresAt
```

OTP, password, access/refresh token, cookie, provider raw response는 이 모델에 저장하지 않는다. AppUser row/advisory lock으로 한 사용자당 활성 attempt를 하나만 허용하고, 오래된 `STARTED`는 자동 성공 처리하지 않고 provider identity와 대조할 reconcile 대상으로 표시한다. `RECOVERY_OTP` attempt가 있을 때만 서버가 confirm의 provider OTP type을 `email`로 선택하며 client가 `invite`/`email` type을 임의 지정하지 못한다.

별도 append-only 감사 모델:

```text
SecurityAuditEvent
- id UUID
- actorUserId UUID nullable only when actorType is SYSTEM/ANONYMOUS
- actorType USER/SYSTEM/ANONYMOUS
- action string/enum
- targetType
- targetId nullable
- result SUCCESS/FAILURE/PARTIAL
- beforeJson nullable, 민감정보 제거
- afterJson nullable, 민감정보 제거
- requestId nullable
- createdAt
```

감사 이벤트 자체를 수정·삭제하는 API는 만들지 않는다. password, token, cookie, secret, 원본 파일 내용, 주문 개인정보를 JSON에 넣지 않는다.

## 7. 초대 saga와 부분 실패

외부 Auth와 PostgreSQL은 하나의 transaction으로 묶을 수 없으므로 성공 순서를 명시적으로 설계한다.

권장 흐름:

1. normalized email, role, name 검증
2. DB에서 중복 active/pending 사용자 확인
3. AppUser를 `PENDING_PROVIDER` 상태로 생성하거나 기존 안전한 pending 재사용
4. Supabase admin invite 호출
5. 반환된 provider Auth user id를 AppUser에 연결하고 `INVITED` 처리; 이 시점은 아직 OTP 검증 전이므로 verified라고 부르지 않음
6. 성공/실패 감사 기록

외부 호출 성공 뒤 DB update가 실패하면:

- 자동 무한 retry 금지
- 가능한 안전한 compensating action 또는 명시적 reconcile 상태 기록
- provider user와 AppUser 불일치를 조회/재처리할 관리 가능한 방법 제공
- 실패했다고 이메일/subject를 다른 AppUser에 임의 연결하지 않음

초대 API의 idempotency와 동일 email 동시 요청을 테스트한다. provider의 “이미 존재” 응답을 내부 raw message로 노출하지 않는다. provider 성공/DB 실패 시 실패한 transaction 안의 상태 기록을 신뢰하지 않는다. 선행 `PENDING_PROVIDER` row/requestId가 남아야 하며 DB 복구 뒤 reconcile worker/관리 API가 provider subject/email과 비교해 별도 transaction으로 `RECONCILE_REQUIRED`를 기록한다. 안전한 취소면 `CANCELLED`로 명시하고 운영자가 raw provider metadata 없이 조회할 수 있게 한다.

v1에는 일반 `resend-invitation` endpoint를 만들지 않는다. 만료 초대는 총관리자가 상태를 확인한 뒤, 공식 provider 동작과 identity 상태를 검증하는 **명시적 reconcile/cancel 후 새 초대** 절차로 처리한다. 확인된 Auth 사용자를 단순 삭제하거나 같은 email에 중복 identity를 만들지 않는다. 재전송은 별도 위협모델과 idempotency 계약이 정해질 때 후속 기능으로 둔다.

`POST /users/:id/reconcile-invitation`은 일반 resend가 아니다. `AuthOnboardingAttempt`가 멈췄거나 provider-confirmed/local-incomplete 불일치가 있는 대상만 받는다. 총관리자가 body의 allowlist action `ISSUE_RECOVERY_OTP` 또는 `CANCEL`을 명시하며, 서버는 provider subject+normalized email+confirmed state와 local target을 다시 대조한다. `ISSUE_RECOVERY_OTP`는 server-side `signInWithOtp({ email, options: { shouldCreateUser: false } })`의 당시 공식 계약을 확인해 기존 confirmed identity에만 recovery OTP를 보내고 `RECOVERY_OTP` attempt를 만든다. email template은 URL token 대신 `{{ .Token }}`을 표시한다. public confirm은 local attempt를 보고 `type: 'email'`을 선택한다. 이 경로는 users.manage, CSRF, 강한 rate, idempotency, audit 대상이며 provider가 새 user를 만들 수 있는 설정은 금지한다.

## 8. 역할·비활성 상태 변경 invariant

서버 transaction에서 다음을 보장한다.

- 마지막 활성 `SUPER_ADMIN`을 ADMIN/USER/GUEST로 강등할 수 없음
- 마지막 활성 `SUPER_ADMIN`을 비활성화할 수 없음
- 자기 자신을 비활성화하거나 최종 관리자 권한을 제거하는 실수를 명시적으로 차단
- target AppUser가 없거나 이미 상태가 같은 경우 안정된 응답
- 역할 문자열 allowlist
- 변경 전/후 audit event
- role/isActive/inviteStatus 변경과 같은 transaction에서 `authzVersion +1`
- 비활성화 또는 민감 역할 변경 transaction에서 해당 사용자의 활성 AppAuthSession `revokedAt`을 먼저 기록한 후 provider session revoke 시도
- provider revoke가 실패해도 DB의 매 요청 `isActive/role/AppAuthSession` 검사 때문에 권한은 즉시 차단
- 실패한 revoke는 운영자가 재시도할 수 있게 감사/로그에 기록

마지막 총관리자 검사는 단순 “조회 후 update” 경쟁조건을 만들지 않는다. 적절한 transaction isolation, row/advisory lock 또는 동등 방식으로 동시 두 강등을 막는다.

## 9. 보안 감사 범위

최소 기록:

- bootstrap super admin
- login success/failure는 과도한 개인정보 없이 rate/관측 로그로 기록
- user invitation, provider 결과, reconcile/cancel
- role change
- activate/deactivate
- session revoke 결과
- 중요 제품 삭제/비활성화
- setting 변경
- upload 삭제
- mapping 변경

위 목록은 선택사항이 아니다. 사용자/역할/상태뿐 아니라 중요 제품 삭제·비활성화, 전역/제품 설정 변경, upload 삭제, mapping 생성·변경·비활성화를 이 단계에서 모두 연결한다. 각 로컬 DB mutation의 상태 변경과 `SUCCESS` 감사 event는 같은 Prisma transaction에 기록해 audit 없이 업무 변경만 commit되지 않게 한다. 외부 provider 호출은 같은 transaction에 넣지 않고 saga 단계별 `PROVIDER_SUCCEEDED`, `PROVIDER_FAILED`, `RECONCILE_REQUIRED` 같은 별도 event로 남긴다. 실패 transaction 안에서 쓴 audit도 rollback되므로, 실패/로그인 실패는 민감정보를 제거한 중앙 보안 운영 log에 best-effort로 기록하고 성공 event인 것처럼 DB에 남기지 않는다.

작업별 원자 경계를 표로 작성한다.

- 순수 DB 제품/setting/mapping 변경: 업무 row와 `SUCCESS` audit가 같은 transaction에서 commit될 때만 성공 응답.
- 여러 내부 DB transaction을 쓰는 작업: 기존 도메인 transaction을 하나로 합칠 수 있는지 먼저 검토하고, 불가능하면 durable operation/outbox row로 단계 상태를 추적한다. 마지막 단계 전에는 최종 `SUCCESS`를 쓰지 않는다.
- upload/report/object 삭제처럼 DB+filesystem/object provider 작업: `REQUESTED/PROVIDER_SUCCEEDED/COMPLETED` 또는 동등 saga event를 구분한다. storage 삭제 전에 DB reference를 잃지 않으며, provider 실패를 `SUCCESS`로 기록하지 않는다. 부분 상태는 `PARTIAL`/`RECONCILE_REQUIRED`와 retry key를 남긴다.
- 외부 Auth 호출: provider 성공과 local commit을 별도 event로 기록하고 동일 requestId/operationId로 연결한다. secret/raw response는 제외한다.

7단계 Storage 추상화가 들어오기 전에는 upload 삭제의 현재 local file 경계를 그대로 감싼 audit/outbox hook을 구현하고, 7단계가 같은 operationId/state machine을 object adapter에 재사용한다. 감사만을 위해 파일 삭제 순서를 임의로 바꿔 reference를 잃지 않는다.

bootstrap은 단계 2 일회성 실행 시 audit 테이블이 아직 없었을 수 있으므로 이 migration/서비스 최초 검증에서 해당 AppUser에 `IMPORTED_BOOTSTRAP` 또는 동등한 합성 system event를 idempotent하게 한 번 만든다. actor가 없을 때는 `actorType=SYSTEM`, 익명 로그인 실패는 `ANONYMOUS`, 일반 mutation은 반드시 `USER`와 actorUserId를 사용한다.

## 11. 초대 확인·비밀번호 설정 고정 흐름

이 단계에서는 구현자마다 PKCE/link callback을 다르게 만들지 않고 **메일 OTP 입력 방식**으로 고정한다.

1. Supabase invite email template는 공식 `{{ .Token }}`을 일회용 코드로 표시하고, token/token_hash를 query나 fragment에 싣지 않은 앱의 `/invite/accept` 주소만 안내한다.
2. `/invite/accept`는 email과 OTP를 입력하는 정적 onboarding 화면이며 URL에서 token을 읽지 않는다. 허용되지 않은 `next`, 외부 redirect를 받지 않는다. 이미 유효한 ACTIVE session handle이 있는 브라우저는 OTP를 받기 전에 `409 ACTIVE_SESSION_PRESENT`로 거부하고 명시적 logout 또는 별도 private browser를 안내한다. 기존 총관리자 cookie를 다른 초대 계정으로 조용히 교체하지 않는다.
3. Web은 `POST /api/auth/invitations/confirm`에 `{ email, otp }`를 보낸다. URL, localStorage, analytics, logger에 OTP를 남기지 않는다.
4. API는 exact Origin/CSRF 또는 fetch metadata, 단계 2의 중앙 `SecurityRateLimiter`를 재사용한 강한 IP+정규화 email hash 제한, 길이/형식 DTO, `Cache-Control: no-store`를 적용한다. controller-local Map/timeout limiter를 새로 만들지 않으며 단계 6에서 production store를 완성한다.
5. provider 호출 **전** DB transaction에서 AppUser를 lock하고 `INVITED` 또는 허용된 `RECONCILE_REQUIRED+RECOVERY_OTP`인지, subject/email, 중복 active attempt를 검사한 뒤 `AuthOnboardingAttempt(STARTED)`를 durable하게 commit한다. secret은 저장하지 않는다.
6. API의 server-only Supabase adapter가 initial invite면 공식 `verifyOtp({ email, token: otp, type: 'invite' })`, recovery attempt면 server가 선택한 `type: 'email'` 계약으로 검증한다. client가 type을 보내지 못하며 raw provider error는 외부에 내보내지 않는다.
7. 반환 identity의 `sub`, 검증 email, JWT `session_id`가 사전 AppUser/attempt와 모두 일치할 때만 다음 DB transaction을 수행한다. AppUser/attempt를 다시 lock하고 `INVITED` 또는 승인된 `RECONCILE_REQUIRED`를 `VERIFIED_PENDING_PASSWORD + isActive=true`로 전환하고, AppAuthSession 생성, attempt `COMPLETED`, SUCCESS audit를 **한 transaction**으로 commit한다.
8. DB commit 뒤에만 access/refresh/signed session-handle HttpOnly cookie를 응답에 설정하고 Web은 모든 Query cache를 clear한 뒤 `account-changed`를 모든 탭에 broadcast하고 새 `/auth/me`를 조회한다. DB transaction 실패 시 cookie를 발급하지 않고 provider session revoke를 best-effort로 시도한다.
9. OTP가 이미 소비됐는데 DB가 실패하면 선행 `STARTED` attempt가 남는다. DB 복구 뒤 총관리자 reconcile이 provider subject/email/confirmed state와 이 attempt를 대조해 `RECONCILE_REQUIRED`로 분류하고 위의 제한된 recovery OTP를 발급한다. email만으로 자동 복구하거나 ACTIVE로 승격하지 않는다.
10. VERIFIED session은 `/complete-invitation`, `/auth/me`, `/auth/password`, `/auth/logout` 외에는 단계 3 중앙 Guard에서 `ACCOUNT_ONBOARDING_REQUIRED`로 거부한다.
11. 사용자가 `POST /api/auth/password`를 보내면 먼저 DB transaction으로 해당 AppUser/session lock과 `PASSWORD_SET STARTED` attempt를 durable commit한다. 그 다음 server-only adapter가 현재 verified identity의 비밀번호를 갱신한다. provider 성공 뒤 두 번째 DB transaction에서 `ACTIVE`, attempt `COMPLETED`, SUCCESS audit를 함께 commit한다.
12. provider password 성공 뒤 최종 DB transaction이 실패해도 실패한 transaction 안에서 `RECONCILE_REQUIRED` 기록이 남는다고 가정하지 않는다. durable `PASSWORD_SET STARTED`가 남고 업무 접근은 계속 닫힌다. 사용자는 동일 onboarding session에서 idempotent password submit을 다시 시도할 수 있다. 또는 이후 정상 password sign-in이 성공하고 subject/email과 open PASSWORD_SET attempt가 정확히 일치하면 login service가 ACTIVE 전환+AppAuthSession+audit transaction을 완료한 뒤에만 일반 cookie를 발급한다. email 일치만으로 finalize하지 않는다.
13. provider password 호출 자체가 실패하면 가능한 별도 transaction으로 attempt를 `FAILED` 처리하되 AppUser는 `VERIFIED_PENDING_PASSWORD`와 제한 session을 유지해 안전하게 재시도한다.

초대 만료, 잘못된/이미 사용된 OTP, email 불일치, replay는 계정 존재를 과도하게 드러내지 않는 안정된 `INVITATION_INVALID_OR_EXPIRED`로 처리한다. 이미 ACTIVE인 사용자의 replay는 새 session을 만들지 않는다. 성공/실패 응답 모두 no-store이며 OTP/password/token/cookie/provider raw response는 로그·audit·URL에 남기지 않는다. 메일 보안 scanner가 앱 URL을 미리 열어도 token이 없으므로 초대가 소비되지 않아야 한다.

OTP UI는 `autocomplete="one-time-code"`, 숫자/붙여넣기 정규화, 중복 submit 방지, 실패 뒤 OTP state 제거, 429의 일반화된 재시도 안내를 제공한다. 만료/오류는 계정 존재를 드러내지 않으면서 총관리자에게 새 초대/reconcile을 요청하라고 안내한다. 성공 즉시 `/complete-invitation`으로 이동하고 bfcache/뒤로 가기로 OTP 입력값이 복원되지 않게 한다.

public signup과 password recovery/reset은 v1에 포함하지 않는다. 비밀번호를 잊은 사용자는 총관리자에게 연락하며, reset은 별도의 공식 flow·세션 전부 폐기·메일 보안 위협모델을 갖춘 후 추가한다.

## 5. 최종 소스 고정

배포 직전:

- 보안 worktree clean
- branch/commit SHA 기록
- dependency lockfile 고정
- production build 재생성
- artifact/image digest 기록
- SBOM 또는 dependency 목록 보존
- secret scan과 Git history scan
- tag 예: `security-rbac-release-YYYYMMDD-HHMM`

- 사용자가 승인한 private Git remote에 security branch와 release tag push
- 암호화된 git bundle과 checksum을 승인된 별도 backup 위치에 저장
- 승인된 artifact registry에 source provenance/SBOM/image digest를 함께 보존

public repository나 계획 폴더에 secret/dump를 올리지 않는다. GitHub 등 특정 plugin/외부 계정이 준비되지 않았으면 임의 설치·로그인하지 말고 이 gate를 blocked로 남긴다.

원본 main에 새 commit이 단계 8 뒤 생겼으면 먼저 보안 branch로 merge하고 전체 단계 8 acceptance를 다시 실행한다. 검증하지 않은 merge commit을 곧바로 배포하지 않는다.

## 6. 운영 backup과 복원 증명

### DB

- provider snapshot과 가능하면 `pg_dump --format=custom`의 서로 독립된 수단
- timestamp, DB identifier, size/checksum 기록
- dump 파일과 password를 repository/worktree에 저장하지 않음
- 임시 복원 DB에 실제 restore
- schema/migration history/핵심 table row count/대표 KPI 확인
- restore 소요시간 기록

배포 전에 업무 기준의 `RPO`(허용 데이터 손실), `RTO`(허용 복구 시간), snapshot 이후 쓰기 처리 방식을 숫자로 합의한다. 단순 배포 전 snapshot은 쓰기 재개 뒤 생성된 데이터를 보호하지 못한다. provider PITR/WAL/continuous backup의 보존창과 복원 시점을 확인하고 staging에서 point-in-time restore를 연습한다. PITR이 없거나 입증되지 않으면 초기 관찰 동안 쓰기를 제한하거나, 승인된 복구 ledger와 수동 reconciliation 절차를 준비한다.

ledger는 단순 요청 ID/시각 목록이 아니라 mutation 종류별 **재구성 가능한 원천**을 가리켜야 한다. 예: append-only audit의 redacted before/after와 target/version, 저장이 승인된 upload object key+SHA-256, idempotency key, 비민감 재실행 payload 또는 별도 승인된 암호화 ledger. 개인정보/원본을 무조건 복제하지 않고 최소화·암호화·접근통제·retention을 적용한다. 재구성 입력이 없는 mutation은 PITR이 없을 때 쓰기 재개 대상에서 제외한다. `RPO=0 + PITR 없음 + 재구성 가능한 원천 없음`이면 운영 쓰기를 열지 않는다.

“backup 명령 성공”만으로 완료하지 않고 restore 검증을 필수로 한다.

### 파일/Object Storage

- versioning/backup/lifecycle 확인
- 기존 local upload/report file inventory와 hash
- 이관 대상/완료/누락 목록
- 검증 전 기존 파일 삭제 금지
- production bucket credential 최소권한
- staging에서 production과 같은 정책의 object를 실제 삭제→복원→hash 대조한 증거와, 운영 object별 version/backup 식별 방법

### Auth

- 운영 Auth project 설정 export/기록 가능한 범위
- redirect URL, site URL, email template/SMTP
- secret key를 backup 문서나 로그에 넣지 않음
- signing key/JWKS와 server secret 회전 시 이전·새 키 overlap 시간, API/Web deploy 순서, rollback 가능한 이전 key 보관/폐기 승인, IAM 최소권한과 비상 credential 절차

## 8. 안전한 배포 순서

업무용 앱이 local dev watcher로 원본 main을 사용 중이면 main merge가 즉시 reload를 일으킬 수 있다. 따라서 유지보수 승인 전에는 원본 main에 merge하지 않는다.

권장 순서:

1. 사용자에게 업무 쓰기 중지를 공지하고 maintenance window 시작
2. **Web/API release와 독립적인** edge/reverse proxy/host maintenance 또는 외부 접근차단을 먼저 켜고 실제 외부 요청이 차단되는지 확인
3. 최종 운영 DB backup과 restore 가능 증거 확인
4. object/local file 최종 backup
5. 운영 Auth 설정과 최초 SUPER_ADMIN Auth user 준비
6. 검토된 additive migration을 `prisma migrate deploy`로 적용
7. 일회성 bootstrap을 dry-run 후 승인된 user에 실행
8. 8단계에서 검증된 digest의 API 배포
9. 8단계에서 검증된 동일 Web digest를 배포하거나, build-time proxy 제약으로 승인된 production-config pre-production slot에서 검증한 동일 digest를 승격
10. 내부 URL에서 SUPER_ADMIN login/me/logout 확인
11. 네 역할 smoke test
12. 핵심 upload/change log/report 흐름과 KPI 검사
13. 공식 domain/DNS를 새 서비스로 전환 또는 maintenance 해제
14. PITR/write ledger 준비와 배포 직후 기준점을 확인한 뒤 제한적으로 쓰기 재개
15. 초기 집중 관찰과 snapshot 이후 write reconciliation
16. 안정 확인 후 보안 branch를 main에 통합하고 원본 업무 환경을 새 안정 버전으로 갱신

API와 Web 사이에 구버전/신버전 계약 불일치가 생기지 않도록 maintenance 상태에서 짧게 연속 배포한다.

DNS 전환 전 TTL을 미리 낮출 시점, 새/이전 endpoint의 TLS 인증서와 hostname 검증, cache/CDN purge, DNS rollback 소요시간을 합의한다. 전환 당일에 처음 maintenance/DNS rollback을 시험하지 말고 staging 또는 비공개 hostname에서 edge 차단→새 upstream→이전 upstream 복귀를 rehearsal한다.

## 9. production migration 규칙

- `prisma migrate dev` 금지
- `prisma db push` 금지
- 기존 migration SQL 수정 금지
- 검토된 `prisma migrate deploy`만 사용
- 대상 DB host/project/schema를 비밀값 없이 이중 확인
- migration 중 lock/connection/error 관찰
- 예상 시간/lock을 넘으면 즉시 중단 판단
- 즉흥적인 수동 ALTER/DELETE/UPDATE 금지
- down migration을 rollback 수단으로 가정하지 않음

additive migration 뒤 이전 code rollback이 가능한지 staging에서 증명돼 있어야 한다.

## 11. 네 역할 smoke test

실제 production에는 기본적으로 기존 읽기 데이터와 validation-only/dry-run endpoint를 사용한다. 대량/삭제 테스트는 하지 않는다. 쓰기 smoke가 꼭 필요하면 사전에 각 작업의 예상 row/file/audit delta와 식별 가능한 테스트 key를 정하고 사용자에게 별도 승인받는다.

### GUEST

- login, dashboard/read/report download
- mutation UI 없음
- 대표 mutation 직접 API 403

### USER

- 조회
- 승인된 synthetic change log 1건 작성 시 change-log `+1`, audit `+1` 등 예상 delta와 작성자 확인
- report generate가 실제 DB/object를 만들면 report `+1`, object `+1`, audit delta를 미리 기록; 가능하면 validation-only 사용
- product/upload/mapping/settings 직접 API 403

### ADMIN

- 제품/규칙 mutation 권한은 validation-only 또는 기존 값에 대한 no-op/idempotency 검증을 우선하고, 실제 변경은 별도 승인 및 예상 audit delta가 있을 때만 수행
- upload 권한 확인은 parser validation-only 또는 이미 처리된 동일 hash가 `SKIP`되는 흐름을 우선한다. 새 import는 업무 집계가 변하므로 단순 smoke 용도로 실행하지 않는다.
- users/audit API 403

### SUPER_ADMIN

- users list/초대 없이 role/status read 가능
- user 관리 권한 확인
- security audit 확인

검증용 기록이 업무 데이터에 남으면 식별 가능한 reason을 사용하고, 삭제가 감사 의미를 훼손하면 임의 삭제하지 않는다. “모든 row count가 같아야 한다”와 “쓰기 smoke 성공”을 동시에 요구하지 않는다. 배포 전후 비교표에는 각 승인된 쓰기의 예상 delta, 실제 delta, 업무 집계 영향, reconciliation 결과를 별도 열로 기록한다.

## 13. 실패 기준

다음 중 하나면 쓰기를 열지 않거나 즉시 maintenance로 되돌린다.

- SUPER_ADMIN 로그인 불가
- 익명/게스트 mutation 성공
- 역할 권한표 위반
- migration 오류/예상 밖 lock
- 핵심 KPI 또는 row count 차이
- upload/import가 데이터를 중복/삭제
- report/storage 접근 실패
- token/secret/DB 정보 노출
- 지속적 5xx/DB pool 고갈
- rollback artifact/backup 복원 가능성을 증명할 수 없음
- snapshot 이후 승인된 write를 PITR/write ledger로 복구·reconcile할 수 없음

정량 임계값은 배포 전 사용자와 합의해 진행상태에 적는다.

## 14. 롤백 원칙

가장 중요한 원칙: **공개 주소에서 인증이 없는 구버전으로 단순 롤백하지 않는다.**

코드 롤백이 필요하면:

1. 공식 주소를 maintenance/접근차단 상태로 전환
2. 현재 DB/file 상태와 로그 보존
3. additive schema와 호환되는 검증된 이전 secure artifact가 있으면 배포
4. 무인증 구버전밖에 없으면 외부 접근은 닫고 원본 업무 앱은 localhost/VPN 등 제한 환경에서만 사용
5. 데이터 손상이 없으면 DB를 불필요하게 restore하지 않음
6. 데이터 손상이 있으면 쓰기를 계속 막고 RPO 안의 PITR 시점을 **새 DB**에 restore한 뒤 검사; snapshot만 가능하면 snapshot 이후 write ledger를 대조하고 사용자가 허용 손실을 승인하지 않은 상태에서 강행 금지
7. 연결 문자열 전환으로 복구하고 손상 DB는 증거로 보존
8. object는 version/backup에서 새 prefix/bucket으로 복원하고 DB key와 hash를 대조한 뒤 전환
9. Auth/JWKS/secret 회전 때문에 실패했다면 이전·새 키 overlap 계획과 IAM break-glass 절차로 복구하고, 서둘러 모든 이전 키를 폐기해 rollback 자체를 막지 않음

운영 DB에서 즉흥 down migration, DELETE, backup 덮어쓰기를 하지 않는다.

## 15. 초기 관찰

최소 초기 집중 관찰 항목:

- 5xx/401/403/429 비율
- login/refresh 실패
- DB connection/slow query
- upload/import duration/memory/error
- storage error/download
- Next proxy timeout
- CSP/browser error
- 사용자별 cache 이상
- audit event

세션이 장시간 지속 모니터링을 할 수 없으면 사용자에게 관찰 대시보드와 후속 확인 시각을 명확히 인계한다. “배포 직후 200 한 번”으로 완료하지 않는다.

PITR/write reconciliation이 검증되지 않았으면 초기 관찰 동안 일반 사용자의 쓰기를 열지 않거나 매우 제한된 승인 계정만 사용한다. 쓰기를 연 뒤에는 마지막 backup/PITR checkpoint 이후 생성된 requestId·업무 key·audit/object 변화가 ledger와 맞는지 집중 관찰 종료 전에 대조한다.

## 16. main 통합과 원본 업무환경

production 안정 확인 뒤에만 사용자 승인 범위에서:

- 원본 main working tree 상태와 해당 폴더를 감시하는 dev process를 확인
- main merge 전에 local 필수 변수 **이름**, Auth project/issuer 식별자, exact Origin, cookie secure mode, storage provider, DB host fingerprint의 readiness를 값 노출 없이 검증하고 신규 secret 주입 승인을 받음
- 기존 local `.env`는 repository 밖의 접근제한된 위치에 복구용 backup/checksum을 만들고, 새 필수값은 merge 후 즉석 작성하지 말고 승인된 secret source에서 미리 준비함. backup/secret 값은 계획·Git·로그에 기록하지 않음
- security worktree의 검증된 release를 별도 포트에서 최종 local 설정으로 먼저 기동해 health/login/read-only smoke를 통과시킴. 기존 watcher/3100/4100은 이 preflight 동안 계속 업무를 처리함
- main merge 실패 시 사용할 이전 main commit의 별도 detached rollback worktree 또는 검증된 old local artifact와 기존 env 복구 절차를 미리 준비하고 승인함
- local 원본이 여전히 업무에 쓰이면 별도의 짧은 local maintenance를 공지하고 **watcher를 먼저 중지**한 뒤에만 main 통합 시작
- 다른 user 변경 보존
- 보안 branch commit을 main에 비파괴적으로 통합; merge 중간 상태에서 업무 process를 다시 시작하지 않음
- 원본에서 test/build
- 원본 main에서 test/build와 새 process health/login을 다시 확인한 뒤에만 기존 포트를 교체
- 새 운영 버전 실행 방법 문서화하고 local smoke 성공 뒤 maintenance 해제

main 통합 또는 신규 env 주입이 실패하면 원본을 reset/checkout으로 덮지 않는다. 외부 접근을 유지보수로 둔 채 준비된 이전 commit의 rollback worktree/artifact와 기존 env backup으로 old process를 재기동하고, 실패한 main 상태는 증거로 보존한다.

hosted production이 이미 유일한 업무 기준이라 local main 통합은 긴급 배포 흐름과 분리해 다음 승인 창에 할 수 있다. 이 경우 old local watcher가 더 이상 업무 요청을 받지 않는다는 사실과 안전한 후속 절차를 기록한다.

force push/reset/checkout으로 main을 맞추지 않는다.

## 17. 최종 기록

진행상태와 별도 배포 기록에 다음을 남긴다.

- 사용자 승인 항목과 시각
- 배포 commit/tag/image digest
- backup identifier/checksum과 restore 증거(비밀 경로 제외)
- 적용 migration
- SUPER_ADMIN bootstrap 결과
- 네 역할/KPI/storage smoke 결과
- DNS/TLS 상태
- 관찰 지표
- 발생 결함과 조치
- rollback 가능 artifact/절차
- RPO/RTO, PITR checkpoint, snapshot 이후 write reconciliation 결과
- source private backup/tag와 artifact provenance
- Auth key/IAM rollback, object 실제 restore 증거
- main 통합 commit
- 남은 운영 위험과 다음 점검일

## 18. 완료 조건

- 실제 restore 가능한 backup 증명
- migration과 deploy 성공
- 네 역할과 핵심 업무/KPI 성공
- 공개 주소 HTTPS/Auth/RBAC/Storage 정상
- 비밀값/내부오류 노출 없음
- 초기 관찰 실패 기준 미도달
- rollback 가능 상태 유지
- 합의 RPO/RTO와 snapshot 이후 write reconciliation 충족
- `RPO=0`이면 PITR 또는 모든 허용 mutation의 재구성 가능한 원천이 증명됨
- 원본 업무환경도 승인된 새 안정 버전으로 인계
- 사용자에게 최종 주소와 운영 방법 전달

9단계도 release 기준 commit과 최종 배포 기록 commit을 분리한다. 운영 명령 전에 검증 가능한 계획/manifest 변경을 첫 commit으로 고정하고, 그 SHA/digest를 배포한다. 운영 결과를 기록한 두 번째 commit을 만든다.

```text
feat(security): release authenticated role-based application
docs(security): record production deployment and recovery evidence
```

두 번째 commit 자신의 SHA를 문서 안에 쓰지 않는다. 최종 branch/worktree가 clean인지 확인하고, main 통합 commit SHA는 Git이 만든 뒤 최종 기록에 별도로 추가하거나 외부 배포 기록에 보존한다.

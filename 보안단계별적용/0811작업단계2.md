## 4. 고정 API 계약

### 4.1 endpoint

```text
POST /api/auth/login
POST /api/auth/refresh
POST /api/auth/logout
GET  /api/auth/me
```

`login`, `refresh`, `logout`은 브라우저 cookie를 변경하므로 이 단계부터 정확한 `Origin` allowlist와 CSRF 계약을 적용한다. 6단계는 이를 모든 업무 mutation으로 확장한다. `logout`은 만료/깨진 cookie도 지울 수 있도록 Guard 의미의 public endpoint로 두되, 제공된 session을 식별할 수 있으면 폐기하고 인증 성공 여부와 무관하게 항상 cookie를 삭제하는 **session-aware public** endpoint다. 무제한 익명 호출을 허용한다는 뜻이 아니며 Origin·CSRF·rate limit 대상이다.

로그인 요청:

```json
{ "email": "user@example.com", "password": "..." }
```

로그인 및 `/auth/me` 응답은 token을 포함하지 않는다.

```json
{
  "user": {
    "id": "app-user-uuid",
    "email": "user@example.com",
    "name": "사용자명",
    "role": "USER",
    "isActive": true
  },
  "permissions": ["data.read", "change_logs.create", "reports.generate"],
  "authorizationVersion": "opaque-version"
}
```

`permissions` 계산 함수는 이 단계에서 중앙화하고 3단계 Guard와 4단계 Web이 그대로 재사용한다. `authorizationVersion`은 DB의 단조 증가 `AppUser.authzVersion`을 외부용 opaque string으로 표현한 값이며 개인정보/role을 encode하지 않는다. role/isActive/inviteStatus를 바꾸는 모든 transaction은 이를 원자적으로 `+1`한다. Web은 값 변경을 감지해 권한 UI와 사용자별 cache를 재동기화한다.

### 4.2 오류 계약

- cookie 없음: `401 AUTHENTICATION_REQUIRED`
- 서명·issuer·audience·형식이 잘못된 access JWT: `401 SESSION_INVALID`
- 정상적으로 만료된 access JWT: `401 ACCESS_TOKEN_EXPIRED`
- DB에서 폐기된 session: `401 SESSION_REVOKED`
- 이메일/비밀번호 로그인 실패: 계정 존재를 구분하지 않는 `401 INVALID_CREDENTIALS`
- 유효한 Supabase 계정이나 AppUser 미등록: `403 ACCOUNT_NOT_PROVISIONED`
- 비활성 AppUser: `403 ACCOUNT_INACTIVE`
- 초대 확인 후 비밀번호 설정 전 계정: `403 ACCOUNT_ONBOARDING_REQUIRED`
- 인증은 유효하나 endpoint 권한 부족: `403 PERMISSION_DENIED`
- Auth 공급자 일시 장애: 내부 세부정보 없는 `503 AUTH_PROVIDER_UNAVAILABLE`
- 동시 refresh 회전 경합으로 바로 한 번 재시도 가능한 경우: `409 REFRESH_RACE_RETRY`

기존 `{ code, message, details }` 응답 형태와 `ApiError` 파싱 호환성을 유지한다. Web은 **오직** `ACCESS_TOKEN_EXPIRED`에서만 refresh하고, 다른 401/403을 모두 refresh로 뭉뚱그리지 않는다.

## 5. Prisma 변경

`apps/api/prisma/schema.prisma`에 다음 개념을 추가한다.

```prisma
enum AppRole {
  SUPER_ADMIN
  ADMIN
  USER
  GUEST
}

enum InviteStatus {
  PENDING_PROVIDER
  INVITED
  VERIFIED_PENDING_PASSWORD
  ACTIVE
  RECONCILE_REQUIRED
  CANCELLED
}
```

`AppUser` 권장 필드:

```text
role              AppRole  @default(GUEST)
inviteStatus      InviteStatus @default(PENDING_PROVIDER)
authUserId        UUID?    unique
normalizedEmail   String?  unique
lastLoginAt       DateTime?
deactivatedAt     DateTime?
authzVersion      Int @default(1)
```

기존 `id`, `email`, `name`, `isActive`, timestamps는 재사용한다. 비밀번호 hash, access token, refresh token을 AppUser에 추가하지 않는다.

Supabase logout만으로 이미 발급된 access JWT를 즉시 무효화할 수 없으므로 다음 개념의 앱 session을 추가한다. 원문 access/refresh token은 절대 저장하지 않는다.

```text
AppAuthSession
- id UUID
- appUserId UUID FK
- providerSessionId string unique       # 검증된 JWT의 session_id claim
- revokedAt DateTime nullable
- lastSeenAt DateTime nullable
- refreshedAt DateTime nullable
- createdAt / updatedAt
```

로그인 때 `session_id`가 있는 JWT만 session row에 연결하고, 매 인증 요청마다 JWT 검증 → AppUser active/onboarding 상태 → `AppAuthSession.revokedAt` 순서로 중앙 확인한다. logout, 사용자 비활성화, 보안상 전체 session 회수 때 `revokedAt`을 먼저 기록해 다음 요청부터 즉시 차단한다. Auth 공급자 session 폐기는 그 다음 외부 작업이며 실패해도 앱 차단은 유지한다.

### 5.1 migration 안전 원칙

1. 개발 DB에서 기존 role 값과 개수를 먼저 감사한다.
2. `SUPER_ADMIN`, `ADMIN`, `USER`, `GUEST` 외 값이 있으면 자동 ADMIN 승격하지 말고 중단·보고한다.
3. 기존 `ADMIN`은 데이터 migration에서 임의로 모두 `SUPER_ADMIN`으로 올리지 않는다.
4. 현재 `role TEXT DEFAULT 'ADMIN'`을 PostgreSQL enum으로 바꿀 때 column drop/recreate를 금지한다. migration SQL은 기존 default 제거 → enum type 생성 → 허용값을 명시한 `USING CASE`/검증된 cast로 in-place 변환 → `DEFAULT 'GUEST'` 설정 순서로 작성한다.
5. 전환 전후 모든 AppUser의 `id → role` 목록/count/checksum이 동일함을 검증하고, SQL에 role column/data 삭제나 전체 ADMIN 일괄 변경이 없는지 migration spec으로 검사한다.
6. 새 기본 역할은 반드시 `GUEST`, 새 기본 초대 상태는 `PENDING_PROVIDER`다. migration 전부터 존재한 AppUser는 기존 업무 호환을 위해 명시적으로 `ACTIVE` backfill하되 `authUserId`가 없으면 여전히 로그인할 수 없다. bootstrap SUPER_ADMIN도 명시적으로 `ACTIVE`를 설정한다.
7. `authUserId`는 최초에는 nullable로 추가해 레거시 행과 기존 앱 호환을 유지한다.
8. `normalizedEmail`은 먼저 nullable/non-unique로 추가한다.
9. 애플리케이션과 동일한 고정 규칙(`trim` 후 Unicode/도메인 정책을 문서화한 lowercase; provider가 보장하지 않는 점 제거나 plus-address 제거는 금지)으로 기존 행을 dry-run 계산한다.
10. 빈 값·형식 오류·정규화 충돌 목록을 내고 임의 병합/삭제/승격하지 않는다. 충돌이 0일 때만 backfill한다.
11. backfill 결과에 NULL/중복이 없음을 재검증한 다음 unique index를 별도 단계로 만든다. 초대/patch도 같은 중앙 정규화 함수를 사용한다.
12. migration SQL은 빈 DB와 대표 데이터가 있는 개발 DB 양쪽에서 검증한다.
13. 기존 migration 파일을 수정하지 않는다.
14. seed가 기존 사용자의 역할을 매 실행마다 덮어쓰지 않게 수정한다.
15. 기존 `admin@meta-ads-performance.local`은 인증 가능한 실제 계정으로 간주하지 않는다.

운영 migration은 이 단계에서 실행하지 않는다.

구체적인 이름은 기존 스타일에 맞춰 조정할 수 있지만 역할은 분리한다.

### 6.1 공급자 추상화

Guard나 Controller에 Supabase SDK 호출을 직접 넣지 않는다. `IdentityProvider` 또는 동등한 인터페이스 뒤에 다음 동작을 둔다.

- password sign-in
- refresh session
- logout/revoke
- access JWT 검증
- 관리자 user 조회는 5단계에서 확장

테스트는 이 인터페이스를 fake로 대체할 수 있어야 한다. 요청별 사용자 token 상태가 module-scope singleton client에 남지 않게 한다. `persistSession`, 자동 refresh 등 브라우저용 동작을 서버에서 끈다.

### 6.2 JWT 검증

- 검증된 JWT 라이브러리와 Supabase JWKS를 사용한다.
- signature, algorithm, `iss`, `aud`, `exp`, `sub`를 모두 검증한다.
- `session_id` claim이 존재하고 합리적인 형식인지 검증하며, 이를 raw token 대신 앱 session 식별자로 사용한다.
- `sub`가 UUID 형식인지 확인한다.
- JWKS key rotation과 합리적인 cache를 지원한다.
- JWT payload를 decode만 하고 서명 검증을 생략하지 않는다.
- Supabase의 Postgres `role` claim을 `AppRole`로 해석하지 않는다.
- 개발 프로젝트가 legacy shared secret signing만 사용하면 공식 권장 검증 방법을 확인하고 임의 secret 비교를 구현하지 않는다.

### 6.3 AppUser 확인

JWT 검증 뒤 `authUserId=sub`인 AppUser와 `providerSessionId=session_id`인 AppAuthSession을 DB에서 읽는다. 매 요청 DB 조회를 기본으로 하여 역할 변경·비활성화·session 폐기가 다음 요청부터 적용되게 한다. 캐시를 도입하지 않는다. 이 상태 판정은 `AuthService`의 한 함수로 중앙화하며 Guard, `/auth/me`, refresh가 각기 다른 규칙을 만들지 않는다.

Principal 예:

```ts
type AuthenticatedUser = {
  id: string;
  authUserId: string;
  email: string | null;
  name: string;
  role: AppRole;
  permissions: Permission[];
};
```

서비스는 Supabase user id가 아니라 애플리케이션 `AppUser.id`를 작성자 ID로 사용한다.

## 7. 쿠키 정책

API가 access/refresh token을 응답 body로 반환하지 않고 쿠키로 설정한다.

운영 cookie 요구사항:

- `HttpOnly=true`
- `Secure=true`
- `SameSite=Lax`
- `Path=/`
- `Domain` 미지정
- access와 refresh를 서로 다른 cookie 이름으로 분리
- access/refresh와 별도로 `AppAuthSession.id`를 HMAC 서명한 opaque HttpOnly session-handle cookie 사용; raw provider token/session_id/role/email을 넣지 않음
- production은 가능하면 `__Host-` prefix 사용
- 개발 localhost에서는 Secure 정책을 환경에 맞게 명시적으로 분기하되 운영에서 false가 될 수 없게 환경 검증

`Path=/api`를 사용하면 브라우저가 실제 `/backend-api` 경로에 cookie를 보내지 않을 수 있으므로 금지한다.

로그인/refresh 응답에는 `Cache-Control: private, no-store`, `Pragma: no-cache`를 설정한다. cookie, password, token은 Logger, exception, 테스트 snapshot에 기록하지 않는다.

## 8. 로그인·refresh·logout 동작

### 로그인

1. DTO로 이메일 형식과 합리적 길이, password 최대 길이를 검증한다.
2. Supabase Auth 로그인 수행
3. 반환된 Auth user id와 검증된 email이 사전 프로비저닝 AppUser와 일치하는지 확인
4. 미등록/비활성/`ACTIVE`가 아닌 계정이면 공급자 세션을 폐기하고 일반 login cookie를 설정하지 않음. onboarding session은 5단계의 일회용 초대 링크 수락 endpoint에서만 발급
5. 반환 JWT의 `session_id`로 AppAuthSession을 생성/갱신하고 `lastLoginAt`을 갱신한 뒤 cookie 설정, `/me` 응답 반환

bootstrap은 AppUser/Auth identity 연결만 만들며 AppAuthSession을 미리 만들지 않는다. session row는 실제 login/초대확인 성공 때만 생성한다.

### refresh

- refresh cookie가 없으면 일반 401
- 서명된 session-handle cookie도 필수로 검증하고 AppAuthSession row를 먼저 조회; access cookie가 만료·삭제돼도 이 handle로 lock key와 revoke 대상을 식별
- provider의 token rotation 결과를 원자적으로 새 cookie로 교체
- 대응 AppUser가 비활성/미등록이면 cookie 삭제 후 거부
- access JWT 수명은 애플리케이션 임의 env가 아니라 Supabase Auth 프로젝트 설정에서 관리한다. 10~15분 수준을 출발안으로 검토하되 당시 공식 권고와 실제 장애 복구 시간을 확인하고, 5분 미만으로 임의 축소하지 않는다. 개발/스테이징/운영 설정값을 secret 없이 기록하며 짧은 TTL은 AppAuthSession의 즉시 폐기를 대체하지 않는다.
- 같은 signed session handle이 가리키는 `AppAuthSession.id`를 기준으로 PostgreSQL advisory lock/row lock 또는 동등한 **서버측 분산 lock**으로 refresh를 직렬화한다. lock 안에서 저장된 providerSessionId와 새 JWT의 `session_id` 일치를 검증한다. 단일 Node process mutex만으로 끝내지 않는다.
- 먼저 성공한 회전과 겹친 요청은 최근 `refreshedAt`/session 상태를 확인한다. 정상 경합이면 기존 cookie를 파괴하지 말고 `409 REFRESH_RACE_RETRY`를 반환해 Web이 상태 동기화 후 한 번만 재시도하게 한다. 진짜 재사용 공격/폐기 session은 `SESSION_REVOKED`로 cookie를 지운다.

### logout

- access JWT가 없거나 만료됐더라도 signed session handle로 해당 AppAuthSession의 `revokedAt`을 먼저 기록. handle이 위조됐으면 row를 건드리지 않고 cookie만 삭제
- 공급자 세션 폐기를 시도
- 공급자 장애가 있더라도 로컬 cookie는 항상 만료
- session-aware public logout도 CSRF/Origin/rate 정책 대상
- token 자체를 응답/로그에 기록하지 않음

### 8.1 이 단계의 최소 CSRF/Origin

- `APP_ALLOWED_ORIGINS`의 exact origin 목록을 login/refresh/logout에 적용하며 wildcard, suffix 비교, production localhost 허용을 금지한다.
- login 응답 또는 별도 안전한 bootstrap 응답에서 non-HttpOnly CSRF cookie를 발급하고, refresh/logout은 cookie+`X-CSRF-Token`의 서명/일치와 Origin을 검사한다.
- CSRF cookie도 `Secure`(production), `SameSite=Lax`, `Path=/`, `Domain` 미지정이며 인증 cookie와 이름이 분리된다.
- login 자체는 사전 CSRF cookie가 없을 수 있으므로 exact Origin, fetch metadata를 검증하고 강한 rate limit을 둔다. 구현자가 단순 임의 header 존재만으로 통과시키지 않는다.
- 인증 시도 제한은 주입 가능한 중앙 `SecurityRateLimiter` 계약 뒤에 둔다. 단계 2 개발/테스트 adapter를 controller 안의 Map으로 중복 구현하지 않으며, 단계 6이 hosting topology에 맞는 atomic distributed store 또는 증명된 single-instance adapter를 연결한다. 단계 6 전 branch는 운영 배포 금지다.
- 4단계 Web은 이 계약을 중앙 client에서 전송하고, 6단계는 같은 검증기를 모든 상태 변경 route에 확대한다. 서로 다른 CSRF 구현을 새로 만들지 않는다.

## 9. 최초 총관리자 bootstrap

public signup이나 “첫 로그인 사용자를 자동 총관리자”로 만드는 로직은 금지한다.

일회성 CLI 또는 script를 만든다.

- 사용자가 Supabase Dashboard에서 만든 실제 Auth user UUID와 email을 명시적으로 입력
- Supabase 관리자 API로 해당 subject와 검증된 email을 확인
- AppUser를 `SUPER_ADMIN`, `isActive=true`, `authUserId`와 연결
- 이미 다른 AppUser에 연결된 subject/email이면 중단
- 실행 대상 DB host/schema와 대상 email/id를 비밀값 없이 확인시킨 뒤 수행
- dry-run 지원
- 실행 결과를 감사 가능한 일반 로그로 남기되 secret/token 미출력
- 앱 startup 때 자동 실행하지 않음

개발/스테이징에서 먼저 검증하고 운영 bootstrap은 9단계 승인 뒤에만 한다.

## 10. 환경변수

`.env.example`에는 값 없이 변수 이름과 설명만 추가한다.

```env
SUPABASE_URL=""
SUPABASE_PUBLISHABLE_KEY=""
SUPABASE_SECRET_KEY=""
SUPABASE_JWT_ISSUER=""
SUPABASE_JWT_AUDIENCE="authenticated"
AUTH_COOKIE_SECURE=false
AUTH_SESSION_HANDLE_SECRET=""
APP_ALLOWED_ORIGINS="http://127.0.0.1:3200,http://localhost:3200"
```

session-handle secret은 충분한 entropy의 별도 secret이며 CSRF/JWT/provider secret과 재사용하지 않는다. secret key는 초대/bootstrap 같은 관리자 작업에만 쓰며 Web env에 추가하지 않는다. DATABASE_URL에서 project id나 credential을 파싱해 대신 사용하지 않는다.

Supabase/JWT/cookie/validation dependency는 기존 lockfile과 당시 공식 문서의 호환 버전을 확인해 root/workspace 중 기존 package 관리 위치 한 곳에만 추가한다. 별도 JWT verifier, 임의 crypto, Supabase client 중복을 만들지 않는다. 이 단계는 auth controller 자체의 method+path·public/authenticated·Origin/CSRF 계약 테스트를 만든다. 전체 애플리케이션의 독립 route expected map과 fail-closed 전역 테스트는 3단계에서 **최초 생성**하며, 그때 이 auth route들을 포함한다.

## 11. 테스트

최소 신규 테스트:

```text
apps/api/src/auth/role-permissions.spec.ts
apps/api/src/auth/supabase-jwt.verifier.spec.ts
apps/api/src/auth/authentication.guard.spec.ts
apps/api/src/auth/auth.service.spec.ts
apps/api/src/auth/auth.controller.spec.ts 또는 auth HTTP 통합 테스트
apps/api/src/auth/bootstrap-super-admin.spec.ts
apps/api/src/auth/security-auth-migration.spec.ts
```

필수 사례:

- 정상 로그인과 cookie 속성
- 잘못된 이메일/비밀번호의 일반화된 오류
- token이 응답 body와 로그에 없음
- signed session handle 위조/누락/다른 사용자 row 교체, handle에는 provider 정보가 없음
- cookie 없음, 위조, 잘못된 alg/issuer/audience, 만료 token
- access 만료만 `ACCESS_TOKEN_EXPIRED`, 위조/폐기/미등록/비활성/onboarding 오류 코드 분리
- JWKS key rotation
- `session_id` 없음/변조, 미등록 AppAuthSession, revoked session
- 유효 Auth user지만 AppUser 없음
- 비활성 AppUser
- role 변경이 다음 요청에 즉시 반영
- refresh 성공/실패/회전, 두 탭 동시 refresh와 서버 lock, `REFRESH_RACE_RETRY`가 기존 cookie를 지우지 않음
- logout cookie 삭제와 provider 실패, 만료 access cookie 상태에서도 AppAuthSession 폐기
- auth endpoint no-store
- login/refresh/logout 허용·비허용 Origin과 CSRF cookie/header 속성
- unknown role migration 거부
- email 정규화 충돌 거부
- bootstrap dry-run, 중복 subject, 잘못된 email, 자동 실행 금지
- 빈 DB와 대표 개발 DB migration 후 기존 업무 테이블 row count/금액 불변

`@nestjs/testing` 등 새 테스트 의존성이 필요하면 기존 package 구조를 확인하고 최소 범위로 추가한다.

## 12. 평가자가 집중할 결함

- JWT를 decode만 하고 검증하지 않음
- issuer/audience/algorithm 미검증
- JWT role을 앱 role로 신뢰
- AppUser를 매 요청 확인하지 않아 비활성화가 늦게 적용
- provider logout만 믿어 이미 발급된 access JWT가 계속 성공
- AppAuthSession을 확인하지 않거나 raw token을 DB에 저장
- access/refresh token이 JSON, localStorage, 로그에 노출
- cookie Path가 `/api`
- production에서 Secure=false 허용
- public signup 또는 첫 사용자 자동 SUPER_ADMIN
- seed가 role을 덮어씀
- 기존 ADMIN 전원을 SUPER_ADMIN으로 자동 승격
- module-scope 사용자별 Supabase client/session 공유
- 여러 API instance에서 process-local refresh mutex만 사용
- provider 오류 message를 그대로 반환
- 운영 DB에서 migration/seed 실행

## 13. 완료 조건

- 개발 DB migration과 rollback이 아닌 restore 전략이 검증됨
- 실제 개발 Auth 계정으로 login → me → refresh → logout 성공
- 비활성/미등록 계정 차단
- token 비노출과 cookie 속성 테스트 통과
- 역할/permissions 응답 계약 고정
- 전체 기존 prisma validate, lint, test, build 통과
- 독립 평가 열린 결함 0
- 신규 auth route의 local method+path/접근 계약 테스트 통과; 3단계 전체 expected map에 넘길 목록이 진행상태에 기록됨
- 진행상태 업데이트

이 단계도 다른 단계와 동일하게 두 commit으로 인계한다.

```text
feat(security-step2): add Supabase-backed API authentication
docs(security-step2): record verified implementation handoff
```

첫 commit SHA와 테스트/평가 결과를 진행상태에 기록한 뒤 두 번째 문서 commit을 만든다. 문서 commit 자신의 SHA를 자기 내용에 쓰지 말고, 3단계 세션이 시작 HEAD로 기록한다. 최종 worktree는 clean이어야 한다.

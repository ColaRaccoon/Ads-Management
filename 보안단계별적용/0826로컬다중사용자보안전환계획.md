# 로컬 다중 사용자 보안 전환 계획 — 기존 Supabase DB만 유지

작성: 2026-08-26  
최종 사용자 결정 반영: 2026-08-27

## 0. 우선순위와 최종 정정

이 문서는 2026-08-27 사용자의 마지막 결정을 반영한다. 문서의 과거 초안,
단계 8의 cloud staging 가정, 중간에 작성된 “Supabase Auth/Storage 유지” 제안보다
아래 결정이 우선한다.

- 기존 **Supabase PostgreSQL DB만** 그대로 사용한다.
- 인증은 이메일/Supabase Auth가 아니라 **local native username Auth**다.
- 파일은 Supabase Storage가 아니라 repository 밖의 **NTFS local Storage**다.
- 로컬 PostgreSQL과 Supabase self-hosting은 사용하지 않는다.
- 기존 Supabase 프로젝트의 Auth, Storage, hosting 기능은 이 배포에서 호출하지 않는다.
- 실제 Supabase production DB 변경은 별도 즉시 승인 없이는 수행하지 않는다.

## 1. 목표 구조

```text
허용된 LAN client
  -> HTTPS 443 (명시한 private server IP의 Windows Edge만 수신)
       -> Web 127.0.0.1:3200
       -> 서명된 내부 요청 -> API 127.0.0.1:4200
            -> TLS verify-full outbound -> 기존 Supabase PostgreSQL :5432
            -> repository 밖 NTFS data/storage
```

Web/API/DB 포트와 파일 경로는 LAN에 직접 노출하지 않는다. 인터넷 공개,
router port forwarding, UPnP, public DNS, cloud hosting, container registry,
외부 배포와 과금은 금지한다. 원본 main worktree 및 기존 3100/4100은 전환
승인 전까지 수정·중지·재시작하지 않는다.

## 2. 이식성 원칙

- hostname, IP, Windows 계정명, drive letter, repository/data/backup 경로를
  코드에 고정하지 않는다.
- 핵심 Node Web/API/Auth/Storage/config 검증은 cross-platform으로 유지한다.
- Windows service, local account right, NTFS ACL, Firewall, CA trust-store 작업은
  `deploy/windows` host 계층으로 분리한다.
- release는 immutable하고 data, secret, evidence, log, backup은 모두 release와
  repository 밖이다.
- 기본 data root는 OS application-data 위치를 사용한다. 설치자가 다른 절대
  경로를 선택할 수 있다.
- 다른 Windows PC에서도 같은 release와 install-time 설정으로 복원할 수 있어야
  하며 코드 변경을 요구하지 않는다.

## 3. 설정과 fail-closed 상태

`deploy/local/config.schema.json`과 `config.example.json`을 설치 설정 계약으로
사용한다. 실제 파일은 Git 밖에 둔다.

설정값이 없는 초기 상태는 다음과 같다.

- `lan.enabled=false`, hostname/bind IP/CIDR/client trust/TLS/firewall 값은 비어 있다.
- Web/API는 외부 address에 bind하지 않는다.
- 준비 증거가 있는 경우 Core만 127.0.0.1:3200/4200에서 실행할 수 있고 Edge는
  Manual/stopped다.
- 준비 증거도 없으면 설정 검증만 가능하고 서비스는 실행하지 않는다.
- LAN이 꺼진 상태는 어떤 경우에도 `operationalReady=true`가 될 수 없다.
- LAN/CIDR을 자동 발견하거나 자동 개방하지 않는다.

설치 시 정할 값은 정확한 Supabase project/host/database/schema/roles/CA,
data root, release, 네 local principal(Core/Edge/Backup/Signer), LAN hostname/private bind IP/CIDRs,
client UUID 목록, backup target/time이다.

## 4. local native Auth와 사용자 수명주기

- 로그인 ID는 정규화된 username이다. 실제 이메일을 요구하거나 발송하지 않는다.
- 비밀번호는 bounded asynchronous scrypt 파생값만 DB에 저장한다. 평문, token,
  secret은 command line, log, audit, 응답, Git에 남기지 않는다.
- 첫 bootstrap은 `SUPER_ADMIN` 한 명만 생성할 수 있다.
- bootstrap 이후 사용자 생성은 관리 화면의 `SUPER_ADMIN`만 수행한다.
- 신규 사용자는 `SETUP_PENDING` 일회 token으로 비밀번호를 설정한 뒤 `ACTIVE`가
  된다. token은 화면에서 한 번 전달하며 이메일을 발송하지 않는다.
- `SUPER_ADMIN`, `ADMIN`, `USER`, `GUEST`, inactive, setup-pending 권한을 서버와
  Web 모두에서 검증한다.
- 유일한 active `SUPER_ADMIN` 비활성화/강등을 금지한다. break-glass 변경은
  maintenance, drain, fresh signed backup 증거를 요구한다.
- session은 idle/absolute/rotation 수명, HttpOnly/Secure cookie, CSRF, exact Origin,
  replay 방지, rate limit을 적용한다. 만료 session/setup/rate/nonce는 주기적으로
  정리하되 append-only security audit는 삭제하지 않는다.

기존 Supabase Auth/초대/email adapter는 legacy mode의 과거 코드일 수 있으나
`local_lan` startup 설정은 관련 변수와 호출을 거부한다.

## 5. 기존 Supabase PostgreSQL 경계

- direct host 또는 Shared Pooler **session** endpoint의 5432만 허용한다.
  transaction pooler 6543, loopback DB, 임의 host는 거부한다.
- project ref, host, database, schema, runtime/migration/backup/restore role과 CA
  경로/hash를 install-time 설정에 정확히 고정한다.
- 모든 연결은 `sslmode=verify-full`과 CA/hostname 검증을 사용한다.
- production의 runtime, migration, backup은 서로 다른 SCRAM credential과 bounded
  connection limit을 사용하고 privileged membership을 갖지 않는다. restore 역할은
  별도 credential을 쓰는 제한된 LOGIN 역할로 식별되며 production DB CONNECT,
  schema/object 권한과 role membership이 모두 없어야 한다. 격리 restore DB에서만
  필요한 권한을 부여한다.
- runtime은 업무 table DML만, backup은 read only, migration은 schema ownership과
  DDL만 가진다. runtime은 `_prisma_migrations`를 읽지 못한다.
- PUBLIC schema/function 권한, security-definer/leakproof function, cross-schema
  privilege, unsafe default privilege를 차단한다.
- production DB secret은 exact one-record pgpass 파일로 분리하고 목적별 ACL class에
  둔다. restore pgpass는 격리 대상 설치 시 별도로 만든다.
- `Test-SupabaseDatabaseBoundary.ps1`은 read-only catalog/TLS/credential 검증과
  비민감 evidence만 생성한다.

role/schema/grant/migration/restore/수동 SQL 등 production Supabase DB 상태를
바꾸는 행위는 정확한 대상·영향·rollback을 제시하고 실행 직전 승인을 받는다.

## 6. local NTFS Storage

- upload/report/trash와 복원 검증 payload는 configured data root 아래에 둔다.
- path traversal, reparse point, overwrite race, symlink/junction, broad inherited
  ACL, oversized/slow body를 fail closed로 거부한다.
- 원본 파일명·내용·개인정보는 receipt/audit/log에 넣지 않는다.
- 업무 DB에는 provider reference, size, SHA-256, 상태와 최소 metadata만 둔다.
- tombstone retain/restore/purge와 report download는 기존 업무·RBAC 계약을 유지한다.
- file restore는 DB reference와 실제 byte SHA-256을 함께 확인한다.
- `local_lan`은 `STORAGE_PROVIDER=local`만 허용하며 Supabase URL/key/token을
  startup에서 거부한다. 과거 Supabase Storage live verifier는 retired다.

## 7. LAN HTTPS와 Windows host 계층

- Edge는 정확한 private IPv4의 443만 bind한다. Web/API는 loopback만 bind한다.
- Edge가 API로 전달하는 client metadata/request는 Ed25519 서명, timestamp,
  nonce, body digest를 사용한다. API direct access와 replay를 거부한다.
- allowed CIDR가 하나 이상이고 bind IP가 그 범위에 속해야 한다.
- Firewall은 Domain/Private profile, exact Node program hash, Edge service SID,
  exact local IP/CIDR/TCP 443만 허용한다. Public profile과 EdgeTraversal은 차단한다.
- 내부 CA/private key와 server key는 export/ACL 경계를 분리한다.
- client는 lowercase UUIDv4로 식별하고 evidence에는 client ID hash와 집합 digest만
  기록한다.
- 모든 명시 client의 CA 설치 및 offline chain/hostname `PreOpen` evidence를
  aggregate하기 전에는 LAN listener를 시작하지 않는다.
- 인증서 교체는 같은 CA, maintenance, zero-request drain, hash-pinned 파일,
  HTTPS SNI/release 검증과 자동 rollback을 요구한다.

client CA 설치/제거, Windows Firewall, service, principal right, NTFS ACL은 각각
대상·영향·rollback을 제시하고 실행 직전 별도 승인을 받는다.

## 8. backup, restore, RPO/RTO

- 목표는 RPO 24시간, RTO 4시간, daily backup이다.
- backup root와 실행 시각은 설치 시 정한다.
- 다른 BitLocker encrypted physical disk 또는 encrypted SMB 3.1.1 NAS와
  snapshot/versioning이 확인되기 전에는 schedule을 만들거나 backup을 실행하지
  않고 경고한다. same disk/repository fallback은 금지한다.
- 전용 non-admin backup principal만 backup target에 쓸 수 있고 Core/Edge는
  접근하지 못한다.
- backup은 read-only Supabase DB dump와 local Storage manifest/payload를 묶고
  서명된 receipt에 hash와 비민감 식별자만 남긴다.
- restore rehearsal은 production DB와 다른, 이미 존재하고 별도 승인된 isolated
  Supabase test/restore DB와 격리 filesystem에서 전용 unprivileged verifier로
  실행한다. 동일한 기존 Supabase project 안의 별도 database도 허용하지만 새
  project/database를 자동 provision하지 않으며 production database는 거부한다.
- DB/schema, migration digest, 업무 KPI, storage reference, 실제 file SHA-256,
  RTO, isolated schema cleanup을 확인하고 receipt를 서명한다.
- 실제 restore PASS 전에는 `operationalReady`를 표시하지 않는다.

## 9. 운영 선택 — 사용자 결정 완료와 설치 시 보류

구현에 필요한 선택은 다음과 같이 결정됐다.

1. 현재 Windows PC를 우선 서버로 쓰되 특정 PC에 종속하지 않는다.
2. LAN CIDR/client/hostname/fixed IP는 설치 시 정하며 미설정 상태는 fail-closed다.
3. CA 설치 권한과 client 수는 배포 시 확정한다. 지금은 생성·설치·제거·검증
   절차만 준비한다.
4. username Auth, 최초 bootstrap `SUPER_ADMIN` 한 명, 이후 관리 UI 생성이다.
5. data/backup 경로는 설정 가능하며 data 기본값은 OS application-data다.
6. daily backup, RPO 24h/RTO 4h이고 실제 restore 전 운영 준비 완료가 아니다.
7. DB는 로컬이 아니라 기존 Supabase PostgreSQL을 그대로 사용한다.
8. Supabase Auth/Storage는 이 local-native 배포에서 사용하지 않는다.

따라서 현재 추가 질문 없이 구현·정적/격리 검증을 진행한다. 실제 배포 직전에는
host/account/path/LAN/CA/client/backup 값과 각 승인 대상만 다시 확인한다.

## 10. 실행 순서와 승인 gate

1. mandatory 문서, HEAD, 전체 dirty diff를 읽고 기존 변경을 유지/로컬용/보류로
   분류한다. reset/checkout/discard하지 않는다.
2. config/schema, Auth/RBAC, local Storage, Supabase DB 경계, Edge/release/recovery
   core를 구현한다.
3. release를 hash manifest로 package/verify한다.
4. Windows principal right와 NTFS ACL은 Plan 후 즉시 승인받아야만 Apply한다.
5. DB boundary를 read-only 검사한다. evidence write도 별도 승인한다.
6. 서비스 Install은 두 서비스 Manual/stopped로 끝낸다. Start는 별도 process
   전환 승인을 요구한다.
7. bootstrap을 수행하고 client PreOpen trust가 모두 확인된 뒤에만 Firewall과
   Edge start를 각각 승인받는다.
8. backup target/schedule/daily backup을 준비하고, verifier scratch에 입력을
   복사해 isolated restore와 이전/대상 release 실제 호환성 rehearsal을 수행한다.
   scratch 밖에는 승인 후 서명된 비민감 receipt만 게시한다.
9. migration은 fresh previous-release backup, maintenance, drain, 실제 restore/
   compatibility receipt와 별도 production DB 승인 후 `Apply`한다. 적용 직후에는
   pending journal만 남기고 fresh DB boundary와 exact migration chain을 검증한 뒤
   `Finalize`한다. target-release backup/restore도 완료 전 readiness로 인정하지 않는다.
10. release/certificate switch는 maintenance와 별도 승인으로 실행하고 health 실패
    시 hash-pinned prior state로 rollback한다.
11. 승인된 reboot 뒤 service/listener/DB/HTTPS/rights/backup을 재검증한다.

현재 세션에서는 host/DB 외부 상태 변경을 실행하지 않고 Plan·schema·script·test를
준비한다.

## 11. 검증 계약

- 전체 API/Web/local test, lint, production build
- Prisma validate/generate, migration SQL 정적 계약
- 승인된 isolated Supabase target에서 migration/restore/integration
- LAN에서 443만 접근, unauthorized subnet과 Web/API/DB/파일 경로 차단
- 네 역할 + inactive + setup-pending의 browser/API matrix
- Meta/Cafe24/Coupang upload/import/mapping/KPI/report 회귀
- local Storage tombstone/restore/reference 및 file SHA-256
- CSRF/Origin/Host/forwarded header/cookie/session/replay/rate/body/path 공격
- daily backup, RPO/RTO, reboot, maintenance, update/rollback
- local 운영·통합, 업무 회귀, 적대적 보안의 독립 평가

실제 대상/승인이 없어 실행하지 못한 항목은 PASS로 기록하지 않고 deployment
gate로 남긴다. 코드/절차 결함인 P0–P3는 수정·재평가해 열린 항목 0개로 만든다.

## 12. 완료 조건

- 최종 아키텍처가 Supabase DB-only + local username Auth + NTFS Storage다.
- 값 미설정 시 loopback-only/fail-closed이고 LAN 자동 개방이 없다.
- 이식 가능한 core와 별도 Windows host 계층이 준비됐다.
- 실제 변경 스크립트가 exact target, impact, rollback, immediate approval을 강제한다.
- test/lint/build/Prisma와 비외부상태 검증이 통과한다.
- 승인된 실제 integration/restore/reboot가 끝나기 전 readiness는 false다.
- 세 독립 평가의 열린 P0–P3가 0개다.
- 진행상태와 운영·복구 절차를 갱신한다.
- 논리적으로 분리된 commit을 만들고 최종 worktree가 clean이다.

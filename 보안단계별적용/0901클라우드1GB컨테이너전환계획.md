제시하고 사용자에게 즉시 승인을 받은 뒤 실행한다.

## 1. 목표 구조

```text
승인된 사용자 브라우저
  -> provider managed HTTPS / public app domain
       -> 1GB Node container의 Next.js Web (공개 PORT 한 개)
            -> same-origin /backend-api rewrite
                 -> NestJS API 127.0.0.1:4200
                      -> Supabase Auth HTTPS
                      -> Supabase PostgreSQL TLS
                      -> private Supabase Storage HTTPS
```

컨테이너는 공급자가 주입한 공개 `PORT`에 Web만 `0.0.0.0`으로 bind한다. API는
동일 컨테이너의 loopback에만 bind하고 외부 포트로 노출하지 않는다. 브라우저는
Supabase secret key, DB URL, Storage 관리 credential을 받지 않으며 모든 업무
권한 판정과 파일 접근은 NestJS API를 통과한다.

공급자 TLS termination을 사용한다. 앱은 전달 헤더를 무조건 신뢰하지 않고 실제
공급자의 proxy topology에 맞춘 고정된 trust proxy 설정만 허용한다. 최초에는
공급자 기본 HTTPS 도메인을 비공개 검증 주소로 사용하고, custom domain과 DNS는
별도 승인 뒤 전환한다.

## 3. 단일 컨테이너 런타임 계약

### 3.1 프로세스와 포트

- 공개 프로세스: Next.js standalone, `0.0.0.0:$PORT`
- 내부 프로세스: NestJS API, `127.0.0.1:4200`
- 외부에 노출하는 포트는 공급자 `PORT` 하나뿐이다.
- production `/backend-api/:path*`는 loopback API로만 전달한다.
- cloud launcher는 Web/API 둘 중 하나가 종료되면 다른 프로세스에도 종료 신호를
  전달하고 컨테이너를 non-zero로 종료한다.
- `SIGTERM`/`SIGINT`에서 신규 요청을 중지하고 진행 중인 요청에 bounded grace
  period를 준 뒤 Prisma 연결과 timer를 닫는다.
- build 단계에는 secret을 주입하지 않는다. runtime secret만 공급자 secret store로
  전달한다.
- image는 non-root user, production dependencies, immutable build output만 포함한다.

### 3.2 health와 배포 승격

- `/health/live`는 secret 없이 최소 상태만 반환하고 provider HTTP probe에 사용한다.
- `/health/ready`는 DB/Auth/Storage와 release fingerprint를 확인하되 일반 외부
  호출에는 내부 상세를 반환하지 않는다.
- 새 deployment가 health를 통과하기 전에는 기존 healthy revision을 교체하지 않는다.
- release에는 Git SHA, image digest, lockfile/SBOM, migration digest를 기록한다.
- `latest` 같은 이동 tag만으로 운영 release를 식별하지 않는다.

### 3.3 1GB 메모리 한계

현재 업로드 상한은 단일 CSV 8MiB, XLSX 24MiB, Coupang bundle 총 48MiB이며
ExcelJS와 압축 해제는 원본 크기보다 훨씬 큰 메모리를 사용할 수 있다. 사용자 수가
5명이어도 큰 import/export가 겹치면 1GB를 초과할 수 있으므로 다음을 강제한다.

- production과 같은 1GB 제한을 둔 container에서 최대 허용 파일과 최악 구조를
  실제 측정한다.
- Web+API baseline, 단일 최대 import, bundle import, report export/download,
  동시에 두 작업을 요청한 경우의 RSS/heap/latency를 기록한다.
- heavy import/export 동시 실행 수를 process 전체에서 제한하고 초과 요청은 안정된
  `429` 또는 `503`과 재시도 안내로 거부한다.
- 임시 파일은 container ephemeral temp에만 두고 요청 종료·오류·재시작 후
  영구 상태로 간주하지 않는다.
- 다운로드와 Storage 전송은 가능한 streaming으로 유지하고 불필요한 Buffer 복사를
  제거한다.
- steady-state RSS는 700MiB 이하, 단일 최대 작업 peak는 850MiB 이하를 초기
  acceptance 목표로 삼는다. 측정상 이를 지킬 수 없으면 파일 상한/동시성을 낮추거나
  사용자 승인 후 2GB로 올린다. OOM을 허용하고 1GB를 고집하지 않는다.
- 단일 replica로 시작한다. 다중 replica 전환은 distributed job lock, rate limit,
  report reconciliation, session refresh lock을 다시 검증한 뒤 별도 승인한다.

## 4. Supabase Auth 전환

- `AUTH_PROVIDER=supabase` production 경로를 다시 활성화한다.
- 공개 signup은 Supabase와 앱 양쪽에서 비활성화한다.
- 최초 `SUPER_ADMIN`은 사용자가 승인한 실제 이메일/Auth subject만 연결한다.
- 이후 사용자는 `SUPER_ADMIN`의 초대 -> 일회용 링크 수락 -> 최초 비밀번호 설정 ->
  `ACTIVE` 순서로 생성한다.
- access/refresh token은 브라우저 JavaScript나 localStorage에 노출하지 않고 secure,
  HttpOnly, host-only cookie로 유지한다.
- 앱 session handle과 DB의 `AppAuthSession` 검증을 유지해 provider token이 남아도
  비활성화·로그아웃·역할 변경을 앱에서 즉시 반영한다.
- production Site URL과 redirect allow-list는 실제 HTTPS origin만 허용한다.
- 개발 localhost URL과 production URL을 같은 환경 설정으로 혼합하지 않는다.
- local username credential/hash/setup token은 운영 로그인 경로에서 접근하지 않는다.
  실제 local 배포가 없었으므로 local 비밀번호를 Supabase Auth로 이관하지 않는다.
- 기존 사용자가 있다면 비밀번호를 복사하지 않고 초대 또는 승인된 계정 연결 절차를
  사용한다.

## 5. Supabase PostgreSQL

- 정확한 기존 Pro project ref, region, DB host, port, database, schema를 값 노출 없이
  확인한다.
- runtime과 migration credential을 분리한다. runtime에는 업무 table에 필요한 최소
  권한만 주고 DDL/role/schema 관리 권한을 주지 않는다.
- Prisma runtime 연결은 공급자가 권장하는 direct 또는 session pooler endpoint를
  사용하되 transaction pooler 호환성은 별도 검증 없이 가정하지 않는다.
- 1GB 단일 replica의 Prisma connection limit을 작게 고정하고 Supabase connection
  사용량과 timeout을 관찰한다.
- production 연결은 TLS와 hostname을 검증한다.
- 기존 migration은 수정하지 않고 additive migration만 추가한다.
- production에는 `prisma migrate dev`, `prisma db push`, seed, 테스트 SQL을 실행하지
  않는다. 승인된 `prisma migrate deploy`만 maintenance gate에서 사용한다.
- Data API로 업무 schema를 직접 공개하지 않는다. `anon`/`authenticated`의 예상 밖
  schema/table/function grant와 RLS 상태를 read-only 검사한다.

## 6. Supabase Storage

- upload/report를 private bucket의 분리된 prefix에 저장한다.
- 브라우저가 bucket을 직접 list/delete하지 못하게 하고 업무 접근은 NestJS API와
  기존 RBAC를 통과시킨다.
- 기존 `SupabaseFileStorage`의 logical key 정규화, 크기 제한, SHA-256, no-upsert,
  tombstone, restore 검증을 재사용한다.
- production credential은 Web이나 `NEXT_PUBLIC_*`에 넣지 않는다.
- 현재 코드가 요구하는 scoped RLS access mode를 우선 검증한다. credential의 발급,
  최소 권한, 만료, rotation, restart 동작을 실제 staging에서 증명한다.
- service-role 방식으로 변경해야 한다면 RLS를 우회한다는 영향을 문서화하고,
  bucket/prefix allowlist와 서버 측 권한·감사를 강화한 별도 보안 검토 및 사용자
  승인을 받기 전에는 production에 적용하지 않는다.
- bucket의 MIME/개별 파일 크기 제한도 앱 제한과 같거나 더 엄격하게 설정한다.
- 컨테이너 filesystem이나 Koyeb volume을 영구 upload/report 저장소로 사용하지 않는다.

## 7. 기존 로컬 파일 이관

기존 업무 프로그램의 upload/report 경로와 실제 파일은 승인 전까지 읽기/쓰기/삭제
하지 않는다. 이관이 필요하면 다음 순서를 사용한다.

1. read-only inventory 계획으로 DB reference, 파일 수, 총 byte, SHA-256 집계 형식을
   정하고 민감한 파일명/내용을 출력하지 않는다.
2. 사용자가 정확한 source path와 read-only inventory를 승인한다.
3. 별도 staging bucket/prefix에서 같은 key/hash의 upload, download, tombstone,
   restore를 검증한다.
4. production 이관 manifest와 예상 DB/object delta를 만든다.
5. maintenance와 별도 승인 뒤 object를 복사하고 hash를 대조한다.
6. 필요하면 additive migration 또는 승인된 reference rewrite를 수행한다.
7. 새 앱에서 download/report/KPI를 검증한다.
8. 최소 보존 기간과 rollback 종료 승인 전에는 기존 파일을 삭제하지 않는다.

DB에 기존 local absolute path가 들어 있다면 이를 그대로 cloud object key로 사용하지
않는다. platform-independent logical reference로 변환하고 path traversal 및 Windows
경로 조각이 object key에 남지 않는지 검증한다.

## 8. 백업·복구

Supabase Pro의 daily DB backup을 사용하되 dashboard에 backup이 보인다는 사실만으로
완료 처리하지 않는다.

- 배포 전 최신 DB backup identifier와 보존 기간을 확인한다.
- 가능한 경우 별도 logical dump를 만들고 checksum을 기록한다.
- production과 분리된 승인된 target에 실제 restore하고 migration history, 핵심
  table count와 고정 KPI를 대조한다.
- custom DB role password는 provider restore 뒤 재설정이 필요할 수 있으므로 recovery
  runbook에 포함한다.
- Supabase DB backup은 Storage object 본문을 포함하지 않으므로 object backup을
  별도로 설계한다.
- object inventory/manifest/hash와 실제 payload를 승인된 독립 backup target에
  보존하고, 삭제 -> 복원 -> hash 대조를 rehearsal한다.
- DB reference와 Storage object가 같은 시점에 복구 가능한지 확인한다.
- 목표는 우선 RPO 24시간, RTO 4시간으로 유지하되 실제 업무 요구와 backup target이
  정해질 때 사용자가 최종 승인한다.

독립 object backup target이 정해지지 않았으면 cloud 앱을 검증할 수는 있지만
`operationalReady=true` 또는 운영 전환 완료로 기록하지 않는다.

## 9. 구현 단계

### C0. 읽기 전용 기준선과 전환 manifest

- `AGENTS.md`, master plan, 이 문서, `진행상태.md`를 끝까지 읽는다.
- HEAD, branch, worktree, status, 전체 diff와 사용자 변경을 확인한다.
- 현재 Supabase Auth/Storage adapter, local mode 결합, Next rewrite, API listener,
  Docker/release launcher, background timer, upload/report memory 흐름을 조사한다.
- 변경 파일 목록, 퇴역 파일 목록, migration 필요 여부와 테스트 matrix를 먼저 적는다.
- 기존 운영 DB/Auth/Storage/Koyeb/Git remote에는 연결하거나 쓰지 않는다.

### C1. cloud deployment mode와 runtime

- `DEPLOYMENT_MODE=cloud_container` 같은 명시적 mode를 추가하고 production에서
  legacy/local_lan의 우연한 fallback을 금지한다.
- provider `PORT` Web + loopback API 구조를 구현한다.
- cloud launcher의 child supervision, signal forwarding, cold start와 health를
  테스트한다.
- local LAN 전용 env, key, evidence가 cloud startup에 필요하지 않음을 증명한다.
- production artifact에서 Windows host script가 실행되지 않음을 검증한다.

### C2. Supabase Auth 복원

- Supabase Auth provider와 invitation/onboarding route/UI를 현재 schema에 맞춰
  활성화한다.
- local username 전용 분기와 Web 문구를 cloud mode에서 제거하거나 비활성화한다.
- 네 역할, inactive, onboarding, refresh race, logout, account switch, CSRF/Origin을
  전체 회귀한다.

### C3. Supabase Storage 복원

- private bucket adapter를 cloud production의 유일한 durable storage로 설정한다.
- upload/report/download/tombstone/restore와 DB transaction compensation을 검증한다.
- ephemeral temp cleanup과 restart reconciliation을 검증한다.
- legacy local file 이관 도구는 source/target/manifest/hash가 명시된 dry-run을 먼저
  제공하고 기본 상태에서는 쓰기를 금지한다.

### C4. 1GB 자원 hardening

- Prisma pool, scrypt/local-only provider, upload concurrency, report generation,
  reconciliation timer의 메모리와 연결 사용량을 조정한다.
- 1GB cgroup 또는 동등한 제한에서 cold start, 최대 upload, bundle, report,
  download와 동시 요청을 측정한다.
- OOM/restart 중 DB row와 Storage object가 불확정 상태로 남아도 다음 시작에서
  안전하게 reconcile되는지 fault injection으로 확인한다.

### C5. container build와 격리 rehearsal

- multi-stage Docker build 또는 동등한 immutable artifact를 만든다.
- non-root, read-only source, writable bounded temp, production dependency closure,
  signal/health를 확인한다.
- local container에서 public port 하나만 열고 API port가 host에 publish되지 않는지
  검사한다.
- source-free image를 별도 복사/재기동해 manifest와 cold start를 재검증한다.

### C6. 승인된 cloud staging

- 기존 개발 Supabase project 또는 사용자가 승인한 별도 staging target만 사용한다.
- staging Koyeb service/resource 생성, secret 주입, Auth URL/redirect, private bucket,
  migration은 각각 외부 변경 승인을 받은 뒤 수행한다.
- staging domain에서 네 역할 browser/API, 업무 회귀, upload/storage, restart,
  1GB peak, 5xx/401/403/429, secret leakage를 검증한다.
- 실제 production project나 실제 업무 파일을 staging test에 사용하지 않는다.

### C7. 독립 평가와 release 고정

- 업무 회귀 평가자는 Meta/Cafe24/Coupang KPI와 import/report를 검토한다.
- 인증·보안 평가자는 Auth/RBAC/CSRF/Origin/cookie/proxy/direct API/Storage를 공격한다.
- 운영 평가자는 1GB/OOM/restart/health/deploy/rollback/backup 복구를 검토한다.
- 발견사항을 P0~P3로 기록하고 수정·재평가해 계획 범위 열린 항목을 0개로 만든다.
- 전체 test/lint/build/Prisma/container 검증 뒤 commit/image digest를 고정한다.

### C8. production cutover

- 아래 승인 gate와 `0811작업단계9.md`의 일반적인 backup/migration/rollback 원칙을
  적용하되 Windows/LAN/local Storage 항목은 이 문서로 대체한다.
- maintenance -> backup/restore 증거 -> migration -> Supabase Auth/Storage 설정 ->
  container deploy -> internal smoke -> role/KPI/object smoke -> public domain 전환 ->
  제한적 쓰기 -> 집중 관찰 순서로 진행한다.
- 실패 시 public endpoint를 maintenance 또는 차단 상태로 두고 검증된 이전 secure
  image로 rollback한다. 무인증 구버전을 인터넷에 공개하지 않는다.

## 10. 외부 변경 승인 gate

다음 항목은 서로 묶어 암묵적으로 승인받지 않는다. 각 실행 직전에 실제 대상,
비밀값을 제외한 명령/API, 영향, 예상 비용·시간, 성공 판정, rollback을 제시한다.

1. Koyeb 또는 대체 provider의 app/service/1GB instance 생성
2. GitHub/private registry 연결, remote push, image publish
3. staging/production secret 생성·등록·회전
4. Supabase Auth Site URL, redirect URL, signup/provider/email template/SMTP 변경
5. Supabase private bucket와 Storage policy/credential 생성·변경
6. staging DB migration/seed 또는 test user 초대
7. production DB snapshot/logical dump/restore rehearsal
8. production `prisma migrate deploy`
9. production 최초 SUPER_ADMIN 연결과 사용자 초대
10. 기존 local file read-only inventory와 Supabase Storage 이관
11. independent object backup 생성·복원
12. staging/production container 배포·재배포·rollback
13. custom domain/DNS 변경
14. 원본 main merge, 원본 watcher/process/.env 변경

사용자가 “이 계획을 진행하라”고 말해도 아직 정확한 target이 없는 gate는 read-only
점검과 로컬 코드·테스트까지만 수행한다.

## 11. 필수 검증 matrix

### 코드와 artifact

- `npm.cmd run prisma:validate`
- `npm.cmd run prisma:generate`
- `npm.cmd run lint`
- 전체 API/Web test
- production build
- `git diff --check`
- dependency audit와 secret/history scan
- Docker image non-root, production-only dependency, source-free cold start

### 인증·권한

- anonymous, onboarding, inactive, GUEST, USER, ADMIN, SUPER_ADMIN
- login/me/refresh/logout/invitation accept/password setup
- 역할 변경과 비활성화 즉시 반영
- direct API, CSRF, Origin/Host/forwarded header, cookie/session replay
- SUPER_ADMIN 전용 users/audit/settings 경계

### 업무

- Meta/Cafe24/Coupang 대표 기간 KPI
- 각 upload/import preview, validation, apply 또는 동일 hash SKIP
- mapping/rematch, decision, manual purchase, change log
- report generate/list/download
- 업로드 전후 DB row/object/audit expected delta

### Storage·복구

- private bucket 비인가 접근 거부
- 최대 파일과 bundle upload/download SHA-256
- tombstone retain/restore/purge
- DB 성공/Storage 실패와 Storage 성공/DB 실패 compensation
- process kill/container restart reconciliation
- DB 실제 restore와 object 실제 restore/hash

### 운영

- 공개 PORT 외 API/관리 포트 비노출
- provider TLS와 exact Origin
- health 실패 시 새 revision 미승격
- 1GB memory/CPU/DB connection peak
- graceful shutdown과 in-flight request
- 이전 secure image rollback
- 배포 뒤 최소 집중 관찰 기간의 5xx/401/403/429, OOM/restart, DB pool,
  Auth/Storage error

## 12. 완료 조건

- 최종 구조가 Supabase Pro Auth/PostgreSQL/private Storage + 1GB Node container다.
- Windows/LAN/NTFS/local Auth가 production startup이나 artifact에 요구되지 않는다.
- 외부에는 managed HTTPS의 Web port 하나만 노출되고 API는 loopback이다.
- Supabase secret과 DB credential이 Web/bundle/log/error/Git에 노출되지 않는다.
- 1GB 제한에서 합의한 최대 업무 흐름과 동시성 제한이 OOM 없이 통과한다.
- 네 역할과 모든 핵심 업무/KPI가 staging과 production smoke에서 통과한다.
- DB와 Storage의 실제 복원 가능한 backup이 각각 증명된다.
- migration, container deploy, health, rollback이 digest로 고정된 release에서 통과한다.
- 독립 평가의 계획 범위 열린 P0/P1/P2/P3가 0개다.
- 실제 배포 전에는 `operationalReady=false`를 유지하고 승인된 production 검증 뒤에만
  true로 기록한다.
- `진행상태.md`에 변경 이유, 구현 commit, image digest, migration, 승인, 테스트,
  backup/restore, 배포 주소, 관찰과 남은 위험을 기록한다.

## 13. 예상 작업 규모

코드·로컬/격리 검증 기준 예상은 5~8 작업일이다. 실제 외부 승인 대기, provider
계정 연결, DNS 전파와 backup restore 시간은 포함하지 않는다.

## 14. 설치·배포 시 확정할 값

다음 값은 코드에 고정하지 않고 해당 gate 직전에 확인한다.

- Koyeb 조직/app/service와 정확한 1GB instance type
- container region과 Supabase project region
- provider 기본 domain, 최종 custom domain 여부
- production Supabase project ref, DB endpoint/database/schema
- runtime/migration DB credential source
- Auth Site URL/redirect URL/SMTP와 최초 SUPER_ADMIN 이메일
- private bucket, prefix, credential/rotation 방식
- 기존 파일 source path와 이관 대상 여부
- independent object backup target
- RPO/RTO와 maintenance window
- rollback 결정자와 실패 임계값

값이 없으면 추정해서 외부 resource를 만들거나 production을 변경하지 않는다.

## 15. 비용 기준

- 기존 Supabase Pro 월 `$25`는 이미 사용 중인 비용이므로 이 전환의 신규 기본
  비용으로 다시 계산하지 않는다.
- Koyeb 1GB standard `small`의 현재 표시 가격은 월 약 `$10.71`이다. 세금, 환율,
  egress와 향후 가격 변경은 별도다.
- 독립 object backup, custom domain, 추가 egress 또는 2GB 승격은 별도 비용 gate다.
- provider resource를 만들기 직전에 실제 결제 통화, instance type, 월 상한과
  자동 증액 가능 여부를 다시 보여주고 승인받는다.
- 가능하면 provider budget alert를 설정하고 자동 scale-up/다중 replica는 끈다.

## 16. 참고한 공급자 계약

- Koyeb Web Service는 공급자 `PORT` 환경변수와 HTTP health check를 지원한다.
  - https://www.koyeb.com/docs/build-and-deploy/environment-variables
  - https://www.koyeb.com/docs/run-and-scale/health-checks
  - https://www.koyeb.com/docs/reference/instances
- Supabase Storage private bucket은 RLS 또는 제한된 server credential로 보호한다.
  - https://supabase.com/docs/guides/storage/security/access-control
  - https://supabase.com/docs/guides/storage/buckets/fundamentals
- Supabase Pro DB backup은 Storage object 본문을 포함하지 않으므로 별도 object
  backup이 필요하다.
  - https://supabase.com/docs/guides/platform/backups

구현 세션은 배포 직전에 공급자 공식 문서와 현재 요금·제한을 다시 확인한다.

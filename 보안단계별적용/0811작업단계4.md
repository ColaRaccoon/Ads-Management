## 1. 이 세션의 단일 목표

이름은 기존 스타일에 맞게 조정할 수 있지만 한 역할을 여러 구현으로 나누지 않는다.

### 5.1 AuthProvider

- Query key는 중앙의 `['auth', 'me']` 하나
- 앱 시작 시 `/auth/me` 조회
- `user`, `permissions`, `isLoading`, `isAuthenticated`, `login`, `logout`, `can` 제공
- 페이지마다 `/auth/me`를 다시 호출하지 않음
- auth query는 `refetchOnWindowFocus`, `refetchOnReconnect`를 켜고 visible 상태에서 30~60초 이내의 짧은 stale/refetch 정책을 둔다. 보호 route 재진입 때 stale이면 재검증한다. 무한 polling/페이지별 중복 query는 금지한다.
- role은 표시용이며 권한 판정은 서버가 반환한 permissions로 수행
- logout과 계정 변경 시 `queryClient.clear()` 또는 동등한 전체 사용자 캐시 제거
- `/auth/me.authorizationVersion`이 이전 값과 달라지면 다른 사용자별 Query cache를 제거하고 permissions/menu를 즉시 다시 계산하며 모든 탭에 authz-changed event를 broadcast한다.
- `api.ts`가 React context/QueryClient/router를 직접 import하지 않도록 한다. API 계층은 안정된 auth lifecycle event 또는 callback(`expired`, `invalid`, `revoked`, `inactive`, `permission-changed`)만 발행하고, AuthProvider가 QueryClient clear/refetch와 redirect를 소유한다.
- 일반 401/403에는 자동 retry하지 않으며 아래 고정 오류 매트릭스를 따른다.

고정 오류/캐시 계약:

| API code | Web 동작 |
|---|---|
| `ACCESS_TOKEN_EXPIRED` | refresh single-flight 1회 후 원 요청 1회 재시도 |
| `SESSION_INVALID`, `SESSION_REVOKED`, `ACCOUNT_INACTIVE` | 모든 사용자 cache 제거, 로그인 화면 이동 |
| `ACCOUNT_NOT_PROVISIONED` | cache 제거, 자동 로그인 반복 없이 지원 안내 차단 화면 |
| `ACCOUNT_ONBOARDING_REQUIRED` | 업무 화면 차단, 단계 4의 `/account-setup` 안내만 표시; 단계 5가 초대 완료 UI로 확장 |
| `PERMISSION_DENIED` | session 유지, `/auth/me`를 1회 갱신해 UI 재계산 후 forbidden/inline 오류 |
| `REFRESH_RACE_RETRY` | 다른 탭의 cookie 회전을 기다려 `/auth/me` 또는 원 요청을 1회만 재시도 |

### 5.2 AppFrame

현재 RootLayout이 항상 AppShell을 렌더링하므로 로그인 화면에도 업무 메뉴가 보일 수 있다. `AppFrame` 또는 동등 계층으로 분기한다.

- 인증 확인 중: 업무 데이터/메뉴가 한 프레임도 보이지 않는 loading 화면
- 비로그인 + `/login`: login 화면만 표시
- 비로그인 + 보호 경로: `/login?next=<내부경로>` 이동
- 로그인 + `/login`: 안전한 next 또는 `/dashboard` 이동
- onboarding + `/account-setup`: 업무 데이터 없는 계정 설정 안내만 표시
- onboarding + 그 외 업무 경로: `/account-setup` 이동; AppShell/업무 query 실행 금지. 단계 5에서 이메일 초대 링크용 `/invite/accept`와 최초 비밀번호 설정용 `/complete-invitation`으로 완성한다.
- 로그인 + 보호 경로: 기존 AppShell 렌더링
- 로그인 + 권한 없는 전용 페이지: `/forbidden`
- `next`는 `/`로 시작하고 `//`, scheme, 외부 host가 없는 내부 경로만 허용

프런트 route gate가 실패해도 API 데이터는 서버 Guard 때문에 노출되지 않아야 한다.

## 6. API client 중앙화

`apps/web/src/lib/api.ts`의 반복 fetch를 내부 `apiRequest<T>()` 하나로 합친다. 기존 `apiGet`, `apiPost`, `apiPatch`, `apiPut`, `apiDelete`, upload 함수의 외부 signature는 가능한 유지해 기존 페이지 변경량을 줄인다.

필수 동작:

- 모든 요청에 `credentials: 'include'`
- JSON body에만 `Content-Type: application/json`
- FormData에는 브라우저가 boundary를 만들도록 Content-Type 수동 설정 금지
- `204 No Content` 정상 처리
- 기존 `ApiError`, 안전한 code/message parsing 유지
- 안정된 error code 기준으로 401과 403 구분
- **오직** `ACCESS_TOKEN_EXPIRED`만 `/auth/refresh`를 single-flight로 한 번 호출하고 원 요청 한 번만 retry
- refresh 실패는 세션 상태와 전체 Query cache를 지우고 login 이동
- `PERMISSION_DENIED`는 logout하지 않고 `/auth/me`를 한 번 갱신한 뒤 권한 부족 UI 유지
- 무한 refresh 재귀와 동시에 여러 redirect 금지
- 2단계가 발급한 CSRF cookie를 중앙에서 읽어 모든 auth mutation에 정해진 header로 첨부하고, 6단계가 업무 mutation 전체로 확대해도 같은 코드를 재사용
- auth endpoint와 일반 endpoint의 retry 규칙 분리
- timeout/AbortSignal을 기존 장시간 업로드에 임의 적용하지 않음

cookie가 `Path=/`인 같은 출처 `/backend-api` 요청에 실제로 전송되는지 브라우저 Network 탭에서 확인한다.

단일 탭 Promise single-flight만으로 끝내지 않는다. 여러 탭은 `BroadcastChannel`과 가능하면 Web Locks API로 refresh 시작/완료/logout/계정변경 이벤트를 조정한다. 지원하지 않는 브라우저에서는 짧은 leader lease와 단계 2 서버 DB lock/`REFRESH_RACE_RETRY`를 fallback으로 사용한다. 어떤 탭도 정상 경합 한 번만으로 cookie/cache를 지우지 않으며, logout은 모든 탭에 cache clear를 방송한다.

원 요청 retry는 Guard에서 handler가 실행되기 전에 명시적인 `ACCESS_TOKEN_EXPIRED`가 발생한 경우에만 허용한다. 네트워크 timeout, 알 수 없는 401, handler 실행 여부가 불명인 POST/PUT/PATCH/DELETE는 자동 재전송하지 않아 중복 mutation을 막는다.

## 7. 로그인·로그아웃 화면

### 로그인

`apps/web/src/app/login/page.tsx`

- 이메일, 비밀번호
- `autocomplete="email"`, `autocomplete="current-password"`
- password/token을 state 외의 로그, URL, localStorage/sessionStorage에 저장하지 않음
- 중복 submit 방지
- 실패 시 계정 존재 여부를 구분하지 않는 일반 메시지
- 성공 후 Query cache 초기화, `/auth/me` 최신화, 검증된 next 이동
- public signup 링크/화면 없음
- password reset은 이번 v1 범위에서 제공하지 않는다. 잊은 사용자는 총관리자에게 연락하며, 공개 reset flow는 별도 위협모델/세션폐기 설계 뒤 추가한다.

### 로그아웃

- POST logout 완료 여부와 무관하게 민감 캐시 제거
- cookie 삭제는 서버 담당
- 뒤로 가기, bfcache, stale query로 이전 데이터가 다시 보이지 않는지 검증
- 실패 시 token/cookie 상세를 오류 메시지에 포함하지 않음

## 10. 컴포넌트와 데이터 흐름 회귀 원칙

- 권한 적용 때문에 기존 React Query key를 임의 변경하지 않음
- mutation 성공 후 기존 invalidateQueries 흐름 보존
- 조회용 필터·정렬·상세보기·행 선택을 쓰기 권한과 혼동하지 않음
- hidden CSS만 적용하지 말고 권한 없는 mutation component/handler를 렌더링하지 않음
- 그러나 UI가 숨겨져도 서버 403 테스트를 반드시 유지
- 권한 조건을 각 page에 복잡하게 복제하지 않고 `useCan`과 작은 readOnly prop 사용
- 보안과 무관한 대형 page 분해/스타일 전면 변경은 하지 않음

페이지 파일명만 확인하고 끝내지 않는다. `rg`로 `apiPost/apiPut/apiPatch/apiDelete`, upload helper, raw `fetch`, form submit, mutation hook, click handler를 모두 수집해 **컴포넌트/handler → method+path → permission → read-only 대체 UI** 표를 만든다. 현재 import되지 않을 수 있는 `UploadDropzone`, `ReportExportButton`, 대문자 중복 component도 활성 import 여부를 기록한다. 미사용이면 억지로 활성화하지 않지만, 이후 사용될 때 무권한 mutation을 만들지 않도록 공통 PermissionGate 계약 또는 테스트 대상에 포함한다.

## 11. 테스트

현재 Web 테스트는 Node Vitest 중심이다. 최소한 순수 auth/permission 로직은 기존 도구로 테스트한다. component 테스트가 필요하면 `jsdom`, React Testing Library, user-event를 최소 dev dependency로 추가하고 이유를 기록한다.

필수 단위 테스트:

- `apiRequest` credentials include
- JSON/FormData Content-Type
- 204 처리
- `ACCESS_TOKEN_EXPIRED`만 refresh single-flight와 1회 retry; 알 수 없는 401과 실행 여부 불명 mutation은 재전송 안 함
- 두 탭 동시 refresh/logout과 BroadcastChannel/Web Locks fallback
- refresh 실패 cache clear
- `PERMISSION_DENIED`에서 session 유지 + `/auth/me` 1회 refetch
- invalid/revoked/inactive/not-provisioned/onboarding의 각 cache/redirect 계약
- 기존 API error parser 회귀
- permissions 검사
- next 내부경로 검증과 open redirect 차단
- role label은 표시만 하고 판정에는 쓰지 않음

필수 component/통합 테스트:

- AuthFrame loading/anonymous/authenticated
- 비로그인 업무 화면 flash 없음
- login 페이지 AppShell 없음
- AppShell menu filter
- PermissionGate
- GUEST change-log form 없음, timeline 있음
- USER decision/upload/product 버튼 없음
- ADMIN user 관리 링크 없음
- readOnly table action column 없음
- Coupang 첫 category 생성 우회 버튼 없음
- logout cache clear
- 다른 관리자가 역할/상태를 바꾼 뒤 대상 브라우저의 focus/reconnect/protected navigation/최대 refetch 주기에서 authorizationVersion 변경과 button/cache 갱신
- onboarding 계정은 account-setup 안내 외 업무 menu/query/handler가 없음
- data-driven 전체 mutation inventory에서 permission 없는 handler 0개

실제 네 계정 브라우저 평가:

- 직접 URL 접근
- 새로고침 로그인 유지
- 401/403 구분
- token/cookie가 DOM/localStorage/응답 JSON에 없음
- 네 역할 UI와 직접 API 결과 일치
- 기존 모든 날짜/필터/정렬/조회/클라이언트 export 정상

## 12. 이 단계에서 하지 않는 일

- 사용자 초대/역할관리 API와 완성 UI(5단계)
- 전역 DTO/CSRF 강제/headers/rate limit(6단계)
- 파일 Storage 교체(7단계)
- 대문자/소문자 중복 component 일괄 삭제
- 운영 배포

## 13. 완료 조건

- 비로그인 화면 데이터 flash 없음
- login/me/refresh/logout browser flow 성공
- 고정 오류/캐시 매트릭스 전체 통과; 만료만 refresh, 일반 권한 403은 session 유지
- logout/계정전환 뒤 Query cache 데이터 재노출 없음
- 네 역할별 모든 mutation UI가 서버 권한표와 일치
- 조회 전용 역할의 필터/상세/다운로드 회귀 없음
- raw fetch가 auth 예외 외에 남지 않거나 정당성이 문서화됨
- 전체 Web/API test, lint, build 통과
- 독립 평가 열린 결함 0

이 단계도 구현 commit과 인계 문서 commit을 분리한다.

```text
feat(security-step4): add authenticated role-aware web UX
docs(security-step4): record verified implementation handoff
```

구현 commit SHA, mutation inventory, 네 역할 브라우저 결과를 진행상태에 기록한 뒤 인계 문서 commit을 만들고 clean worktree로 종료한다.

## 3. 열린 release blocker와 위험

### P1-REL-001: base image 취약점

최종 local image의 Docker Scout 결과는 2 Critical/5 High이며 당시 모두 no-fix였다.

- `perl-base 5.36.0-7+deb12u3`
  - Critical: `CVE-2026-13221`, `CVE-2026-12087`
  - High: `CVE-2026-48959`, `CVE-2026-48962`
- `openssl 3.0.20-1~deb12u2`
  - High: `CVE-2026-63076`, `CVE-2026-63072`, `CVE-2026-54874`

staging publish 전에 최신 official Node 22 bookworm-slim digest와 Debian package fix
상태를 다시 조회하고 rebuild/rescan한다. fixed digest가 있으면 그 digest로 교체한다.
없다면 도달 가능성, container 사용 경로, compensating control, 수용 기간, 재검토일을
문서화하고 **사용자에게 이 release에 한정된 명시적 risk acceptance**를 받아야 한다.
일반적인 “전부 승인”을 이 위험 수용으로 간주하지 않는다.

성공 판정은 Critical/High 0이 원칙이다. no-fix 위험을 수용하는 경우에도 열린 P1을
숨기지 않고 예외 번호, 만료일, 소유자와 rollback image를 기록한다.

### P1-REL-002: 실제 production CMD 미검증

source-free final image의 수정하지 않은 `CMD ["node", "deploy/launch-bundle.mjs"]`로
실제 Next.js+NestJS를 함께 띄우는 cold start, live, ready, DB/Auth/Storage dependency,
SIGTERM, restart를 아직 수행하지 않았다. fixture PASS를 대체 증거로 사용하지 않는다.

### P1-OPS-001: cloud 최초 SUPER_ADMIN·기존 사용자 연결 도구 부재

`BootstrapSuperAdminService`의 provider identity/email 충돌 검사 로직은 존재하지만
`apps/api/src/auth/bootstrap-super-admin.cli.ts`는
`LEGACY_SUPABASE_AUTH_BOOTSTRAP_DISABLED`로 의도적으로 비활성이다. runtime image에는
안전한 cloud one-shot 운영 계약도 없다. 따라서 승인된 Supabase Auth subject와 이메일을
최초 `AppUser.SUPER_ADMIN`에 연결하는 실제 경로가 아직 없다.

또한 `20260824110000_add_security_auth` 뒤 기존 `AppUser.authUserId`가 null일 수 있고,
같은 normalized email을 단순 재초대하면 `USER_EMAIL_EXISTS`가 될 수 있다. 전 사용자별
`keep/link/re-invite/disable` disposition manifest가 필요하다. legacy CLI를 다시
활성화하지 말고 exact project/DB fingerprint, provider identity 대조, dry-run,
idempotency, PostgreSQL advisory lock, audit, exact confirmation을 갖춘 **cloud 전용 one-shot
runner**를 별도 maintenance artifact로 구현한다. public runtime image에 관리 CLI나
Prisma schema/migrations를 무심코 추가하지 않는다.

### P1-OPS-002: Storage scoped JWT 발급·회전 운영 경로 부재

production startup은 `storage_app` role과 exact issuer/audience/subject/project를 가진
독립 scoped JWT만 허용한다. 허용 수명은 1~7일이고 readiness는 만료 5분 전부터 닫힌다.
그러나 현재 repository에는 승인된 issuer custody, 새 token 발급, Koyeb secret 갱신,
overlap deploy, old token 제거 또는 최대 TTL 만료 확인, 만료 24시간 전 경보를 연결한
운영 경로가 없다.

지원되는 Supabase signing 방식과 key custody를 공식 계약으로 확인한 뒤 rotation
runner/runbook을 만든다. Auth admin Secret Key를 Storage token으로 재사용하거나 signing
material을 image/Git에 넣지 않는다. staging에서 정기 회전과 긴급 회전을 실제
rehearsal하기 전 production 준비 완료로 보지 않는다.

### P1-OPS-003: cloud migration·backup/restore maintenance 경로 부재

runtime image는 의도적으로 Prisma CLI/schema/migrations와 backup 도구를 싣지 않는다.
현재 `npm run prisma:migrate`는 개발용 `prisma migrate dev`이므로 production에 사용할 수
없다. exact source SHA와 migration checksum에 고정된 별도 one-shot maintenance
artifact/job이 필요하다. DB backup과 별개의 Storage payload/manifest/hash backup,
두 restore를 함께 검증하는 cloud runbook/tool도 아직 없다.

이번 cloud 보정에서 새 migration을 만들지 않았다는 사실은 production에 pending
migration이 0이라는 뜻이 아니다. 운영 target에서 37개 migration의 history/checksum과
실제 pending 상태를 읽기 전용으로 확인해야 한다. 특히 security Auth migration의
null/invalid/duplicate email·unknown role 실패 조건과 raw-row 최소화 migration의
비가역적 scrub 영향을 clone restore target에서 검증한다.

### P1-OPS-004: 실제 target RBAC/KPI/E2E runner 부재

기존 local release용 Auth/업무 CLI는 local release identity와 mock/local Auth 계약에
묶여 있고 production build에서 제외된다. 실제 Supabase 사용자의 네 역할, browser
cookie/CSRF/Origin, private Storage, KPI/report digest를 비밀·개인정보 없이 검증하는
release-neutral 외부 runner가 필요하다. 기존
`business-flow.supabase.integration.spec.ts`가 LocalFileStorage를 사용한다면 이를
Supabase Storage 증거로 승격하지 않는다.

### P1-OPS-005: provider rollout의 ready-before-traffic 보장 부재

현재 Docker/Koyeb health path는 secret 없는 `live`이고 protected `ready`는 내부 probe
header가 필요하다. live만 성공한 새 revision이 DB/Auth/Storage ready 전에 traffic을
받지 않는다는 provider 계약 또는 코드 barrier가 아직 없다.

R0에서 Koyeb health check의 custom header, rollout promotion, traffic switch 계약을
공식 문서와 실제 staging으로 확인한다. custom header를 안전하게 지원하지 않으면
launcher가 API를 먼저 시작해 loopback protected ready가 성공한 뒤에만 Web 공개
listener를 bind하는 startup barrier 등 secret을 공개하지 않는 fail-closed 방식을
구현·검증한다. 어느 방식도 확정되지 않으면 public staging blocker다.

### P1-ISO-001: 동일 UID의 sibling-process 경계

단일 컨테이너 요구 때문에 Web/API가 동일한 non-root UID와 process namespace를
공유한다. Web process compromise 시 host에 따라 `/proc/<api-pid>/environ` 가시성이
남을 수 있다. Web env allowlist는 defense in depth일 뿐 강한 격리가 아니다.

staging에서 실제 provider의 `/proc` mount/hidepid와 process visibility를 확인한다.
위험 허용이 불가능하면 1컨테이너 요구 자체를 재결정해야 하므로 임의로 두 컨테이너로
분리하지 않고 사용자에게 아키텍처 gate로 올린다. public staging 전에 실제 차단 증거
또는 기한·범위가 명시된 별도 위험 수용이 없으면 release blocker로 유지한다.

### P2-OPS-001: 실제 target·backup·rollback 미검증

운영 Supabase project, runtime/migration role, Koyeb service, registry, domain, backup
target이 확정되지 않았다. DB/object 실제 restore, image rollback, DNS rollback도 0회다.

### 비릴리스 로컬 유지보수 메모: 전체 BuildKit cache 잔여

폐기 cloud image tag 5개와 Scout 임시 digest directory 3개는 제거했다. 그러나
`desktop-linux` 전체 BuildKit cache prune은 다른 프로젝트 cache도 지우므로 하지
않았다. 이것은 cloud release finding이 아니며 `operationalReady`를 막지 않는다.
수행하려면 정확한 전체 영향과 재build 비용을 제시한 별도 승인이 필요하다.

## 4. 실행 전에 사용자에게 받아야 할 값

값을 추측하지 않는다. secret은 채팅에 붙이지 말고 provider secret manager 또는
ignored local env를 통해 주입한다.

### 4.1 격리된 Supabase staging

- exact 조직/project/ref/region/plan과 비용; 새 project면 생성 gate
- 현재 개발 project `ehnfrrmbkvlsbpvqcvkr`를 staging으로 재사용할지 여부
- direct PostgreSQL health, DB host/port/database/schema와 staging 전용
  runtime/migration/backup role
- staging Auth Site URL/redirect/SMTP 또는 승인된 test email 전달 방식
- staging private bucket/prefix/RLS/scoped JWT subject와 독립 test identity
- staging fixture 보존/cleanup 시점, object/DB backup·restore target

현재 개발 project를 선택해도 기존 metadata read PASS를 app staging PASS로 승격하지
않는다. direct PostgreSQL, 37 migration, 실제 Auth/object lifecycle을 새로 검증해야 한다.
Koyeb staging은 이 격리 target만 사용하며 production Supabase credential, data, user,
bucket을 절대 주입하지 않는다.

### 4.2 Supabase production

- 정확한 조직명/ID, project 명/ref, plan이 Pro인지, region
- project URL, DB host, port, database, schema
- runtime 연결을 direct 또는 session pooler 중 무엇으로 할지와 그 근거
- migration owner role과 최소권한 runtime role; password는 비밀 경로로만 전달
- production data의 현재 schema/migration history와 예상 row/object 규모
- public signup, Email provider, confirm-email 정책
- Site URL, 정확한 invite redirect URL, 추가 허용 redirect 0개 또는 목록
- custom SMTP 사용 여부, sender, 승인된 email template와 실제 시험 수신자
- 최초 SUPER_ADMIN의 정확한 이메일과 Supabase Auth subject 연결 방식
- private bucket ID, logical prefix, RLS policy, scoped short-lived Storage JWT subject
- Storage JWT의 공식 issuer, signing-key custody, 담당자, rotation 주기, overlap과 alert
- Storage retention 30일의 업무 승인 여부
- DB backup 보존/restore target, object backup target, RPO/RTO 최종값

기본 목표는 RPO 24시간/RTO 4시간이지만 사용자가 확정하기 전 약속하지 않는다.
Supabase DB backup은 Storage object 본문을 포함하지 않으므로 object backup은 별개다.

### 4.3 Koyeb/registry/domain

- Koyeb 조직, app, service, region, 정확한 1GB instance type
- provider가 강제하는 `PORT`, health path와 readiness/rollout 동작
- private registry 종류, 조직/repository, immutable digest 사용 가능 여부
- staging 기본 provider URL과 production custom domain
- DNS zone/record, TTL, 변경 권한자, maintenance 창
- 월 비용 상한과 egress/registry/object-backup 비용 수용 여부
- 장애 시 rollback 결정자와 자동/수동 임계값

가격, instance 명칭, 무료/유료 조건은 변할 수 있으므로 생성 직전 공식 화면/문서에서
다시 확인한다. 과거 문서의 Koyeb 월 `$10.71` 표시는 승인 근거로 재사용하지 않는다.

### 4.4 기존 업무 data/file

- source DB와 production DB가 같은 것인지, 별도 이관인지
- 기존 upload/report 파일의 정확한 source path와 소유자
- read-only inventory 허용 범위, 파일 수/총 bytes/hash 산출 허용 여부
- 이관 대상/제외 대상, 중복 key 정책, reference rewrite 필요 여부
- 원본 보존 기간과 삭제 승인 책임자
- 대표 Meta/Cafe24/Coupang KPI 기간과 기대값; 문서에는 개인정보/원문 row를 남기지 않음
- 환율 API가 필요한 업무 흐름의 `KOREA_EXIM_API_KEY` 주입·egress 여부 또는 synthetic
  exchange-rate fixture 사용 결정

## 5. 병렬 작업 운영

메인 포함 동시 슬롯은 최대 4개다. 메인 에이전트만 commit하고 외부 승인 요청을
정리하며 shared 파일과 최종 diff를 통합한다. 서브에이전트는 commit, push, secret
출력, 외부 mutation을 하지 않는다.

### 5.1 역할

| 역할 | 전담 범위 | 기본 소유 파일/증거 |
|---|---|---|
| 메인/오케스트레이터 | 기준선, 승인 gate, 충돌 조정, plan/status, commit, 최종 판정 | shared config, lockfile, `진행상태.md`, commit |
| A 플랫폼·컨테이너 | base digest/CVE, Docker/launcher, registry/Koyeb, port/TLS/health, 1GB/cold/signal/rollback | `deploy/**`, image/SBOM/scan/runtime evidence |
| B Supabase·DB | target fingerprint, role/pool, migration, Auth/SMTP, Storage policy, DB/object backup/restore | `apps/api/prisma/**`, non-secret Supabase evidence |
| C 앱·업무검증 | 실제 Auth/RBAC/CSRF/Origin, 네 역할, Meta/Cafe24/Coupang, upload/report/KPI/fault test | API/Web test fixtures와 redacted result |
| D 독립 평가자 | P0~P3, 증거/과장/secret/rollback 검토; 수정하지 않음 | review report only |

### 5.2 실행 wave

1. **Wave 0 — 메인:** HEAD/status/diff, 필수 문서, exact target·approval inventory.
2. **Wave 1 — A/B/C 병렬:** 모두 read-only 조사와 로컬 준비만 한다. A는 provider/runtime,
   B는 Supabase/DB, C는 업무 기대값·test matrix를 작성한다.
3. **Wave 2 — 메인 통합:** 파일 소유권과 외부 gate를 확정하고, 필요한 코드 변경을
   역할별로 분리한다. shared env example/lockfile은 메인이 편집한다.
4. **Wave 3 — A/B/C 병렬:** 승인된 staging target에서 각각 runtime, provider,
   business/security 검증을 수행한다. 같은 resource를 동시에 mutate하지 않는다.
5. **Wave 4 — D 독립 평가:** 한 서브에이전트가 끝난 뒤 빈 슬롯에 D를 투입한다.
   D는 source diff, scan, target evidence, PASS/NOT RUN, rollback을 P0~P3로 평가한다.
6. **Wave 5 — 수정·재검증:** 각 발견을 원 소유자에게 돌려보내고 D가 재평가한다.
7. **Wave 6 — 메인:** release SHA/image digest 동결, 전체 검증, staging 판정,
   production gate 제안. production 승인 전에는 배포하지 않는다.

각 서브에이전트 프롬프트에는 다음을 반드시 넣는다.

```text
읽기 전용 조사부터 수행하고 사용자 변경을 보존하라. reset/checkout/clean/stash 금지.
외부 상태 변경, secret 출력, commit/push 금지. 담당 파일과 증거만 메인에게 보고하라.
PASS는 직접 실행한 항목만, 나머지는 NOT RUN으로 표시하라. blocker는 P0~P3와
재현/성공/rollback 조건을 함께 보고하라.
```

파일 충돌을 피하기 위해 A/B/C가 같은 파일을 수정해야 하면 먼저 메인에게 요청한다.
서브에이전트가 만든 변경은 메인이 `git diff`로 모두 검토한 뒤에만 commit한다.

## 6. 단계별 잔여 실행 계획

### R0. read-only preflight와 target fingerprint

담당: 메인 + A/B/C 병렬. 외부 mutation 없음.

1. Git 기준선과 전체 diff를 확인한다.
2. Docker Desktop/context, final image 존재 여부, cgroup/architecture를 읽기 전용 확인한다.
3. Koyeb/registry/Supabase CLI 또는 Dashboard의 로그인 상태만 확인한다. 로그인 자체가
   새 key/resource를 만드는 흐름이면 실행하지 않는다.
4. 사용자에게 production Supabase/Koyeb/registry/domain/data 항목을 받아 비밀 아닌
   target fingerprint를 만든다.
5. 현재 공식 가격, instance memory/CPU, health/rollout, registry digest, Supabase
   connection/backup 계약을 공식 문서에서 다시 확인하고 날짜와 링크를 기록한다.
6. 현재 release와 target 간 gap을 `PASS/FAIL/NOT RUN/BLOCKED`로 작성한다.

성공 판정:

- 정확한 staging과 production target이 서로 구별된다.
- 비용과 mutation gate가 분리된다.
- 어떤 secret도 출력되지 않는다.
- 잘못된 Free 개발 project를 production으로 승격하지 않는다.

### R1. release blocker 해소와 새 immutable image

담당: A, 메인 검토, D 독립 평가.

1. official Node 22 bookworm-slim의 최신 지원 digest와 Debian fix 상태를 확인한다.
2. digest를 full `sha256`로 고정하고 `RELEASE_GIT_SHA`를 실제 build commit에 묶는다.
3. 필요하면 Dockerfile/package만 최소 수정하고 업무 코드와 섞지 않는다.
4. clean build context 검사를 통과시켜 image를 재build한다.
5. image user, port, source/package-manager 부재, OCI revision을 inspect한다.
6. SBOM을 SPDX로 생성하고 Critical/High를 재scan한다.
7. online dependency advisory를 현재 registry 기준으로 새로 확인한다. 기존 offline audit
   0건만으로 공개 배포를 판정하지 않는다.
8. fixed base가 없으면 P1-REL-001의 한시적 위험 수용 gate를 사용자에게 제시한다.
9. 정확한 image digest와 source SHA를 release manifest에 기록한다.

대표 로컬 명령 형태:

```powershell
git status --porcelain=v1 --untracked-files=all
$env:RELEASE_GIT_SHA = git rev-parse HEAD
$env:NODE_IMAGE = 'node:22-bookworm-slim@sha256:<APPROVED_DIGEST>'
$releaseTag = "meta-ads-cloud:$env:RELEASE_GIT_SHA"
docker compose -f deploy/cloud/compose.local.yaml config --quiet --no-env-resolution
docker buildx build --pull --platform linux/amd64 --build-arg "NODE_IMAGE=$env:NODE_IMAGE" --build-arg "RELEASE_GIT_SHA=$env:RELEASE_GIT_SHA" --tag $releaseTag --provenance=mode=max --sbom=true --load --file deploy/Dockerfile .
docker image inspect $releaseTag
docker scout sbom --format spdx $releaseTag
docker scout cves $releaseTag
```

첫 `git status` 출력은 반드시 0줄이어야 하고 HEAD는 commit된 의도한 source여야 한다.
출력이 있으면 build하지 말고 사용자 변경을 보존한 채 메인이 release source를 정리한다.
`config --quiet --no-env-resolution`만 허용하며 일반 `docker compose config` 출력을 증거로
남기지 않는다. 일반 config는 `env_file`의 secret을 해석·출력할 수 있다. 비밀 아닌
구조는 `config --services`, `config --images` 또는 별도 redacted parser로 확인한다.
`--pull`은 registry network read가 필요하므로 실행 환경 승인을 거친다. registry
publish는 이 단계에 포함하지 않는다. buildx/Compose 버전이 위 옵션을 지원하지 않으면
더 약한 명령으로 우회하지 말고 안전한 동등 절차를 먼저 문서화한다.
local inspect로 config/image ID를 기록하고, G-REG-02 publish 뒤에는
`docker buildx imagetools inspect <registry>/<repo>@sha256:<digest>`로 remote index와
linux/amd64 platform manifest가 local release manifest와 일치하는지 확인한다.

성공 판정:

- build input base와 결과 image가 digest로 고정된다.
- source-free/non-root/8000-only 불변 조건을 통과한다.
- Critical/High 0 또는 만료일 있는 명시적 위험 수용이 존재한다.
- R1의 image/base/CVE 범위에서 D의 열린 P0/P1이 0이다. 실제 CMD와 OPS blocker는
  후속 R1A/R2B~R6에서 닫는다.

rollback: 이전 검증 image digest와 Dockerfile commit을 보존하고, 새 image 실패 시
publish하지 않는다.

### R1A. cloud maintenance tooling과 운영 계약 보정

담당: B가 Auth/DB, C가 Storage/업무 runner, A가 별도 artifact와 image closure를 맡고
메인이 shared config·file ownership·commit을 통합한다. 외부 target write 없이 mock과
격리 local DB로 먼저 구현한다.

필수 산출물:

1. **cloud SUPER_ADMIN/user disposition runner**
   - 기존 `BootstrapSuperAdminService`의 identity/email conflict 검사를 재사용한다.
   - exact project ref, DB host/name/schema, Auth subject/email, release SHA를 대조한다.
   - 전 사용자 `keep/link/re-invite/disable` manifest를 먼저 dry-run하고 PII 대신 count와
     opaque ID만 출력한다.
   - exact email/subject가 필요한 입력 manifest와 reversible before-state는 Git 밖의
     승인된 encrypted/ACL-protected 위치에 두고 보존·삭제 시점을 정한다. provider에서
     subject/email/confirmed/disabled 상태를 apply 직전 다시 조회한다.
   - apply는 exact confirmation, advisory lock, idempotency와 security audit를 요구한다.
   - `link`, `re-invite`, `disable`은 서로 다른 confirmation과 외부 gate로 실행하며,
     부분 성공 시 before-state 기반 compensation/rollback을 남긴다.
   - legacy local credential/setup-token을 cloud 로그인으로 재활성화하지 않는다.
2. **immutable migration runner**
   - `prisma migrate deploy`만 수행하는 source SHA/checksum 고정 one-shot artifact다.
   - public app runtime image와 migration owner credential을 분리한다.
   - status/dry-run impact report, timeout/lock 관찰, non-zero fail-closed를 제공한다.
3. **Storage policy·token rotation artifact**
   - tracked SQL/policy 또는 동등한 reviewable artifact로 bucket/prefix별 최소
     SELECT/INSERT/DELETE와 browser anonymous/authenticated 직접 접근 거부를 정의한다.
   - official issuer에서 1~7일 scoped `storage_app` JWT를 발급하고 값은 secret manager에만
     전달한다. 새 token deploy→readiness/lifecycle PASS→Koyeb의 구 secret 제거→공식
     revoke 또는 최대 TTL expiry 확인 순서를 강제한다.
   - 만료 24시간 이상 전 alert와 긴급 rotation 절차를 제공한다. provider가 개별 token
     revoke를 공식 지원하면 revoke하고, stateless JWT라 지원하지 않으면 Koyeb에서 제거한
     뒤 최대 TTL 만료와 구 token 거부 시점을 확인한다.
4. **DB+object backup/restore manifest 도구**
   - maintenance write block→in-flight drain→pending/creating 0→DB cut/watermark→Storage
     key/size/hash/payload inventory→DB watermark/reference 재검증 순서로 일관성을 만든다.
     같은 cut ID 표기만으로 cross-system consistency를 주장하지 않는다. 중간 mismatch가
     생기면 backup을 PASS로 기록하지 않고 재시도 또는 abort한다.
   - independent encrypted target, retention, key custody와 restore verification을 지원한다.
5. **legacy reference inventory/조건부 이관 도구**
   - `UploadBatch`, `Cafe24UploadBatch`, `CoupangUploadBatch`, `ReportExport`,
     `StorageTombstone`의 provider/key 상태를 전수 count/hash로 조사한다.
   - local/absolute reference가 0이 아니면 source hash→no-overwrite target copy→hash 대조→
     DB reference update를 manifest 단위로 수행하고 원본은 보존한다.
6. **release-neutral E2E evidence runner**
   - 실제 Supabase Auth/RBAC/browser/API, private Storage, Meta/Cafe24/Coupang KPI와 report
     canonical digest를 검증한다.
   - test identity/fixture exact cleanup manifest와 redaction을 기본으로 한다.
7. **ready-before-traffic rollout barrier**
   - Koyeb가 protected ready header와 traffic promotion을 지원하면 exact 설정 artifact와
     staging proof를 만든다.
   - 지원하지 않으면 launcher/API startup 순서를 보정해 dependency ready 전에는 Web이
     bind하지 않도록 하고 timeout/failure/child supervision test를 추가한다.

구체 파일명은 기존 구조 조사 뒤 메인이 확정하되, cloud 산출물은 `deploy/cloud/**`와
필요한 `apps/api/src/**` test/service에만 두고 `deploy/local/**`를 복사해 생산 경로에
섞지 않는다. 예정 파일 목록과 소유 에이전트를 코드 수정 전에 이 문서 또는 후속
`진행상태.md`에 고정한다.

성공 판정:

- 각 runner가 dry-run, exact target binding, idempotency, fail-closed, secret redaction을
  unit/integration test로 증명한다.
- migration/Auth/backup credential이 public runtime과 분리된다.
- runtime image에는 maintenance CLI/schema/migrations/signing key가 새로 포함되지 않는다.
- 전체 source 회귀와 새 image/SBOM/CVE/1GiB 검증을 새 SHA로 다시 고정한다.

이 단계에서 코드가 바뀌면 기존 `64fa25f` image의 test/scan 수치를 새 release PASS로
재사용하지 않는다.

### R2A. 격리된 Supabase staging 준비

담당: B, C 지원, 메인 외부 gate 관리. production Supabase는 사용하지 않는다.

1. §4.1의 exact staging target을 고정한다. 현재 Free 개발 project를 재사용하더라도
   target/비용/데이터 영향과 direct DB repair가 필요한지 별도 승인받는다.
2. read-only로 project/DB/Auth/Storage fingerprint, migration history, role/grant,
   user/reference collision을 조사한다.
3. G-DB-00/G-DB-02 뒤 staging 전용 runtime/migration/backup role과 37 migration을
   pristine/clone 경로로 rehearsal한다.
4. G-AUTH-01/02/07 뒤 staging Site URL/redirect/template/test identity를 준비한다.
5. G-STO-01/02/03 뒤 staging private bucket/prefix/RLS/scoped JWT/readiness sentinel을
   준비한다.
6. G-DATA-01에 따라 synthetic DB fixture와 expected KPI/count digest를 만든다.
7. staging DB/object backup과 exact cleanup manifest를 만든다.

성공 판정:

- production ref/credential/data가 staging env와 evidence에 0건이다.
- direct/session-pooler 선택, TLS verify-full, connection limit 2와 최소권한이 PASS다.
- 37 migration history/checksum과 startup transaction이 PASS다.
- public signup OFF, private bucket과 anonymous/browser direct access deny가 확인된다.
- 모든 mutation이 staging 전용 manifest와 rollback/cleanup 범위에 묶인다.

### R2B. 수정하지 않은 full production CMD의 로컬/승인 staging 검증

담당: A + B, C는 실제 기능 smoke, D 평가.

fixture override 없이 최종 `CMD`를 사용한다. secret은 ignored env/secret manager로만
주입한다. 먼저 승인된 non-production Supabase target에서 수행한다.

검증 항목:

- cold start 시간과 child PID; Next/Web, Nest/API 둘 다 실제 entry 사용
- host 공개 port는 Web 하나, API 4200은 host 미노출
- `/backend-api/health/live` 200
- container 내부 token 포함 `/api/health/ready` 200, release ID와 runtime fingerprint 일치
- DB/Auth/private Storage dependency failure 시 ready 실패와 revision 미승격
- SIGTERM에서 in-flight 요청 처리, 15초 안 종료, OOMKilled false
- child 하나 crash 시 sibling 종료와 non-zero failure
- restart 뒤 reconciliation, stale temp/partial object 없음
- 동일 UID `/proc` 실제 가시성 조사와 위험 판정

1GiB 조건은 `memory=1g`, `memory-swap=1g`, tmpfs 192MiB,
`PidsLimit=256`을 그대로 유지한다.
기존 max upload/bundle/report/concurrent scenario를 **실제 app route와 실제 adapter**로
재실행한다. parser harness 결과를 app PASS로 재사용하지 않는다.

성공 판정:

- cgroup `memory.max=1,073,741,824`, OOM/oom_kill delta 0.
- 일반 baseline은 700MiB 이하, 합의한 최대 workload는 850MiB 이하.
- cold/live/ready/signal/restart가 실제 CMD에서 모두 PASS.
- 실제 업무 입력 상한과 동시성 1이 문서와 일치.

실패 시 OOM을 숨기지 않는다. 먼저 upload/object/report row/동시성 상한을 낮춘 안과
업무 영향을 수치로 제시한다. 그래도 불충분하면 Koyeb 2GB instance의 당시 실제 가격,
예상 peak 여유, rollback을 제시하고 사용자 승인을 받는다. 자동 승격하지 않는다.

### R3. Supabase production read-only 준비와 복구 증거

담당: B, C가 Auth/업무 전환 manifest를 설계하고 메인이 승인 gate를 관리한다.
R6 frozen staging PASS 전에는 production role/key/user/Auth 설정/Storage policy/token/data/
migration을 변경하지 않는다. 이 단계의 production 범위는 read-only inventory와 별도
승인된 backup restore rehearsal뿐이다.

#### R3-1. read-only inventory

- project ref/region/plan/health와 Auth/Storage/DB endpoint를 비밀 없이 확인한다.
- migration table, schema, extension, role/grant, table/row 규모, DB version을 read-only로
  수집한다. 개인정보/row body는 출력하지 않는다.
- 현재 Auth Site URL/provider/signup/template/SMTP와 private bucket/policy를 export 가능한
  비밀 아닌 형태로 기록한다.
- production DB와 현재 Prisma migration chain의 drift를 확인한다.
- `AppUser`의 email/auth_user_id/invite_status/role, local credential/session/setup-token은
  원문 없이 상태별 count와 collision digest만 만든다.
- 모든 upload/report/tombstone Storage reference의 provider/prefix 상태, orphan,
  duplicate, pending/creating 상태를 count/hash로 조사한다.

#### R3-2. DB backup/restore rehearsal

- 최신 backup identifier와 보존 기간을 확인한다.
- 별도 승인된 격리 target에 실제 restore한다.
- migration history, 핵심 table/count/KPI, role/grant, audit를 확인한다.
- restore 시간을 측정해 RTO를 판단한다.
- restore rehearsal 없는 dashboard backup 표시는 PASS가 아니다.

#### R3-3. production migration/role 계획과 clone rehearsal

- 복원 target에서 전체 migration SQL의 lock/시간/데이터 변환/되돌리기 영향을 검토한다.
- production에서 만들 `migration owner`와 최소권한 `runtime role`의 grant manifest를
  작성하되 이 단계에서는 생성하지 않는다.
- runtime role은 앱 schema의 필요한 DML만 허용하고 DDL/TEMP/role 관리 권한을 주지
  않으며, backup role은 필요한 read-only 범위로 분리한다.
- runtime connection limit 기본 2가 Supabase pool/provider limit과 맞는지 계산한다.
- direct/session pooler 선택 시 IPv4/IPv6, TLS verify-full, hostname, username suffix,
  prepared statement/transaction 제약을 현재 공식 계약으로 검증한다.
- cloud에서 사용하지 않는 local-auth/local-edge table이 migration chain에 남는 것은
  역사 보존이며, 운영 runtime이 그 기능을 활성화하지 않는지 확인한다. 대량 drop하지 않는다.
- 승인된 격리 clone에서 37 migration을 pristine과 기존 data 두 경로로 검증한다. Auth migration의
  email/role precondition과 raw-row scrub은 production 전에 별도 backup/영향 증거가 필요하다.

read-only 상태 확인 예시는 승인된 local/clone target에만 사용한다.

```powershell
.\node_modules\.bin\prisma.cmd validate --schema apps/api/prisma/schema.prisma
.\node_modules\.bin\prisma.cmd migrate status --schema apps/api/prisma/schema.prisma
```

`DATABASE_URL`은 clone용 비밀 경로로 주입하고 command/log에 URL을 찍지 않는다. production
`migrate deploy`를 developer host의 Prisma CLI로 직접 실행하지 않는다. R1A에서 만든
source SHA·migration checksum·tool version이 고정된 maintenance image/job digest와 별도
migration credential을 준비한다. production 실행은 R8에서 G-DB-00/G-DB-03을 각각
승인받은 뒤에만 한다. 그 exact invocation은 artifact 구현·staging rehearsal 후 release
manifest에 고정한다.

#### R3-4. production Auth와 사용자 전환 manifest

- public signup/provider/Site URL/redirect/template/SMTP의 before-state와 desired-state를
  read-only로 작성한다. 설정은 R8 gate 전 변경하지 않는다.
- 최초 SUPER_ADMIN과 기존 사용자별 `keep/link/re-invite/disable` disposition을 secure
  manifest로 만들고 provider identity를 read-only 대조한다. 연결·초대·disable은 R8이다.
- provider role claim을 앱 role로 신뢰하지 않는 계약과 네 역할 test case를 동결한다.
- staging에서 이미 통과한 invite/login/refresh/logout 결과를 production PASS로 재사용하지
  않고 R8 smoke 항목으로 예약한다.

#### R3-5. production private Storage inventory와 object backup

- private bucket/RLS policy/prefix/token subject/TTL의 before-state와 desired-state를
  read-only로 작성한다. policy/token은 R8 gate 전 변경하지 않는다.
- server Auth admin secret을 Storage runtime token으로 재사용하지 않는지 manifest에서
  확인한다.
- production object write/delete 없이 inventory/manifest/hash backup을 만든다. 실제
  restore는 승인된 격리 target에서 수행한다.
- synthetic lifecycle/max upload/tombstone/compensation은 R2A/R2B/R4/R5 staging에서
  통과해야 하며 production에서는 R8 제한 smoke만 한다.
- 독립 object backup에 inventory/manifest/hash/payload를 저장하고 별도 target에 실제
  restore/hash 대조한다.

성공 판정:

- production 동일 project ref의 Auth/DB/Storage desired manifest가 완전하다.
- production-like restore target에서 migration/rollback 시간이 측정된다.
- 실제 Auth와 object body lifecycle은 격리 staging에서 PASS이고 production smoke가
  R8에 예약된다.
- DB와 Storage 각각 복원 가능한 증거가 있다.

### R4. registry와 Koyeb staging

담당: A, B secret/health, C smoke, 메인 승인.

1. 생성 직전 공식 화면에서 조직/service/region/1GB instance/월 예상 비용을 확인한다.
   replica는 1개, autoscale은 비활성 또는 승인된 exact 상한인지 확인한다.
2. private registry/repository와 deploy identity의 최소권한을 설계한다.
3. 사용자가 registry gate를 승인한 뒤 exact digest image를 publish한다.
4. 사용자가 Koyeb 생성 gate를 승인한 뒤 staging app/service를 만든다.
5. secret은 Koyeb secret 기능으로 주입하고 Web build/public env에는 넣지 않는다.
   §4.1/R2A에서 승인된 격리 staging Supabase 값만 사용하며 production credential은 0건이다.
6. provider `PORT` 하나, API loopback, TLS, proxy hop, health/live/ready, rollout failure
   동작을 확인한다.
   로컬 compose의 read-only root/cap-drop/PID/no-swap 설정이 Koyeb에 자동 적용된다고
   가정하지 말고 provider가 실제 지원·적용하는 항목과 불가능한 항목을 분리해 기록한다.
   provider health는 secret 없는 live path로 수행하고 protected ready는 별도 operator
   promotion gate에서 exact release/config fingerprint와 함께 확인한다.
7. staging 기본 provider domain에서 먼저 검증하고 custom DNS는 건드리지 않는다.

성공 판정:

- 배포 revision이 source SHA와 image digest에 대응한다.
- public scan에서 HTTPS Web port 외 API/관리 port가 닫혀 있다.
- ready 실패 revision은 traffic을 받지 않는다.
- restart/OOM/event/log에 secret이 없고 1GB limit이 실제 적용된다.
- 이전 secure digest로 staging rollback을 실제 1회 수행하고 다시 새 digest로 복귀한다.

인증·권한 matrix:

- anonymous, onboarding, inactive, GUEST, USER, ADMIN, SUPER_ADMIN
- login/me/refresh/logout/invite accept/password setup
- role change/deactivation/session revocation 즉시 반영
- direct API, CSRF, Origin/Host/forwarded header, secure cookie
- SUPER_ADMIN 전용 users/audit/settings
- 401/403/429와 audit actor/result가 기대대로 구분되는지

업무 matrix:

- 사용자 승인 대표 기간의 Meta/Cafe24/Coupang KPI
- 각 upload/import preview, validation, apply와 동일 hash SKIP
- mapping/rematch, decision, manual purchase, change log
- report generate/list/download
- 전후 DB row/object/audit expected delta
- 최대 upload/bundle/report와 두 동시 요청의 RSS/heap/cgroup/tmp peak
- 5개 승인 test identity의 가벼운 동시 browse/API session과 DB pool/latency peak

Storage/fault matrix:

- unauthenticated private object 거부
- 실제 body upload/download SHA-256
- DB 성공/Storage 실패 및 Storage 성공/DB 실패 compensation
- process kill/container restart reconciliation
- tombstone retain/restore/purge
- DB restore와 object restore/hash

각 test는 synthetic 또는 승인된 비식별 fixture를 사용한다. production data/file을
staging에 복제하지 않는다. 외부 이메일 발송은 정확한 시험 수신자 승인 없이는 하지 않는다.

### R6. release freeze와 독립 평가

담당: D 평가, 메인 통합.

D는 다음 세 관점으로 별도 보고한다.

1. 업무: KPI/import/report/data delta.
2. 인증·보안: Auth/RBAC/CSRF/Origin/cookie/proxy/direct API/Storage/secret.
3. 운영: 1GB/OOM/restart/health/deploy/rollback/DB·object restore/CVE.

발견사항은 P0~P3, 근거, 재현, 영향, 수정 소유자, 재검증으로 기록한다. 계획 범위의
열린 P0/P1/P2/P3가 0이 될 때까지 release를 freeze하지 않는다. 예외 수용은 명시적으로
승인되고 만료일이 있는 항목만 닫힌 것으로 취급한다.

freeze할 값:

- full Git SHA, base digest, image digest, SBOM hash, scan timestamp
- Prisma migration head와 target schema fingerprint
- non-secret runtime config fingerprint
- Koyeb revision/service/region/instance
- Supabase project ref/DB schema/bucket ID
- test/evidence commit

### R7. production preflight와 cutover 승인안

담당: 메인, A/B/C read-only 병렬, D 최종 검토.

cutover 직전 다시 확인한다.

- maintenance 시작/종료, 연락자, rollback 결정자
- 최신 DB backup과 실제 restore rehearsal
- 최신 object backup과 실제 restore/hash
- migration 예상 시간/lock/rollback
- frozen image digest와 staging PASS 일치
- production secret 주입, Auth URL/template, Storage policy
- DNS TTL과 기존 endpoint rollback
- 1GB instance/월 비용/상한; 2GB 자동 승격 금지
- 제한적 쓰기와 집중 관찰 시간

하나라도 누락되면 production 승인을 요청하지 않고 `operationalReady=false`를 유지한다.

### R8. production cutover

각 외부 gate의 명시 승인 뒤 다음 순서를 지킨다.

1. maintenance 진입 및 write 차단 확인
2. write block→in-flight drain→pending/creating 0→R1A의 DB cut/watermark와 Storage
   payload/manifest/hash backup→DB watermark/reference 재검증 순서로 cutover 직전
   일관된 backup을 만든다. mismatch면 중단·재시도하고, 이 exact cut manifest의 격리
   restore 증거가 없으면 다음 단계로 가지 않는다.
3. 승인된 production `prisma migrate deploy`
4. Auth Site URL/redirect/template/SMTP와 private Storage policy/token 적용
5. frozen digest container 배포; ready 전 traffic 0
6. 내부 live/ready, 네 역할, 대표 KPI, synthetic object smoke
7. provider domain에서 제한적 쓰기
8. custom domain/DNS 전환
9. 집중 관찰: 5xx/401/403/429, OOM/restart, DB pool, Auth/Storage, latency
10. 성공 판정 후 maintenance 종료

rollback trigger 예시:

- ready 실패 또는 release/config fingerprint 불일치
- migration 오류/예상 밖 lock 또는 대표 KPI 불일치
- Auth login/refresh/invite/role boundary 실패
- private object 비인가 접근 또는 object hash/data loss
- OOM/oom_kill, 반복 restart, memory 상한 초과
- 지속적인 5xx/DB pool 고갈/Storage failure

rollback 순서:

1. public endpoint를 maintenance/차단 상태로 둔다.
2. 쓰기를 중지하고 마지막 성공 transaction/object 범위를 식별한다.
3. Auth URL/provider/template/SMTP, Koyeb secret revision, Storage policy/token과
   SUPER_ADMIN/user disposition의 승인된 before-state를 확인한다. reversible 설정은
   아직 유효한 이전 credential/config로 복구하고, 잘못 연결된 DB identity는 disposition
   compensation manifest로만 되돌린다.
4. 이미 발송된 invite email은 회수할 수 없으므로 해당 invite/session을 revoke 또는
   expire하고 수신자·영향을 incident에 기록한다. 발송을 rollback됐다고 표현하지 않는다.
5. schema가 forward-compatible이면 검증된 이전 secure image digest로 되돌린다.
6. 그렇지 않으면 승인된 DB restore/forward-fix 절차를 사용한다. 임의 down migration을
   만들지 않는다.
7. DNS를 바꿨다면 이전 record/TTL로 복구한다.
8. object manifest/hash를 대조하고 compensation/reconciliation을 수행한다.
9. incident evidence를 비밀/개인정보 없이 기록한다.

무인증 구버전을 인터넷에 공개하는 rollback은 금지한다.
첫 cloud production 배포라 호환되는 이전 cloud digest가 없다면 traffic을 maintenance/off
상태로 유지하는 것이 rollback이다. 과거 LAN/local 앱을 public endpoint에 다시 열지 않는다.

## 7. 외부 변경 승인 gate

gate를 묶어 포괄 승인으로 처리하지 않는다. 매 실행 직전에 메인은 아래 형식으로
사용자에게 제시한다.

```text
Gate ID / 정확한 target:
실행할 명령 또는 Dashboard/API 작업(비밀값 제외):
읽기/쓰기/삭제 범위와 사용자·업무 영향:
예상 비용과 소요 시간:
성공 판정:
실패 판정과 rollback:
실행 후 남길 비밀 아닌 증거:
```

필수 gate 목록:

| ID | 별도 승인이 필요한 작업 |
|---|---|
| G-REG-01 | GitHub/private registry 연결과 repository 생성 |
| G-REG-02 | frozen image digest 최초 publish |
| G-REG-03 | registry artifact/tag 삭제·비공개 전환 또는 credential revoke |
| G-KOY-01 | Koyeb app/service/1GB instance 생성과 월 비용 |
| G-KOY-02 | Koyeb secret 최초 등록·갱신·회전 |
| G-KOY-03 | staging/production exact digest deploy·redeploy |
| G-KOY-04 | revision rollback 또는 service disable/delete |
| G-SUP-STG-01 | 기존 Supabase project의 staging 재사용/resume와 데이터 영향 |
| G-SUP-STG-02 | 새 staging Supabase project/plan 생성과 비용 |
| G-SUP-STG-03 | staging Supabase read-only fingerprint/backup 조회 범위 |
| G-SUP-PRD-01 | production Supabase read-only fingerprint/backup 조회 범위 |
| G-SUP-KEY-01 | exact target의 Supabase backend Secret Key 생성·회전과 새 key 검증 |
| G-SUP-KEY-02 | exact target의 이전 Supabase backend Secret Key revoke/delete |
| G-DB-00 | runtime/migration/backup DB role·grant·password 생성·회전 |
| G-DB-01 | production DB snapshot/logical backup과 격리 restore rehearsal |
| G-DB-02 | staging migration |

### 7.1 R 단계와 gate 연결

| 단계 | 실행 전 필요한 gate |

| R2B | staging 실제 app mutation은 G-DATA-01, G-AUTH-07, G-STO-05; provider token 전환은 G-STO-04 |
| R3 | production read-only G-SUP-PRD-01과 backup/restore G-DB-01/G-BKP-01만; production 설정/data mutation 금지 |
| R4 | G-REG-01 → G-REG-02 → G-KOY-01 → G-KOY-02 → G-KOY-03 |

직전에 다시 제시한다. destructive cleanup/delete/revoke는 create/write 승인에 포함되지 않는다.

## 8. 검증 명령과 증거 규격

### 8.1 release 전 전체 source 검증

```powershell
npm.cmd run prisma:validate
npm.cmd run prisma:generate
npm.cmd run lint
npm.cmd test
npm.cmd run build
npm.cmd audit --omit=dev --offline
npm.cmd run cloud:test-runtime
git diff --check
git status --short --branch
```

`npm.cmd test`에 launcher test가 포함되지만 종료 전에는 결과 가독성을 위해
`cloud:test-runtime`도 별도 기록할 수 있다. 외부 target 의존 skip은 개수와 이유를
기록하며 PASS로 바꾸지 않는다.

### 8.2 container 증거

아래를 release별로 기록한다.

- source full SHA, base index/platform digest, result image digest/size
- runtime user/capabilities/read-only/tmpfs/PID/memory/swap/public port
- image source/package-manager 부재와 OCI revision
- SBOM 파일 hash, scan 도구/버전/시간, CVE/fix 상태
- cold start, live/ready, child exit, SIGTERM, restart/rollback 시간
- cgroup `memory.max/current/peak/events`, process RSS/heap/external, `/tmp` peak
- max workload fixture의 byte/row 수, 동시 요청 결과, OOM delta

### 8.3 target 증거

- UTC/KST timestamp, environment ID, non-secret target fingerprint
- 실행 주체/승인 gate/명령 형태와 exit/status
- Supabase project ref, DB schema/migration head, bucket ID; secret 제외
- Auth flow별 HTTP/화면 결과, role, audit event ID; 이메일/개인정보 redaction
- object key는 synthetic prefix만, size와 SHA-256, lifecycle result
- KPI는 승인된 기간/집계/expected vs actual과 허용 오차만
- Koyeb revision/image digest/health/resource/OOM/restart
- backup identifier, restore target, elapsed time, row/object/hash 검증
- rollback 시작/완료 시간과 복구된 digest/config fingerprint

증거 파일에 console dump 전체나 `.env`를 복사하지 않는다. provider 응답에 secret 또는
개인정보가 있으면 필요한 field만 allowlist로 추출한다.

## 9. commit 경계와 작업 종료 조건

메인 에이전트만 다음처럼 논리적으로 분리해 commit한다. 실제 변경이 없으면 빈 commit을
만들지 않는다.

1. `docs: record cloud deployment preflight` — target/gate/기준선 문서만
2. `fix: resolve cloud release blockers` — base/runtime/security 최소 변경
3. `test: add cloud staging verification` — 비식별 fixture/test만
4. `docs: record cloud staging evidence` — digest/측정/PASS·NOT RUN
5. `docs: record cloud production cutover` — 승인·backup/restore/deploy/rollback 결과

각 commit 전에 staged diff를 확인하고 secret scan과 `git diff --check`를 수행한다.
push/main merge/tag는 G-GIT-01 승인 전 금지한다. 작업 종료 시 메인이 전체 diff를
검토하고 의도한 변경만 남겼는지 확인한다. 사용자 요청이 clean worktree까지 포함하면
허용된 변경을 commit해 clean하게 만들되, 남의 변경을 없애서 clean하게 만들지 않는다.

즉시 중단하고 사용자에게 보고할 조건:

- target/project/account가 계획과 다름
- secret/개인정보 노출 가능성 또는 실제 노출
- migration drift, destructive SQL, 예상 밖 대량 update/delete
- 비용/instance/plan이 승인안과 다름
- production data나 원본 파일을 staging에 써야만 진행 가능
- 1GB OOM, 850MiB 초과, 반복 restart
- Critical/High가 남았는데 명시적 risk acceptance가 없음
- backup restore 또는 rollback이 재현되지 않음
- DNS/public traffic 변경이 승인 범위를 벗어남

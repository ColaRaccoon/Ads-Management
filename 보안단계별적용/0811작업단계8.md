## 1. 이 세션의 단일 목표

개발 기간 동안 업무용 main에 추가된 변경을 보안 branch로 통합하고 전체 테스트를 다시 수행한다. 승인된 스테이징 환경에 배포해 네 역할, 모든 업무 데이터 흐름, migration, storage, 보안 공격을 실제 브라우저/API에서 검증한다. 발견 결함이 0개가 될 때까지 개발자↔평가자 루프를 반복한다.

운영 main에 보안 branch를 병합하거나 운영 DNS/DB를 변경하지 않는다.

## 3. 하위 에이전트 역할

최소 세 역할을 둔다.

1. **통합/배포 개발 담당**: 최신 main 통합, conflict 해결, build artifact, staging deploy, migration rehearsal
2. **업무 회귀 평가 담당**: Meta/Cafe24/Coupang/보고서/수정기록의 기존 수치와 data flow 검증
3. **적대적 보안 평가 담당**: 익명·네 역할 직접 API, CSRF, session, file, rate, error, cache, user 관리 공격

평가자 둘은 개발 완료 전 독립 expected matrix와 fixture를 준비한다. 결함은 개발 담당에게 반환하고 수정 후 동일 항목+전체 suite를 다시 실행한다.

## 4. 최신 main 통합

### 4.1 사전 확인

```powershell
git status --short --branch
git worktree list --porcelain
git log --oneline --decorate --graph -20
```

- 보안 worktree clean 확인
- 원본 main의 현재 commit 확인
- 원격 확인이 필요하면 사용자 승인된 `git fetch`만 수행
- 원본 업무 폴더의 파일/branch/process는 변경하지 않음
- 이 단계의 merge는 별도 security worktree 안에서만 하므로 원본 main watcher를 중지할 필요가 없고 업무 앱은 계속 쓸 수 있어야 한다. 명령의 `cwd`, branch, `git rev-parse --show-toplevel`을 확인해 원본 폴더를 실수로 수정하지 않는다. 원본 main에 security branch를 통합하는 9단계에는 별도의 명시적 local maintenance gate가 있다.

### 4.2 통합 방식

보안 worktree에서 최신 `main`을 **보안 branch로 merge**한다. 보안 branch를 원본 main으로 병합하지 않는다. 임의 rebase/force push 금지.

충돌 해결 원칙:

- 최신 main의 업무 계산/리포트 개선을 보존
- 보안 branch의 auth/RBAC/DTO/Storage 계약 보존
- 한쪽을 통째로 선택하지 말고 data flow별로 재통합
- generated Prisma client나 lockfile 충돌은 원천 schema/package를 기준으로 재생성
- 충돌 해결 뒤 관련 unit + 전체 suite 실행
- main에 새 controller/route가 추가되면 default deny route expected matrix에 명시 권한 추가
- main에 새 mutation UI가 추가되면 PermissionGate/readOnly 적용

통합 commit과 이전 단계 commit을 진행상태에 기록한다.

## 5. 배포 구조 요구사항

권장 논리 구조:

```text
브라우저
  -> https://staging.<domain>
  -> Next.js
  -> same-origin /backend-api reverse proxy
  -> 내부 NestJS API
  -> staging PostgreSQL
  -> staging Supabase Auth
  -> staging private object storage
```

가능하면 Nest API를 인터넷에 직접 공개하지 않고 Web/reverse proxy 내부 네트워크에서만 접근하게 한다. 직접 공개해야 하면 exact CORS, firewall, TLS, rate limit을 별도로 검증한다.

## 6. 배포 artifact

선택한 hosting 공식 문서에 맞춰 최소한 다음을 준비한다.

- reproducible production build
- API/Web multi-stage Dockerfile 또는 provider manifest
- `.dockerignore`: `.env*`, `.git`, node_modules, `.next`, dist, storage, dumps, logs, test artifacts 제외
- non-root runtime user
- read-only filesystem 가능 범위와 temp directory
- health/live/readiness
- graceful shutdown
- Web `API_PROXY_TARGET` 내부 URL
- secret manager env injection
- DB SSL/connection limit
- object storage credential 최소권한
- production과 다른 staging cookie 이름/host/origin
- authenticated response CDN no-store

`API_PROXY_TARGET`가 Next build 시점에 rewrite로 고정되는지 실제 artifact에서 확인한다. 다음 중 하나를 선택해 문서화한다.

1. Web image는 환경과 무관하고 runtime reverse proxy/sidecar/host route가 내부 API target을 주입하여 **같은 image digest**를 staging→production으로 승격한다.
2. provider 특성상 build-time 값이 필수면 production과 동일 proxy target/config로 만든 release artifact를 production과 동등한 pre-production slot에서 완전 검증한 뒤 그 **동일 digest**만 승격한다.

staging용 target으로 빌드한 Web을 production에서 다시 빌드 없이 쓸 수 있다고 가정하거나, staging 검증 후 production에서 임의 재빌드하지 않는다. 배포 기록에는 non-secret runtime config fingerprint(origin host, cookie mode, API target 식별자, Auth project ref, DB/storage 환경 식별자)를 남겨 환경 혼선을 잡는다.

`next.config.ts`/`.mjs` 중 실제 사용 파일 하나를 확인한다. 둘에 다른 rewrite/header를 남겨 환경별 결과가 달라지지 않게 하되, 무관한 정리는 최소화한다.

현재 import가 최대 수분 걸릴 수 있고 Next proxy timeout이 300초로 설정되어 있다. 선택 host의 request timeout, memory, CPU, connection 유지 한계를 공식 문서로 검증한다. 맞지 않으면 임의 timeout 증가보다 background job 구조를 별도 결함으로 처리한다.

## 7. staging 환경 격리

- staging DB/project/schema는 production과 다름
- staging Auth project/redirect URL 별도
- staging object bucket/credential 별도
- production secret 재사용 금지
- staging email 초대가 실제 고객/업무 email로 발송되지 않음
- staging 검색엔진 차단과 필요하면 추가 access control
- synthetic 또는 승인된 익명화 snapshot만 사용
- storage lifecycle로 test 파일 정리
- production snapshot을 staging에 복원했다면 이전 main 호환성 검사는 **read-only DB credential**로 수행한다. 구버전 binary가 staging snapshot에 쓰게 하지 않는다.

환경변수 값은 secret manager에 넣고 계획/CI log에 출력하지 않는다.

## 8. migration rehearsal와 복구

1. production과 유사한 크기/shape의 staging snapshot 확보
2. backup 생성
3. 별도 임시 DB에 backup restore 성공 확인
4. `prisma migrate deploy` 실행
5. migration 시간, lock, DB CPU/connection 기록
6. 전후 schema, 주요 table row count, 대표 KPI 비교
7. 기존 main build가 additive migration 뒤 여전히 읽기 가능한지 확인
8. migration 실패 시 down SQL이 아니라 snapshot/새 DB restore 절차 연습
9. staging object 하나를 실제로 삭제/손상한 뒤 version/backup에서 복원하고 SHA-256 일치 확인

이미 적용된 migration을 수정하지 않는다. destructive SQL이나 장시간 lock이 보이면 운영에 가지 않고 expand/contract 새 migration으로 수정한다.

## 12. 적대적 보안 시나리오

- unknown DTO field/malformed UUID/date/boolean/range
- oversized JSON
- login brute force/rate limit
- CSRF/Origin spoof
- token 위조/만료/wrong issuer/audience
- refresh replay/concurrency
- 두 API instance를 쓸 계획이면 instance를 바꿔도 refresh DB lock과 distributed rate limit이 동작; single instance면 topology 고정 증거
- open redirect
- 500/Prisma/path/secret 정보누출
- oversized/disguised/malformed/ZIP bomb/formula file
- path traversal/report unauthorized download
- signed URL 재사용/만료
- user invite duplicate/concurrency
- two last-super-admin demotions
- object storage outage와 DB 부분 실패
- maintenance endpoint/edge가 Web/API artifact와 독립적으로 켜지고 꺼지는지, 잘못된 release 중에도 접근차단 가능한지
- Auth signing key/secret 회전 시 이전·새 키의 검증 overlap과 rollback 가능성
- dependency/secret scan

실제 서비스에 피해를 주는 대량 공격은 staging limit 안에서 synthetic하게 수행한다.

테스트를 삭제/완화해 통과시키거나 expected 업무 수치를 새 잘못된 값으로 갱신하지 않는다.

이 단계도 검증 구현/수정 commit과 인계 문서 commit을 분리한다.

```text
test(security-step8): validate staging security and business flows
docs(security-step8): record verified staging handoff
```

첫 commit SHA, image digest, runtime config fingerprint, staging URL, migration/restore 시간, object 복원, 결함 루프 결과를 진행상태에 기록한 뒤 문서 commit을 만든다. 문서 commit 자신의 SHA는 9단계가 시작 HEAD로 기록하며 worktree는 clean이어야 한다.

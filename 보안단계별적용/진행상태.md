### 2단계 구현·계약

- Supabase Auth를 서버측 `IdentityProvider` adapter 뒤에 연결하고 요청별 stateless client(`persistSession=false`, `autoRefreshToken=false`)를 사용한다. JWT는 JWKS로 signature, ES256 algorithm, issuer, audience, expiry, UUID `sub`, UUID `session_id`를 검증하며 Supabase의 PostgreSQL role claim은 앱 role로 사용하지 않는다.
- `AppRole`(`SUPER_ADMIN`, `ADMIN`, `USER`, `GUEST`), `InviteStatus`, `AppUser` 인증 연결 필드와 raw token을 저장하지 않는 `AppAuthSession`을 추가했다. 중앙 상태 판정은 매 요청 현재 `AppUser`와 session 폐기 상태를 다시 읽는다.
- access/refresh/session-handle은 서로 다른 HttpOnly root-path cookie이고 CSRF cookie만 JavaScript에서 읽을 수 있다. production `Secure=true` 강제, `SameSite=Lax`, Domain 미지정, HMAC session handle, exact Origin·fetch metadata·double-submit CSRF, bounded rate limiter 계약과 PostgreSQL advisory lock 기반 분산 refresh 직렬화를 구현했다.
- 역할→권한 단일 매핑과 opaque `authorizationVersion` 응답 계약을 고정했다. `SUPER_ADMIN`은 10개 권한, `ADMIN` 7개, `USER` 3개, `GUEST` 1개다.
- 안정된 오류 코드를 구현했다: `AUTHENTICATION_REQUIRED`, `SESSION_INVALID`, `ACCESS_TOKEN_EXPIRED`, `SESSION_REVOKED`, `INVALID_CREDENTIALS`, `ACCOUNT_NOT_PROVISIONED`, `ACCOUNT_INACTIVE`, `ACCOUNT_ONBOARDING_REQUIRED`, `AUTH_PROVIDER_UNAVAILABLE`, `REFRESH_RACE_RETRY`. Auth 응답·오류는 모두 `private, no-store`다.
- 일회성 `auth:bootstrap-super-admin` CLI는 dry-run, DB host/name/schema와 대상 subject/email의 exact confirmation, 공급자 확인, 중복 subject/email fail-closed를 지원하며 앱 startup에서 실행되지 않는다.

- 공통 `FileStorage`에 방어적 local/Supabase adapter를 구현했다. key 정규화와 domain prefix 소유, bounded spool/stream, 실제 SHA-256·size 검증, atomic no-replace, duplicate race, timeout/abort, chunked object metadata, provider status-body 정리, 401/403/404/409/5xx 안정 오류 매핑을 적용했다. bucket/key/provider 원문과 credential은 응답·감사·로그에 노출하지 않는다.
- Meta 원본과 report만 durable storage를 사용한다. 신규 Meta active key는 batch UUID를 포함해 동일 content 재업로드에서도 재사용되지 않는다. Cafe24/Coupang 원본 저장은 추가하지 않았고 `20260825170000_minimize_cafe24_coupang_raw_rows`로 네 정규화 raw JSON 대상을 NULL scrub했다. Meta raw row 예외는 유지했다.
- `StorageTombstone`은 서버 key, hash, size, 업무 record id, 상태·보존기한·actor·안정 failure code만 저장한다. retain/restore/purge 전체 transition은 tombstone별 PostgreSQL advisory transaction으로 직렬화하고 부분 실패 재시도, hash/size 재검증, 30일 만료, SUPER_ADMIN `settings.manage` 복원·명시 purge, dry-run 기본 maintenance를 구현했다. 원본 filename·내용·개인정보는 tombstone/audit에 저장하지 않는다.
- upload 삭제는 업무 metric 정리 의미를 유지하면서 원본을 trash에 보존한다. 복원은 관리자 재검토·재업로드용 원본 복구이며 삭제된 metric을 자동 부활시키지 않는다. report는 CREATING/CREATED/FAILED와 private authenticated stream, bounded size/hash, 안전한 attachment header를 사용한다. API/Web CSV·XLSX formula injection과 HTML escape도 적용했다.

### 8단계 Supabase DB-only local 전환 구현

- local native username 인증에 bounded asynchronous scrypt, opaque session/setup
  token, idle/absolute/rotation 만료, CSRF/Origin/Secure cookie, replay·rate limit,
  bootstrap `SUPER_ADMIN` 단일성, setup-pending/inactive 및 유일한 active
  `SUPER_ADMIN` 불변식을 구현했다. 실제 이메일은 사용하지 않는다.
- 기존 Supabase에는 PostgreSQL만 outbound TLS verify-full 5432로 연결한다.
  project/host/DB/schema와 runtime/migration/backup 역할, production에 존재하지
  않는 것이 아니라 제한된 LOGIN이되 production DB CONNECT/schema/object 접근과
  membership이 모두 없어야 하는 restore 역할명, CA hash,
  privilege/ownership/default grant, audit function의 exact source와 UPDATE/DELETE/
  TRUNCATE trigger의 function OID·type을 증거 v6에 고정한다. migration owner는
  maintenance 중에만 사용하는 full-data privileged role이며 애플리케이션 runtime
  credential과 분리한다. local DB와 transaction
  pooler 6543는 거부한다.
- local Storage와 signed Edge→API metadata/nonces, exact private-IP HTTPS 443 Edge,
  loopback Web/API, client PreOpen trust, Windows service/principal/ACL/firewall/CA
  계층을 분리했다. 값이 없으면 config-only 또는 prepared Core loopback이고 Edge는
  stopped다.
- release full-tree hash manifest, recovery kit, signed daily backup/restore receipt,
  업무 KPI·storage reference·file byte SHA-256, RPO 24h/RTO 4h, maintenance/drain,
  additive migration compatibility, atomic switch/rollback, reboot readiness 절차를
  구현했다.
- 최초 전환은 기존 3100/4100 실행본이 local Auth/Storage smoke를 제공한다고
  가장하지 않는다. clean Git tree·migration chain·listener/process identity를
  hash-pinned legacy baseline으로 서명하고, 격리 restore DB에서 이전 업무 KPI
  adapter를 migration 전후에 실행한다. process rollback은 검증 중 그대로 둔 기존
  3100/4100 실행본이며, DB rollback은 별도 승인을 받는 restore다.
- restore의 전체 4시간 deadline은 모든 psql/pg_restore/Prisma/업무·API·권한 smoke
  자식 process에 적용하고 초과 시 process tree를 종료한다. compatibility proof는
  같은 backup ID와 manifest hash의 24시간 이내 signed backup receipt에 묶인다.
- release 검증은 Next `required-server-files`, API/Web production dependency closure,
  Prisma generated client/native engine과 실제 business smoke CLI까지 inventory/hash로
  고정한다. restore verifier는 production과 다른 database를 사용하므로 기존
  Supabase project 안의 별도 DB도 허용하지만 새 cloud project/database를 만들지
  않는다. verifier scratch의 입력 복사본만 복원하고 완료 후 DB schema/storage/
  입력 snapshot을 제거하며 승인된 게시 스크립트는 signed receipt만 반출한다.
- production migration은 INTENT journal을 먼저 남기는 `Apply`와 fresh post-boundary/
  exact applied-chain 뒤 final evidence를 쓰는 `Finalize`로 분리했다. Edge request
  body는 제한된 spool에서 hash를 먼저 계산해 서명하며 API가 일반/multipart body
  digest를 다시 확인한다. 방화벽은 모든 profile enabled/default inbound Block까지
  전제로 exact 443 규칙만 허용한다.
- backup/restore의 PostgreSQL·Prisma·업무 smoke 자식 process, 파일 열거·copy·hash,
  output capture에 monotonic 4시간 hard deadline, 크기 상한, process-tree 종료와 별도
  cleanup window를 적용했다. recovery evidence v6는 current-source hash, stable
  host-instance digest, local alias가 아닌 안정적인 NAS/별도 volume identity,
  clean-PC disaster rehearsal, exact credential/key/tool inventory와 추출 후 정리를
  모두 증명해야 한다. 같은 Windows 설치에서 만든 disaster 증거와 구형 증거는
  fail-closed다.
- Windows mutation 및 증거 writer 27개는 대상·영향·rollback과 exact argument/file
  hash, CSPRNG nonce, 10분 TTL, instance ID가 묶이고 ADMIN_ONLY ledger에서 원자 소비되는
  일회성 approval plan 없이는 실행되지 않는다. backup task는 설치 시
  지정하는 daily trigger가 실제 enabled여야 하고, 별도 물리 대상과 restore 증거가
  없으면 `operationalReady=false`다.
- Supabase DB 경계 증거 v6, client trust 증거 v4, exact private IPv4 `/32` client와
  signed ownership plan, firewall profile/default-deny 충돌 검사를 고정했다. migration은
  모든 child process의 deadline/output cap과 maintenance journal을 사용한다.
- upload 삭제는 outer transaction COMMIT/ack 불확실성을 fresh advisory lock으로
  재조정하고, active Meta 업무 row가 남아 있는 tombstone purge를 거부한다. 최초
  cutover는 기존 process의 executable/command line/working directory digest와 health
  smoke를 rollback 사양에 고정한다.
- backup receipt private key는 DB/file reader인 BACKUP_ONLY와 분리된 SIGNER_ONLY가
  보유한다. 별도 publisher는 실제 manifest/HMAC/dump/storage inventory와 exact
  schedule authorization을 재검증한 뒤만 v6 receipt를 게시하며 일반 attestation
  signer는 `backup-latest`를 거부한다.
- backup·restore·quiesce 공개키를 attestation type별로 분리했고 cross-key를 거부한다.
  production rollback은 별도 즉시 승인과 maintenance/drain/quiesce를 요구하는
  `Manage-SupabaseRollbackRestore.ps1` Plan/Apply/VerifyEvidence 계약으로만 수행하며,
  signed pre-change backup, exact Supabase target, KPI와 storage hash를 묶은 뒤에도
  legacy restart는 별도 승인으로 남긴다.
- backup receipt는 관리자가 만든 exact request와 단기 signer authorization을
  SIGNER_STATE replay ledger에서 한 번만 소비한다. one-time signer authorization
  v3와 schedule authorization v4는 pgpass, `pg_restore`, integrity/signing key,
  publisher/signer와 실행 파일 hash를 모두 묶고 NAS identity helper hash까지
  묶으며 알 수 없는 필드·다른 key·재사용
  authorization은 거부한다. backup target/schedule evidence는 v7, target
  fingerprint는 v8이고 helper drift 시 readiness가 닫힌다.
- signer account의 publisher는 hash-pinned `pg_restore --list`로 dump TOC를 직접
  검사해 application schema 밖 항목과 unsafe entry를 거부하고, fresh TOC digest,
  entry count와 tool hash를 signed latest receipt에 포함한다. backup ID의 시작 시각,
  완료 시각, elapsed와 현재 시각도 상호 결속해 미래 receipt가 latest를 고정하지
  못하게 한다.
- rollback은 원래 production schema를 preserved schema로 원자 rename한 뒤 빈 원래
  schema에 복원하며, INTENT/FAILED journal과 전체 4시간 deadline 안에서 KPI·storage
  hash를 확인한다. 실패하면 preserved schema를 되돌리는 절차까지 같은 계약에
  포함하고 기존 process 재시작은 여전히 별도 즉시 승인이다.
- recovery는 escrow kit뿐 아니라 source-path-free worksheet도 별도 매체에 hash-verified
  복사하고, stdout/stderr 동시 bounded drain·timeout·tree kill 뒤 v6 증거 하나만
  pending→atomic publish한다. release 검증은 dependency main/module/exports/bin/native
  entrypoint와 source-free cold-start/CLI smoke까지 확인한다.
- Windows local Storage는 root/parent/file을 reparse-point 거부 및 delete-share 없는
  native NTFS handle로 열고, 같은 handle의 final path/link count를 확인한 뒤 read/write/
  rename/delete한다. 경합 중 junction·hard-link 교체 테스트를 실제 Windows에서
  반복해 root 밖 byte read/write/delete가 없음을 확인했다.
- NAS backup target은 설치 PC의 hostname/IP/interface뿐 아니라 CNAME alias와 안정적인
  remote identity까지 비교해 local volume 별칭을 거부한다. recovery deadline은
  고집스럽게 살아남는 descendant까지 process tree 종료 후 exit을 재확인하며,
  release closure는 기본 `index.js` entrypoint 누락도 거부한다.
- report export의 final DB COMMIT/ACK가 불명확하면 fresh read와 DB에 이미 commit된
  byte hash/size로만 `CREATED`를 확정한다. 재시작 전부터 남은 `CREATING`은 발견된
  payload 자체를 성공으로 승격하지 않고 조건부 `FAILED`로 정리하며, exact byte
  재확인 뒤에만 삭제한다. DB 결과 또는 byte가 불명확하면 payload를 보존하고
  backup/restore의 공통 transition query가 `CREATING` snapshot을 차단한다. 이
  reconciliation은 시작 시 한 번으로 끝나지 않고 1분마다 5분 이상 stale row를
  30초 제한 안에서 재시도하며, 불확실성이 남아 있으면 readiness를 계속 닫는다.
- 기존 단계 8 Docker/compose staging 및 Supabase Auth/Storage adapter는 역사적
  보류 코드로 유지했다. local 배포 README가 이를 설치하지 않도록 명시하고,
  API `local_lan` config는 환경과 무관하게 `AUTH_PROVIDER=local`만 허용하고 cloud
  Auth/Storage 환경값을 거부한다. 과거 Supabase Auth bootstrap npm 명령과 release
  실행물은 제거했으며 clean API build가 stale `dist`까지 삭제한다.
- bootstrap authorization request v2는 username을 argv/stdout에 싣지 않은 채
  SIGNER_ONLY private key hash, SHARED_RUNTIME public key hash와 Ed25519 signing key
  ID를 exact request에 묶는다. producer/consumer 모두 filesystem class, reparse,
  hard-link, cross-key, hash drift를 거부하고 authorization은 DB mutation 직전의
  fresh clock으로 TTL을 다시 확인한 뒤 create-new ledger로 한 번만 소비한다.
  recover authorization은 unsigned/signed-v1 drain을 거부하고 signed Edge drain v2의
  public key, release manifest, runtime config, Node executable identity까지 고정한다.
- Windows NTFS helper process tree는 hash-pinned .NET Framework Job Object guard의
  `KILL_ON_JOB_CLOSE`에 붙이고 retained child handle로만 종료한다. PID snapshot,
  `taskkill`, mutable/reused PID lookup은 사용하지 않으며 stream `close`는 helper
  종료와 NTFS handle 해제가 끝난 뒤에만 완료된다. local native release에는
  Supabase Auth CLI가 포함될 수 없다.

  handle의 동일 bytes를 hash한 뒤 strict UTF-8 in-memory ScriptBlock으로 실행한다.

  거부된다.
- release manifest v4는 exact Windows host bundle(39 PS1 + 2 service XML)과 staged
  cold-start contract digest를 묶는다. 실제 source-free Windows 합성 릴리스에서
  API fail-closed, 7상태 역할 행렬, Prisma CLI, Web loopback 기동과 explicit
  runtime allowlist/full-tree 재해시를 통과한다. 공통 production config preloader가
  CLI별 오류보다 먼저 거부하는 실제 시작 순서도 cold-start 계약이 인정하되,
  누락 config에서 0 exit 또는 다른 오류는 허용하지 않는다.

  `USAGE/SELECT`만 runtime role에 부여하고, schema CREATE·TRUNCATE·trigger 및

  경로로 Meta/Cafe24/Coupang import·mapping/rematch/delete, decision, manual purchase,
  report export/download, upload delete와 tombstone byte-hash restore까지 하나의 외부
  transaction에서 실행하고 rollback한다. target migration 뒤 신규 객체에도 같은
  권한을 다시 적용하며 local release target의 mutation contract digest는 previous와
  같아야 한다. business contract v2는 전체 Meta product/adset, Cafe24 product
  performance, Coupang dashboard/profit/ads/daily-report 값을 결정적으로 canonicalize해
  count-only 회귀를 허용하지 않는다. production DB와 운영 Storage는 변경하지 않는다.
- mapping 수동 legacy-adset 채택과 rematch는 같은 advisory fence 순서를 사용하고
  fence 뒤 identity를 다시 읽어 row/advisory lock 역순 deadlock과 stale 채택을 막는다.
- Edge는 maintenance 중 active request 0이 된 동일 process에서 one-shot Ed25519
  drain v2를 발행한다. migration/certificate/release switch의 Plan·action·journal은
  exact service tree PID/start time, Node/command/release/runtime, 443 listener owner에
  묶이며 switch 후 direct private address + SNI + pinned CA/server certificate + release
  응답을 bounded HTTPS로 확인한다. 실패 시 이전 release도 같은 HTTPS probe로
  확인하면서 자동 rollback한다.
- 최초 legacy cutover migration/rollback은 존재하지 않는 Edge drain을 요구하지 않는다.
  `LEGACY_BASELINE`/`LEGACY_QUIESCED_NO_EDGE`는 signed legacy-quiesce v2와 exact
  3100/4100 process/listener 부재, 443 listener 부재, Edge absent 또는
  stopped Manual/Disabled 상태를 요구한다. 이후 local release는
  `LOCAL_RELEASE`/`ACTIVE_LOCAL_EDGE`와 signed Edge drain v2를 요구한다.
- rollback restore는 migration `INTENT`, `FAILED_MAINTENANCE_REQUIRED`,
  `APPLIED_PENDING_BOUNDARY`, `APPLIED` 중 exact target/backup/quiescence/maintenance에
  결박된 journal만 승인 가능한 입력으로 인정한다. host/process power loss 뒤에는
  기존 rollback journal hash를 새 `Recover` 승인에 묶고 durable `RECOVERY_INTENT`를
  쓴 다음 부분 current schema만 제거하고 exact preserved original을 되돌린다.
  `VerifyRecovery`가 `current=present/preserved=absent`를 별도 승인으로 증명할 때까지
  maintenance와 writer quiescence를 유지하며 rollback 재시도도 새 Apply 승인이 필요하다.
- `LOCAL_RELEASE` rollback은 previous release manifest와 exact
  `appliedMigrationDigest`, migration journal, 현재 backup/restore chain, signed Edge drain
  v2에 결박되고 live local Storage inventory가 backup `storage-payload`와 byte hash까지
  같을 때만 진행한다. 공통 signed receipt type은 `database-rollback`이며 legacy 전용
  명칭으로 local release 복구를 오표시하지 않는다.
- rollback schema finalizer는 exact maintenance JSON의 release/approval digest와 현재
  signed drain 또는 legacy quiesce를 Plan·action·DDL 직전에 재검증한다. Node,
  verifier, `psql`, migration pgpass, DB CA, public key, runtime/release, NTFS ACL class를
  모두 승인 계획에 묶고 destructive transaction 전에 durable v4 `INTENT`를 쓴다.
  양쪽 schema의 catalog owner/ACL/object/column/constraint/index/function/trigger/type/
  default ACL, 완료 Prisma migration chain과 모든 app relation의 모든 column/row(Auth,
  session, Storage reference/tombstone, 업무 데이터 포함)를 deterministic live fingerprint로
  계산해 plan, journal, DDL 전후, crash reconcile, Verify에 결박한다. advisory transaction
  lock과 양쪽 schema 전체 app table `ACCESS EXCLUSIVE`, drop/rename, post-state full-row
  fingerprint를 하나의 transaction에서 수행해 fingerprint 이후 write 경합을 차단한다.
  commit 직후 crash는 hash-pinned 기존 journal과 새 one-time approval로 live `1|0`을
  재실행 없이 COMPLETE로 조정하고, `1|1`만 exact retry하며, 그 밖의 상태는
  `FAILED_MAINTENANCE_REQUIRED`로 유지한다. maintenance 해제와 writer 재시작은 여전히
  별도 즉시 승인이다.
- 일일 backup 복구는 `DAILY_BACKUP_RECOVERY`/`STOPPED_LOCAL_EDGE` 전용 경계로
  분리했다. exact Core·Edge 서비스가 모두 `Stopped`/`Disabled`이고, filesystem
  evidence의 service SID와 일치하며, 두 SID의 권리가 service-logon + 네 deny
  right로 정확하고, 해당 SID process와 443/3200/4200 listener가 모두 없을 때만
  진행한다. 이 proof를 Storage copy·DDL·directory switch·실패 복구·finalization
  직전에 다시 만든다. 정상 Apply/Verify/Finalize 상태에서는 live Storage가 exact
  `CORE_MODIFY`, 별도 `RecoveryWorkspaceRoot`와 staged/preserved Storage가 exact
  `ADMIN_ONLY`다. hash-pinned Recover의 crash 중단 복구에 한해 stopped-service 경계와
  journal/helper/workspace/topology/original-digest 결박을 먼저 검증하고, 모든 객체가
  이미 두 exact ACL descriptor 중 하나일 때만 `ADMIN_ONLY`로 정규화한 뒤 DB·Storage
  복구를 수행한다. 최종 live Storage는 exact `CORE_MODIFY`로 되돌리며 임의 ACL
  drift는 허용하지 않는다.
- 보고서 호환 계약은 row count뿐 아니라 실제 생성 XLSX를 다시 읽은 canonical
  content digest까지 v4 계약에 묶었다. 실행별 UUID와 timestamp는 참조 그래프의
  동형성을 보존하는 exact canonical form으로 정규화하고, 비동형 관계·끊어진 참조·
  업무 cell 변조는 digest 차이로 검출한다. Change Logs 필수 열은 실제 Prisma·보고서
  schema와 같은 `targetType`에 결박했다. 순열×cell 작업량이 1,000,000을 넘으면 계산
  전에 fail-closed한다. singleton UUID class는 반복 처리하고 실제 분기가 있는 bounded
  ambiguous class만 재귀해 허용된 6,000행 입력도 stack-safe하다. Coupang unmatched
  source의 전역 우선순위와 Cafe24/Meta/Coupang 조회의 동일시각 tie-breaker도 고정해
  source starvation과 비결정적 결과를 제거했다.
- source-free release 조립기를 `deploy/local/assemble-local-release.mjs`로 추적하고
  API/Web 양쪽의 완전한 설치 dependency tree를 복사한 뒤 공식 packager/verifier만
  manifest v4를 발행하도록 했다. 임시 루트 조립기에 의존하지 않는다.
- release manifest consumer는 모두 v4와 staged release verifier를 요구한다.
  packager는 검증 script가 trusted source와 동일한지 확인하고, 검증 전후 inventory와
  전체 hash가 하나라도 바뀌면 manifest를 쓰지 않는다. CommonJS implicit `index.js`
  closure도 명시적인 data-only/tooling 예외 외에는 누락을 거부한다.
- mutation 요청은 bounded pre-auth IP abuse/CSRF gate 뒤 authenticated user+IP 업무
  quota를 별도로 적용하므로 공유 LAN IP의 익명 실패 요청이 정상 사용자의 업무
  quota를 고갈시키지 못한다.
- backup receipt publisher는 `latest` 변경 전에 authorization/candidate hash를
  flush된 `RESERVED` ledger로 남기고 게시 뒤 `COMMITTED`로 전환한다. 중간 crash는
  같은 후보만 idempotent replay하며 더 오래된 후보는 `SUPERSEDED`로 소비되어
  최신 receipt를 rollback하지 못한다.
- 계획 재부팅은 별도 승인된 `PrepareReboot`가 Core Automatic/running, Edge
  Manual/stopped 상태를 만들고, current-boot v3 pre-edge 증거와 별도 승인된
  `ResumeEdge` 뒤에만 443을 연다. 이전 boot·drift·증거 부재는
  `operationalReady=false`이고 예상 밖 재부팅도 443 closed다. 일반 Windows mutation
  approval TTL은 문서와 동일하게 최대 10분이다.

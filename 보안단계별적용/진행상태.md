### 2단계 구현·계약

- Supabase Auth를 서버측 `IdentityProvider` adapter 뒤에 연결하고 요청별 stateless client(`persistSession=false`, `autoRefreshToken=false`)를 사용한다. JWT는 JWKS로 signature, ES256 algorithm, issuer, audience, expiry, UUID `sub`, UUID `session_id`를 검증하며 Supabase의 PostgreSQL role claim은 앱 role로 사용하지 않는다.
- `AppRole`(`SUPER_ADMIN`, `ADMIN`, `USER`, `GUEST`), `InviteStatus`, `AppUser` 인증 연결 필드와 raw token을 저장하지 않는 `AppAuthSession`을 추가했다. 중앙 상태 판정은 매 요청 현재 `AppUser`와 session 폐기 상태를 다시 읽는다.
- access/refresh/session-handle은 서로 다른 HttpOnly root-path cookie이고 CSRF cookie만 JavaScript에서 읽을 수 있다. production `Secure=true` 강제, `SameSite=Lax`, Domain 미지정, HMAC session handle, exact Origin·fetch metadata·double-submit CSRF, bounded rate limiter 계약과 PostgreSQL advisory lock 기반 분산 refresh 직렬화를 구현했다.
- 역할→권한 단일 매핑과 opaque `authorizationVersion` 응답 계약을 고정했다. `SUPER_ADMIN`은 10개 권한, `ADMIN` 7개, `USER` 3개, `GUEST` 1개다.
- 안정된 오류 코드를 구현했다: `AUTHENTICATION_REQUIRED`, `SESSION_INVALID`, `ACCESS_TOKEN_EXPIRED`, `SESSION_REVOKED`, `INVALID_CREDENTIALS`, `ACCOUNT_NOT_PROVISIONED`, `ACCOUNT_INACTIVE`, `ACCOUNT_ONBOARDING_REQUIRED`, `AUTH_PROVIDER_UNAVAILABLE`, `REFRESH_RACE_RETRY`. Auth 응답·오류는 모두 `private, no-store`다.
- 일회성 `auth:bootstrap-super-admin` CLI는 dry-run, DB host/name/schema와 대상 subject/email의 exact confirmation, 공급자 확인, 중복 subject/email fail-closed를 지원하며 앱 startup에서 실행되지 않는다.

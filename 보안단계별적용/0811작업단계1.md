# 0811 작업단계 1 — 업무 환경 격리와 기준선 확정

## 1. 이 세션의 단일 목표

업무용 `main` 폴더와 프로세스에 손대지 않고 보안 개발 전용 worktree를 만든다. 개발 Web/API/DB/스토리지/인증 프로젝트를 운영과 분리하고, 보안 변경 전 전체 테스트·lint·build 기준선을 기록한다.

이 단계는 애플리케이션 보안 기능을 구현하는 단계가 아니다. 환경이 실제로 분리되었다는 증거를 남기는 것이 완료 조건이다.

## 3. 하위 에이전트 역할

최소 두 명을 사용한다.

1. **환경 개발 담당**: 저장소 구조, worktree, Node 의존성, 개발 포트와 안전한 env 예제를 준비한다.
2. **독립 격리 평가 담당**: 원본 Git/프로세스가 보존되는지, DB/schema/storage가 운영과 다른지, 테스트 명령이 운영 자원에 쓰지 않는지 검증한다.

평가 담당은 worktree 생성 전 체크리스트를 만들고, 생성 후 실제 경로·branch·환경 키와 명령 결과를 읽기 전용으로 검증한다. 하위 에이전트는 commit하지 않는다.

원본 폴더에서 읽기 전용으로 다음을 확인한다.

git -C "C:\Users\seong\Desktop\workspace\Meta-Ads-Performance" log -5 --oneline --decorate

다음 상황이면 자동 조치하지 말고 중단·보고한다.

- sibling 목표 폴더가 다른 파일을 담고 있음
- 같은 branch가 다른 worktree에서 이미 checkout됨
- 원본에 계획 폴더 외의 미커밋 변경이 있고 그 의미가 불명확함
- 업무용 HEAD가 실행 중인 코드와 일치하는지 확인할 수 없음
- worktree 생성이 권한 승인 없이 불가능함

## 5. worktree 생성

목표 경로:

```text
C:\Users\seong\Desktop\workspace\Meta-Ads-Performance-security-rbac
```

branch와 폴더가 모두 없을 때만 다음 형태로 생성한다.

```powershell
git -C "C:\Users\seong\Desktop\workspace\Meta-Ads-Performance" worktree add `
  -b codex/security-rbac `
  "C:\Users\seong\Desktop\workspace\Meta-Ads-Performance-security-rbac" `
  main
```

branch만 이미 존재하면 `-b`를 다시 사용하지 말고 먼저 해당 branch의 commit과 사용 worktree를 확인한다. 폴더가 존재하면 절대 삭제하지 않는다.

생성 뒤 확인:

```powershell
git -C "C:\Users\seong\Desktop\workspace\Meta-Ads-Performance" worktree list --porcelain
git -C "C:\Users\seong\Desktop\workspace\Meta-Ads-Performance-security-rbac" status --short --branch
git -C "C:\Users\seong\Desktop\workspace\Meta-Ads-Performance-security-rbac" branch --show-current
```

원본 `main`의 branch와 파일이 바뀌지 않았음을 다시 검사한다.

## 6. 계획 파일과 진행상태 인수인계

원본의 `보안단계별적용` 폴더를 새 worktree로 **복사**한다. 이동하지 않는다. 복사 시 파일 목록과 SHA-256 bundle hash를 진행상태에 기록한다. 이 시점부터 worktree 안의 계획서가 단일 실행 원본이며, 2단계 이후 세션은 worktree 복사본만 읽는다. 새 worktree 안에 다음 파일을 새로 만든다.

```text
보안단계별적용/진행상태.md
```

진행상태 문서 초기 항목:

- 원본/개발 절대경로
- 원본 branch와 시작 commit
- 개발 branch와 시작 commit
- 생성 시각과 담당 세션
- 업무용/개발용 포트
- 운영/개발 DB가 다르다는 검증 결과(비밀값 제외)
- 운영/개발 schema 이름
- 개발/테스트/shadow DB 또는 schema 구분
- 업로드/보고서 저장 경로 구분
- 기준선 명령과 결과
- 각 단계 commit과 평가 결과를 추가할 표

DB URL, 비밀번호, token, API key는 기록하지 않는다.

## 7. 개발 환경 분리

### 7.1 포트

| 환경 | Web | API |
|---|---:|---:|
| 업무용 원본 | 3100 | 4100 |
| 보안 개발 | 3200 | 4200 |

Web은 기존 코드의 hard-coded `next dev -p 3100`을 이 단계에서 바꾸지 말고 개발 터미널에서 명시적으로 실행한다.

```powershell
Set-Location "C:\Users\seong\Desktop\workspace\Meta-Ads-Performance-security-rbac\apps\web"
npx.cmd next dev -p 3200
```

API는 보안 worktree 전용 `.env`의 `PORT=4200`을 사용한다.

### 7.2 Web env

운영 `.env`를 복사하지 않고 `.env.example`을 기준으로 `apps/web/.env.local`을 새로 만든다.

```env
NEXT_PUBLIC_API_BASE_URL="/backend-api"
API_PROXY_TARGET="http://127.0.0.1:4200/api"
```

이 파일은 commit하지 않는다.

### 7.3 API env와 DB

운영 DATABASE_URL을 복사하지 않는다. 완료 기준은 **별도 Supabase 개발 프로젝트 또는 최소 별도 물리 database/cluster와 별도 개발 DB 사용자**다. 같은 운영 PostgreSQL 인스턴스의 별도 schema는 CPU, connection, I/O, migration 실수로 운영을 방해할 수 있으므로 기본 대안으로 인정하지 않는다.

동일 인스턴스·별도 schema는 사용자가 위험을 이해하고 명시적으로 승인한 예외일 때만 허용한다. 이 예외에서는 대용량 import, 부하/ZIP bomb test, migration rehearsal을 금지하고 connection/resource quota와 운영 schema 무권한을 증명한다. 실제 운영 schema 이름을 `meta_ads`로 가정하지 말고 DB host/project/database/schema fingerprint를 직접 비교한다.

테스트는 `meta_ads_security_test`, Prisma shadow DB/schema도 별도로 둔다. 개발 계정은 앞에서 실제 fingerprint로 확인한 **모든 운영 schema**에 `USAGE/CREATE/INSERT/UPDATE/DELETE/TRUNCATE` 권한이 없어야 한다. 운영 schema 이름을 계획서의 예시 문자열로 고정하지 않는다.

개발 `.env`에는 최소 다음 종류의 값만 넣고 commit하지 않는다.

```env
APP_ENV="development"
DATABASE_URL="<DEVELOPMENT-ONLY>"
SHADOW_DATABASE_URL="<DEVELOPMENT-ONLY>"
PORT=4200
UPLOAD_STORAGE_DIR="./storage/security-dev/uploads"
REPORT_STORAGE_DIR="./storage/security-dev/reports"
APP_ALLOWED_ORIGINS="http://127.0.0.1:3200,http://localhost:3200"
```

Supabase Auth 관련 실제 값은 2단계 직전 개발 프로젝트에서 발급한다. 이 단계에서는 변수 이름만 문서화할 수 있다.

### 7.4 DB 격리 증거

마이그레이션이나 seed 전에 비밀값을 출력하지 않는 방식으로 다음을 확인한다.

- DB host 또는 project가 운영과 다른지
- `current_database()`
- `current_user`
- `current_schema()`와 `search_path`
- 개발 계정이 운영 schema에 CREATE/UPDATE/DELETE 권한이 없는지

운영과 같은 물리 DB/cluster/schema/user이거나 구분을 증명하지 못하면 DB 명령을 실행하지 않고 blocked로 보고한다. 사용자 승인 예외가 없는 동일 인스턴스 schema는 완료 조건을 충족하지 못한다.

대표 데이터가 필요하면 운영 DB에 직접 테스트하지 않는다. 사용자가 승인한 읽기 전용 스냅샷을 개인정보·주문정보·토큰 없이 익명화해 개발 DB에 복원한다.

## 8. 의존성과 기준선

새 worktree에는 ignored `node_modules`가 없으므로 다음을 실행한다.

```powershell
Set-Location "C:\Users\seong\Desktop\workspace\Meta-Ads-Performance-security-rbac"
npm.cmd ci
npm.cmd run prisma:validate
npm.cmd run lint
npm.cmd run test
npm.cmd run build
git diff --check
```

의존성 설치에 네트워크/승인이 필요하면 정식 승인을 요청한다. `package-lock.json`을 이 단계에서 임의 갱신하지 않는다.

기준선 실패 시:

1. 실패 명령과 전체 핵심 오류를 진행상태에 기록한다.
2. 보안 변경 전 기존 실패인지 원본에서 동일 명령으로 확인한다. 운영 프로세스를 중지하지 않는다.
3. 이 단계에서 무관한 코드 결함을 고치지 않는다.
4. 다음 단계가 안전하게 진행 가능한지 평가자가 판단하고, 불가능하면 blocked로 보고한다.

## 9. 독립 실행 확인

가능하면 업무용 앱을 그대로 둔 상태에서 개발 앱을 3200/4200으로 실행해 다음을 확인한다.

- 3100과 3200이 서로 다른 worktree 코드를 제공
- 4100과 4200이 서로 다른 env/DB를 사용
- 개발 업로드가 운영 upload 폴더에 생기지 않음
- 개발 앱 종료가 업무 앱에 영향을 주지 않음
- 업무 앱의 주요 대시보드 조회가 계속 정상

포트 프로세스를 강제 종료하지 않는다. 어떤 PID가 어떤 경로에서 실행됐는지 확인한 뒤 보안 개발 프로세스만 종료할 수 있다.

## 11. 평가 체크리스트

- [ ] 원본 branch가 계속 `main`이다.
- [ ] 원본 HEAD와 업무 파일이 바뀌지 않았다.
- [ ] 보안 branch는 `codex/security-rbac`이다.
- [ ] 모든 수정 명령이 보안 worktree에서 실행됐다.
- [ ] 개발 DB 사용자/schema/storage가 운영과 다르다.
- [ ] 원본 `.env`가 복사·출력·commit되지 않았다.
- [ ] 3200/4200과 3100/4100이 충돌하지 않는다.
- [ ] `npm ci`, prisma validate, lint, test, build의 기준선이 기록됐다.
- [ ] 계획 파일과 진행상태가 보안 branch에 있다.
- [ ] 계획 bundle hash와 이후 worktree 문서가 단일 실행 원본이라는 규칙이 기록됐다.
- [ ] 원본 업무 앱의 주요 화면이 계속 동작한다.

## 12. 완료 조건과 commit

위 체크리스트를 모두 증명해야 완료다. 먼저 구현/환경 문서 commit을 만든다. commit 메시지 예:

```text
chore(security-step1): isolate security worktree baseline
docs(security-step1): record verified environment handoff
```

그 구현 commit SHA와 테스트 결과를 진행상태에 기록한 뒤 별도 handoff 문서 commit을 만든다. handoff commit 자신의 SHA는 같은 문서에 기록하지 않고 2단계가 시작 HEAD로 기록한다. 최종 worktree는 clean이어야 한다. DB/Auth 준비가 부족하면 완료로 표시하지 말고 정확한 외부 준비 항목을 blocked 사유로 남긴다.

2단계 착수 전에는 Supabase Auth를 신원 공급자로 사용하는 것 자체와 개발 Auth 프로젝트 생성에 대한 사용자 승인을 진행상태에 기록한다. 또한 사용자가 직접 지정한 핵심 권한 외의 upload/import, mapping/rematch, decision/manual-purchase, 새 server report 생성 권한을 마스터 표의 제안대로 ADMIN/USER에 배정할지 최종 확인한다. 승인 전에는 임의로 더 넓은 권한으로 바꾸지 않는다.

## 3. 외부 선택 승인 게이트

운영 adapter를 만들기 전에 당시 최신 공식 문서로 후보를 비교한다.

필수 조건:

- private bucket/container
- server-side API 또는 S3 호환 API
- object encryption
- signed URL 또는 API stream
- lifecycle/versioning/backup
- 한국 리전과 비용
- staging/prod 완전 분리
- 선택 호스팅 API에서 접근 가능

기존 Supabase 사용만으로 Supabase Storage를 자동 선택하지 않는다. 비교 결과와 예상 비용·운영 부담을 사용자에게 제시하고 승인받는다. 유료 bucket/project 생성이나 실제 외부 upload는 승인 뒤 수행한다.

승인이 늦어져도 LocalStorage abstraction과 테스트는 진행할 수 있지만, production adapter와 단계 완료는 blocked로 남긴다.

## 4. 하위 에이전트 역할

1. **파일 방어 개발 담당**: upload profile, signature/size/row/ZIP 검사, parser 회귀
2. **Storage 개발 담당**: interface, local adapter, 승인된 object adapter, report/download, legacy migration
3. **독립 파일보안 평가 담당**: 과대/위장/경로/ZIP/formula/부분실패/권한 없는 download 공격과 정상 업무 파일 회귀

각 개발 담당이 upload 검증과 storage 파일을 분리 소유한다. 평가자는 악성 fixture를 작고 합법적인 synthetic 파일로 만들며 실제 업무 파일을 변조·commit하지 않는다.

## 5. 정상 파일 기준 측정

제한값을 임의로 낮게 정하지 않는다. 사용자가 승인한 개발용 복사본과 최근 정상 업무 파일에서 **내용이 아닌 metadata**만 측정한다. 원본 업무 폴더를 자동 탐색·복사하거나 정상 파일 자체를 저장소/fixture/object bucket에 올리지 않는다.

- 파일 유형별 크기 min/median/p95/max
- CSV row/column 수
- XLSX worksheet, row, column 수
- Coupang bundle 파일 수와 총량
- import 처리 시간과 peak memory 가능 범위

측정 결과에서 안전 여유를 둔 기본 제한을 설정하고 env로 더 낮출 수 있게 한다. 무제한 또는 수백 MB의 과도한 기본값을 두지 않는다.

## 6. 공통 upload profile

현재 Meta, Cafe24, Coupang 모듈의 중복 `MulterModule.register({})` 또는 기본 FileInterceptor 설정을 공통 factory/profile로 합친다.

프로파일 예:

| profile | 허용 업무 형식 |
|---|---|
| Meta | `.csv` |
| Cafe24 | `.csv` |
| Coupang sales/ads/promotion | `.xlsx` |
| Coupang margin | `.csv`, 필요 시 `.tsv` |
| Coupang price text | `.txt`, `.csv`, `.tsv` |
| Coupang bundle | 지정 field 각 최대 1개, 전체 총량 제한 |

검사 계층:

1. multipart field 이름과 개수
2. 파일별/요청 총 size limit — 초과 시 413
3. 원본 filename에서 경로 제거와 길이 제한
4. extension allowlist
5. MIME allowlist — 브라우저 값만 신뢰하지 않음
6. magic signature/실제 content 검사
7. 빈 파일 거부
8. parser 전 row/column/ZIP 안전 한도
9. 기존 header/domain validation

`file.buffer` 전체 메모리 방식은 명확한 낮은 size limit 안에서만 유지한다. 정상 파일이 커서 limit을 높여야 한다면 streaming/temp file 방식과 worker/background import를 별도 평가한다. 임시 파일은 전용 디렉터리, 제한, cleanup을 갖는다.

## 7. XLSX/CSV 특별 방어

### XLSX

XLSX는 ZIP 컨테이너이므로 확장자와 `PK` 두 바이트만 확인해서는 부족하다.

- central directory/필수 XLSX entry 확인
- entry 수 제한
- 압축 해제 총량 제한
- 압축비 제한
- worksheet/row/column/cell string 길이 제한
- external link/macro가 필요한지 검토하고 불필요하면 거부
- parser 오류를 내부 stack 없이 400/415로 변환

검증 라이브러리는 검증된 유지보수 패키지를 사용하고 직접 ZIP parser를 새로 만들지 않는다.

### CSV/text

- 허용 encoding과 기존 `common/encoding.ts` 재사용
- NUL/control character 정책
- row/column/field 길이와 총 row 제한
- delimiter/quote 파싱 오류
- 파일 전체를 오류 응답에 되돌리지 않음

### export formula injection

서버/클라이언트가 사용자가 입력한 문자열을 CSV/XLSX 셀로 내보낼 때 `=`, `+`, `-`, `@` 시작 값을 수식으로 실행하지 않게 escape/safe-cell 함수를 중앙화한다. 숫자/정상 계산식을 무조건 문자열로 바꿔 기존 report 수치를 깨뜨리지 않도록 외부 문자열에만 적용한다. 기존 HTML report의 `escapeHtml`은 유지한다.

## 8. Storage abstraction

권장 interface 개념:

```ts
interface FileStorage {
  put(input): Promise<{ key: string; hash: string; size: number }>;
  getStream(key): Promise<Readable>;
  delete(key): Promise<void>;
  exists?(key): Promise<boolean>;
  createDownload?(key, options): Promise<stream-or-short-lived-url>;
}
```

구체 signature는 현재 service 흐름과 테스트 가능성을 기준으로 조정한다.

운영 `get` 계약은 stream을 기본으로 고정한다. Buffer 편의 함수가 필요하면 작은 상한이 강제된 local/test 전용 helper로 분리하고 production의 대용량 object를 무제한 메모리에 올리지 못하게 한다.

구현:

- `LocalFileStorage`: 개발/테스트
- 승인된 private object storage adapter: staging/production
- provider 선택은 Config로 주입
- 저장이 승인된 upload 원본과 report가 같은 interface 사용
- object key는 사용자 filename을 경로로 사용하지 않고 server-generated prefix/UUID/hash 사용
- 원본 filename은 display metadata로만 안전하게 보관

기존 `UploadStorageService`의 다음을 재사용한다.

- filename 정규화
- 월별 key/path 개념
- 삭제 전 storage root containment
- SHA-256 기반 식별

중복된 provider SDK 호출을 각 import service에 넣지 않는다.

### 8.1 데이터 최소화와 보존

보안 강화가 기존보다 더 많은 민감 원본을 영구 저장하는 결과가 되어서는 안 된다.

- 현재 이미 원본 보존 계약이 있는 Meta upload만 private storage 대상으로 유지한다. 실제 현재 동작을 먼저 확인하고 임의 확대하지 않는다.
- Cafe24와 Coupang은 파싱/검증 후 필요한 정규화 DB 결과만 유지하고 **원본 파일은 기본적으로 저장하지 않는다**. 임시 파일을 썼다면 성공/실패 모두 제한 시간 내 cleanup한다.
- Cafe24/Coupang 원본 보존이 감사상 꼭 필요하면 개인정보 범위, 암호화, access 권한, 짧은 retention, 삭제/복원 책임과 비용을 별도로 사용자 승인받은 뒤에만 추가한다.
- 생성 report는 기존 업무 기능상 필요한 기간만 보존하며 upload 원본과 다른 lifecycle prefix/policy를 둘 수 있다.
- bucket/object metadata에도 주문자명·연락처·주소·원문 행을 복제하지 않는다.

## 9. report 저장·다운로드

현재 `ReportsService.download`는 DB `filePath`를 `path.resolve`하지만 report storage root containment를 다시 검사하지 않는다.

- Local adapter에서도 key가 report root 밖으로 벗어나면 거부
- Object adapter에서는 private object만 사용
- `GET /reports/:id/download`는 `data.read` Guard 뒤에서만 제공
- 선택안 1: API가 stream하며 Content-Disposition/Content-Type/nosniff 설정
- 선택안 2: 권한 확인 뒤 매우 짧은 signed URL 발급
- signed URL을 DB, audit metadata, 일반 로그에 저장하지 않음
- 추측 가능한 object key여도 bucket 자체는 public 금지
- filename header injection 방지

Web의 download가 같은 출처 cookie를 포함하는지 테스트한다. 단순 public URL로 바꾸지 않는다.

## 10. DB와 파일의 부분 실패

파일과 DB는 원자 transaction이 아니므로 상태 전이를 명시한다.

- upload DB row 생성 전/후 storage put 실패
- import 성공 후 원본 저장 실패
- DB delete 성공/스토리지 delete 실패
- report DB row CREATING 후 render/store 실패
- object store timeout/retry/idempotency

권장 원칙:

- 각 도메인의 기존 상태를 먼저 조사하고 Meta upload, Cafe24 import, Coupang bundle, report마다 허용 전이표를 따로 만든다. 하나의 `PENDING/STORING/CREATED/FAILED` 문자열을 의미가 다른 모든 모델에 무리하게 공용 적용하지 않는다.
- 같은 key에 idempotent put
- 실패 파일/DB row 정리용 안전한 retry job 또는 관리 명령
- delete는 key containment와 record ownership 확인 뒤 수행
- 실패를 성공으로 응답하지 않음
- storage delete 실패 때문에 DB reference를 잃지 않도록 정책 명시
- orphan 정리 도구는 dry-run 기본, 범위 제한, production 승인 필요

## 11. legacy 로컬 파일 호환과 이관

기존 DB의 `filePath`/stored path를 무조건 새 object key로 해석하지 않는다.

전략:

1. provider/key를 구분할 metadata가 필요한지 조사
2. 필요하면 nullable `storageProvider`를 additive migration으로 추가
3. 기존 NULL/LOCAL row는 Local fallback으로 읽기
4. migration tool은 dry-run에서 파일 존재, size, SHA-256, target key를 출력하되 내용/secret 미출력
5. object upload 뒤 hash 대조
6. DB reference update
7. 전체 검증과 backup 완료 전 local 원본 삭제 금지
8. staging에서 실제 이관 rehearsal

운영 local 파일이 사용자 PC에만 있고 host에서 접근할 수 없다면 자동 가정하지 말고 전송 절차와 downtime 영향을 8/9단계에 기록한다.

## 12. 객체 저장소 보안

- bucket public access 차단
- staging/prod bucket 또는 credential와 prefix 완전 분리
- API secret만 write/delete 가능
- 최소권한 credential
- server-side encryption
- TLS
- lifecycle/versioning/retention 정책
- CORS는 필요한 origin/method만
- 객체 metadata에 token, DB URL, 주문 개인정보를 과도하게 넣지 않음
- provider access log/비용 alert
- signed URL 짧은 만료
- 선택 provider의 versioning/backup만 켜고 끝내지 않고 staging object를 put → backup/version 확인 → 삭제/손상 → 실제 복원 → hash 비교하는 복구 시험 수행
- 업로드 악성코드 검사가 조직/호스팅 정책상 필요한지 위협모델로 결정한다. 도입하면 quarantine→scan→release 상태와 scanner 장애 정책을 명시하고, 미도입이면 허용 문서형식과 sandbox parser/다운로드 정책으로 위험을 수용한 근거를 기록한다.

## 14. 평가자가 집중할 결함

- extension/MIME만 검사
- Multer memory upload에 size limit 없음
- bundle 각 파일만 제한하고 총량 없음
- ZIP `PK`만 확인하고 압축 해제 제한 없음
- object bucket public
- signed URL이 로그/DB에 남음
- report path traversal
- storage 실패 후 DB가 CREATED
- delete 부분 실패로 reference 상실
- legacy 파일을 검증 전 삭제
- 각 service가 provider SDK를 중복 호출

- versioning 설정만 확인하고 실제 object restore를 하지 않음
- 보안 작업을 이유로 Cafe24/Coupang 개인정보 원본을 새로 영구 저장
- formula injection 방어가 정상 숫자/수식을 깨뜨림

## 첫 배포에서 발견·수정한 회귀

로컬 합성 데이터에서 빨랐던 원천별 DISTINCT가 운영 카탈로그 기반 실행계획에서는 쿠팡의 `Parallel Append`/`Gather Merge`를 없애고 순차 원천 스캔을 만들었다. 첫 운영 정규 실행의 쿠팡 날짜 탐색은 14.916초였고, 컨테이너 시작→결과 로그는 95.917초, 18건 검사·16건 변경 없음·2건 발행·실패 0·시간 예산 소진이었다. 2건 발행 자체의 추가 작업도 있어 전체 시간 증가를 SQL 하나의 영향으로 전부 돌리지 않았다.

실제 운영에서 EXPLAIN ANALYZE는 실행하지 않았다. read-only 관리 역할의 `EXPLAIN (FORMAT JSON)` 전후 계획은 원인 보조 근거이며, 실제 worker 역할의 실행시간과는 구분한다.

최종 수정은 **원천별 DISTINCT만 제거**하여 UNION 분기를 단순하게 유지했다. 전체 날짜 중복 제거, native date 타입 유지, 검사 이력 LEFT JOIN은 유지했다. 최종 계획에서 Gather가 다시 나타나는 것을 확인했다. 14개 대사 회귀 + 실제 PostgreSQL 회귀·성능 6개, 총 20개가 통과했다. 전체 기존 테스트를 다시 돌리지는 않았다. 최종 Railway 빌드도 성공했다.

첫 실행의 Cafe24 2026-06-01·06-02 재발행은 이전 실행 대비 fingerprint만 달랐고 계산 버전은 같았다. 이전/새 run의 상품·컴포넌트·금액·수량·통화·귀속 및 native 매출/광고비/이익을 EXCEPT ALL로 양방향 대조하여 **차이 0**을 확인했다. 개인정보·실제 금액은 출력하지 않았다. fingerprint가 달라진 원천의 정확한 변경 요인까지 확정한 것은 아니다.

## 디스크 측정의 범위

기존 보호 자격으로 공식 관리 API `GET /v1/projects/{ref}/analytics/endpoints/metrics`에서 장치별 `node_disk_*` 카운터를 읽었다. 새 secret, 역할, 수집기, Grafana 통합을 만들지 않았다. counter 차분을 관측 시간으로 나누어 IOPS·KiB/s·busy 비율을 계산했다. 장치를 합쳐 중복 계산하지 않았다.

이 수치는 **DB 전체 장치 활동**이며 대사 쿼리만의 I/O가 아니다. 대사 없는 기준 구간에도 읽기가 있었다. 변경 전 정상 cron을 포함한 물리 I/O 기준 구간은 사전에 확보하지 못했고, 첫 배포는 성능 회귀와 추가 발행이 있어 최종 버전의 공정한 대조군으로 취급하지 않는다. 따라서 짧은 구간의 전후 카운터만으로 최종 수정이 실제 디스크 I/O를 줄였다고 단정할 수 없다.

| 장치 | 대사 없는 기준 구간 읽기/쓰기 IOPS | 최종 2회 포함 구간 읽기/쓰기 IOPS | 읽기/쓰기 KiB/s 전→후 | busy 전→후 |
|---|---:|---:|---|---|
| nvme0n1 | 44.207 / 1.852 | 192.881 / 73.817 | 1,276.596 / 19.302 → 4,017.776 / 947.738 | 1.820% → 7.408% |
| nvme1n1 | 2.729 / 1.090 | 10.037 / 2.503 | 186.405 / 129.901 → 406.459 / 180.988 | 0.107% → 0.412% |

기준 구간은 15:02:32~15:04:43, 최종 구간은 15:14:17~15:23:07 KST다. 최종 구간에는 원천 재읽기·실제 재발행 6건·다른 DB 활동과 최소 진단 조회도 포함한다. idle→작업 구간 증가이지 최적화 전후의 악화율/개선율이 아니다. 장치 역할을 추측해 root/data로 이름 붙이지 않았으며 이 busy 비율을 Supabase의 burst I/O budget 소비율과 혼동하지 않았다.

현재 서비스는 최종 SHA에 고정된 SUCCESS 상태다. 필요 시 검증한 원본 deployment `6c349c61-0650-405f-8251-7e81eed8d783`의 이미지를 재배포한다. 성능 회귀가 있었던 첫 후보 이미지를 rollback 대상으로 고르지 않는다. 코드 롤백은 이미 발행한 run을 삭제하거나 publication pointer를 자동 복원하지 않는다. 현재 데이터의 복원은 별도 검토·승인 범위다.

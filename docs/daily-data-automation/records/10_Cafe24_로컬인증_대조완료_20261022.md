## 실제 실행과 대조

사용자가 기존 쇼핑몰 로그인·본인 인증을 완료했다. 요청 범위는 기존 `mall.read_order`만 사용했다. 기존 등록 callback으로 리다이렉트한 뒤 Railway `Not Found`가 표시됐지만, 브라우저의 반환 URL에는 OAuth 코드가 도착했다. 코드는 원문 출력·공개 저장 없이 메모리/표준입력으로만 전달했다.

1. 실제 새 secret + 새 OAuth code → **200**, 같은 Client ID·mall·shop 1·주문 읽기 범위 및 유효 만료 확인. 응답은 다음 요청 전에 DPAPI 보호 저장했다.
2. 정확한 노출 옛 secret + 방금 발급된 refresh token G → **400 `invalid_grant`**.
3. 실제 새 secret + **동일한 refresh token G** → **200**. 교체된 최신 pair를 DPAPI 보호 저장했다.

2→3에서 변경한 인증 요소는 secret이며, 같은 grant가 음성 요청 직후 정상 요청에서 성공했다. 따라서 2의 거절은 이미 만료/무효인 grant 또는 잘못된 code를 사용한 과거 검사와 다르다. **`invalid_grant` 문자열만으로 판정하지 않고, 동일한 유효 grant의 양성 대조를 결속해 옛 secret의 인증 거절을 판정한다.** 전체 3개 토큰 요청은 약 0.61초 안에 완료됐다.

공급자는 전용 `invalid_client` 오류를 반환하지 않았다. `auth-result.json`의 `oldSecretExplicitRejection=false`와 보수적인 `...EXPLICIT_CLIENT_ERROR_PENDING` 표시는 해당 오류 이름 여부를 기록한 것이다. 동일 grant의 후속 200을 반영한 최종 gate 판정은 `closeout.json`의 `PASS_CONTROLLED_VALID_GRANT`이다. 과거 invalid-code 검사에 대한 판정 정정은 철회하지 않는다.

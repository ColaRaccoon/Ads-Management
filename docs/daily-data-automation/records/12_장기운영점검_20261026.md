## 3. 장기 운영에서 우선 처리할 항목

### P1 — Cafe24 검증 유효기간이 지나면 수집이 중단된다

적용 코드 `sync-contract.ts`의 앱 버전·판매자 옵션·전체 품목 검증은 최근30일 증거만 인정한다. `cafe24-orders.client.ts`는 수집 전에 이를 검사한다. 원천 토큰 자동 갱신과 별개의 조건이다.

10/24 운영 기록에 남은 검증일을 기준으로 보면:

| 설정 | 기록된 검증일 | 갱신하지 않을 때 최초 기한 초과일 |
|---|---|---|
| 판매자 드롭다운 | 10/1 | **11/1** |
| 전체 품목 포함 규칙 | 10/14 | **11/14** |
| 앱 API 버전 설정 | 10/24 | **11/24** |

이 날짜값은 이번 Railway OAuth connector에서 값이 숨겨져 있어 최신 런타임 값까지 다시 읽지는 못했다. 위 기한은 마지막 운영 기록 기준이며, 중간 재검증이 없다면 적용된다. 실제 설정·원천 의미를 재확인한 후 증거일과 운영 설정을 갱신해야 한다. 날짜만 임의로 연장하거나 검사를 제거해서는 안 된다. 담당자와 매월 재검증 절차가 필요하다.

### P1 — Meta 재로그인 기한은 일일 수집 기준으로 앞당겨야 한다

운영 DB의 Meta credential_expires_at는 **2026-12-23 10:11:49 KST**다. `meta-credential-resolver.ts`는 잔여 유효기간이7일 이하이면 요청을 거절한다. 현재 자격을 유지하면 차단 기준은 **12/16 10:11:49 KST**, 다음 일일 예약인 **12/17 02:03부터 실패 예상**이다.

이전 운영 문서의 “12/19 주간 실행 전 재로그인”은 일일 수집 추가 후에는 늦다. **12/16까지 재인증·운영 반영·정상 읽기 검증**을 끝내는 일정이 필요하다. 사용자 권한 철회·공급자 차단은 이 날짜 이전에도 별도로 발생할 수 있다. 현재 Cafe24 만료값은11/9 02:00:12 KST지만 자동 refresh 대상이므로 Meta의 수동 재로그인 조건과 같게 취급하지 않는다.

### P2 — 새 상품 미매핑6행이 남아 있다

오늘 Cafe24 395행 중 product_id가 없는 행은6개다. 상품번호181(1행),202(1행),203(2행),204(1행),210(1행). coverage도 CAFE24_PRODUCT_MAPPING_INCOMPLETE를 표시한다. 수집 완료와 매출·마진 전체 반영은 다르며, 현재 매칭된 상품 중심 계산에서 해당 행이 빠질 수 있다. 정확한 상품·구성·원가 관계를 확인해 정상 매핑해야 한다. 이번에는 상품 규칙을 변경하지 않았다.

### P2 — 장애를 발견하고 누락 날짜를 복구할 운영 체계가 필요하다

운영 scheduler에는 시간창·횟수 제한, 단일 HTTP 요청, 계정 lease, checkpoint 재개, 완료 응답 범위 검증이 있다. 그러나 ACTION_REQUIRED/만료된 슬롯은 계속 자동 복구하지 않는다. `scheduled-sync.service.ts`는 `automaticBackfill=false`이며 경고 조회도 일일 최근31회/주간 최근5회로 제한된다. Meta 주간 재조회가 일일 실행 성공 기록을 대신하지 않는다.

현재 자료의 Codex04:05/14회 후속 점검은 로컬 앱·로그인과 한시적 관측에 의존한다. 이것만으로 영구적인 클라우드 장애 알림을 보장할 수 없다. 클라우드에서 실행 누락/실패/기한임박을 알리고 담당자가 명시적 날짜별 복구를 수행하는 운영 절차를 확정해야 한다. 기존 알림 자동화의 현재 실행 상태 자체는 이번에 조회하지 않았다.

### P2 — 운영량 증가·공유 DB·보관 용량을 추적해야 한다

- Cafe24345주문 처리가44분으로110분 시간창 안에 완료됐다. 현재 성공은 확인했지만 주문량 증가 및 주간4개 일정 동시 도래 때의 처리 여유는 추가 관측이 필요하다. 주문량에 정비례한다고 단정할 수는 없다.
- Railway 최근24시간 60초 표본1441개: 메모리 최대0.324251648GB, 평균0.172430075GB, 제한약1GB. CPU 지표 최대0.104703367. 평균에는 절전 표본이 포함되며 개별 짧은 spike를 모두 포착하는 값은 아니다.
- Supabase DB 전체 크기700,755,091바이트(약701MB). 새 수집 attempt 표는64KiB, checkpoint live행0이다. 현재 크기로 누적 장애는 확인되지 않았으나 canonical 버전·run/attempt·cron 이력의 장기 보관·아카이브 정책은 따로 필요하다.
- DB 대시보드는 Healthy/NANO, 당시 CPU5%·RAM67%·연결10/60을 표시했다. 공유 DB의 다른 업무 부하가 존재하므로 현재 수집기 메모리만으로 DB 여유를 보증할 수 없다. 미래 월 청구액·원천quota·사용량 증가율은 미확정이다.
- Postgres 로그에 `3F000: schema "pg_pgrst_no_exposed_schemas" does not exist`가 약32초 간격으로 반복되며 최근1시간 오류 필터112건을 표시했다. 확인한 표본은 이 메시지였다. 수집 성공 기록과는 구분해야 하며, 원인 설정·다른 소비자 영향은 추가 진단 대상이다. 오류를 없애려고 업무 schema를 Data API에 노출하는 변경을 해서는 안 된다.

### P2 — 격리 테스트 자원이 아직 남아 있다

Railway `cafe24-order-read-test` 프로젝트가 현재 존재한다. Postgres 서비스 SUCCESS 및5,000MB 볼륨, callback 서비스 SUCCESS, phase08 서비스 CRASHED가 조회됐다. phase08의 CRASHED는 과거 격리 중지 맥락과 함께 해석해야 하며 운영 수집 장애로 세지 않는다. 현재 테스트 자원이 모두 삭제됐다고 보고할 수 없고, 볼륨 등 향후 비용 가능성도 남아 있다. 의존성 종료·필요 증거 보존·승인된 정리 후 사용량까지 확인해야12단계 완료 조건을 만족한다. 이번에는 삭제하지 않았다.

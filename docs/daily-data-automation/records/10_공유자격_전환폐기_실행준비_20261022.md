## 최신 사용자 확인과 06 콜백의 의미

**외부 소비자 확인은 완료다.** 사용자는 공유 자격을 쓰는 외부 소비자가 없고, 프로그램의 업로드 등 제어는 본인만 하며 나머지 이용자는 읽기 전용이라고 확인했다. 같은 질문을 다시 요청하지 않는다. 다른 이용자의 프로그램 읽기 권한은 변경·회수하지 않는다. 조사된 내부 소비자와 플랫폼 내부 자격의 영향은 기존 준비안에 계속 포함한다.

**06 콜백은 06단계 Cafe24 OAuth 검증을 위해 운영 서비스와 분리한 인증 수신 서버다.** Cafe24에서 사용자가 연결을 승인하면 인증 코드가 callback으로 돌아오고 서버가 이를 token pair로 교환한다. 업로드 파일을 받는 서버나 일반 리포트 화면을 뜻하는 이름이 아니다. 후속08에는 별도 callback URI가 있어 06·08이 같은 서비스인 것도 아니다. 다만 둘은 같은 Cafe24 앱의 Client ID를 참조했으므로 client secret 교체의 내부 영향 대상에는 06을 포함한다.

기존10/21 읽기 영수증은06 연결 disabled·lease0·기존 revision11 pair와477행 보존을 기록했다. 그때 서비스 배포는 중지 상태가 아니었고 feature=false였다. **현재 상태를 새로 재검증했다는 뜻은 아니다.** 기존 도구를 재실행하지 않았다.

이 문서의 **‘06 유지’는 기존 검증 서비스·DB·증거를 그대로 보존하는 기본안**이다. 지금 영구 종료 여부를 결정하거나 실제 서비스 STOP을 할 필요는 없다. 06을 향후 운영의 필수 영구 서비스로 추가하지도 않는다. 실제 운영 callback이 확정된 뒤 06을 더 사용하지 않는다면 별도 정리할 수 있지만 이번에는 삭제·중지하지 않는다.

**‘중단 시간’은 전체 프로그램·쇼핑몰·업로드를 멈추라는 뜻이 아니라, 실제 자격 교체 중 Cafe24 연결/재연결·관련 외부 조회·refresh가 겹치지 않게 하는 짧은 작업 창이다.** 기존의 짧은 점검 중단 허용을 재사용한다. 준비 단계에서 날짜/시각을 지금 선택할 필요는 없다. 실제 변경이 요청될 때, 영향 경로 대기 시작부터 옛 자격 거절·필요한 대체 인증 정상 확인까지의 작업 시간만 잡는다. 본인 OAuth 동의/MFA 시간이 포함될 수 있어 완료 시간을 근거 없이 몇 분으로 보장하지 않는다. 추가 예약이나 중단 일정을 생성하지 않았다.

권한도 구분한다. 코드상 연결 시작은 `settings.manage`를 요구하지만 일부 Cafe24 검증용 실시간 GET은 `data.read`이고 백엔드의 `accessToken()`을 통해 만료 시 refresh를 호출할 수 있다. **읽기 전용 사용자가 비밀을 소유하거나 설정을 바꾼다는 뜻은 아니지만, ‘읽기 권한뿐이므로 백엔드 자격이 절대 사용되지 않는다’고도 단정할 수 없다.** 따라서 후속 실제 작업 때 해당 자격을 쓰는 외부 조회/refresh 경로만 대기시킨다. 일반 저장 데이터 조회·사용자 역할·파일·DB를 일괄 중단/삭제하는 계획은 아니다. 이 코드 경로를 이번에 호출하거나 새 수집·refresh 시험을 한 것은 아니다.

사용자에게 새로 넘길 계정/관리자 조사·전체 UI 확인 작업은 없다. 본인에게 남는 것은 **실제 변경 때 필요한 로그인/MFA와 OAuth 동의**다. 자격 발급·전환·폐기·검증 등 나머지 실행은 기존 권한과 후속 실제 변경 승인 범위 안에서 내가 맡을 수 있다. 실제 폐기 쓰기 권한은 아직 실행으로 검증하지 않았다.

## 로그인 후 관리자 읽기 최종 보완

**Cafe24:** App 관리의 두 앱 중 기존 보호 원본 Client ID와 ‘일일 데이터 자동화’만 정확 일치했고 다른 앱은 불일치였다. 보호 원본은 메모리에서 해당 Client ID만 비교하고 전후 파일 SHA256이 같았다. ‘개발정보 → 인증정보’에서 유형 Web application(일반)/Authorization Code, Client Secret Key 행의 **보기·재발급**을 확인했다. Front API/서비스 키/Webhook 키 재발급은 별개 제어이며 이번 대상이 아니다. Client Secret Key 재발급을 누르지 않았고 보기·복사·저장도 하지 않았다.

현재 가시적인 주변 안내에는 secret 교체의 즉시 무효화 여부·이전/신규 동시 보유 기간·기존 access/refresh에 미치는 영향이 표시되지 않았다. 숨겨진 확인창을 보기 위해 재발급을 누르지 않았다. 따라서 ‘무중단 교체 가능’ 또는 ‘secret 재발급으로 pair까지 폐기’라고 확정할 수 없다. **중단·pair 별도 폐기·secret 교체·필요 재승인의 보수적 기본안**을 유지한다. 이 공백을 같은 화면을 다시 읽어 달라는 사용자 작업으로 넘기지 않는다.

**Meta 앱:** 기본 설정의 실제 앱 ID SHA256은 기존 예상 앱 지문과 일치했다. 기본 설정의 앱 시크릿은 ‘보기’ 상태로 유지했고 표시하지 않았다. 고급 설정에서 보이는 **‘클라이언트 토큰 → 재설정’은 APP inspector 폐기의 대체 수단으로 간주하지 않는다.** ‘앱 시크릿 코드 요청’ 스위치는 관측 당시 OFF였고 변경하지 않았다. 앱 시크릿·proof를 쓰는 소비자에 대한 가능한 영향은 남지만 이 스위치만으로 현재 외부 소비자 부재를 증명하지 않는다.

**Meta 시스템 사용자:** 현재 비즈니스의 시스템 사용자에는 ‘토큰 생성/토큰 취소’가 보이고 설치된 앱의 ‘보기’는 정확한 대상 앱 설정으로 연결됐다. 그 앱은 할당 자산에도 표시됐다. 다만 UI 사용자 ID 지문은 `9b5ae53bad9d3fff34ac842b52e02565b6f3c5e929fa10c58f5090b61b2bb8b9`, 기존 debug/me의 app-scoped 주체 지문은 `47fa78bc840495351e6558f5973bed7a4b0d6b65cbba5f17a94840f2e0baed97`로 다르다. **동일 주체의 ID 범위 차이인지 다른 주체인지 매핑을 확인하지 못했다.** 앞선 진행 설명에서 ‘다른 사용자’라고 한 표현은 확정 사실로 사용하지 않는다. 토큰 취소 버튼은 누르지 않았다.

**Meta 공식 안내:** 로그인 후 브라우저에서는 공식 문서를 읽을 수 있었다. [시스템 사용자 만들기/검색/업데이트의 무효화 절](https://developers.facebook.com/docs/business-management-apis/system-users/create-retrieve-update#delete-token)은 `DELETE /{APP_SCOPED_SYSTEM_USER_ID}/access_tokens`로 **지정한 시스템 사용자의 모든 access token**을 무효화하고 그 뒤 새 token을 생성할 수 있다고 설명한다. ‘노출 token1개만 선택 폐기’나 ‘다른 앱에는 반드시 영향 없음’을 뜻하지 않는다. 기존 가정 분기를 이 전체 무효화 범위로 좁혀 수정한다.

**v3 추가 ID 준비 마감:** 같은 공식 문서는 API 호출에 Business Manager 화면의 표준 ID가 아닌 **앱 범위 ID**를 쓰도록 명시한다. 따라서 이번 준비에서는 이미 보호 원본/기존 debug·me 증거에 결속된 앱 범위 ID를 사용하는 API 경로를 채택한다. 선택하지 않을 UI 경로의 ID 매핑을 사용자에게 새 필수 작업으로 요구하지 않는다. 정확 대상의 실행 직전 재결속은 내가 맡는다.

[Meta 공식 SDK의 SystemUser 식별 필드](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/systemuser.py)를 근거로 기존 보호 token의 `/v26.0/me?fields=id,system_user_id`를 **GET1회만** 읽었다. HTTP400/code100이어서 매핑은 확인하지 못했다. 같은 조회를 반복하거나 새 scope·token·로그인을 요청하지 않았다. 표준 ID와 앱 범위 ID가 실제로 같은 주체인지의 매핑은 여전히 미확정이며, 이를 다른 사용자/권한 부재/자격 무효로 단정하지 않는다. 응답·ID 원문을 저장하지 않았고 보호 파일도 불변이다. 이는 광고 데이터 수집·token 발급·refresh·철회 요청이 아니다.

[공식 token 종류 안내](https://developers.facebook.com/documentation/facebook-login/guides/access-tokens)는 APP token이 앱 시크릿으로 생성돼 앱 설정 읽기·수정에 쓰인다는 점, client token은 다른 종류라는 점을 구분한다. [공식 로그인 보안](https://developers.facebook.com/documentation/facebook-login/security)은 기본 설정의 앱 시크릿 재설정 위치와 OAuth/appsecret_proof 영향 경로를 설명한다. **이 안내와 현재 가시 UI만으로 개별 APP token의 선택 폐기 지원, reset 뒤 모든 기존 token의 정확한 무효화/유예 범위까지 확인한 것은 아니다.** 문서가 연결한 과거 만료/연장 URL은 페이지 없음이어서 추가 확정 근거로 쓰지 않았다. APP reset은 별도 영향 결정 없이 자동 실행하지 않는다.

## 공통 실행 규칙과 증거

후속 변경 직전에 대상 프로젝트/앱/Client ID·자격 지문·소비자 위치를 재결속한다. 비밀 원문은 메모리/기존 보호 저장소에서만 다루고 새 보호 참조에는 새 버전 식별자를 사용한다. 관리 응답·HTTP URL/헤더/본문·환경변수 전체를 로그에 쓰지 않는다. 기존 영수증·소비한 도구·암호화 백업은 덮어쓰거나 일괄 삭제하지 않는다.

소비자의 첫 전환은 ‘대체 자격 사용’ 또는 ‘외부 호출 중지·새 보호 참조 대기’ 중 하나다. 같은 grant/앱 전체 폐기처럼 대체 자격까지 영향을 받는 경우에는 후자를 사용한다. 이미 중지된08 앱과149예약은 자격 확인을 위해 켜지 않는다. 제한된 자격 검증도 후속 승인 범위에 결속하며 새 날짜 수집·전체 회귀·운영 배포로 확대하지 않는다.

각 묶음은 소비자 전환/사용 중지, 공급자 폐기 근거, 옛 자격 거절, 필요한 대체 자격 정상이라는 네 결과를 각각 기록한다. 중단하기로 한 소비자에는 대체 정상 대신 ‘폐기 대상 소비자, 재시작 금지’와 승인된 사용 중지 근거를 남긴다. 소비자0/폐기완료/거절성공의 미확정은 null로 유지한다.

검증 실패 시 해당 소비자를 중지·대기 상태로 유지한다. 노출 자격을 복원하는 rollback은 없다. 부수 영향이 예상보다 넓으면 다른 토큰·프로젝트·계정을 일괄 폐기하지 않고 그 묶음에서 중단한다. 철회 전파 지연은 제한된 횟수의 후속 확인으로 다루며 지금 재확인 예약을 만들지 않는다.

## 1. Supabase 공유 secret key

**대상:** `ehnfrrmbkvlsbpvqcvkr`에 속한 정확 노출 key1개. 기존 소비자 조사 도구의 허용 API 경로와 일치 개수로 프로젝트를 결속했다. UI에 보이는 여러 key 중 이름만으로 대상을 추정하지 않는다. JWT signing key·legacy service_role 전체·운영 Pro key는 자동 변경 대상이 아니다.

**순서**

1. 기존 보호 원본의 지문으로 현재 관리 목록의 key ID/종류·프로젝트를 메모리 대조한다. 일치0개/복수개/종류 불일치면 삭제를 시작하지 않는다. 공개 증거에는 key ID의 지문과 일치 여부만 남긴다.
2. 중지된08을 계속 사용하지 않을 때는 옛 참조를 제거하고 ‘새 자격 대기/재시작 금지’로 전환한다. 계속 사용할 필요가 있으면 해당 격리 프로젝트의 별도 대체 secret key를 보호 저장소에 준비하고 필요한 소비자만 새 참조로 바꾼다. 새 key 발급을 무조건 요구하지 않는다.
3. 이번 사용자 확인으로 외부 소비자는 없음으로 정리했다. 이 확인을 다시 요청하지 않는다. 조사된 내부 소비자의 참조 전환/사용 중지만 정확히 결속한다. 사용자 확인을 전 세계 기술적 전수 조사로 확대하지 않는다.
4. 정확 ID의 secret key를 폐기한다. 공식 Management 경로는 `DELETE /v1/projects/{ref}/api-keys/{id}`다. 문서상 `secrets:write` 또는 fine-grained `api_gateway_keys_write`가 필요하며 기존 PAT의 이 쓰기 권한은 아직 검증하지 않았다. 응답은 key를 포함할 수 있어 원문을 출력/보존하지 않는다.
5. 관리 목록에서 정확 대상 부재/폐기 상태와 시각을 기록한다. 존재하던 환경값 제거만으로 공급자 폐기를 완료 처리하지 않는다.

**영향:** 같은 key의 API 인증을 사용하는 서버·도구가 거절될 수 있다. 중지된08 자체를 가동할 필요는 없다. DB 데이터·RLS·역할·예약·다른 key 변경은 이 절차에 포함하지 않는다.

**검증:** 후속 승인된 비캐시 보호 GET(예: Storage 버킷 목록의 메타데이터만)에서 대체 key 성공과 정확 옛 key의 gateway 인증 거절을 같은 대상/조건으로 비교한다. 응답 본문은 출력하지 않는다. RLS/권한403·네트워크 오류·앱 중지·empty 결과를 key 무효화로 분류하지 않는다. 관리 목록 확인과 인증 거절은 별개다. 대체 key를 사용하지 않는 소비자는 중지/참조 제거를 확인한다. 제외한 sentinel 객체·signed URL·CDN은 읽지 않는다.

**내가 할 수 있는 부분:** 정확 key 결속, 참조 변경안·관리 API 작업·메타데이터 대조와 제한 GET의 후속 실행. 외부 소비자 확인은 완료다. 중지된08은 현재 보존하며 필요한 새 보호 참조가 준비되기 전 재시작하지 않는다. **사용자만 필요한 부분:** 실제 변경 때 플랫폼이 요구하는 본인 인증. 지금 새 관리자 권한을 요청하지 않는다.

공식 근거: [key 전환과 폐기](https://supabase.com/docs/guides/getting-started/api-keys), [개별 key 삭제와 권한](https://supabase.com/docs/reference/api/v1-delete-project-api-key).

## 2. Cafe24 client secret과 노출 token pair

**서로 다른 두 작업:** 앱의 client secret 교체는 그 Client ID의 인증에 영향을 주며, 노출 access/refresh pair 처분의 증거가 아니다. pair 만료·회전 이력도 secret 폐기의 증거가 아니다. 원 실패 pair와 후속 정상 pair를 지문으로 구분한다.

**기본안 — 짧은 OAuth 점검 중단:** 교체 중 옛/새 secret 병행 지원을 확인하지 못했으므로 병행 무중단을 약속하지 않는다.

1. 06 콜백의 OAuth 교환/refresh 처리를 중단·대기시키고 진행 중 콜백/refresh가 없는 시점을 잡는다. 같은 Client ID의 다른 소비자도 새 자격 대기로 전환한다. 쇼핑몰 영업 전체를 중단하는 계획은 아니다. 지금 서비스 중지·변수 변경·배포는 하지 않는다.
2. 정확 몰/앱/노출 pair의 결속과 현재 유효 client 인증 수단을 확보한 뒤, 노출 pair의 access를 명시적으로 폐기하고 연결 refresh의 처분 근거도 기록한다. 현재 공식 경로는 `POST https://{mall_id}.cafe24api.com/api/v2/oauth/revoke`, form body `token`·`token_hint`, Basic client 인증이다. 오래된 도구/DELETE 예시를 복사 실행하지 않는다.
3. access 폐기가 연결 refresh도 폐기한다는 공식 설명을 적용하되, access가 이미 만료돼 처리 결과가 불명확하거나 연결 근거가 부족하면 정확 노출 refresh도 별도 대상에 넣는다. 200 응답만으로 어느 pair가 폐기됐는지 추정하지 않는다. 앱 삭제/몰 전체 연결 해제를 자동 대안으로 사용하지 않는다.
4. 현재 확인한 Client Secret Key 전용 제어로만 교체한다. 이를 먼저 하면 옛 pair 폐기 인증에 필요한 secret을 잃을 수 있으므로, 기본안에서는 pair 폐기를 먼저 배치했다. 현재 UI에 적용·유예 설명이 없으므로 즉시 전환에 대비한 점검 창을 사용한다. 후속 실제 변경 때 공급자 안내가 다른 순서를 요구하면 멈추고 해당 분기만 수정한다.
5. 06의 `DAILY_SYNC_CAFE24_CLIENT_SECRET` 및 같은 Client ID를 계속 쓸 소비자에 새 보호 참조를 적용한다. 중지된08은 새 참조 대기 상태로 두며 임의 기동하지 않는다. 기존 콜백 URL·Client ID·몰 결속은 유지한다.
6. 같은 승인 계열의 정상 pair까지 영향을 받았거나 새 pair가 필요하면 **본인 쇼핑몰 승인 후** 대체 pair를 확보한다. 기존 미노출 정상 pair가 유효하다는 근거가 있으면 불필요하게 다시 발급하지 않는다. 필요한 승인 범위는 기존 계약의 read 범위이며 주문/설정 쓰기를 추가하지 않는다.
7. 새 secret 사용 OAuth 정상·몰/앱/scope 일치를 확인하고 제한된 토큰 읽기 검증을 끝낸 뒤 승인된 콜백 처리만 복구한다. 이는 수집 예약 활성화나11 배포 승인이 아니다.

**검증을 세 칸으로 분리:** (a) 옛 client secret의 client 인증 거절, (b) 옛 access의 인증 거절과 옛 refresh 처분/거절, (c) 필요한 대체 secret/pair의 정상 동작. `invalid_grant`만으로 옛 client secret 거절을 증명할 수 없다. 401이더라도 원인이 scope·버전·클라이언트·토큰 중 무엇인지 안전한 enum으로 구분한다. 실패/에러 원문은 저장하지 않는다.

**중요한 실행 경계:** 옛 secret/refresh로 token endpoint를 호출하는 음성 검증도 예상과 달리 성공하면 토큰을 발급·갱신한다. 지금 읽기 확인으로 실행하지 않는다. 후속 실제 자격 작업에 그 가능성과 수습을 포함해 승인됐을 때만 수행한다. 예상 밖 발급이 일어나면 성공으로 간주하지 않고 새로 생긴 자격도 처분 대상에 결속한다. 자동 refresh·자동 재시도는 끈 한정 작업을 사용한다.

**사용자만 필요한 부분:** 실제 변경 때 필요한 쇼핑몰 본인 동의·MFA. 외부 소비자 확인과 관리자 로그인은 완료다. 06은 보존 기본안이며 기존에 허용한 짧은 점검 창을 사용하므로 준비 단계에서 영구 유지/종료나 중단 시각을 다시 선택할 필요가 없다. 현재 없는 안내를 얻기 위해 사용자에게 재발급 버튼을 눌러 달라고 요청하지 않는다. secret 원문을 채팅에 제공할 필요는 없다.

공식 근거: [현재 OAuth 인증·token 폐기 문서](https://apidocs.cafe24.com/en/docs/guide/oauth2-authentication#-token-revoke). secret 교체의 즉시 적용/동시 보유 방식은 이 공개 문서만으로 확정하지 않았다.

## 3. Google 원 OAuth grant / gcloud ADC

**이미 확인한 대상:** 05단계 기록과 현재 연결 Gmail이 같은 원 계정, 앱 표시명 Google Auth Library, 연결 시각9/30 10:48, 현재 표시 권한 cloud-platform(Cloud 확인·수정·구성·삭제 및 이메일 확인). 개인 이름/메일 원문을 이 문서에 복사하지 않는다. 과거 source refresh/client 조합과 ADC의 정확 일치는 재사용한다.

**순서 — 중지·대기 전환 후 철회, 그 뒤 재승인**

1. 동일 source ADC를 쓰는 알려진 도구를 자동 인증/자동 refresh 없이 중지·새 참조 대기 상태로 전환한다. 외부 소비자 없음은 사용자 확인으로 반영했고 같은 질문을 다시 요청하지 않는다.
2. 기본 ADC OAuth client를 사용자 소유의 별도 앱으로 보고 client secret을 재발급/삭제하지 않는다. 서비스 계정 IAM 변경, SA key 삭제, ADC 파일 삭제를 원 사용자 grant 폐기의 대체 수단으로 쓰지 않는다.
3. 후속 변경 승인 시에는 기존 보호 source refresh를 메모리에서 읽어 `POST https://oauth2.googleapis.com/revoke`의 form body로 철회하는 경로를 내가 사용할 수 있다. token을 URL·콘솔·영수증에 넣지 않는다. UI를 선택하는 경우에만 원 계정의 [Google 연결 앱](https://myaccount.google.com/connections)에서 **Google Auth Library → Google 계정 액세스**의 정확 승인 항목을 본인이 철회한다. 같은 사용자의 해당 OAuth 프로젝트에 부여한 scope·그 프로젝트의 client token 전체가 영향을 받을 수 있음을 적용한다. Gmail connector 등 다른 앱이 같은 프로젝트인지 확인 없이 연쇄 철회하지 않는다.
4. 같은 영향 범위의 새 grant를 미리 만들어 두지 않는다. 분리된 OAuth 프로젝트/대체 인증이라는 근거가 이미 있지 않으면 철회 뒤 본인 재승인하고 새 보호 참조로 연결한다. 서비스 계정 impersonation 같은 업무 구조는 기존 계약을 따르며 새 IAM 권한을 추가하지 않는다.
5. 원 grant 철회 시각·범위의 공급자 근거를 남긴다. 오래된 ADC는 참조를 제거/격리하고 나중에 재사용되지 않게 한다. 보호 백업 일괄 삭제는 하지 않는다. `gcloud auth application-default revoke`는 **철회+로컬 파일 삭제를 하는 변경 명령**이며 단순 읽기 명령이나 지금 실행할 청소 명령이 아니다.
6. 필요한 대체 승인·최소 업무 권한·예상 계정/고정 연결·대체 인증의 정상 읽기를 확인한다. 새 수집이나 과거 날짜 backfill은 하지 않는다.

**영향:** 같은 승인 프로젝트의 ADC를 사용하는 다른 기기/도구의 Cloud 인증이 끊길 수 있다. Cloud 자원의 데이터 자체를 삭제하는 절차는 아니다. scope가 넓어도 실제 자원 접근은 IAM에도 제한되며, grant 폐기를 IAM 조정으로 대신하지 않는다.

**검증:** 원 grant 철회 근거와 옛 refresh의 거절을 분리한다. 같은 grant의 유효 cached access는 기존 조사에서 찾지 못했으므로 없는 토큰을 만들거나 refresh해 옛 access 거절 자료를 생성하지 않는다. 후속 옛 refresh 거절 확인은 성공 시 발급될 수 있는 변경성 작업으로 Cafe24와 같은 경계를 적용한다. `invalid_grant` 등 실제 거절이 관측되기 전까지 `oldRefreshRejected=null`이다. 네트워크 실패·동의 화면 부재·파일 삭제만으로 거절 PASS를 쓰지 않는다. 대체 정상은 새 승인이 원 철회 영향 밖/철회 이후인지까지 결속한다.

**사용자만 필요한 부분:** 지금 원 사용자·날짜·표시 권한 재확인은 필요 없다. 실제 처분 후 원 계정의 로그인/MFA와 필요한 재승인/동의는 본인이 수행한다. 철회 자체를 사용자 UI 작업으로 무조건 넘기지 않는다. 나는 승인된 원 refresh의 API 철회·기존 보호 참조 전환·로그 정리·한정 검증·비민감 영수증 결속을 맡을 수 있다.

공식 근거: [Google OAuth token 철회 영향·전파](https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke), [ADC revoke의 실제 범위](https://docs.cloud.google.com/sdk/gcloud/reference/auth/application-default/revoke).

## 5. Meta APP inspector

APP token이라는 사실만으로 개별 폐기 지원이나 app secret 유출 여부·필수 reset을 단정하지 않는다. 기존 APP inspector도 노출 자격이므로 폐기 검증의 유일한 신뢰 수단으로 계속 사용하지 않는다.

1. 정확 앱 ID와 기본/고급 설정 읽기는 완료했다. 가시 UI에서는 개별 APP token 폐기 제어가 관측되지 않았지만 ‘지원되지 않는다’고 전역 단정하지 않는다. 기본 설정의 앱 시크릿 재설정은 공식적으로 안내된 앱 차원 후보이며 현재 ‘보기’ 뒤의 제어·영향 확인창은 열지 않았다. 고급 설정의 클라이언트 토큰 재설정으로 APP inspector를 처분하지 않는다.
2. 앱 차원 secret 변경이 필요한 경우 inspector뿐 아니라 OAuth callback/token 교환·appsecret_proof·signed request 검증 등 그 secret을 실제 쓰는 소비자를 영향 목록에 넣는다. 이 경로는 가능한 영향 항목이지 이번에 사용자가 모두 사용한다고 확인한 목록은 아니다.
3. 관련 소비자를 새 참조 대기로 전환한다. 앱 secret reset/앱 전체 token 폐기 같은 넓은 동작은 좁은 APP token 폐기로 승인한 것으로 처리하지 않는다. 범위가 확인되기 전에는 실행 API·버튼을 확정하지 않는다.
4. 후속 변경 시 채택할 APP 처분과 그 영향이 승인된 경우에만 실행하고, 새 inspector를 준비해 유효성을 먼저 확인한다. 현재 APP별 정확 폐기/유예 범위는 미확정이다. 앱 시크릿 변경을 선택하더라도 옛 APP 무효화를 가정만으로 완료 처리하지 않는다. 앱 전체 영향이 있는 경우 **SYSTEM_USER 전체 무효화 → APP 처분 → 새 inspector → 대체 SYSTEM_USER** 순서다. 먼저 만든 대체 token까지 함께 무효화하는 순서를 피한다.
5. 새 inspector와 기존에 성공했던 APP 검사 방식을 기준으로 옛 APP 무효/인증 거절을 확인한다. 새 inspector로 정상 token을 검사할 수 있어야 옛 token 검사 오류와 구분할 수 있다. APP token에서 사용자용 /permissions나 /adaccounts가400인 것만으로 폐기 성공이라고 표시하지 않는다.

**사용자만 필요한 부분:** 실제 앱 차원 자격 처리가 요청될 때 플랫폼이 요구하는 본인 인증. 앱 관리자 로그인과 외부 소비자 확인은 완료했다. 화면 읽기·앱 시크릿 변경을 포함할 수 있는 전환안·넓은 영향 명시·검증·증거 정리는 내가 맡는다. 앱 시크릿 교체 후보를 개별 APP token만 폐기하는 좁은 동작으로 표현하지 않는다. 지금 secret 보기/reset이나 client token reset을 요청하지 않는다.

Meta 공식 문서는 위 ‘로그인 후 관리자 읽기 최종 보완’ 절의 실제 읽은 canonical 경로를 따른다. 이전429 한계는 현재 읽힌 범위에서 갱신했다. APP 개별 무효화의 공백은 제3자 자료나 client token reset으로 메우지 않았다. 기존 debug_token 성공 근거는 재사용하며 새 introspection을 반복하지 않았다.

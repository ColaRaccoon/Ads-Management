# Meta 사용자 OAuth 대안 검토 — 2026-10-24

## 판정

회사 PC와 다른 비즈니스 관리자의 승인 없이 시도할 수 있는 **공식 사용자 액세스 토큰 경로가 있다**. 다만 현재 제품은 SYSTEM_USER만 허용하므로 설정만으로 전환할 수 없다. 사용자 지시는 현재 대안 검토이며, 이 문서 작성까지 USER 자격 발급·교환·운영 바인딩이나 이 인증 방식의 코드 변경은 실행하지 않았다. 실제 사용자 동의 화면에서 추가 승인이 요구되지 않을지는 아직 확인되지 않았으므로 성공을 보장하지 않는다.

현재 막힌 것은 새 SYSTEM_USER 토큰을 생성하는 요청이다. Meta UI가 다른 비즈니스 관리자의 승인 필요를 표시했고 요청을 접수했다. 기존 유효 대체 토큰은 인계상 회사 PC의 보호 저장소에 있다. 현재 원격 08의 변수 **이름만** 읽어 `PHASE08_META_RECORD_B64`와 `DAILY_SYNC_META_VAULT_KEY` 부재를 확인했으며, 중지 서비스 재개·자격 값 읽기·옛 자격 검사를 하지 않았다. 사용자는 회사 PC 접근이 불가능하므로 USER OAuth 대안 검토를 선택했다.

## 공식 근거

2026-10-24 정상 로그인된 Meta 개발자 문서를 직접 읽었다. 웹 검색 도구의 해당 문서 접근 오류를 근거 없음으로 해석하지 않았다.

- [Ads MCP 시작하기](https://developers.facebook.com/documentation/ads-commerce/ads-ai-connectors/ads-mcp-server/ads-mcp-server-get-started), 2026-09-04 갱신: OAuth, 사용자 토큰, 직원 역할 시스템 사용자 토큰을 지원한다. 사용자 토큰도 MCP Bearer로 보낼 수 있다. 최소 권한은 ads_mcp_management와 ads_read 또는 ads_management다. 이번 제안은 **ads_read와 ads_mcp_management만** 사용한다.
- [장기 사용자 토큰](https://developers.facebook.com/documentation/facebook-login/guides/access-tokens/get-long-lived), 2026-06-30 갱신: 유효한 단기 사용자 토큰을 앱 ID·앱 secret과 함께 서버에서 교환할 수 있으며 일반적으로 약60일 유효하다. 만료 후에는 새 사용자 로그인 흐름이 필요하다. 서버 보고 조회만으로 무기한 갱신된다고 가정하지 않는다.

## 필요한 최소 제품 변경

1. `meta-credential-resolver.ts`: 기본 SYSTEM_USER는 보존하고, MCP에서만 명시적으로 선택한 USER 모드를 추가한다. 실제 앱에 속한 사용자 ID를 지정해 검증하며 자동 인증 방식 fallback은 두지 않는다.
2. `meta-protected-credential-resolver.ts`: USER 암호화 레코드는 인증 종류와 앱 범위 사용자 ID까지 AAD에 결속한다. 기존 SYSTEM_USER 레코드와 구분해 다른 사람·인증 종류의 암호문을 재사용하지 못하게 한다. 실제 debug와 `/me`·대상 광고계정 응답의 앱4474691502806219·사용자·두 scope·유효성·만료·USD·Asia/Seoul을 모두 검사한다. 현재의 **7일 이상 만료 여유** 조건을 완화하지 않는다.
3. 위 두 모듈의 허용/거절·암호문 교차 사용·만료·scope 검사와 기존 SYSTEM_USER 호환 검증을 추가하고 컨테이너 패치 허용 목록을 갱신한다. 새 검증 이미지로 배포한다.

보고 수집 MCP transport, 10/23 하루 제한, 광고계정 allowlist, 구매 지표 계약, 기존 원천 충돌 검사와 감사, 예약 OFF를 유지한다. DB migration·광고 예산 변경 API·신규 Meta 앱·ads_management/business_management 권한은 필요 범위에 넣지 않는다.

초기 자격은 기존 Daily Data Automation 앱의 공식 사용자 OAuth/Graph API Explorer 흐름을 통해 직접 동의하고, 서버 측 장기 토큰 교환 및 검증 후 보호 저장한다. 제품에 완전한 Meta 로그인 UI와 callback을 새로 만드는 것은 이 최소안의 범위 밖이다. 앱 secret은 현재 값을 보호 입력으로 사용하며 다시 발급하지 않는다.

## 운영상의 차이와 실행 순서

USER 토큰은 로그인한 사람의 권한과 로그인 상태 변화에 종속된다. 앱 권한 철회·계정 변화·만료 시 수집은 실패로 닫혀야 하며, 서버의 만료 전 여유 조건에 맞춰 재로그인이 필요할 수 있다. 회사 PC의 기존 토큰을 옮기는 방식보다 최초 코드 검증과 새 배포가 추가된다.

실행 순서는 변경 범위 결정 → 코드·국소 검증 → 실제 사용자 동의 범위 확인 → 장기화/주체·권한 확인 → 보호 저장·바인딩 → 10/23 단일 수집이다. 이 검토를 실제 새 자격 성공이나 수집 성공으로 세지 않는다.

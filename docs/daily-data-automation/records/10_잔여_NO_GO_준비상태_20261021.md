# 잔여 운영 NO GO 조건과 해소 준비 상태

2026-10-21 KST 기준, 공유 자격 처분과 Supabase 조직 월간 사용량 두 조건은 **미해결**이다. 이번에는 기존 소비자 조사와 권한 근거를 재사용하고, 브라우저의 현재 접근 한계와 자격별 처분 절차를 정리했다. 운영 판정은 NO-GO, 11·12는 NOT_STARTED다. [최신 마감](10_범위조정_최종마감_20261021.md)의 완료 범위를 다시 검증하지 않았다.

## 향후 변경을 위한 절차

이 절차는 준비안이며 지금 실행할 승인이나 실행 명령이 아니다. 현재 자격 발급·refresh·교체·폐기·OAuth 철회는 모두 금지 상태다.

1. **대상과 영향 확정:** 기존 조사 지문으로 자격·프로젝트·앱·소비자를 결속한다. 사용자가 외부 소비자 목록과 중단 시간을 보완하고, 실제 변경 범위와 시점을 결정한다. 기존 관리자 세션을 재사용하되 로그인/MFA는 사용자가 수행한다. 읽기 성공을 폐기 쓰기 권한 검증으로 취급하지 않는다.
2. **소비자 전환 준비:** 대체 자격의 보호 참조·최소 scope·소비자별 전환 순서와 복귀 방식을 고정한다. 운영 배포나 예약을 켜지 않고 검증 가능한 한정 경로를 별도 승인 범위에 포함한다. 중지된08 앱을 자격 점검 때문에 가동하지 않는다. 폐기 뒤 노출 자격으로 되돌리는 복귀는 준비하지 않는다.
3. **실제 처분과 검증:** 공급자별 실제 처분 영수증을 받은 뒤, 정확한 옛 자격의 거절과 대체 자격의 같은 대상 정상 동작을 모두 확인한다. 공개 증거는 시각·대상 지문·상태 코드·판정만 남긴다. 인증 응답 원문과 고객 자료는 저장하지 않는다. 아래의 자격별 차이를 적용한다.

| 자격 | 향후 처분과 검증의 구체적 차이 |
|---|---|
| Supabase | 알려진 소비자에 대체 key를 전환한 뒤 정확한 노출 secret key를 폐기한다. 관리 목록의 대상 제거/폐기 상태와 인증이 필요한 원본 경로의 옛 key 거절, 같은 경로의 대체 key 성공을 대조한다. 단순히 새 key를 만들거나 JWT signing key만 변경한 것을 해당 secret key 폐기로 취급하지 않는다. [공식 API key 절차](https://supabase.com/docs/guides/getting-started/api-keys)는 소비자 전환 후 노출 key를 처분하도록 안내한다. |
| Cafe24 |06 콜백의 secret 전환과 기존 access/refresh pair의 처분을 각각 기록한다. [공식 OAuth 안내](https://apidocs.cafe24.com/en/docs/guide/oauth2-authentication#-token-revoke)에 따르면 access token 폐기는 연결 refresh token도 폐기한다. secret만 교체한 뒤 기존 pair까지 폐기됐다고 표시하지 않는다. 대상 mall·client·pair 지문을 고정하고 옛 access 거절과 refresh 재사용 불가, 대체 pair의 필요한 읽기 성공을 별도로 검증한다. 향후 refresh 거절 시험은 폐기 실패 시 새 token이 발급될 수 있으므로 별도 승인된 실행 범위에서만 한다. |
| Google | [공식 철회 안내](https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke)는 해당 사용자가 프로젝트에 부여한 전체 scope와 같은 프로젝트의 모든 client token에 철회 영향이 있다고 설명한다. 대체 grant를 먼저 만들어도 같은 영향 범위면 함께 무효화될 수 있다. 따라서 소비자를 새 참조를 기다리는 중지 상태로 전환한 뒤 원 grant를 철회하고 본인 재승인을 받는 순서, 또는 영향이 분리됐음을 확인한 대체 grant 전환을 사용자가 선택해야 한다. ADC 삭제나 SA IAM 변경은 원 OAuth grant 철회를 대신하지 않는다. 향후 원 grant 철회 증거·옛 refresh 거절·대체 승인 정상 동작을 결속한다. 철회 전파 지연과 실패 시 token 발급 가능성을 고려해 refresh 거절 시험도 별도 승인하며 지금은 하지 않는다. |
| Meta | SYSTEM_USER/MCP는 해당 system user·앱·토큰을 대상으로 한 처분과 MCP 소비자 전환을 결속한다. APP inspector는 앱 차원의 자격 무효화 수단과 영향 범위를 먼저 확정한다. SYSTEM_USER 하나의 처분으로 APP 토큰까지 폐기됐다고 주장하지 않는다. 기존 inspector 자체도 노출 토큰이므로 검증 신뢰 수단을 별도로 준비한다. 향후 정확한 두 옛 token의 invalid 판정과 필요한 읽기 거절, 각각 대체 token의 예상 앱·광고 계정·scope 정상 동작을 확인한다. 최신 관리 UI의 처분 범위 확인 전에는 특정 API나 app secret 재설정 명령을 확정하지 않는다. |

해소 기준은 소비자별 전환/사용 중지 근거, 실제 폐기 근거, 정확한 옛 자격 거절과 대체 정상 동작, 외부 소비자 미확정 범위에 대한 사용자 확인이다. 읽기 조사 완료만으로 해소하지 않는다. 영구 Meta token과 별도 MCP 무료 선언을 새 필수 조건으로 추가하지 않는다.

## 사용자가 제공할 최소 사용량 자료

본인이 [대상 프로젝트](https://supabase.com/dashboard/project/ehnfrrmbkvlsbpvqcvkr)에서 소속 조직을 선택해 **조직 Usage의 현재 집계 기간과 전체 프로젝트 범위**를 읽는다. 로그인/MFA가 요구되면 본인이 처리한다. 자동 제어가 현재 화면을 읽지 못하므로 아래 비민감 값이 필요하다. 비밀키·PAT·비밀번호·쿠키·인증 응답은 필요하지 않다.

- 대상 조직을 구별할 이름 또는 slug와 프로젝트 소속 일치 여부. 개인 이름은 가려도 된다.
- 화면의 집계 시작/종료, timezone, 조회 시각, 표시된 데이터 갱신 시각/지연. 월초~월말로 임의 보정하지 않는다. Usage 기간과 Billing 기간이 다르면 둘 다 적는다.
- 항목별 실제 소비, 무료 포함량, 표시된 잔여량, 단위, 초과·경고·제한 문구. 잔여가 없으면 소비/포함량으로 계산하되 계산값이라고 구분한다.

## 구현·계약

로컬 코드 범위: `apps/api/prisma/schema.prisma`, `apps/api/prisma/migrations/20260929090000_common_sync_foundation/migration.sql`, `apps/api/src/daily-sync/*`, `apps/api/src/auth/machine-sync.guard.ts`, 기존 auth guard/route decorator·경로 인벤토리 테스트, `apps/api/src/app.module.ts`, `apps/api/src/main.ts`. 기존 사용자 미추적 문서를 지우거나 덮어쓰지 않았다.

신규 테이블 10개(`SourceConnection`, `SourcePolicy`, `SyncRun`, `RunUnit`, `SyncLease`, `SourceCoverage`, `GoogleCampaignDailyCost`, `SourceRecordLink`, `Cafe24OrderApiVersion`, `SourceCredential`)와 enum/FK/partial unique/정책 겹침 trigger를 additive로 추가했다. 기존 CSV 테이블과 구 업무 행은 변경하지 않는다. 신규 테이블은 runtime/migration 역할의 명시 grant·RLS와 Data API 역할 차단을 가진다.

공통 실행 기반은 계정별 DB lease owner/generation/expiry와 publish fencing, requestKey 멱등, RunUnit checkpoint·업무 행·coverage의 단일 publish transaction, last attempt/last success 분리, bounded page/body/retry/deadline, HeavyOperationGate 및 stale 재개·SYSTEM/사용자 감사를 포함한다. Meta 광고와 광고세트는 동일 날짜의 다중 slice를 한 transaction으로 publish한다. feature off에서는 신규 폴링·외부 fetch를 시작하지 않는다.

HTTP 계약은 `POST/GET /api/source-connections`, `PATCH /api/source-connections/:id/policy`, `POST/GET /api/sync-runs`, `POST /api/sync-runs/:id/resume`, `GET /api/source-coverage`, machine 전용 `POST /internal/daily-sync`다. 사용자 경로는 기존 권한/CSRF/프록시 경계를 따르고, machine 경로는 별도 token·target guard로만 진입한다. 03에는 실제 provider adapter/수집 실행·예약·화면이 없으므로 run 요청은 DB에 durable하게 큐잉되며 외부 API 작업은 시작하지 않는다. API primary 정책 승격은 shadow 대조 증거가 없는 동안 거부한다.

02 계약은 [v1.2](02_확정계약.md)로 갱신했다. 03의 회전 refresh token을 안전하게 영속화하려면 기존 9개 모델 외 `SourceCredential`이 필요하다. 암호문·IV·인증 태그·키 버전·revision CAS·갱신 소유/만료만 DB에 두며 키 값은 DB 밖에 둔다. 영향은 신규 테이블·migration·권한/RLS, credential 경쟁/실패 테스트와 향후 Cafe24 연결 절차다. Google/Meta는 원문 대신 provider별 불투명 `vault://` 참조를 CAS로 관리하고 만료 시 재인증 필요·수집 비활성으로 전이한다. 참조 형식만으로 실제 권한을 증명하거나 READY로 승격하지 않는다. 정책 겹침은 extension에 의존하지 않는 부모 행 직렬화 trigger로 구체화했다. HeavyOperationGate로 오래 대기한 run이 영구 만료되지 않도록 `deadlineAt`은 QUEUED 중 null이고 실제 claim 시 최대 10분으로 설정하도록 계약을 고쳤다. `SourceCoverage.totalAmount`는 Google micros를 6자리 소수까지 보존하도록 `Decimal(24,6)`로 명시하고 `warningCodes`의 non-null 기본값도 고정했다. 이는 실행 시작점과 정밀도·schema 정합성을 명확히 한 변경이며 기존 업무 데이터 의미·API 원천 우선순위는 바꾸지 않는다.

## 검증·평가

개발자 서브에이전트가 구현하고 평가자 서브에이전트가 기존 기능 회귀·데이터 흐름·스타일/유지보수성·보안·migration 호환성을 독립 검토했다. 평가 과정에서 Meta 다중 slice 원자성, KST coverage 날짜, API source 조기 승격, machine token 교체, credential 초기 저장·교차 provider·lock upgrade, nullable/정밀도 불일치, 성공 unit 실패 덮기 등을 수정하고 재평가했다. 최종 평가 판정은 **미해결 결함 없음**이다.

DB 대상 확인: 로컬 `apps/api/.env`의 `DATABASE_URL`은 운영 Supabase ref로 판정되어 검증에 사용하지 않았다. 초기 Docker 서비스 시작은 OS 권한 거부였고, 사용자 기동 후 `desktop-linux`/Engine 29.3.1이 응답했다. 기존 중지 컨테이너는 변경하지 않고 `meta-ads-phase03-pg-0929` 전용 PostgreSQL 17.6을 루프백 `127.0.0.1:55433`에 만들었다. 격리 fingerprint는 `local Docker / phase03 / meta_ads / meta_ads_stg_runtime`이며 운영 Supabase ref와 다르다.

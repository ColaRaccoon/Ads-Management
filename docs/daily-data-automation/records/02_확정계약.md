Cafe24 문서의 필드 설명과 실제 객체 타입은 입력 후보의 근거일 뿐, 중첩 `order_price_amount`를 기존 CSV `총 주문금액`으로 투영하는 계약은 주문별 값·쿠폰 규칙 대조 전 확정하지 않는다.
- 중첩 금액 후보의 `amount-compare`는 허용 CSV 열 `주문번호`·`품목별 주문번호`·`발주일`·`총 주문금액`·`총 결제금액`·`결제수단`만 메모리에서 읽는다. 두 Orders 목록과 전후 건수를 검증하고, 일회용 연결되지 않은 HMAC으로 주문별 CSV 총 주문금액/총 결제금액과 API `actual_order_amount`·`initial_order_amount` 각각의 `order_price_amount`/`payment_amount`를 대조한다. 10/1 실측은 422주문 중 현재/최초 상품 소계와 CSV 총 주문금액 97/101건, 현재/최초 결제액과 CSV 총 결제금액 419/414건만 일치했다. CSV 정확 `쿠폰`은 34주문이다. 새 안전 출력에서는 API 쿠폰 후보 수·공통 후보 수·쿠폰 여부 일치 수의 1~9건 차집합을 억제하며, 그 불일치는 미해결이다. **10/1 결제액 3건 차이와 쿠폰 후보 불일치는 9/30의 3/348 수용 예외가 아니며 원인 미확정이다.** [Cafe24 주문 금액 문서](https://developers.cafe24.com/docs/en/api/admin/)가 상품 소계·배송비·배송비 할인을 별도 필드로 설명하므로, 현재/최초의 `소계+배송비`와 `소계+배송비-배송비할인` 네 후보식만 비발행 주문별 HMAC으로 추가 대조한다. 10/1 추가 실측에서 현재 `소계+배송비` 및 배송비 할인 차감 후보는 각각 398/422, 최초 후보는 각각 415/422만 일치했다. CSV 정확 쿠폰 34주문의 현재/최초 총액과 부호 있는 총액-결제액 후보는 각각 11/34만 일치했다. 누락된 성분은 0으로 대체하지 않고 후보별 평가 가능 건수와 일치 건수만 반환한다. 쿠폰 입력은 CSV 정확 쿠폰 주문에 한정해 현재/최초 총액·결제액 각각과 **부호 있는 총액-결제액** 후보를 HMAC으로 대조한다. 쿠폰 하위 집계와 그 차집합이 1~9건이면 역산되지 않도록 관련 수치를 억제한다. API 배열의 NFKC·trim·소문자화 후 정확 `coupon`/`쿠폰` 코드 존재와 CSV의 NFKC 정규화 후 정확 `쿠폰` 토큰은 **후보 여부**일 뿐이다. 결과는 일치 건수만 반환하며 원문·식별자·개별 HMAC·금액 합계·비쿠폰 라벨 매핑을 반환하지 않는다. 10주문 미만 또는 500주문 초과, 중첩 타입/금액 이상, 목록 변동, CSV 형제 행의 금액·쿠폰 여부 불일치 시 결과 없이 중단한다. 이 진단의 결과만으로 금액 의미나 API primary 전환을 승인하지 않는다.
- 10/1의 422주문 날짜 HMAC 대조는 기존 1,800개 지문 한도에서 주문당 5개인 최대 2,110개가 필요해 로컬 진단 상한을 2,500개/192KiB(최대 500주문 날짜 튜플)로 늘렸다. 품목 요청의 500ms 간격 pacing, 10분 실행 deadline과 12분 job TTL은 유지한다. 형제 품목의 CSV 발주시각이 서로 달라도 같은 주문일의 유효한 시각 집합이면 HMAC-only/날짜/옵션 대조에서 허용하며, 날짜·시각 형식 혼합과 빈 값 혼합은 계속 거부한다. 10/1 재실행의 비발행 전량 날짜 대조는 완료됐다. 발주일이 있는 419주문의 KST 주문일은 419/419, 정확 시각은 any 388/419·all 387/419로 일치했고 빈 발주일 3주문·API place_date 부재 422주문은 별도로 남는다. 같은 날 주문·품목 키 422/422·477/477과 옵션 후보 전량 대조 및 위 금액 후보 대조도 비발행으로 완료됐지만, 이는 canonical 발행·업무 의미·source 전환의 승인 증거가 아니다.

## v1.4 — 비용 상한과 데이터 최신성 계약

- 자동 예약: Cafe24는 몰 현지시간의 완료된 전일 주문일 **하루만 매일** 조회한다. Google·Meta는 각 계정 현지시간 기준 **7일마다 한 번, 직전 완료 7개 날짜를 각각 한 번씩** 조회한다. 계정 시간대가 다르면 KST 어제 날짜를 일률 적용하지 않는다. 실패 재시도는 원래 선정한 같은 날짜 범위 안에서만 제한적으로 수행한다. 다음 예약에서 누락된 과거 날짜를 자동 추가하지 않는다.
- 자동 최근 7일 반복 재조회, 미완료 주문일 추적, 과거 월 순환 대사, 월초 전월 보정, 장기 공백 자동 backfill은 **세 원천 모두 폐기**한다. Google·Meta의 주간 7일은 매주 새로 완료된 날짜를 한 번씩 읽는 범위이지 이전 주를 다시 읽는 lookback이 아니다. 과거 날짜가 필요하면 관리자가 날짜 **하나를 명시**해 수동 실행하고 원천 충돌을 검토한다.
- Cafe24의 과거 주문 취소·환불·수정, Google·Meta의 늦은 정산·전환/보고 수정은 자동 반영되지 않을 수 있다. 모든 업무 조회는 원천별 마지막 성공 시각·수집 대상 날짜·누락 경고를 제공하며, 수집 당시 snapshot을 최종 확정 수치로 표시하지 않는다. 비용·호출량·작업 시간은 10에서 측정하고 한도를 넘으면 부분 publish 없이 중단한다.
- Cafe24 하루 관찰 버전의 nullable `providerUpdatedAt`·`fetchedAt`·보호 내용 지문과 동일일 재실행은 로컬 및 실제 격리에서 검증했다. 실제10/1은CSV shadow 보존 후 하루API primary로 명시 전환했고 matched-only 쿠폰 추정·원가 계산·실패 및 인증 복구가 검증됐다. 캐시 최신성은미검증 경고로 유지하며 과거 수정의 자동 발견을 보장하지 않는다. 환불 반영 순매출은 별도 nullable v2로 보류하며 그 필드의 미제공을 v1 자체의 실패로 취급하지 않는다. **관찰시각을 공급자 수정시각으로 대체하지 않는다.**

## v1.3 — Cafe24 옵션 업무 키의 실증 범위

이 절은 두 날짜의 초기 실증 이력이다. 미래 날짜별 CSV/옵션/C·R parity를 요구하던 문장은 v1.6의 전량 품목 정책·상태/형식/매핑·전체 snapshot 검증으로 대체했다. 옵션 문자열 형식과 충돌 검사는 유지한다.

- `didadi0729/shop1`의 2026-09-21 전량 287주문·318품목과 2026-09-30 전량 348주문·378품목을 비발행 HMAC으로 대조했다. 두 조회일 모두 주문·품목 identity 전건 일치, `product_no`/수량/CSV `판매가`와 API `product_price` 각각 **696/696 품목 일치**, CSV `주문상품명(옵션포함)`과 API `product_name + '(' + option_value + ')'` **696/696 품목 일치**다. API `product_price + option_price`는 672/696만 일치하므로 CSV 판매가로 채택하지 않는다. 이 결과는 해당 몰·두 날짜의 관찰 증거이며 Cafe24 전체 또는 미래일의 보편적 포맷 보증이 아니다. 이 초기 날짜별 후보 게이트는 v1.6으로 교체했다. 새 완료일은 승인된 몰/옵션 정책 아래 전체 응답·조합 충돌·내부 매핑을 다시 검사한다.
- 사용자는 2026-10-01 KST에 이 몰에서 구매자가 옵션을 자유 입력할 수 없고 판매자가 정의한 드롭다운만 선택하며 옵션에 따라 원가가 달라진다고 확인했다. 지정 몰의 `api.optionName`은 위 문자열을 **원문 그대로 조합**해 기존 CSV 업무 키와 `Cafe24ProductMatcher`의 옵션 원가 규칙에 전달한다. 주문자·수령인 식별정보는 요청·저장하지 않는다. `option_value`가 누락/null/빈 값, 문자열 양끝 공백, 제어 문자 또는 합성 결과514자 초과이면 `FIELD_UNSUPPORTED`로 중단한다. 초기256자 조합 제한은10/7 실제 입력의 길이 진단을 근거로514자로 보완한다. 미래일의 날짜별 CSV 증거 요구는 폐기했으며 전체 옵션 형식·충돌·매핑 검사를 유지한다. 다른 몰/숍은 별도 대조 전 중단한다.
- 조합 문자열은 일반적으로 원본 두 문자열에 대해 단사 함수가 아니다. 한 날짜 전체 스냅샷에서 `(productNo, optionName)`이 서로 다른 `(product_name, option_value)`로 만들어지면 `RECONCILIATION_FAILED`로 중단한다. 이 검사는 날짜 간 충돌이나 과거 전체의 옵션 원가 규칙 동등성을 증명하지 않는다. API primary는 명시한 하루만 전환하고 v1.6의 해당 하루 검증·원천 선택 계약을 따른다.
- 실제 Orders 응답에서는 주문 `updated_date`/`order_status`가 없고 `payment_method`는 배열이다. 취소·환불 원본 금액과 provider 캐시 신선도는 미확정이다. 당시 C/R 품목의 대상일 CSV parity를 요구했지만, v1.6은 알려진 상태의 전량 품목·원래 수량/판매가를 포함한다. 실 관찰 코드 집합을 독립 검토한 뒤 명시 허용하고 미확인 코드는 중단한다. 상태를 환불 반영 순매출로 해석하지 않는다. `order_date` 또는 관찰시각을 `providerUpdatedAt`으로 대체하지 않는다. v1.3의 변경시각 창 목표는 v1.4 자동 경로에서 폐기했다. 현재 실계정의 자동 canonical publish·source 전환 근거는 아직 없고, v2 순매출은 `null/PENDING_RECONCILIATION`, 기존 CSV primary는 유지한다.

## 1. 불변 의미와 범위

- 자사몰 매출 원천은 Cafe24 하나다. Meta/Google의 전환매출은 참고 지표이며 합산 매출이 아니다. Meta 광고 행과 광고세트 행은 비용에서 한 번만 센다. Google 미매핑 비용은 공통 미배분으로 남긴다.
- 내부 계정 키는 `provider + externalAccountId + shopKey`이다. `provider=CAFE24`는 `mallId + shopNo`(현재 `didadi0729/shop1`), `GOOGLE`은 하이픈 없는 광고 고객 ID + `shopKey=default`, `META`는 비즈니스 ID를 계정 속성으로 보유한 광고계정 ID + `shopKey=default`를 쓴다. 숫자처럼 보이는 ID도 문자열이다. 다른 계정의 동일 주문/캠페인/광고 ID는 다른 키다.
- 업무 키는 Cafe24 `accountId + orderNo + lineOrderNo + productNo + optionName`(각 trim, 상품번호의 `.0` 정규화), Google `accountId + metricDate + campaignId`, Meta 광고 `accountId + metricDate + campaignId + adsetId + adIdentityKey`, Meta 광고세트 `accountId + metricDate + adsetId`다. Meta의 ID 없는 구 CSV는 기존 synthetic/name key를 유지하되 **단일 계정으로 명시 결속**하고 ID 있는 API 행과 자동 이름 매칭하지 않는다. 충돌·이름 변경은 검토 큐다.
- 일자는 계정 원본 시간대의 calendar date다. 현재 확인된 세 대상은 `Asia/Seoul`; Google/Cafe24는 KRW, Meta는 USD다. 계정 통화·시간대 변경 감지 시 publish 중단, 과거 데이터의 당시 값 보존. 통화/시간대가 다른 계정은 원본 조회만 허용하고 공통 일별 합산은 변환·일자 정렬이 검증될 때까지 `INCOMPATIBLE_SCOPE`다.
- 금액 저장은 원본 단위 그대로 한다. Google `costMicros: BigInt`(JSON decimal string), Cafe24 KRW `Decimal(18,2)`, Meta USD `Decimal(18,4)`. JS Number를 변환/누적 중간형으로 쓰지 않는다. Google 비용 표시만 `costMicros / 1_000_000`이며 통화의 최소 표시 단위에서 한 번 반올림한다. USD→KRW는 기존 `ExchangeRate`의 적용일·원천·fallback을 기록하고 환율이 없으면 KRW 합계/MER를 `null`로 둔다.
- 매출 `legacyRevenueKrw`는 현재 `sales-metrics.service.ts`와 `cafe24-sales-calculator.ts`의 `revenueKrw` 정의다. 유효·current·완전 업로드 품목 중 매핑된 상품의 **원가 규칙 판매가 또는 상품 override × 수량**(1+1 bundle 규칙은 기존 배수 처리), 규칙 없으면 CSV 판매가 fallback이다. `totalPaidKrw`는 현재 품목 행별 값을 별도로 합산한다. 같은 주문 총결제액이 품목마다 반복되면 현재 합계가 부풀 수 있으므로 다품목 표본으로 검증해야 하며, API 투영에서도 기존 표시값을 조용히 재정의하지 않는다. 쿠폰은 `총 주문금액 - 총 결제금액`과 `결제수단`/쿠폰 규칙을 통해 추정되어 margin에서 별도 차감된다. `revenueKrw` 자체에서 쿠폰을 빼지 않는다. 기존 CSV에는 주문 상태·취소/환불 금액·시각이 없고, 코드에도 이를 반영한 순매출 계산이 없다. 따라서 `legacyRevenueKrw`를 **순매출이라고 부르지 않는다**. 과거 환불은 별도 입력이 없었다면 기존 매출에 반영되지 않았고, 재업로드로 품목 자체가 수정된 경우만 현행 current 값에 반영됐을 수 있다. 실제 과거 업무 수치와의 정량 감사는 미실시다.
- 새 `reconciledNetSalesKrw`는 별도 nullable v2 지표다. 정의는 동일 주문 범위의 실제 결제액에서 **확인된** 환불액을 차감한 금액이며 배송비·세금 포함 범위, 할인 중복 여부, 부분 취소의 품목 배분은 실계정 샘플로 결정하기 전 `null/PENDING_RECONCILIATION`이다. v1 화면·보고서의 `revenueKrw`를 자동 교체하지 않는다. 전환은 대표 주문/부분환불/쿠폰 샘플 대조, 기간 병행 집계, 차이 원인·허용 오차, 사용자 승인 및 명시적 새 metric version 이후에만 한다.

## 3. 저장 모델과 공개 계약

이름과 타입은 03 이후 additive migration의 목표다. `id`, 내부 `*Id` FK, `ownerRunId`, `last*RunId`, `changedByUserId`, `actorUserId`는 UUID(`@db.Uuid`), provider 외부 ID·`shopKey`·`unitKey`·`requestKey`·`credentialRef`·`checkpointValue`·코드는 `String`(길이 상한 256, checkpoint 512), `*Date`는 `@db.Date`, `*At`/`expiresAt`/`deadlineAt`은 `timestamptz`, `version`/`attempts`/`*Count`/`*Fetched`/`*Published`는 `Int`(별도 BigInt 지정 우선), `enabled`/`isCurrent`는 Boolean이다. 금액은 별도 지정이 없으면 `Decimal(18,2)`, 원본 수치/카운트의 예외는 행에 표시한다. enum은 CHECK/Prisma enum, `connectionId` FK는 `ON DELETE RESTRICT`다. nullable로 적힌 항목만 nullable이며 credential 참조는 연결 전 `null` 허용. 2. 기존 CSV 업로드는 계속 받는다. API가 primary인 기간의 CSV는 검증/보관/비교만 허용하며 current 업무값을 조용히 덮지 않는다. 보정 요청은 `source`·기간·충돌 정책·이유를 명시해야 한다. `SKIP/OVERWRITE/NEW_VERSION`은 기존 CSV 이력에만 적용하고 API 재조회는 새 version + current pointer를 원자 갱신한다. 동일 requestKey 재실행은 기존 run 반환. 수동 보정 후 예약 재조회는 보정이 명시적으로 해제되기 전 자동 대체하지 않는다.
3. Google은 계정×날짜 모든 페이지와 계정 합계를 검사한 완전 스냅샷만 publish한다. 이전 current 캠페인이 새 완전 응답에 없으면 비활성화하되 이력을 보존한다. 정상 0은 접근·페이지·계정합계 검증 후 `COMPLETE_ZERO`; 인증/중간 페이지 실패는 기존 current 유지, coverage의 last attempt만 FAILED/PARTIAL. Meta는 광고/광고세트 전체 페이지·동일 요청 reporting time/windows·행별 실제 attribution 및 조건부 null/이유·계정 기본 지표 합계를 검증한 뒤 해당 계정×날짜의 광고 current와 광고세트 집계를 **한 트랜잭션**으로 바꾼다. 광고와 광고세트 비용을 더하지 않는다. 재조회가 2026-09-28 수치를 바꿀 수 있으므로 version history와 fetchedAt을 남긴다.
4. Cafe24는 완료된 전일 주문일 **하루의 완전 snapshot**만 목표로 한다. 주문·품목의 전체 페이지/건수와 두 번째 목록·품목 내용 재검사를 통과하고, 선택한 금액/상태 의미·캐시 최신성 미검증 경고·CSV 원천 충돌 검사가 계약대로 처리된 경우에만 하루 current/version/coverage를 함께 갱신한다. 현 실응답에는 주문 `updated_date`가 없으므로 공급자 변경시각 checkpoint 경로는 실행하지 않는다. 하루 전량 재조회와 보호 내용 지문은 그 시점의 관찰 차이만 찾으며 provider 변경시각·캐시 신선도·오래된 변경 전건 발견을 증명하지 않는다. 취소/환불 상태·금액도 실증 전 추정하거나 0으로 채우지 않는다. API 응답에 빠진 주문을 곧바로 삭제하거나 0으로 만들지 않고 완전성 실패면 기존 성공 current를 보존한다. 과거 날짜는 자동 조회하지 않으며 명시적 수동 하루 재실행 때만 별도 대조한다.
5. 모든 provider는 fetch/검증을 트랜잭션 밖에서 하고, 제한된 크기로 staging 후 lease generation 재확인·source policy 버전 확인·행/coverage/RunUnit/checkpoint 갱신을 짧은 트랜잭션으로 묶는다. 실패·stale lease는 기존 성공 current를 보존한다.
6. rollback은 먼저 `enabled=false`/정책을 CSV로 되돌리고 읽기 projection을 구버전으로 바꾼다. 새 데이터/이력은 유지한다. 이미 API primary 중 입력된 CSV가 없던 날짜는 `NOT_COLLECTED`로 드러나며 **과거 CSV 값을 만들어 복원하지 않는다**. 필요하면 원본 CSV 재업로드 또는 검증된 API snapshot 재승격을 별도 run으로 한다.

## 5. HTTP·권한·운영 상한

- `POST /api/source-connections`와 `PATCH /api/source-connections/:id/policy`: `settings.manage`; account allowlist, provider, externalAccountId, shopKey, 통화/시간대, `fromDate`, `primarySource`, `reason`, optimistic `expectedVersion` 필수. credential 원문은 요청·응답에 포함하지 않는다.
- `POST /api/sync-runs`: `imports.manage`; `{connectionId,fromDate,toDate,mode:"MANUAL"|"BACKFILL",requestKey,reason?}`. 세 원천 모두 관리자가 **완료된 하루를 명시**해야 하며 `fromDate=toDate`; 미래·당일·다일 요청은 거부한다. 단일 계정, run 비동기 202 Accepted. 수동 재조회도 같은 endpoint와 lease를 쓴다. `GET /api/sync-runs/:id`, `GET /api/source-coverage?connectionId&from&to`, `GET /api/source-connections`는 `data.read`. 응답은 last attempt/status와 last success/coverage를 따로 보여준다.
- `POST /internal/daily-sync`는 브라우저 사용자 권한을 받지 않는 예약 전용 machine guard: 좁은 scope의 서버 secret, replay 방지 requestKey, 격리/운영 target guard, rate limit. `SYSTEM` audit event에는 `actorType=SYSTEM`, `actorUserId=null`, run ID/request ID를 기록한다. 수동 작업은 실제 사용자 ID를 기록한다.
- 안전 오류 코드: `SOURCE_SELECTION_REQUIRED`, `ACCOUNT_SCOPE_MISMATCH`, `CURRENCY_MISMATCH`, `TIMEZONE_MISMATCH`, `FIELD_UNSUPPORTED`, `ATTRIBUTION_MISMATCH`, `PARTIAL_PAGE`, `RECONCILIATION_FAILED`, `LEASE_LOST`, `RUN_LIMIT_EXCEEDED`, `PROVIDER_AUTH_REQUIRED`, `PROVIDER_RATE_LIMITED`, `PROVIDER_UNAVAILABLE`. provider 원문·토큰·PII를 오류에 넣지 않는다. 400/409은 입력·정책 충돌, 403은 권한, 429은 제한, 502/503은 provider/일시 실패다.
- 날짜별 최대 10,000 Google 캠페인 행, 50,000 Meta 광고 행, Cafe24 전일 10,000 품목을 초기 보수 상한으로 두고 초과 시 실패하며 무제한 메모리 적재 금지. Cafe24 예약/수동 1일, Google·Meta 예약 7일·수동 1일, 동시 heavy operation 1개, Prisma connection limit 3 유지. API 호출당 deadline 20초, run 최대 10분, lease 2분과 generation 재검증, 재시도는 네트워크/429/5xx 최대 3회·Retry-After/jitter·남은 예산 내. 주간 7일이 한 run의 예산을 넘으면 08에서 **같은 주간 trigger 안의 일별 bounded runs**로 분할 검증하고 실패 시 부분 publish/과거 범위 확대를 금지한다. 숫자는 10단계 부하 실측 후 버전 갱신한다.
- 실행 이력 요약/coverage/업무 행은 보존하고, 비밀·PII 없는 상세 진단 로그는 90일, request ID는 90일 보존한다. Cafe24 매일 02:00 KST 기동·전일 1일 02:30 완료를 초기 SLA로 둔다. Google·Meta는 계정 현지 완료일 기준 7일마다 1회 기동하고 날짜·완료시각은 08/10의 격리 부하 실측으로 확정한다. 실패 날짜는 자동 따라잡지 않으며 coverage 경고와 관리자의 명시적 수동 1일 복구로 처리한다. Meta Limited의 정기 운영 허용량은 현재 **미확정**이다.

## 7. 단계별 실증 게이트

- 03/04: 신규 모델·FK/partial unique·겹침 제약을 additive로 만들고, 구버전 읽기/쓰기와 CSV 삭제·복원 회귀를 확인한다. 순서는 (A) 구코드가 무시하는 새 테이블/nullable 열, (B) source off 상태의 구코드 호환 읽기·쓰기 projection, (C) 격리 dry-run/backfill·검증, (D) 격리 API source 승격, (E) 구버전 쓰기 경로가 안전해진 후 제약 강화다. 01~10에는 이를 운영 배포하지 않는다. 구 행의 account binding은 01에서 확인한 **단일 대상 계정이라는 근거**, 원본 batch 기간, 고유 키 충돌 조사, dry-run 건수/해시, 승인된 binding manifest를 거쳐 chunk backfill한다. 모호한 행은 `UNBOUND`로 남겨 조회 제외/검토; 임의 다중 계정 병합 금지. 신규 FK는 nullable → backfill → 검증 → 신규 행에 필수 → 구 행 제약 강화 순서. 새 테이블은 기존 `meta_ads` schema의 runtime/migration role grant와 RLS/Data API 차단, anon/authenticated/Vault 무권한을 재현한다. `SourceCredential`의 암호문은 API 업무 행과 분리하고 Cafe24 토큰 갱신 경쟁·응답 유실·저장 실패를 테스트한다.
- 05: Google 실제 API·GAQL 지원 버전/필드, 계정 합계, 빈 날, 페이지, KRW/KST를 격리 조회로 검증한다. keyless 인증 경로가 01에서 미확정이므로 완료 전 수집 GO 불가.
- 06: Cafe24 callback·테스트 설치 후 주문/품목/결제/할인/취소/환불/변경시각 필드의 접근 및 의미를 대표 샘플로 대조한다. 제공되지 않는 필드는 `UNSUPPORTED`로 유지하고 net v2를 활성화하지 않는다.

## 2026-10-15 — 08 신규 격리 관찰의 제한 확장 및 복구 검토

이 추가 계약은 08의 새 관찰과 이후 검증할 구현에 적용한다. 위 07의 기존 실증·원문·발행 결과·부모 구매값이 제공된 관찰의 증거를 수정하거나 재분류하지 않는다. 계약 수용, 구현·합성 테스트 통과, 실제 예약 재개·발행 성공은 각각 별개다. 이 절을 작성한 시점에는 아래 변경의 실제 설정 적용·복구 발행 성공을 주장하지 않는다. 새 CSV 제출을 요구하지 않으며 Meta 구매 건수·구매금액 필수와 영상 요청 제외를 유지한다.

### Cafe24: 실제 관측한 N00만 명시 검토

08의 2026-10-14 주문일에 대한 제한 수동 진단에서 현재 `2026-09-01` API의 품목 상태 `N00`를 실제 관측했고, 기존 승인 8개 코드 밖이어서 상태 승인 관문이 중단됐다. [Cafe24 공식 공지](https://developers.cafe24.com/cs/front/notice/35)는 N00를 입금전으로 설명하며, [2026-06-01 공식 예약 조회 문서](https://apidocs.cafe24.com/en/docs/2026-06-01/admin/get-reservations)도 awaiting payment로 열거한다. 이는 해당 코드 정의의 교차 근거이며 현재 Orders Items 전체 스키마의 독립 검증으로 확대하지 않는다. 이전 버전 문서 주소가 최신 소개 페이지로 이동하는 것만으로 N00 필드 정의를 검증했다고 표시하지 않는다.

v1.6의 주문일 전량 주문·품목 계약에 따라, 지정 새 격리 연결의 명시 승인 상태 집합을 기존 8개에서 **N00만 더한 9개**로 변경하는 계획을 수용한다. 입금전이라는 이유로 주문·품목을 제외하거나 수량·판매가·주문금액을 0으로 바꾸지 않는다. 원래 API 수량·`product_price`와 nullable 결제·미확정 결과의 출처를 보존한다. 다른 N/E 코드나 미관측 코드는 자동 승인하지 않는다. 전체 snapshot·두 번 읽기·옵션 충돌·매핑·정책·리스·활성화 관문은 유지한다.

### Meta: 계정 관측값에서 내려가는 paired-null 부모의 0 잔차 증명

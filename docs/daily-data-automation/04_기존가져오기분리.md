목표: API가 기존 업무 저장·버전·집계를 재사용하도록 만들면서 CSV의 기존 결과를 유지한다.

## 범위와 작업
- [ ] Cafe24UploadsService와 MetaAdDailyImportService/MetaAdsetImportService의 파일 검증·파싱, canonical validation, business write, 원본 보관·삭제 이력 경계를 분리한다.
- [ ] CSV 경로는 그대로 공통 import service를 호출한다. API 전용 정규화 레코드도 동일 저장 경로를 호출할 수 있게 한다. API 결과를 가짜 CSV/Multer 파일로 위장하는 구현은 최종 구조로 삼지 않는다.
- [ ] CSV 파일 hash와 API business key/revision의 중복 개념을 구분한다. source/sourceAccount/runId/importVersion·SYSTEM attribution을 보존한다.
- [ ] 기존 Meta original storage pending/restore/purge/version 및 current 집계를 유지한다. API에 파일 원본이 없음을 명시하며 가짜 Storage 참조를 생성하지 않는다.
- [ ] Cafe24 매칭·쿠폰 계산·이전 current 버전 전환·rawRow 개인정보 제거를 유지한다. 배치 삭제/복원 기능이 API 수집 결과에 잘못 적용되지 않도록 source별 정책을 구현한다.
- [ ] CSV와 API의 동시 실행·수동 override가 같은 계정/날짜의 version을 꼬이게 하지 않도록 공통 write lock/fence와 source policy를 적용한다.
- [ ] 기존 계정 미지정 자료의 귀속 backfill을 운영 미실행 script/계획으로 준비한다. 모호한 자료는 별도 unresolved 상태를 둔다.

## 완료 검증
- [ ] 동일 기존 fixture에 대해 refactor 전후 정규화 행·KPI·현재 버전·중복 처리·오류 메시지의 의도된 동등성을 증명한다.
- [ ] SKIP/overwrite/실패 후 재시도, CSV/API 경쟁, Meta 광고→광고세트 집계 중복 없음을 검사한다.

## 실제 실행 순서
- [ ] 예약은 아직 비활성 상태로 유지한다. 잠깐 작동하다 다시 끄는 임시 운영 Cron을 만들지 않는다.
- [ ] 검토된 additive migration을 운영에 적용한다. production migrate dev/db push/reset 금지. 구버전 앱 정상 조회·쓰기와 DDL 지연을 즉시 검증한다.
- [ ] 검증된 동일 이미지와 운영 설정을 준비하고 feature/수집 flag는 off로 시작한다. 이것은 완성 릴리스의 전환 절차이며 개발 중 조기 배포가 아니다.
- [ ] Railway 실제 health와 보호 readiness가 올바른 release SHA/fingerprint를 반환한 후보만 전환한다. 기존 서비스가 준비 전 중지되지 않는 검증된 방식만 쓴다.
- [ ] 기존 로그인/Meta·Cafe24 CSV/쿠팡 조회/핵심 KPI/Storage의 비파괴 운영 smoke를 수행한다. 업무에 보이는 가짜 주문/광고 데이터를 넣지 않는다.
- [ ] 보호된 운영 credential·callback을 연결하고 실제 계정 metadata를 확인한다. staging token 공유로 refresh 회전이 충돌하지 않게 staging 예약을 먼저 안전하게 중지한다.
- [ ] source policy 전환을 계정·기간별 manifest에 기록한다. 이 시점의 최신 운영 current 데이터와 업무 writes를 기준으로 한다. 개발 시작 당시 snapshot을 덮어쓰지 않는다.
- [ ] 공통 수집 경로로 작은 실제 기간을 운영 적재하고 대조한다. 기존 데이터와 신규 API를 중복 집계하지 않는다. 문제가 생기면 전체 자동화 활성화 전에 중지/rollback한다.
- [ ] 세 원천 모두 정상임을 확인한 뒤 정해진 cutoff 정책과 UI를 활성화한다. cutoff 이전 자료는 기존 CSV 원천으로 유지하고 자동 과거 적재는 시작하지 않는다. 필요한 이전 날짜는 별도 검토 후 하루씩 수동 처리한다.
- [ ] Cafe24 매일 전일 1일, Google·Meta 각각 7일마다 직전 완료 7일의 전용 Cron·동일 범위 제한 재시도·미실행 점검 job만 고유 이름으로 등록/활성화한다. 과거/월 보정 job은 만들지 않는다. 기존 Storage job 개수·내용·시각은 불변인지 검사한다.
- [ ] 외부 예약 호출 경로의 인증 거부·정상 호출·구조화된 결과를 확인한다. 이후 실제 02:00 실행은 12가 관측한다.

## 장애 시
전용 자동화 예약 pause 및 kill switch → in-flight publish drain/fence → 승인된 원천 policy/current 복구 → 필요시 이전 이미지로 복귀한다. 신규 Google 표·로그·migration은 유지한다. 최근 사용자 변경과 다른 정상 source 데이터는 보존한다.
old image가 신규 데이터 의미를 이해하지 못하면 10에서 검증한 pointer/version 복구를 먼저 수행한다. 무조건 이미지 rollback만 하면 된다고 가정하지 않는다.
복구 후 기존 업무 smoke와 마지막 정상 데이터 기준을 기록하고 상태를 FAILED/NO-GO로 돌린다. 한 source 실패를 숨긴 채 전체 배포 완료로 보고하지 않는다.

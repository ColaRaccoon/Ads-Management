# 01 기준선과 데이터 계약

## 목표와 필수 읽기

실제 상품명·판매단위·매출·비용·원천 선택 기준을 확정해 이후 세션들이 서로 다른 계산을 구현하지 않도록 한다. 선행 단계는 없다.

먼저 [시작 안내](00_시작안내.md), [공통 규칙](공통_작업규칙.md), [전체 설계](../../제품별_통합성과측정_코드수정계획서_20261027.md)를 읽는다. `research/`의 스키마·권한 결과는 조사 당시 증거이며 현재 상태를 필요한 범위만 다시 확인한다.

## 이번 단계 작업

- Git 기준선과 기존 변경을 기록하고 제품별 신규 기능이 이미 생겼는지 확인한다.
- 기존 프로그램들의 고정 기준 제품명과 이름 규칙을 추출한다. 예시 문자열을 실제 제품이라고 꾸미지 말고 실제 이름을 가진 대표 제품과 단품/세트 표본을 고른다.
- 계정·스토어·판매처 범위와 쿠팡의 계정 미식별 자료를 확인한다. 이름 충돌과 옵션 조건을 정리한다.
- 원천 보유기간·최근 누락·매핑/원가 완전성을 계정·날짜별 제한된 읽기로 조사한다. 이전 20초 타임아웃 쿼리를 그대로 반복하지 않는다.
- Meta·Google·Cafe24·쿠팡·네이버의 하루/7일 대조표를 준비한다. 공통 구간이 없으면 그 사실과 가능한 구간을 적는다.
- 매출, 쿠폰, 취소·반품, VAT, 배송, 가구매, 미배분 비용, 환율, 날짜 기준, 세트 수량의 산식을 확정한다. 등록 비용 기준 추정이익과 실결제액을 구분한다.
- 공통 어댑터 입력/출력, Decimal 경계, 품질 상태, 원천 추적, 이름/계산 버전, API 응답 초안을 구체적인 필드 단위로 확정한다.
- 전용 네이버 읽기 역할의 최소 테이블, 격리 DB 준비 방식, 운영 역할 변경 계획을 작성한다. 실제 운영 권한 변경은 하지 않는다.

## 필수 병렬 분담

서브에이전트 A는 현재 앱의 판매/광고/원가를, B는 네이버의 JSONB·그룹·이름·공통비를 조사한다. 주 에이전트가 업무 계약을 통합하고 독립 검토를 맡겨 누락과 중복 산식을 확인한다. 조사와 계약 문서의 파일 소유권을 나눈다.

## 완료 조건과 인계

각 원천의 이름 취득 경로, 자동 분류 원칙, 판매단위 비용, 광고 전/후 이익, 공통비, 기간 비교, 완전성, 갱신 계약이 필드와 산식으로 명시되어야 한다. 실제 데이터로 확인한 것과 제안/미확정을 구분한다.

이후 구현을 좌우하는 업무 결정이 남으면 질문을 구체화하고 완료로 표시하지 않는다. 독립적으로 조사 가능한 영역은 계속 진행한다. 사소한 구현 선택 때문에 중단하지 않는다.

`records/01_확정계약.md`와 `records/01_결과.md`를 작성하고 진행표를 갱신한다. 후속 단계는 계약 버전을 참조한다. 제품 코드 구현 전체를 이 단계에서 시작하지 않는다.

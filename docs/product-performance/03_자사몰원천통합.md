# 03 자사몰 원천 통합

이 세션은 Meta·Google 광고비와 Cafe24 판매를 통합 집계용 사실 데이터로 변환한다. 화면이나 최종 제품 손익을 만들기 전에, 자사몰 매출이 한 번만 계산되고 광고비가 별도 금액으로 보존되는 상태를 완성한다.

## 시작 전 읽기

- [시작 안내](00_시작안내.md), [공통 작업규칙](공통_작업규칙.md).
- [마스터 계획서](../../제품별_통합성과측정_코드수정계획서_20261027.md)의 제품명 분류, 매출 중복 제거, 이익 계약, 완전성과 갱신 절.
- [01 확정 계약](records/01_확정계약.md), [02 결과](records/02_결과.md).
- 현재 작업 트리와 적용되는 AGENTS.md. 기존 미커밋 변경과 진행표 상태를 확인한다.

선행 조건은 02의 완료 기록과 사용할 공통 계약·이름 resolver·판매단위 모델이다. 사용자 세션 순서는 03 → 04 → 05이며, 세 어댑터 단계 사이에는 논리적 선행 의존성이 없다. 02 산출물이 누락되면 임의의 대체 계약으로 구현하지 않고 누락을 기록한다.

## 목표와 이번 범위

1. Meta 광고세트 일별 비용, Google 캠페인 일별 비용, Cafe24 판매행을 공통 계약으로 변환한다.
2. 원천 이름을 02의 resolver로 판정한다. 외부 상품/캠페인 ID 변경 때문에 수동 재연결을 요구하지 않는다.
3. 판매단위별 매출·원가·쿠폰을 계산하고 광고비 차감 전 구성요소를 반환한다.
4. 계정·업무 날짜·원천 버전·규칙 버전·금액 출처·누락 상태를 보존한다.

수정 대상 제안은 `apps/api/src/unified-performance/adapters/`의 `meta.adapter.ts`, `google.adapter.ts`, `cafe24.adapter.ts`와 각각의 검증 파일이다. 실제 파일명은 02에서 정한 계약을 우선한다. 원천 DB 변경, 수집기 개편, 운영 권한 변경, 최종 집계 발행과 화면 구현은 이번 범위가 아니다. 구현 검증은 격리 환경에서 수행한다.

## 참고 코드

- `apps/api/src/common/source-read-policy.ts`: 계정·기간별 API/CSV 선택과 현재 원천 정책.
- `apps/api/src/storefront/storefront-read.service.ts`: 선택 원천, coverage, 환율, 알려진 금액과 완전한 합계 구분.
- `apps/api/src/google/google-read.service.ts`, `google-campaign-matcher.ts`, `google-sale-configuration.ts`, `google-performance.ts`.
- `apps/api/src/sales/sales-metrics.service.ts`, `domain/cafe24-matcher.ts`, `domain/cafe24-sales-calculator.ts`, `domain/cafe24-coupon-matcher.ts`.
- `apps/api/prisma/schema.prisma`: 현재 버전, 주문행 키, 광고세트 일별 금액, 캠페인 micros, 환율 및 적용기간 필드.

## 구현 규칙

- Meta 비용은 선택된 광고세트 일별 데이터로 집계한다. 개별 광고 비용을 추가 합산하지 않는다. USD 원금액과 적용 환율·환율 날짜·KRW 결과를 함께 반환한다.
- Google 비용은 원통화의 `cost_micros / 1,000,000`을 정확하게 계산하고 필요한 환율을 적용한다. 캠페인명으로 제품을 판정하며 전환매출은 실제 판매 매출 합계에 넣지 않는다.
- Cafe24는 원천 선택 정책을 통과한 현재 주문행을 한 번만 사용한다. Google 보고서용 매출과 Cafe24 보고서용 매출을 서로 더하지 않는다.
- 주문번호만으로 서로 다른 몰/원천을 묶지 않는다. 주문행 키·버전·계정 범위를 보존하고, 동일 제품명의 서로 다른 주문은 각각 유지한다.
- 주문 쿠폰은 상품 필터 적용 전에 필요한 주문 전체 문맥에서 계산·배분한다. 이미 반영된 쿠폰을 재차 차감하거나 필터마다 주문 쿠폰 전액을 반복 배정하지 않는다.
- `[유튜브]` 등 기존 판매 설정의 가격·원가는 기준 제품명 + 판매단위/옵션 이름 + 적용기간 계약으로 해석한다. 상품번호가 바뀌어도 같은 이름·단위면 규칙이 적용되어야 한다.
- 단품·1+1·세트의 수량과 판매가격·원가는 각각 유지한다. 설정 판매가 기반 운영매출과 수집 결제액을 구분하며 미확인 환불을 반영한 실결제 순매출이라고 표시하지 않는다.
- 원가·매핑·환율·수집 상태가 미확정이면 원인과 알려진 부분 금액을 보존한다. 누락을 0으로 채우지 않는다. 실제 수집 완료 0건과 구별한다.
- 공통 계산 추출이 필요하면 기존 화면 동작을 먼저 기준선으로 확보한다. 기존 서비스 전체를 재작성하지 않고 최소 범위로 추출한다.

## 필수 병렬 분담

주 담당자는 최소 2명의 서브에이전트를 사용하고 처음에 계약과 파일 소유권을 공유한다.

| 담당 | 독립 소유 범위 | 제출 내용 |
| --- | --- | --- |
| 서브에이전트 A | Meta·Google 어댑터와 해당 검증 파일 | 비용·환율·micros·이름 변경·중복 원천 대조 |
| 서브에이전트 B | Cafe24 어댑터와 해당 검증 파일 | 판매단위·쿠폰·매출 중복 방지 대조 |
| 주 담당자 | 공통 계약 변경 조정, 서비스 추출, 모듈 연결, 통합 검증 | 두 결과 통합과 기존 보고서 회귀 확인 |

공통 schema, 타입, 모듈 파일은 주 담당자만 수정한다. 서브에이전트는 필요한 계약 변경을 제안하고 다른 담당 파일을 동시에 수정하지 않는다. 완료 후 서로의 경계 사례를 검토하도록 한다.

## 완료 검증

1. 01에서 선정한 제품과 기간의 하루·7일·30일 결과를 원천 선택 기준과 함께 대조한다. 확보하지 못한 기간은 검증했다고 기록하지 않는다.
2. 같은 상품명·판매단위에 새 상품 ID/캠페인 ID를 부여해도 자동 분류와 비용 규칙이 유지된다. 이름 충돌은 미확정으로 남는다.
3. Meta 광고세트/개별 광고 중복, API/CSV 중첩, Google micros·환율 누락을 검증한다.
4. Cafe24의 여러 상품 주문·쿠폰·세트·같은 이름의 다른 주문·Google 판매 설정에서 금액이 한 번만 반영된다.
5. 기존 Meta·Google·Cafe24 결과와 비교하고 차이를 금액 및 산식으로 설명한다. 의도하지 않은 회귀를 해소한다.
6. 어댑터별 판매액/비용과 미분류 금액 합이 선택 원천 금액을 보존한다. 전체 통합 손익이 아직 없다는 이유로 이 검증을 생략하지 않는다.
7. 변경에 필요한 타입·계산·격리 DB 검증을 실행하고 실제 명령, 결과, 실패 및 미검증 범위를 기록한다.

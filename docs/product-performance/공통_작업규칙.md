# 제품별 통합 성과측정 공통 작업규칙

## 작업 범위

사용자가 지정한 단계 하나만 수행한다. 선행 단계의 DONE 기록과 산출물을 확인하고 해당 단계의 완료 조건까지 구현·검증한다. 다음 단계는 새 세션이 맡는다. 이전 세션 대화에 의존하지 않도록 결과를 파일에 남긴다.

작업 시작 시 적용되는 AGENTS.md, Git 상태, 관련 코드와 설치된 패키지 버전을 확인한다. 기존 미커밋 수정·삭제·사용자 문서를 임의로 되돌리거나 덮어쓰지 않는다. Next.js 작성 전 `apps/web/AGENTS.md`의 설치 버전 문서 지침을 따른다. 필요한 스킬은 해당 작업에 맞춰 읽는다.

## 반드시 유지할 업무 기준

- 고정 기준 제품명과 이름 규칙으로 자동 분류한다. 플랫폼 상품 ID가 바뀌어도 같은 이름/판매단위라면 수동 재연결 없이 처리한다.
- 외부 ID는 원천 참조·중복 수집 방지에만 사용한다. 같은 제품명인 여러 주문을 한 건으로 지우지 않는다.
- 제품과 판매단위를 분리해 단품·세트·옵션별 가격/원가를 보존한다. 이름 유사도만으로 여러 후보 중 하나를 임의 확정하지 않는다.
- 판매처 실적과 광고 매체 비용을 분리한다. Cafe24 매출을 Meta/Google 보고서별로 중복 합산하지 않는다.
- 광고·쿠폰·가구매·배송비·VAT는 한 번만 반영한다. 직접 귀속과 공통비 배분을 구분하고 금액 보존을 검증한다.
- 미수집·미매핑·원가 미입력을 0으로 만들지 않는다. 확인된 부분 금액과 완전한 총액을 구분한다.
- 이름 규칙·원가·환율·원천 정정으로 과거 결과가 바뀌면 버전과 영향 범위를 추적한다.
- 기존 화면의 계산 정책을 통합 작업에 편승해 바꾸지 않는다. 필요한 공통 함수 추출은 변경 전후 결과를 대조한다.
- 관측 관계를 인과효과로 단정하지 않는다. 통합 총이익은 분석용 광고 매체 필터에 따라 바뀌면 안 된다.

## 필수 병렬 작업

각 단계는 주 에이전트와 최소 2개의 서브에이전트를 사용한다. 구현·조사·독립 검증 중 서로 독립적인 작업을 동시에 진행한다. 단순히 에이전트를 생성한 사실만으로 병렬 검증을 완료했다고 하지 않는다.

주 에이전트가 먼저 범위·공통 타입·API 계약·파일 소유권을 정한다. 서브에이전트에 입력, 산출물, 수정 가능 경로, 검증 기준을 명시한다. `schema.prisma`, 공통 타입, 모듈 등록, 메뉴 등 충돌하기 쉬운 파일은 한 담당자만 수정한다. 독립 파일 구현을 마친 뒤 통합한다.

구현 담당과 검토 담당을 구분하고 주 에이전트가 검토 지적을 해결한다. 의존 작업과 운영 변경은 순차 처리한다. 운영 배포·마이그레이션을 여러 에이전트가 동시에 실행하지 않는다. 서브에이전트 기능을 사용할 수 없으면 그 사실을 기록하고 병렬 작업을 했다고 주장하지 않는다.

## 환경과 검증

01~10은 조사·코드·격리 DB 검증·배포 준비 단계다. 운영 DB 조사는 읽기 전용이고, 운영 스키마/권한/예약/배포 변경은 11단계에서 준비된 범위로 수행한다. 격리 테스트가 관리 조회로 우회되거나 운영 환경에 실행되지 않도록 실제 연결 대상을 검증한다. 네이버 원천은 읽기 대상으로 유지한다.

비밀값·주문 개인정보를 코드, 화면, 결과 기록에 남기지 않는다. 원천 입력은 필요한 필드만 추출한다. 권한은 실제 런타임 역할에서 검증하며 관리 역할의 성공을 대신 쓰지 않는다.

검증은 변경에 맞춰 실행한다. 금액 보존, ID 변경 후 이름 분류, 원천 중복 제거, 날짜·비율 경계, 실패 복구, 권한을 우선한다. 실제 존재하는 명령을 확인하고 타입/스키마/빌드 검증을 수행한다. 미래 실행이나 아직 없는 실데이터 검증을 성공으로 적지 않는다. 의미 없는 반복 테스트보다 발생한 실패와 불확실성을 해결한다.

## 인계 규칙

`진행표.md`는 NOT_STARTED → IN_PROGRESS → DONE으로 관리한다. 외부 조건 때문에 중단되면 BLOCKED와 필요한 조건을 적는다. 조건부 12는 DEFERRED로 시작한다. 한 세션이 끝났다는 이유로 DONE으로 바꾸지 않는다.

각 단계 결과는 `records/NN_결과.md`에 다음을 남긴다.

1. 단계·작업일·상태와 실제 기준 커밋/작업 트리 상태.
2. 결정한 업무 계약과 변경 이유. 공통 계약 변경 시 영향 단계와 재검증 결과.
3. 변경 파일, DB 변경 파일, feature flag와 환경 구분.
4. 병렬 담당·소유 파일·독립 검토 지적과 해결 결과.
5. 실행한 검증 명령과 결과·미실행 이유·증거 경로.
6. 완료 조건별 통과/실패/미확인, 잔여 작업, 다음 세션의 정확한 시작점.

01은 추가로 `records/01_확정계약.md`를 작성한다. 06은 통합 API/집계 계약을, 10은 배포·복구 계획을 기록한다. 단계별 결과를 읽으면 이전 대화나 모든 과거 기록을 다시 읽지 않아도 이어갈 수 있어야 한다.

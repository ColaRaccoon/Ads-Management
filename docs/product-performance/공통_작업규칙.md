# 제품별 통합 성과측정 공통 작업규칙

## 작업 범위

사용자가 지정한 단계 하나만 수행한다. 선행 단계의 DONE 기록과 산출물을 확인하고 해당 단계의 완료 조건까지 구현·검증한다. 다음 단계는 새 세션이 맡는다. 이전 세션 대화에 의존하지 않도록 결과를 파일에 남긴다.

작업 시작 시 적용되는 AGENTS.md, Git 상태, 관련 코드와 설치된 패키지 버전을 확인한다. 기존 미커밋 수정·삭제·사용자 문서를 임의로 되돌리거나 덮어쓰지 않는다. Next.js 작성 전 `apps/web/AGENTS.md`의 설치 버전 문서 지침을 따른다. 필요한 스킬은 해당 작업에 맞춰 읽는다.

## 반드시 유지할 업무 기준

- 고정 기준 제품명과 이름 규칙으로 자동 분류한다. 플랫폼 상품 ID가 바뀌어도 같은 이름/판매단위라면 수동 재연결 없이 처리한다.
- 외부 ID는 원천 참조·중복 수집 방지에만 사용한다. 같은 제품명인 여러 주문을 한 건으로 지우지 않는다.
- 제품과 판매단위를 분리해 단품·세트·옵션별 가격/원가를 보존한다. 이름 유사도만으로 여러 후보 중 하나를 임의 확정하지 않는다.
- 판매처 실적과 광고 매체 비용을 분리한다. Cafe24 매출을 Meta/Google 보고서별로 중복 합산하지 않는다.
- 광고·쿠폰·가구매·배송비·VAT는 한 번만 반영한다. 직접 귀속과 공통비 배분을 구분하고 금액 보존을 검증한다.
- 미수집·미매핑·원가 미입력을 0으로 만들지 않는다. 확인된 부분 금액과 완전한 총액을 구분한다.
- 이름 규칙·원가·환율·원천 정정으로 과거 결과가 바뀌면 버전과 영향 범위를 추적한다.
- 기존 화면의 계산 정책을 통합 작업에 편승해 바꾸지 않는다. 필요한 공통 함수 추출은 변경 전후 결과를 대조한다.
- 관측 관계를 인과효과로 단정하지 않는다. 통합 총이익은 분석용 광고 매체 필터에 따라 바뀌면 안 된다.

## 필수 병렬 작업

각 단계는 주 에이전트와 최소 2개의 서브에이전트를 사용한다. 구현·조사·독립 검증 중 서로 독립적인 작업을 동시에 진행한다. 단순히 에이전트를 생성한 사실만으로 병렬 검증을 완료했다고 하지 않는다.

주 에이전트가 먼저 범위·공통 타입·API 계약·파일 소유권을 정한다. 서브에이전트에 입력, 산출물, 수정 가능 경로, 검증 기준을 명시한다. `schema.prisma`, 공통 타입, 모듈 등록, 메뉴 등 충돌하기 쉬운 파일은 한 담당자만 수정한다. 독립 파일 구현을 마친 뒤 통합한다.

구현 담당과 검토 담당을 구분하고 주 에이전트가 검토 지적을 해결한다. 의존 작업과 운영 변경은 순차 처리한다. 운영 배포·마이그레이션을 여러 에이전트가 동시에 실행하지 않는다. 서브에이전트 기능을 사용할 수 없으면 그 사실을 기록하고 병렬 작업을 했다고 주장하지 않는다.

## 환경과 검증

01~10은 조사·코드·격리 DB 검증·배포 준비 단계다. 운영 DB 조사는 읽기 전용이고, 운영 스키마/권한/예약/배포 변경은 11단계에서 준비된 범위로 수행한다. 격리 테스트가 관리 조회로 우회되거나 운영 환경에 실행되지 않도록 실제 연결 대상을 검증한다. 네이버 원천은 읽기 대상으로 유지한다.

비밀값·주문 개인정보를 코드, 화면, 결과 기록에 남기지 않는다. 원천 입력은 필요한 필드만 추출한다. 권한은 실제 런타임 역할에서 검증하며 관리 역할의 성공을 대신 쓰지 않는다.

검증은 변경에 맞춰 실행한다. 금액 보존, ID 변경 후 이름 분류, 원천 중복 제거, 날짜·비율 경계, 실패 복구, 권한을 우선한다. 실제 존재하는 명령을 확인하고 타입/스키마/빌드 검증을 수행한다. 미래 실행이나 아직 없는 실데이터 검증을 성공으로 적지 않는다. 의미 없는 반복 테스트보다 발생한 실패와 불확실성을 해결한다.

## 인계 규칙

단계 종료 시 아래 **단계별 Git 기록과 원격 반영** 절차까지 수행한다. 코드 구현과 원격 업로드는 별도로 확인하며, 사용자가 지정한 단계 작업에는 해당 단계 결과의 커밋·개발 브랜치 푸시를 포함한다. 매 단계마다 같은 푸시 허락을 다시 요청하지 않는다. 운영 브랜치 병합·배포는 11단계의 별도 범위를 따른다.

`진행표.md`는 NOT_STARTED → IN_PROGRESS → DONE으로 관리한다. 외부 조건 때문에 중단되면 BLOCKED와 필요한 조건을 적는다. 조건부 12는 DEFERRED로 시작한다. 한 세션이 끝났다는 이유로 DONE으로 바꾸지 않는다.

각 단계 결과는 `records/NN_결과.md`에 다음을 남긴다.

1. 단계·작업일·상태와 실제 기준 커밋/작업 트리 상태.
2. 결정한 업무 계약과 변경 이유. 공통 계약 변경 시 영향 단계와 재검증 결과.
3. 변경 파일, DB 변경 파일, feature flag와 환경 구분.
4. 병렬 담당·소유 파일·독립 검토 지적과 해결 결과.
5. 실행한 검증 명령과 결과·미실행 이유·증거 경로.
6. 완료 조건별 통과/실패/미확인, 잔여 작업, 다음 세션의 정확한 시작점.
7. 작업 브랜치, 포함/제외한 변경 범위, 커밋 제목, Git 상태와 원격 반영 여부. 최종 답변에는 실제 커밋 해시와 원격 브랜치를 명시한다.

01은 추가로 `records/01_확정계약.md`를 작성한다. 06은 통합 API/집계 계약을, 10은 배포·복구 계획을 기록한다. 단계별 결과를 읽으면 이전 대화나 모든 과거 기록을 다시 읽지 않아도 이어갈 수 있어야 한다.

## 단계별 Git 기록과 원격 반영

단계별 복구 지점과 다른 세션의 기준선을 남기기 위해 **각 단계가 끝날 때 커밋하고 원격 개발 브랜치에 푸시한다.** 서브에이전트는 코드와 검증 결과만 전달하고 Git index·commit·push·branch 조작은 주 에이전트 한 명이 담당한다.

### 시작할 때

1. 현재 브랜치, HEAD, upstream, 미커밋/미추적/이미 staged된 변경을 기록한다. 기존 변경을 이번 단계 성과로 간주하지 않는다.
2. 다른 세션이 같은 체크아웃을 사용 중이면 임의로 브랜치를 전환하거나 그 세션의 작업을 커밋하지 않는다. 단계 시작/종료의 Git 변경은 충돌 없이 조정한다.
3. 이 기능의 기존 개발 브랜치가 있으면 이어서 사용한다. 새 전용 브랜치가 필요하고 다른 세션이 쓰고 있지 않다면 `codex/product-performance` 또는 같은 접두사의 용도별 이름을 사용한다. 매 단계마다 브랜치를 새로 만들 필요는 없다.
4. 원격과 대상 브랜치의 배포 연동을 실제 설정으로 확인한다. 브랜치 이름에 `codex/`가 있다는 사실만으로 비배포 브랜치라고 단정하지 않는다. 01~10은 운영 배포를 유발하지 않는 개발 브랜치에 기록한다. 설정을 확인하지 못하면 로컬 커밋과 푸시 대기를 구분하고 필요한 확인 사항을 남긴다.

### 단계가 끝날 때

1. 단계별 완료 검증과 독립 검토를 마친다. 실패를 숨기거나 완료 범위를 임의 확대하지 않는다.
2. 해당 단계 결과와 진행표에 실제 구현·검증 상태를 기록한다. 코드, migration, 필요한 검증 도구와 비식별 증거, 계획/계약 변경을 함께 정리한다. 비밀값·개인정보·대용량 임시파일은 커밋하지 않는다.
3. `git diff`와 `git diff --cached`로 내용을 검토하고 **이번 단계에 속한 파일/변경 부분만 명시적으로 stage**한다. `git add .` 또는 `git add -A`로 다른 세션의 변경까지 일괄 포함하지 않는다. 기존 staged 변경도 확인하고 타 작업의 index를 임의 초기화하지 않는다.
4. 단계 번호와 내용을 드러내는 커밋을 만든다. 예: `docs: 통합 성과측정 01단계 데이터 계약 확정`, `feat: 통합 성과측정 02단계 제품명 분류 기반 구현`. 필요한 수정 커밋이 여러 개여도 되며, 완료 시점의 기준 커밋을 식별한다.
5. 확인한 원격/개발 브랜치를 명시해 일반 push를 수행한다. 새 upstream은 필요한 경우에만 설정한다. 사용자 지정 없이 force push, 과거 커밋 amend/rebase, 원격 이력 삭제를 하지 않는다. 원격 선행 변경이나 충돌이 있으면 일반 병합/동기화로 해결하고 해당 변경에 필요한 검증을 다시 한다.
6. 푸시 종료 상태와 원격 ref를 조회해 목표 커밋이 원격 브랜치에 반영됐는지 확인한다. 로컬 커밋만 존재하거나 push를 시도했다는 이유로 업로드 완료라고 하지 않는다.
7. 최종 답변에 구현 상태, 검증 결과, 브랜치, 실제 커밋 해시, push 성공/실패와 남은 미커밋 범위를 보고한다. 결과 문서 안에 그 문서 자신을 포함한 커밋 해시를 넣으려고 반복 amend하지 않는다. 해시는 최종 보고에 남기고 다음 세션이 시작 시 기록에 보완할 수 있다.

### 완료와 실패를 구분

기존 단계의 구현 상태 DONE을 Git 이력 유무 때문에 거짓으로 되돌리지 않는다. 대신 결과에 Git 상태를 `PENDING`, `COMMITTED`, `PUSHED`로 별도 기록한다. 새 단계의 종료 보고는 구현 완료와 원격 기록 완료를 각각 충족했는지 보여준다. Git 상태를 파일에 갱신한 뒤 추가 문서 커밋을 만들었다면 그것도 푸시하고 최종 답변에는 마지막 원격 반영 해시를 보고한다.

인증·연결·브랜치 보호·배포 연동 미확인으로 푸시하지 못하면 로컬 커밋을 보존하고 원인과 다음 조치를 남긴다. 미완료 단계의 중간 저장이 필요하면 `chore: 통합 성과측정 NN단계 진행 내용 저장`처럼 미완료임을 명시하고 구현 상태는 IN_PROGRESS로 유지한다.

이미 완료했지만 커밋되지 않은 단계는 결과 기록과 diff를 대조해 분리 가능한 변경부터 기록한다. 진행 중인 다른 단계와 같은 파일에서 섞여 있으면 임의로 과거 완료 스냅샷을 만들어내지 않는다. 실제 분리 가능한 범위를 기준으로 커밋하고 포함 단계와 제외 범위를 설명한다. 이 규칙을 추가한 세션이 다른 진행 세션의 구현물을 자동으로 일괄 업로드하는 것은 아니다.

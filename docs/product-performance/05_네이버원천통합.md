# 05 네이버 원천 통합

> 02단계 이후 필수 적용: [플랫폼 선택과 네이버 데이터 정책](플랫폼선택과네이버데이터정책.md). 이 추가 정책은 플랫폼 포함/제외·네이버 정확도에 한해 기존 전체 설계·공통 규칙·01 계약의 상충 문구보다 우선한다. 진행 중인 01 문서와 기록은 변경하지 않는다.

네이버의 기존 업무상 추정 정확도는 허용한다. 실제 정산/매출 정답과의 일치를 완료 조건으로 요구하지 않고, 가져온 입력의 파싱·분류·중복/이중 차감 검증에 집중한다. 네이버 매출·광고·모든 비용을 함께 제외할 수 있게 소속을 보존하고 추정 표시는 수집 실패와 구별한다.

이 세션은 같은 운영 DB의 네이버 JSONB 원천을 통합 계약으로 읽는 어댑터를 만든다. 네이버 상품/주문 수집을 새로 구현하지 않고 이름 기반 분류, 원천 선택, 비용 구성과 완전성 전달을 완성한다.

## 목표와 이번 범위

1. 주문·이름 참조·광고 업로드·광고비·판매단위·비용·동기화 상태를 스토어·날짜 단위로 읽는다.
2. 고정 제품명으로 주문과 광고를 자동 판정하고 네이버 그룹의 부모/자식 중복을 제거한다.
3. 상품 비용과 스토어 공통 배송/가구매 비용을 분리해 공통 계약으로 반환한다.
4. 저장 손익의 신선도, 주문/광고 수집 공백, 계산 불가 상태를 통합 진단으로 전달한다.

수정 대상 제안은 `apps/api/src/unified-performance/adapters/naver.adapter.ts`, 네이버 전용 reader/변환 함수와 검증 파일이다. 네이버 `public` 원천 DB 변경, 수집기/네이버 UI 개편, 운영 권한 부여는 이번 범위가 아니다. 전용 읽기 역할의 최소 권한을 격리 환경에서 검증하고 운영 적용 자료는 후속 단계로 넘긴다.

## 구현 규칙

- 모든 원천은 `public`을 명시하고 타입 검증된 필요한 JSONB 필드만 읽는다. 인증정보 테이블을 읽지 않으며 주문 개인정보/원문 payload를 API나 로그로 반환하지 않는다.
- 주문행에 이름이 생략되어 있으면 `order_source_signatures`에서 복원한다. 참조 ID는 이름을 읽기 위한 수단이며 외부 상품 ID 연결표를 통합 분류 기준으로 사용하지 않는다.
- 광고는 `isActive=true`, `state=CONFIRMED`, `weekdayValidationStatus=PASSED` 업로드와 연결된 비용만 선택한다. 교체·삭제·미확정 업로드는 활성 비용에 섞지 않는다.
- 원천 이름·별칭·옵션을 02의 resolver에 전달한다. 기존 ID 기반 보조 매핑을 복제하거나 재등록 상품마다 수동 연결을 요구하지 않는다.
- 주문은 스토어·원천 상품주문 키·현재 판매상태와 업무 날짜를 보존한다. 기존 기준인 `SALE` 및 결제일 해석을 01 계약과 대조한다. 취소/반품 금액을 중복 차감하지 않는다.
- 부모 그룹 합계와 자식 상세를 동시에 더하지 않는다. 그룹 직접 광고비는 한 번만 기록하고 여러 통합 제품에 걸치면 미배분 비용/명시적 배분 대상으로 남긴다.
- 상품매출·원가·수수료·기타비용·업무상 VAT는 구성요소로 반환한다. 비용 적용일·스냅샷/개별 설정 우선순위를 현행 코드와 대조한다. 없는 원가를 명시적인 0원과 구별한다.
- 스토어 배송수입·배송비와 `daily_fake_purchases`는 제품 귀속 정보가 없는 공통 금액으로 보존한다. 임의 제품에 전액 차감하거나 모든 제품에 반복 반영하지 않는다.
- 저장 손익의 계산 버전과 시각을 기록하되, 비용/매핑 지문 부재나 원천 정확도 한계만으로 사용 가능한 값을 모두 폐기하거나 전수 재계산하지 않는다. 저장 결과 또는 기존 계산 규칙으로 얻는 값을 추정 표시와 함께 제공한다. 단위·그룹 중복 등 통합 변환에 필요한 범위만 대조하며 원천 정답을 증명하기 위한 수집기 개편은 하지 않는다.
- 주문행이 없다는 이유로 완료 0건을 만들지 않는다. 스토어·날짜별 동기화와 광고 업로드 상태, 변경 수집 공백, 계산 시각을 함께 반환한다. 오래된 주문의 반품이 모두 최신이라는 가정은 하지 않는다.
- 전체 DB snapshot을 화면 요청마다 로딩하거나 로컬 네이버 저장소를 런타임 import하지 않는다. 어댑터는 제한된 조회와 버전 관리되는 변환 함수로 구성한다.

## 필수 병렬 분담

최소 2명의 서브에이전트를 사용하고 SQL reader의 테이블 범위와 파일 소유권을 먼저 정한다.

| 담당 | 독립 소유 범위 | 제출 내용 |
| --- | --- | --- |
| 서브에이전트 A | 네이버 주문·이름 복원·판매/비용 변환과 해당 검증 | 이름 변경, 판매상태, 비용 이력, 상품 구성요소 |
| 서브에이전트 B | 광고·업로드 선택·공통비/coverage 변환과 해당 검증 | 교체 업로드, 그룹 광고비, 배송/가구매, 수집 공백 |
| 주 담당자 | 어댑터 조합, 권한 경계, 공통 계약과 통합 대조 | 일관된 읽기, 금액 보존, 기존 네이버 계산 대조 |

공유 reader·타입·모듈은 주 담당자가 소유하거나 테이블별 파일로 분리한다. 네이버 참고 저장소를 함께 수정하지 않는다. 각 담당의 구현 완료 후 다른 담당이 중복/누락 경계 사례를 검토한다.

## 완료 검증

1. 01 기준 제품·스토어의 확보 가능한 표본으로 채택한 네이버 입력과 통합 변환 결과를 대조한다. 실제 정산액/실매출 정답과 일치시키거나 모든 하루·7일·30일 구간의 정확도를 입증하는 것은 완료 조건이 아니다. 기존 추정 오차와 새 구현 버그를 구분하고 미확인 범위를 기록한다.
2. 외부 상품/옵션/캠페인 ID 변경 후에도 같은 제품명·판매단위는 자동 처리된다. 이름 누락 복원과 서로 다른 주문의 보존을 검증한다.
3. 부모/자식 그룹, 그룹 직접 광고비, 미매칭 광고비에서 합계가 원천과 일치한다. 재업로드/교체/삭제/0건 정정에서 이전 비용이 잔존하지 않는다.
4. 원가 누락·명시 0원·적용일 경계·수수료 fallback·가구매·배송 공통비를 대조한다. 등록되지 않은 상품 비용을 0원으로 간주하지 않는다.
5. 저장 손익 구버전/시각·지문 부재·동기화 공백을 설명하고, 읽을 수 있는 추정값과 실제 미수집/계산 불가를 구분한다. 추정 표시만으로 전체 집계를 막지 않는다. 네이버 OFF 시 네이버 구성요소와 그 누락 경고가 선택 결과에서 빠져야 한다.
6. 격리 DB에서 필요한 SELECT만 허용되고 원천 UPDATE/DELETE·인증정보 접근은 거부되는지 확인한다. 실제 쿼리 범위·시간·행수와 실패 복구를 기록한다.
7. 변경에 필요한 타입·계산·격리 DB 검증을 실행하고 코드 계약과 실제 데이터 대조가 각각 어디까지 완료됐는지 구분한다.

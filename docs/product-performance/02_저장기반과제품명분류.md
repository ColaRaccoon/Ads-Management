# 02 저장 기반과 제품명 분류

## 목표와 선행 조건

고정 제품명 자동 분류와 이후 어댑터/집계가 사용할 저장 계약을 구현한다. 01 DONE과 확정 계약이 필요하다.

[시작 안내](00_시작안내.md), [공통 규칙](공통_작업규칙.md), 전체 설계의 3·4·8·9절, `records/01_확정계약.md`, `records/01_결과.md`를 읽는다.

## 이번 단계 작업

- `UnifiedProduct`, 이름 규칙, 자동 판정 결과, 판매단위, 배분, coverage, 집계 실행과 일별 사실 모델을 01 계약에 맞춰 추가한다. 계획상의 모델명을 무조건 모두 별도 테이블로 만들기보다 확정 계약의 책임·제약을 보존한다.
- 원천별 어댑터 공통 타입, repository 경계, 금액/날짜/품질 타입을 구현한다. 통합 집계 작업 자체는 06에 남긴다.
- `domain/product-name-resolver.ts`에 이름 정규화, 정확 이름/별칭/포함·제외어, 옵션 조건, 기간, 충돌 판정과 근거 기록을 구현한다.
- 기존 이름 규칙 이관 자료와 미리보기 검증을 만든다. 외부 상품 ID를 필수 입력 또는 캐시 키의 유일 기준으로 삼지 않는다.
- 이름·판매단위·배분 규칙의 CRUD/미리보기/감사·권한 기반을 만든다. 07은 이를 사용하는 UI를 맡는다.
- 배분 총합, 동일 범위 중복/충돌, 버전 변경, 낙관적 동시 수정 검사와 입력 검증을 구현한다.
- 신규 migration은 저장소 절차에 맞춰 생성하고 격리 DB에서 적용·재적용 상태·복구를 검증한다. 기존 네이버 테이블을 Prisma 소유로 편입하지 않는다.

## 필수 병렬 분담

서브에이전트 A는 이름 분류기와 단위 검증, B는 repository/관리 API를 담당한다. 주 에이전트는 공통 타입과 schema/migration을 단독 소유하고 통합한다. 다른 담당자가 이름 충돌·ID 변경·권한을 독립 검토한다.

## 완료 조건

- 플랫폼 ID 변경에도 같은 이름/판매단위가 동일하게 분류된다. 같은 ID의 이름이 달라지면 과거 판정을 잘못 재사용하지 않는다.
- 공백·기호·숫자·용량·세트·유사한 이름을 처리하며 서로 다른 제품의 정규화 충돌을 검출한다.
- 새 ID 수동 등록 없이 기존 이름 규칙을 적용한다. 미분류/복수 후보는 원인과 함께 남긴다.
- 규칙 미리보기는 데이터를 쓰지 않으며 변경 권한 없는 사용자의 저장은 거부한다.
- 기존 모델과 화면을 깨뜨리지 않고 스키마/타입 검증이 통과한다.

`records/02_결과.md`에 공통 타입 위치, migration, 관리 API, 규칙 버전, 테스트와 어댑터 구현 시작점을 남긴다. 운영 migration/권한 적용은 11단계다.

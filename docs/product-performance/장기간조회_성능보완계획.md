# 장기간 제품 성과 조회 성능 보완 계획

작성: 2026-10-30 KST. **계획 작성 완료 / 구현·성능 목표 검증 전**.

이번 전체 제품 연결 후속 작업과 별개로 실행할 성능 개선 계획이다. 12단계 조건부 효과 추정은 계속 DEFERRED다. 이 문서를 작성하면서 운영 SQL·인덱스·요금제·배포·권한을 변경하지 않는다.

## 1. 기준선과 문제

현재 운영 코드는 `44cd2a54ccbb351c92d3ece9fd6722481a80ae66`이며 Railway 1 CPU / 1 GB, report pool 3 / worker pool 2다. 보고서의 READ ONLY / REPEATABLE READ 스냅샷에만 20초 상한을 적용했고, 원천 reader 및 기본 transaction의 5초 상한은 유지했다.

이번 연결 범위는 기존 풀업바 포함 **124개 대표 제품·판매단위 설정**, 실제 광고·상품 제목에 대한 신규46개 NAME 규칙, 2026-02-26~10-29의 246일 달력 범위, 기존 현재 발행 범위를 포함한 **830개 원천·계정·날짜 구간**이다. 제품 수는 상품군 수가 아니며 단품·세트 구분을 유지한 수다. 구간별 실제 데이터 유무·시작일은 다르다. 등록·재집계의 최종 성공 여부는 [전체 제품 연결 결과](records/11_전체제품연결.md)와 해당 증거를 따른다.

| 구분 | 관측 / 한계 | 근거 |
| --- | --- | --- |
| 풀업바 170일 조회 | summary 6,252ms, options 6,270ms, diagnostics 6,276ms, timeseries 6,380ms; 다음 페이지 3,534ms; relationships 2,843ms. 모두 HTTP200 | `research/11-history-http-final.json`; 이전 단회 관측이며 p95가 아님 |

현재 repository는 `to_jsonb(r)`로 전체 집계 run을, `jsonb_agg(f.payload)`로 선택 범위의 전체 fact payload를 큰 JSON frame에 담는다. 필요한 필드보다 큰 checkpoint·설정·상세 객체를 읽는 비용과 DB JSON 생성·전송·애플리케이션 해석 비용을 분리해서 측정해야 한다.

현재 timeseries는 서명된 커서가 있어도 전체 스냅샷을 먼저 읽고 애플리케이션에서 페이지를 자른다. DB OFFSET 문제로 단정하지 않는다. 다음 페이지가 같은 전체 frame과 계산을 반복하는 구조가 문제다. 네 대시보드 요청은 진행 중인 frame만 공유하며, 완료된 결과를 페이지·후속 요청 간 재사용하지 않는다.

## 2. 지켜야 하는 계약

- 돈은 기존 정밀 decimal 문자열과 산식을 유지한다. 부분합 `knownTotals`, 완전합 `completeTotals`, 확인된0·미수집·원가 누락·추정값을 구별한다. 누락을0으로 만들지 않는다.
- 제품명·판매단위·묶음 수량·플랫폼별 유효기간과 원가·환율·가구매·배송·공통비 정책을 유지한다. 다른 플랫폼의 비용을 빌리지 않는다.
- 원천·계정·날짜 전체의 검산과 미분류 잔액을 보존한다. 제품 필터가 미분류 금액을 임의 배분하지 않는다. Cafe24 매출에 Meta·Google 전환매출을 중복 합산하지 않는다.
- 같은 화면의 요약·그래프·진단·후속 페이지는 같은 발행 run 집합과 설정 버전에 근거한다. 공개 중인 포인터가 바뀌면 혼합하지 않고 명시적으로 재조회한다.
- 기존 수집기·예약·원천 데이터·이름·비용 설정·공유 권한을 수정하지 않는다. 최소 권한 실제 report/worker 역할을 사용하고 RLS·권한 경계를 우회하지 않는다.
- 인과효과로 확대 해석하지 않으며 기존 관계 분석의 통계·제외·부적합 판정도 유지한다.

## 3. 실행 순서와 완료 조건

### P0. 재현 가능한 측정과 가벼운 옵션 조회

1. 새 124개 설정과 현재 830개 구간 발행 후 작업이 없는 시점의 기준을 고정한다. release/configuration/publication fingerprint, 선택·비교 기간, 실제 fact/run 수, 허용 계정 범위와 응답 크기를 기록한다.
2. DB 실행, 전송, JSON 해석, hydrate/계산, 응답 직렬화, 네트워크, 브라우저 그리기를 따로 측정한다. 민감 원문·주문·토큰을 로그에 남기지 않는다.
3. 옵션은 허용된 제품명·플랫폼·계정·가용 날짜·버전 정보만 조회하는 metadata 전용 경로로 분리한다. 금융 frame·금액 계산·coverage 전체 해석이 필요 없어야 한다. 현재 응답 계약을 조용히 바꾸지 않고 별도 DTO/명시된 경로와 프런트 사용처를 함께 검증한다. 기존 등록 제품과 허용 범위의 과거 발행 제품명은 계속 선택할 수 있어야 한다.

완료 조건: 옵션 경로의 쿼리가 금액 payload·checkpoint를 읽지 않음, 권한·필터·가용 날짜·과거 이름 동일, 30/90/180/246일의 응답 크기와 실행시간 전후 기록. 쿼리·HTTP 시간을 구분하고 실제 p95 측정 전에는 단회 시간을 p95로 쓰지 않는다.

### P1. 필요한 필드·집계 결과만 읽기

1. 요약·시계열·진단에서 실제 사용하는 run/fact/coverage 필드를 목록화한다. 전체 `to_jsonb(r)`와 사용하지 않는 checkpoint·설정 복제를 제거하고 필요한 projection만 읽는다. 기간·허용 계정·제품 조건을 DB에서 적용한다.
2. 요약·차트의 원천·날짜·제품별 집계는 DB에서 필요한 grain으로 줄인다. JSON payload 전부를 읽어 합산하는 경로와 기존 계산 결과를 대조한다. SQL SUM의 null 처리, 확인된0, 미분류 잔액, 공통비 중복 및 정밀도는 계약대로 명시한다.
3. 기존 저장 구조로 충분한지 먼저 확인한다. 부족할 때만 통합 영역에 typed 일별 읽기 모델 또는 발행 run 기준 요약 테이블을 제안한다. 가변 포인터만 기준으로 금액을 덮어쓰지 않고 불변 run과 원자 발행에 연결한다. 원천 테이블 변경은 하지 않는다. 신규 migration·역할 권한·롤백은 별도 검토한다.
4. 좁은 SQL을 실제 제한 report 역할의 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`로 확인한다. 실행 행 수·row width·정렬·버퍼·디스크 사용·선택도와 실제 전송 시간을 구분한다. 인덱스 후보는 발행 run과 product 필터의 복합 인덱스 등으로 제한하고 기존 인덱스와 비교 후 결정한다. 큰 JSON payload를 그대로 INCLUDE하는 인덱스는 기본안으로 삼지 않는다.

완료 조건: 같은 발행 버전의 구/신 결과가 원천·날짜·제품별로 정확히 일치하고, 전체 제품 장기간 조회가 payload 상한·P2028 없이 통과한다. 실제 쿼리 계획과 읽기·전송량 감소 증거를 남긴다. 인덱스가 빨라질 것이라는 추정만으로 운영 DDL을 실행하지 않는다.

### P2. 같은 스냅샷의 재사용과 실제 페이지 제한

1. 화면 최초 조회가 허용된 불변 run 집합·설정 버전·선택 hash를 고정한다. 요약·차트·진단·후속 페이지가 이 버전을 사용하게 한다. 요청마다 접근 권한을 확인하고, actor/권한·허용 scope·제품·기간·비교·grain·버전이 다른 결과를 공유하지 않는다.
2. 완료된 결과의 크기·개수·TTL을 제한하는 버전 기반 캐시를 검토한다. 진행 중 요청 병합도 유지한다. 발행·설정 변경 시 무효화, 권한 변경 차단, 메모리 제한과 복수 프로세스 간 일관성을 설계한다. 단순 사용자 무관 URL 캐시는 사용하지 않는다.
3. 시계열·진단은 고정 버전에서 안정적인 정렬 키로 DB 집계·페이지 제한을 적용한다. 필요하면 keyset 커서의 버전을 추가하고 변조·선택 변경·발행 변경 시 기존409 재조회 계약을 유지한다. 기존 서명 커서를 버리고 무검증 숫자 페이지로 대체하지 않는다.
4. 누락 날짜를 유지하는 calendar spine, 선택 일/주 grain, 연속7일의 완전성 및 이동평균을 지킨다. 페이지 경계의 계산에 필요한 이전 날짜만 추가로 읽는다. 빈 날짜를 제거해 그래프가 연결된 것처럼 만들지 않는다.

완료 조건: 두 번째 페이지가 전체 금융 frame을 재전송·재계산하지 않으며, 발행/설정 변경·권한 차이·동시 조회에서 누락·중복·다른 사용자 결과 공유가 없다. 스냅샷 고정 때문에 긴 DB transaction을 화면 수명 동안 유지하지 않는다.

### P3. 화면 우선순위와 배포

요약·네 기본 그래프를 먼저 표시하고 관계 분석·긴 진단은 별도 요청으로 읽는다. 선택 변경 시 이전 요청 취소·불필요 중복 요청 방지를 적용한다. 지연·실패·부분 데이터와 실제 빈 데이터를 구별한다. 관계 분석 계산을 생략한 채 정상 완료처럼 표시하지 않는다.

격리 PG17 및 제한 역할 회귀 → 운영 읽기 전용 표본 비교 → 소수 선택의 기능 플래그 배포 → 기간·제품 범위 확대 순서다. 실제 배포 시 불변 release SHA와 readiness, C7 보호 경로/원천 보존 검증, 이전 릴리스 복귀를 확인한다. 신규 읽기 모델은 기능 플래그로 기존 경로에 복귀 가능하게 하고 기존 원천이나 발행 이력을 삭제하지 않는다. 자세한 절차는 `records/10_배포복구계획.md`를 따른다.

현재 지연의 분해 측정 전에는 완료 시간이나 요금제 증설 효과를 확정하지 않는다. 타임아웃 증가, 인프라 유료 증설, 원천 수집 변경만으로 해결했다고 판정하지 않는다. 구현 중 필요한 schema·권한·API 계약 변화가 있으면 구체적 diff와 검증·복구 경로를 먼저 준비한다.

집계 도중 별도로 관측한 쿠팡 source P2028은 조회 p95와 분리해 개선한다. 현재 쿠팡은 READ ONLY transaction 안에서 순수 정규화도 수행한다. 향후에는 같은 스냅샷에서 원천·설정·유효기간 입력을 제한량으로 캡처하고, DB를 다시 읽지 않는 정규화·검산을 transaction 밖으로 옮기는 안을 검증한다. source/default5초를 늘리는 대신 동일 입력·정밀 금액·원자 발행과 실제 제한 역할 회귀를 통과해야 한다. 신규 규칙의 전역 버전 때문에 영향 없는 플랫폼도 재발행하는 비용은 별도 버전 계약 개선 후보이며 이번에 구현하지 않는다.

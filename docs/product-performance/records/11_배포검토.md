## 발견과 보완

운영 `production-reporting.Dockerfile`은 고정 C7 이미지의 API 산출물과 새 TypeScript 산출물을 `verify-source-setup-patch.mjs reporting`으로 대조한다. 기존 reporting 허용 목록에는 신규 `unified-performance` 모듈이 없어, 10까지 구현을 그대로 배포하면 `Unreviewed C7 API change`로 실패한다.

초기 `apps/api/dist/unified-performance`의 **66개 JS 파일**을 소스 역할별로 검토하고 reporting profile에 각각의 정확한 경로를 추가했다. 이후 B의 전용 런타임 DB 클라이언트와 테스트인 `runtime-prisma.js`/`runtime-prisma.test.js`를 각각 검토해 최종 정확 목록은 **68개**다. 기존 tsconfig가 `.test.ts`를 제외하지 않아 배출하는 테스트 JS도 Google의 기존 방식과 동일하게 명시했다. 신규 어댑터/컨트롤러/도우미를 패턴으로 허용하지 않는다. 테스트 파일은 앱 모듈의 import 경로에 없고 배포 시 테스트 runner를 실행하지 않는다. 원래 source-setup profile에는 통합 모듈을 허용하지 않았다.

검토 범위는 계약/십진수/제품명·판매단위/플랫폼·배분·관계 계산, 기존 저장 원천 reader와 어댑터, management/report controller·service·repository·DTO, 큐/불변 발행·별도 worker, Nest 모듈 등록이다. `assertUnifiedEnabled()` 기본 OFF와 `data.read`/`products.manage`/`mappings.manage`/`operations.run`, 조회의 저장 집계 전용 경계를 확인했다. 역할·운영 데이터의 적합성은 A/B와 주 담당 검증 범위이며 이 빌드 목록 확인이 대신하지 않는다.

전용 runtime client는 ON일 때 `UNIFIED_RUNTIME_DATABASE_URL`을 요구하고 기존 앱 DB 사용자 fallback을 금지한다. 동일 host/port/database/명시 meta_ads schema·Supabase pooler의 같은 프로젝트 suffix를 확인하며 실제 로그인 관리자 flag·테이블 소유를 startup에서 거부한다. OFF는 DB에 연결하지 않고 accidental repository 접근도 차단한다. Nest 모듈 내부 override가 기존 화면의 global Prisma를 바꾸지 않는 fixture와 기존 TLS 변환·idle pool 재사용을 소스/테스트로 독립 검토했다. 실역할 상속·실제 GRANT·API의 사용자 권한은 별도 운영 검증이다.

기존 Meta·Cafe24·쿠팡·margin 계산기 해시와 원래 모듈 삭제 감지는 유지했다. 이후 운영 e80을 통합하면서 그 운영 버전이 C7 대비 이미 검토한 mappings 3개 경로도 함께 보존했다. 허용된 경로 안의 의미 변경을 이 경로 목록만으로 검증하는 것은 아니며, 기존 endpoint 보존은 별도 소스 비교·회귀로 확인해야 한다. 그 밖의 mappings helper와 기존 계산기 변경은 계속 거부한다. `app.module.js`는 기존 reporting 목록에 이미 포함되어 있으며 통합 모듈의 추가 import·등록을 확인했다.

## 실제 검증과 한계

`node --test scripts/verify-source-setup-patch.test.mjs` → 병합 후 최종 **10 pass, fail/skip0**(초기9개). 완전한 검토 집합의 허용, 새로운 unified 모듈 거부, 누락/변경되지 않은 필수 모듈 거부, 알 수 없는 mappings helper·재무 코드 변경 거부, 검토한 운영 mappings controller 삭제 거부, 원래 profile의 Google/unified 추가 거부, 기존 모듈 삭제 감지를 확인했다.

검증 코드와 별도로 현재 로컬 compiled 파일 집합을 guard의 신규 정확 목록과 비교했다. 초기66개, B의 전용 runtime client를 포함한 주 담당 최종 빌드 이후에는 양쪽68개로 완전히 같았다. 최종68개 목록과 각 compiled 파일 SHA256, 테스트10개 원문은 `research/11-deploy-guard-result.json`에 보존했다. 이 SHA는 당시 로컬 빌드의 값이며 이후 소스 변경/전체 빌드는 새 산출물을 만들 수 있다.

주 담당의 `unified-stage11-migrate.ps1`도 원격 실행 전에 읽기 검토했다. foundation/report 2개 DDL과 Prisma history 2개 INSERT를 동일 transaction으로 묶고 3초 lock/45초 statement timeout·명시 schema·advisory lock을 사용하는 점을 확인했다. 기존 원천 DML은 없다. metadata 이후 history 변경을 잡는 transaction 내부 name/checksum 집합 일치와 HTTP200 뒤 정확한2개 완료행 대조, HTTP timeout 후 재실행 전 실제 상태 확인을 주 담당에게 보완 요청했다. 기존 btree_gist가 extensions schema에 있음을 반영한 search_path 수정은 운영 환경 차이 대응이며 기존 migration SQL을 임의 변경하지 않는다. 실제 실행은 주 담당만 수행한다.

관리 세션의 owner 역할 전환 wrapper도 추가 검토했다. PostgreSQL17에서는 기존 ADMIN=true/INHERIT=false/SET=false 행과 별개로 현재 grantor의 임시 행을 만들 수 있어 SET FALSE만 되돌리면 새 membership 행이 남는다. 새 loopback PG17의 실제 비관리자 ADMIN fixture로 이를 재현했다(`11-deploy-role-rehearsal.mjs`, `11-deploy-role-rehearsal-result.json`). 주 담당은 기존 supabase_admin grantor 행1개의 정확 사전조건, 임시 self-grant의 ADMIN=false/INHERIT=false/SET=true, owner DDL 후 RESET ROLE와 `REVOKE ... GRANTED BY postgres`, 마지막 원래 전체 membership 행의 oid/grantor/세 옵션 JSON 일치까지 같은 transaction에 넣었다. C는 이 최신 구조가 원상복귀 검증을 수행함을 코드로 확인했다. 실패하면 transaction rollback으로 복구하며, 성공한 운영 상태는 주 담당의 별도 실행·재조회 증거를 따른다.

실제 고정 C7 이미지 안의 baseline을 꺼내 이 변경과 대조하거나 Railway에서 새 Docker 빌드를 실행한 검증은 **미실행**이다. fixture10개 통과를 실제 Docker/Railway 배포 성공으로 확대하지 않는다. 신규 migration/역할·runtime credential·실제 준비 상태·원천 갱신 주기 관측은 주 담당의 운영 적용 순서에 남아 있다.

## 운영 성능 후속 수정의 독립 검토

주 담당은 최초 운영 측정에서 p95가2초를 초과하여 기능을 OFF로 복귀하고 기존 발행을 보존한 뒤, B에게 조회 중복 대기를 줄이는 수정을 맡겼다. C는 `report.repository.ts`와 기존 `report.service.test.ts`의 singleflight diff를 읽기 검토하고 다음을 확인했다.

- repository 인스턴스는 고정된 전용 런타임 역할에 연결되며, 공유 Map은 그 인스턴스 안의 아직 완료되지 않은 Promise만 보존한다. 다른 DB 역할/인스턴스에 공유하지 않는다. 모든 service 호출의 기존 사용자 권한 검사도 먼저 실행된다.
- 키는 당기·전기·실제 lookback, 정규화한 platform·계정 scope·제품, 서버 legacy/Naver 허용목록을 포함한다. `scopeKeys` 생략과 빈 배열은 구별한다. DB 입력에 영향을 주지 않는 응답 grain/page/cursor/분석매체만 키에서 제외한다.
- query 배열과 서버 정책 문자열을 호출 시점에 복사하여 대기 중 선택/환경 변경이 원래 읽기의 범위를 바꾸지 않는다. 성공과 실패 양쪽에서 Map을 비운다. 완료 후 다음 요청은 DB를 새로 읽어 새 설정·발행을 확인한다. 완료된 보고서 결과를 재사용하는 TTL 캐시는 없다.
- 현재 계산 소비자들은 shared snapshot을 변이하지 않는다. deep-freeze·JSON 전후 동등성 회귀가 summary/timeseries/diagnostics/options와 relationships의 공유 읽기를 검사한다. rejected Promise를 처리하지 않는 별도 finally Promise도 만들지 않는다.

`TSX_TSCONFIG_PATH=apps/api/tsconfig.json node --import tsx --test apps/api/src/unified-performance/report.service.test.ts`를 C가 직접 재실행하여 **17 pass, fail/skip0**를 확인했다(신규6개 포함). 신규 모듈 파일은 없어 기존 C7 정확68개 경로가 유지된다. 코드 검토에서 차단 결함은 발견하지 않았으며, 실제 운영 p95·메모리·연결 수의 개선 여부는 주 담당의 새 릴리스·ON 재측정 결과로 판정한다. 과거 운영 실패를 이 단위 회귀 성공으로 덮어쓰지 않는다.

후속으로 B가 여러 Prisma 읽기를 단일 parameterized CTE/JSON frame으로 합친 `report.repository.ts`를 C가 독립 검토했다. SQL 식별자는 고정 schema/table이며 값·목록은 `Prisma.sql` 바인딩으로 전달한다. 판매와 광고 원장을 조인하지 않고 이미 발행된 통합 사실을 읽으며, `source_connections`는 id/provider/display_name3열만 명시한다. 기존 전용 역할의 RLS·읽기 전용 RR·singleflight 경계는 유지한다. 날짜 두 범위의 OR, 허용 계정 선택, 제품과 null 잔액, 구성/사실/coverage/실패의 max+1 한도와 새 발행·stale 판정을 소스로 대조했다.

top-level 모델 날짜만 Date로 hydrate하고 JSON payload를 재귀 변환하거나 금액 문자열을 Number로 바꾸지 않는다. RLS로 연결 run이 보이지 않으면 기존 Prisma 관계 오류 대신 안전한 `UNIFIED_REPORT_REBUILD_REQUIRED`503을 반환한다.

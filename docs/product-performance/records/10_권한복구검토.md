| 명령 | 현재 최종 결과 | 증거 |

| `node scripts/unified-stage10-permissions.mjs` | 실제 configuration/viewer/worker 별도 로그인, HTTP/DB 9 pass, fail/skip0, PG stopExit0 | `research/10-recovery-permissions-result.json` |

각 실행은 새 임시 PG17 클러스터에서 서버 loopback/DB/current_user/version을 확인한 후 전체 migration 58개와 재적용 무변경을 검증한다. 기존 fixture의 고정 식별자를 재사용하지만 이전 클러스터나 원격 DB에 연결하지 않는다. publication은 `127.0.0.1:55451/unified_stage06`, management는 `127.0.0.1:55452/unified_stage07`, 복원은 별도 data 디렉터리와 `127.0.0.1:55458/unified_stage06`다. 가명 운영 캡처도 넣지 않은 순수 합성 입력이다.

9개 management 회귀는 실제 Nest PermissionGuard/DTO/controller/service/DB transaction을 사용하며 외부 인증 principal만 fixture로 제공한다. 미인증/권한거부, 이름 미리보기 무쓰기, 외부 ID 없는 분류·모호성, CAS 동시 수정/오래된 저장 거부, audit 복원, 원가0/null, 비중 검증, 구·신규 영향범위 합집합, rebuild 멱등·실패·재시도·발행을 검증했다.

2개 publication 회귀는 실제 비소유자 NOSUPERUSER/NOBYPASSRLS/NOCREATEDB/NOCREATEROLE writer/API 로그인에서 실행했다. 원천/credential SELECT와 원천 DML 거부, API의 제한된 QUEUED/STAGING INSERT 허용·READY/집계 UPDATE/포인터 쓰기 거부, 무권한 사용자/허용 밖 scope 거부, 원문/lease/credential 미노출을 확인했다. 병렬 claim 1승, 멱등 payload 충돌, 유실 lease 재claim·옛 token fencing, 실패 후 이전100 유지+STALE, 잘못된 coverage/999금액 손상 무발행, read-only RR 포인터 일관성, READY/PUBLISHED 불변,100→120→확정0건 발행을 검증했다. Cafe24는 같은 원천행의 원가60→70, 이름A→B, 매출200→250, 확정0건삭제로 revision1~5를 발행하고 과거 사실/이름계보와 합계를 보존했다.

## 배포·복구 rehearsal

현재 전체 migration 적용과 재적용을 통과한 DB를 정상 중지한 뒤 data 디렉터리를 새 임시 하위 경로로 복제했다. 동일 PG17 binary의 **정상 종료 물리 백업**이다. 원본을 다시 시작하고 `pg_ctl -m immediate`로 비정상 중단·재기동하여 WAL 복구를 확인했다. 이후 복사본을 별도 포트에서 기동했다. 원본/복원 모두 다음 테이블의 정렬 JSON SHA256·행수와 일치했다.

| 보존 대상 | 행수 |
| --- | ---: |
| migration 적용 이력 | 58 |
| 제품/규칙 | 2/1 |
| 집계 실행/발행 포인터 | 13/2 |
| 과거 일별 사실/coverage/이름 audit | 6/18/6 |

복원 후에도 실제 writer/API 역할로 발행 포인터 조회가 정상이며 credential SELECT/원천 INSERT와 API 포인터 UPDATE가 거부됐다. 운영 복귀 절차는 additive schema/발행 이력을 보존하고 기능 플래그와 신규 worker를 정지하는 방식을 우선해야 한다. 공유 DB에서 신규 테이블/원천 삭제나 이전 DB 전체 덮어쓰기를 자동 rollback으로 삼지 않는다.

초기 실행에서 embedded PG의 `pg_dump/pg_restore` 부재 때문에 논리 덤프 단계가 실패했다. 정상 종료 물리 백업으로 바꿔 최종 통과했다. 별도 실행계획 추가 시 `pg` direct 연결의 기본 search_path가 public이어서 포인터 trigger의 관계 조회가 실패했다. Prisma와 같은 `SET search_path TO meta_ads`를 테스트 연결에 명시한 뒤 재실행을 통과했다. 이전 실패를 최종 성공으로 계산하지 않았다. **논리 덤프/복원·교차 PG버전·호스팅 제공자 PITR/스냅샷 복구는 검증하지 않았다.** lease 만료는 owner fixture가 만료 시각을 과거로 바꾸어 실제 repository의 재claim/fencing을 검증한 것이다. OS worker 프로세스를 in-flight transaction 도중 종료하는 시나리오는 수행하지 않았으며 PG 프로세스 immediate 종료 검증과 구별한다.

13개 실행의 작은 합성 fixture에서 실제 writer 역할로 `EXPLAIN(ANALYZE,BUFFERS,FORMAT JSON)`을 기록했다. claim 후보 SELECT 실행0.075ms, 포인터 CAS UPDATE 실행3.441ms다. UPDATE는 transaction에서 rollback했고 백업 전 데이터는 변하지 않았다. 실행계획은 대표 SQL이며 전체 worker 처리량/p95·운영 규모를 입증하지 않는다. publication 회귀2개 전체는 각각525.762ms/380.5562ms였다.

## 재사용 권한 자료와 활성화 차단조건

`scripts/unified-stage10-permissions.sql`을 별도 파일로 추출하여 management fixture에서 **실제 SQL 실행 후** 위9개 회귀를 통과했다. 신규 unified 설정 읽기/설정 INSERT·UPDATE/audit INSERT, 조회 SELECT, 제한 큐 INSERT, worker publication DML을 분리한다. `source_connections`는 실제 reader가 쓰는 id/provider/display_name/currency_code/time_zone5개 열만 SELECT 허용하며 configuration/viewer/worker3개 실제 로그인에서 credential_ref와 external_account_id 조회 거부도 확인했다. 로그인·암호·role membership·원천 SELECT를 부여하지 않는다. 기존 권한이 없는 새 fixture 역할에 적용한 일회성 SQL이며 중복 POLICY 생성 재실행을 허용하지 않는다. SQL transaction은 조건 실패 시 원자적으로 실패한다. 앱 관리 권한명은 제품 `products.manage`, 이름/배분 규칙 `mappings.manage`다.

이 파일의 role명은 `unified_stage07_config/viewer/worker`다. 11은 실제 app/worker 연결과 역할을 매핑하고 기존 상속 권한·소유권·RLS·계정/스토어 범위를 확인해야 한다. 특히 운영 연결에 기존 `source_connections` 테이블 전체 SELECT나 상속 GRANT가 있으면 이번 열별 GRANT만으로 credential_ref 차단이 보장되지 않으므로 effective privilege를 직접 검증한다. 정책의 `USING(true)`는 공유 앱 연결용이며 사용자별/계정별 DB 격리를 주장하지 않는다. 사용자의 허용 계정/스토어와 관리/조회 권한은 실제 HTTP app guard/service가 확인한다. 기존 API가 설정·조회에 같은 연결을 쓰는 경우에도 이 사실을 감추지 않는다.

다음은 **운영 활성화 전 차단조건**이다. 10의 합성 검증 성공으로 자동 충족하지 않는다.

- 운영 `DATABASE_URL`/`UNIFIED_AGGREGATION_DATABASE_URL`이 비소유자·비관리자·별도 역할인지, 실제 해당 역할로 허용/거부/테넌트 범위가 맞는지 확인한다.
- worker의 Meta/Google/Cafe24/쿠팡 `meta_ads` reader와 네이버 `public` reader에 필요한 정확한 SELECT allowlist·RLS를 확정하고 실제 역할로 어댑터를 실행한다. 이 검증의 worker는 합성 batch/adapter를 사용하므로 원천 접근권한을 입증하지 않는다. 특히 `ad-reader.ts`, `cafe24.adapter.ts`, `coupang.adapter.ts`, `naver-reader.ts`의 고정 조회를 기준으로 하며 ALL TABLES 또는 credential 쓰기 권한을 기본 부여하지 않는다.
- 운영 호스팅 방식의 백업을 확보하고 그 방식의 독립 복원·연결 전환·다음 worker lease 처리 절차를 검증한다. 이번 같은 binary 물리 복원으로 관리형 DB PITR를 대체하지 않는다.
- 실제 운영 계정/스토어 allowlist, 최근7일/최초백필 범위, 기존 수집 schedule과 신규 worker 동시성/연결 pool·timeout을 확인하고 feature flag는 그 이후 활성화한다.

네이버 업무상 추정 오차 자체는 이 차단조건이 아니다. 원천 쓰기 권한/예약 변경은 수행하지 않았고, 미포함 네이버를 조회 실패나 품질 저하 원인으로 전파하지 않아야 한다는 정책을 유지했다.

## 교차 검토

B는 주 담당의 `report.service.ts` request-local participation memoization과 timeseries 페이지 선택 후 계산 변경을 읽고 순수 `summarizeReport`가 입력을 변이하지 않음을 확인했다. 조건·스냅샷이 요청 안에서 고정되어 선택 캐시 오염/범위 누수 결함을 발견하지 않았다. A의 정수 마이크로원 기대값 matrix에서 AD unit 반복 factKey 중복을 지적했고 A가 고유 ordinal과 전역 uniqueness assertion을 추가했다. A는 B의 역할 deny/명시적100·120·0 대조/999손상 거부·hash 보존·동일버전 정상종료 물리복원 범위를 독립 검토하여 차단 결함이 없음을 보고했다.

## 어댑터 입출력과 후속 계약

공통 계약 `product-performance-v1.1.0`을 재사용한다. 생성자는 `(PrismaService, UnifiedManagementRepository)`, 진입점은 `read(AdapterRequest): Promise<AdapterBatch>`다. 입력은 한 플랫폼·한 명시 scope, 최대92일, limit1~10000이다. 날짜 cursor `YYYY-MM-DD`로 하루씩 반환한다. 하루가 limit를 넘으면 원천/주문 문맥을 임의 절단하지 않고 명시 오류를 반환하므로 limit 증가 또는 수집 입도 검토가 필요하다.

이름·판매단위·배분·범위 규칙 버전은 같은 RR 트랜잭션에서 읽은 `management.snapshot(tx).versions`와 일치해야 한다. UUID 연결의 provider를 먼저 확인하고, 기존 workspace data.read 권한 내에서만 사용한다. 별도 내부 scope `LEGACY_UNBOUND`는 기존 정책이 허용하는 과거 CSV만 대상으로 한다. 이를 현재 연결로 강제 합치지 않는다. 일별 스냅샷 지문에는 선택 행/원천 정책/계보 및 적용 환율·비용 근거를 포함한다. 새로운 외부 API 호출이나 환율 취득은 없다.

`ControlTotal.measure?`를 후방 호환 선택 필드로 추가했다. 생략은 기존 플랫폼 주 금액이다. 이번 어댑터는 AD_SPEND / OPERATING_REVENUE / REGISTERED_GROSS / SOURCE_LIST_PRICE_GROSS / PRODUCT_COST / DIRECT_SHIPPING_COST / OTHER_DIRECT_COST / VAT_EXPENSE / COUPON을 구분한다. 04/05 기존 필수 필드를 늘리지 않으며 06은 같은 원천·통화라도 서로 다른 measure를 합치지 않아야 한다. 부분 금액은 assignedAmount/unmatchedAmount에 보존하고, Cafe24의 완전한 selectedAmount/difference는 모든 매출 입력이 확인될 때만 제공한다.

StorefrontAdaptersService.read는 플랫폼과 각 범위의 request 목록을 받는다. 같은 플랫폼/범위의 중복 입력은 전체 source read 전에 거부한다. 제외 플랫폼은 어댑터를 호출하지 않는다. 선택 원천별 성공 batch 또는 안전한 SOURCE_READ_FAILED를 반환하며 다른 성공 결과를 지우지 않는다. 실패를 0원 batch로 바꾸지 않는다. 06은 READY/발행에 필요한 완결성·원천 포인터·권한·선택 스냅샷을 추가 구현해야 한다.

## 금액·원천 처리

- Meta는 광고세트 일별만 읽는다. 개별 광고를 합산하지 않는다. USD·저장 일별 FX/날짜·KRW·양자화 전 지문과 소수6자리 잔여를 보존한다. 저장 환율이 없으면 이름으로 유일한 기존 제품 원가 환율 fallback만 출처를 표시해 사용하고, 없으면 KRW null이다.
- Google은 micros 정수문자열을 Decimal로 나눠 원통화와 KRW를 보존한다. 캠페인 이름으로 분류하고 광고전환매출은 referenceConversionRevenue에만 둔다. API 일자 coverage/run unit/source links/version/원금액 대조가 깨지면 비용 사실을 반환하지 않고 관측 행수·PARTIAL·진단을 남긴다. 변경 없는 D-7 reread의 기존 행 run/version 유지와 이후 실패 시 이전 성공 보존은 기존 reader 의미를 유지한다.
- Cafe24는 current·완료배치·원천 선택을 통과한 비오류 주문행을 한 번만 사용한다. ERROR 형제행도 쿠폰 문맥에는 남겨 미완전한 주문을 확정 계산하지 않는다. 같은 이름의 다른 주문은 유지하며 API/CSV·몰/원천 범위를 주문키에 보존한다.
- 판매단위 가격·원가·배송·기타는 계산수량 기준이다. 세트의 실물수량과 계산수량을 구별한다. `[유튜브]`의 유일하고 완전한 Google SALE 4항목 설정을 우선하며 상품번호를 조건으로 삼지 않는다. Google 광고 제외와 무관하게 Cafe24 판매 설정으로 사용한다. 일부 설정·충돌은 임의 혼합하지 않는다.
- 주문 쿠폰을 전체 주문에 먼저 계산·배분하고 운영매출에서 1회 반영한다. CSV 일부 행에만 쿠폰 토큰이 있는 기존 주문의 any(true) 의미를 보존했다. API coupon unknown은 null이다. 수집 주문 결제액은 정렬된 첫 사실에 주문 참조로만 1회 보존하며 제품별 배분액이 아니다.
- VAT는 등록 판매가×0.1×계산수량이며 기존 별도 vatKrw를 재차감하지 않는다. 운영매출과 수집 목록가 fallback은 quality 및 gross 참조 구성요소로 구별한다. 미확인 환불을 반영한 실결제 순매출로 표시하지 않는다. 미확정 비용·쿠폰·매출은 null과 알려진 부분 금액을 유지한다.

## Git 기록

Git 상태는 아래 최종 저장 내역으로 보완한다. 현재 live checkout에 연결된 Railway `grand-fascination` 서비스의 실제 source repo가 ColaRaccoon/Ads-Management, branch가 codex/google-daily-d1-d7임을 읽기 도구로 확인했다. 이 브랜치에 push하지 않는다. 확인한 다른 서비스는 다른 repo/main 또는 Git source 미연결이며 `.github/workflows`는 비어 있다. 별도 개발 ref `codex/product-performance-stage03`에서 이번03 파일만 중간 저장한다.

공통02 파일 types.ts/adapter-contract.ts/unified-performance.module.ts 자체가 시작부터 미추적이므로 기존02 구현을 통째로 이번03 커밋에 넣지 않는다. 그 세 파일 및 진행표의03 변경은 별도 integration patch에 보존한다. 패치는 현재 작업 트리에 이미 적용된 상태다. 02를 별도로 기록한 checkout에서만 `git apply --check`로 먼저 확인 후 적용하며 현재 파일에 중복 적용하지 않는다. 선행01/02 코드·migration·증거와 타 세션 계획 문서는 커밋 대상에서 제외한다. 따라서03 개발 ref의 중간 저장만으로 단독 clean checkout 빌드가 된다는 주장은 하지 않는다. 현재 전체 작업 트리에서 위 검증을 수행했으며 선행02의 별도 Git 기록·통합이 필요하다.

Git 상태 **PUSHED**. 공유 checkout의 브랜치/실제 index를 바꾸지 않기 위해 별도 임시 index로03 파일19개만 명시적으로 stage하고 새 개발 ref에 checkpoint commit을 만들었다. 기존 체크아웃 HEAD와 빈 사용자 index는 유지했다. 커밋 제목은 `chore: 통합 성과측정 03단계 진행 내용 저장`, 코드 체크포인트는 `82a1e34844b14312e566bd1c48f0d1e152031b57`이다.

`git push origin codex/product-performance-stage03:refs/heads/codex/product-performance-stage03` exit0, `git ls-remote --heads origin refs/heads/codex/product-performance-stage03`에서 위 해시 일치를 확인했다. 이 원격 확인 문서만 별도 후속 커밋으로 기록하며 최종 보고에는 마지막 원격 해시를 남긴다. 기존01/02·타 세션 미커밋 파일은 포함하지 않았다. 공통03 변경/진행표는 현재 작업 트리와 integration patch에 보존되어 있으며, 공유 HEAD에서 새03 파일이 계속 미추적으로 표시되는 것은 체크아웃을 바꾸지 않은 결과다. 코드의 remote checkpoint 존재와 작업 트리 표시를 구별한다.

위 3개만 임의 실행하지 않는다. 운영 `_prisma_migrations`와 명세의 **전체 순서**를 비교해 미적용 항목을 확정한다. 그 외 미적용 migration이 발견되면 원래 기능의 변경을 포함하므로 실행을 중단하고 영향·복구를 따로 검토한다. `npm run prisma:migrate`는 개발용 `migrate dev`이므로 운영에서 사용하지 않는다. 운영 후보 명령은 준비한 관리 연결에서 `node node_modules/prisma/build/index.js migrate status --schema apps/api/prisma/schema.prisma`, 확인 후 `migrate deploy`다. URL과 비밀번호는 환경/secret manager로만 주입한다.

공유 DB 영향은 foundation DDL의 테이블/인덱스 생성, Cafe24 열/제약 추가, publication ALTER/trigger DDL 잠금이다. 운영 행수·잠금 시간은 로컬 fixture 수치로 대체할 수 없다. 11에서 기존 수집 작업과 겹치지 않는 변경 창을 잡고 DB `lock_timeout`/`statement_timeout`을 설정해 실패 시 먼저 종료 원인을 확인한다. timeout을 없애 반복 실행하지 않는다.

## 환경·역할과 활성화 사전 조건

| 설정 | 배포 준비값 / 의미 |
| --- | --- |
| `UNIFIED_PERFORMANCE_ENABLED` | API/worker 기본 `false`; UI는 비활성 응답을 안내. 검증한 대표 범위 이후에만 true |
| `DATABASE_URL` | 기존 앱 런타임 연결. 실제 로그인·상속·RLS를 조사하며 관리자 연결로 통과를 대신하지 않음 |
| `UNIFIED_AGGREGATION_DATABASE_URL` | 앱과 다른 전용 worker 로그인. 비소유자 NOSUPERUSER/NOBYPASSRLS/NOCREATEDB/NOCREATEROLE. 필요시 제한된 pool/connection timeout 지정 |
| `UNIFIED_NAVER_ALLOWED_STORE_IDS` | 읽기를 허용한 실제 UUID만 API/worker에 동일 반영. 빈 값이면 허용 스토어 없음 |
| `UNIFIED_REPORT_LEGACY_PLATFORMS` | 기존 기본 `META,CAFE24` 유지. CSV 계보 확인 없이 변경하지 않음 |
| 기존 수집 설정 | `DAILY_SYNC_FEATURE_ENABLED`, SourceReadPolicy·연결·수집 예약을 이번 배포 때문에 변경하지 않음 |

통합 8개 테이블의 조회/큐/설정/worker 권한은 B의 `10_권한복구검토.md`와 `scripts/unified-stage10-permissions.sql`을 따른다. 이 SQL은 새 격리 역할에 한 번 적용하는 검증 artifact이며 반복 POLICY 생성은 실패한다. 운영에서 역할명을 매핑하고 기존 정책/권한을 먼저 대조한다. 보고서에는 설정 SELECT·발행/사실/coverage SELECT·source_connections의 필요한 메타데이터만 필요하다. 큐 INSERT는 STAGING/QUEUED 초기값 제약으로 제한한다. 제품 변경은 `products.manage`, 이름/배분 규칙 변경은 `mappings.manage`, 큐 제출은 `operations.run`, 조회는 `data.read`를 HTTP에서 재확인한다. DB 연결을 가진 모든 사람이 앱 권한을 얻는 것으로 해석하지 않는다.

**운영 활성화 차단:** 실제 앱/worker 역할의 원천 SELECT allowlist와 기존 RLS/상속 권한을 확인해야 한다. worker는 각 어댑터가 사용하는 원천/원가/환율/계보 테이블 SELECT만 받으며 원천 INSERT/UPDATE/DELETE·credential 접근을 거부해야 한다. 네이버의 허용 테이블 목록은 `adapters/naver-reader.ts`의 `NAVER_READ_TABLES`를 사용하고 공유 public 스키마 전체 SELECT를 부여하지 않는다. 기존 원천 RLS를 지우거나 PUBLIC 권한을 바꾸지 않는다. `source_connections`의 비밀 필드까지 읽을 수 있는지 별도 점검한다. 격리용 역할을 운영에 그대로 복사했다고 검증 완료로 간주하지 않는다.

## 11 실행 순서

1. 현재 서비스의 repo·branch·commit·staged 변경, DB identity와 배포 직전 릴리스를 기록한다. 10에서 확인한 Railway Ads-Management 서비스는 `grand-fascination`, `codex/sidebar-scroll`, `e80f7d1f3f6c574caebe16a962c74aca4cf24dfb`, staged=null이다. 10 개발 push로 운영 배포를 실행하지 않는다. 11은 현 설정을 다시 읽어 대상이 맞는지 확인한다.
2. 현재 릴리스 artifact·환경 설정·수집 일정·DB 백업과 복원 가능성을 확보한다. 전체 DB PITR/백업은 공유 DB 담당 정책을 따른다. Cafe24의 별도 이름 재처리가 필요할 때만 해당 변경 행의 두 이름 필드와 키를 접근 통제된 백업에 보관한다. 이 DDL 자체는 이름을 UPDATE하지 않는다. 주문/비밀값을 저장소에 넣지 않는다.
3. 기능 OFF·worker 예약 없음 상태에서 미적용 migration 목록을 검토하고 적용한다. Prisma generate와 API/Web 릴리스를 함께 고정한다. 역할 SQL/원천 allowlist를 실제 대상에 맞춰 검증하고 최소 권한으로 적용한다.
4. 실제 앱 역할로 query SELECT와 거부 동작, 실제 worker 역할로 저장 원천 SELECT/credential·쓰기 거부를 확인한다. 기존 4개 플랫폼 화면의 고정 기간 기준선과 응답을 저장한다. 네이버는 원천 갱신시각과 알려진 추정 한계만 기록한다.
5. 이름/단위/원가가 확인된 대표 제품 1개를 고른다. 초기 백필은 **KST 어제 1일, 명시한 계정 1개**부터다. productNames를 지정해도 `FULL_SOURCE_DAY`라 같은 계정·날짜의 모든 제품과 공통비가 계산됨을 확인한다. 자동 30일 전체계정 백필을 시작하지 않는다.
6. 내부 검증 가능한 범위에서 플래그를 true로 하여 POST `/api/unified-performance/rebuild`에 명시한 platforms/scopeKeys/from/to·계약버전·사유·새 멱등키를 전달한다. HTTP 202는 발행 완료가 아니다. 비밀값을 출력하지 않는 환경에서 `node --import tsx scripts/unified-aggregation-worker.ts --job=<UUID>`로 한 작업씩 처리한다. 별도 검증 환경 없이 true가 모든 조회자에게 노출되는 배포 구조라면, 노출 창을 먼저 확정한다.
7. job PUBLISHED, 원천 control difference=0, 명칭·판매단위·미배분 잔액·기존 화면 금액을 대조한다. 미수집/원가 누락은 null/부분합을 유지한다. 네이버 추정 자체는 차단 사유가 아니며 새 계산 중복·누락·선택 잔존은 차단한다.
8. 1일 통과 후 동일 계정 7일→30일로 확대한다. rebuild 최대 92일, 원천/계정/하루 단위, worker 동시성 **1**로 고정한다. 대규모 요청은 나누고 한 실행 `--limit=100` 이내를 초기 운영값으로 둔다. 재시도는 새 멱등키를 사용한다. 자동 예약은 초기에는 만들지 않는다.
9. UI 전체→네이버 OFF→ON, 빈 선택·광고만·판매만·비교기간·관계분석을 실제 로그인으로 확인한다. 기존 수집 예약을 바꾸지 않은 상태에서 원천 갱신 이후 통합 재집계/새 발행까지 적어도 한 주기를 관측한다. 자동화가 필요하면 수집과 별도인 집계 일정·중복 방지·동시성을 명시해 11 범위에서 적용한다.

## 관측·중단·복귀

최근30일 API별 p95의 초기 목표는 2,000ms다. 합성 로컬 측정 결과와 한계는 `10_UI성능검토.md` 및 `10-performance-metrics.json`을 따른다. 운영 목표 충족 여부는 같은 선택·제품·계정·행수·샘플 수를 기록한 운영 측정으로 판단한다. 앱 RSS, DB 연결 수, 원천/집계 쿼리 시간, lock 대기, FAILED/lease 만료, stale coverage를 함께 본다.

금액 보존 차이≠0, 제외 플랫폼 잔존, 원천/credential 권한 누출, 기존 화면 회귀, 다른 플랫폼을 막는 실패는 즉시 중단한다. 최근30일 p95>2초가 반복되거나 연결 한도/메모리/timeout/기존 수집 지연이 관찰되면 백필 확대를 중단하고 범위·인덱스·처리 비용을 조사한다. 단순 timeout 연장으로 성공 처리하지 않는다.

복귀 순서는 **새 큐 제출 중지 → worker 실행 중지 → 기능 OFF → 기존 검증 릴리스로 앱 복귀**다. DB의 신규 테이블/발행 포인터/불변 과거 run·설정 audit를 유지하고 네이버/Meta/Google/쿠팡/Cafe24 원천을 삭제하지 않는다. 실행 중 transaction은 rollback되며 lease는 만료 후 다시 claim한다. PUBLISHED 행을 수정/삭제하지 않는다. 이전 정상 결과는 실패 다음 조회에서 stale로 남는다. 문제가 있는 이미 발행된 계산은 설정/코드를 고친 새 run으로 교체하고 이력을 보존한다.

정상 롤백은 additive migration을 역삭제하지 않는다. Cafe24의 별도 이름 재처리를 실행한 경우에만 수집/후속 변경과 충돌하는 행을 대조하고 백업의 두 필드만 제한 복구하는 별도 검증을 수행한다. 공유 DB 전체 복원은 다른 앱의 최신 쓰기를 잃을 수 있으므로 기능 롤백 수단으로 사용하지 않는다.

격리 복구 명령은 `node scripts/unified-stage10-recovery.mjs`다. 고정 loopback 새 PG17을 생성하고 migration 반복 적용·역할 검증·중단 후 재시작·백업 복원 대조를 수행한다. 이 절차의 성공은 운영 DB의 PITR/온라인 백업/승계 역할 적용 성공을 뜻하지 않는다. 운영용 백업 수단과 Cafe24 선택 복원은 11 실행 전 차단 조건으로 남긴다.

# 02 이름 분류와 판매단위 구현

작업일: 2026-10-27 KST. 담당: 서브에이전트 A (`name_resolver`). 이 기록은 해당 순수 함수와 합성 입력 검증의 결과이며 실제 운영 이관 완료를 의미하지 않는다.

## 판정 규칙

정규화는 `name-nfc-v1`: NFC, 앞뒤 공백 제거, 연속 공백 축약, ASCII 영문 소문자화만 한다. 숫자·용량·기호·`1+1`·옵션 표기는 남긴다. 공백을 없애 유사 이름을 자동 확정하지 않는다.

기간·플랫폼·스토어/계정·이름필드·포함/제외어·옵션 조건을 적용한 정확 이름/정확 별칭을 우선한다. 정확 후보가 없으면 등록된 포함 조건을 모두 평가한다. `EXACT`의 terms는 별칭 OR, `CONTAINS`의 terms는 AND다. 여러 제품 후보는 `AMBIGUOUS`로 남기고 priority나 문자열 길이로 결정하지 않는다. 서로 다른 기준 이름이 정규화 후 충돌해도 후보와 사유가 남는다.

제품명은 확정되지만 판매단위가 필요하거나 여러 단위가 남으면 `UNIT_REQUIRED`이며 제품 근거는 보존한다. 이름 없음은 `NAME_MISSING`, 규칙 없음은 `UNMATCHED`다. 원문/정규화값/후보/적용 규칙/버전/사유를 결과에 남긴다.

비활성 제품은 무조건적인 기준명 정확 일치에서 제외하되, 당시 날짜에 유효한 명시적 NAME 규칙이 있으면 과거 분류 후보로 남긴다. 비활성화로 역사 규칙을 삭제하지 않는다. 활성 제품과 비활성 역사 규칙이 같은 이름을 차지하면 AMBIGUOUS로 보존한다. B의 독립 검토 지적에 따라 이 계약과 회귀 테스트를 추가했다.

외부 상품 ID는 입력 타입에도 없고 해시에도 들어가지 않는다. `nameInputHash`는 원문 이름·옵션·원문 필드/복원 경로·플랫폼/범위·업무일·판매단위·요구 상태·이름 규칙 버전의 SHA256이다. 같은 이름으로 ID만 바뀌면 같은 판정이고, 같은 ID에 이름이 달라지면 해시와 판정이 달라진다. 내부 캐시는 없다. 추후 캐시는 기준제품 변경도 반영한 catalog/name 버전을 사용해야 한다.

## 판매단위

금액과 수량은 십진 문자열로 검증하고 Decimal precision 80을 사용한다. `numeric(30,6)` 금액, `numeric(24,6)` 수량 범위를 확인한다. 음수·지수표기·비유한값·범위 초과를 거부한다. 누락 비용 null은 유지하고 명시적 0은 허용한다.

`quantityBasis=SALE_UNIT_TOTAL`이며 `calculationQuantity=orderedQuantity`다. 실물개수만 `orderedQuantity × unitsPerSaleUnit`로 계산한다. 1+1 두 세트의 원가 9,000원은 18,000원이며 36,000원으로 다시 곱하지 않는다. 구성개수가 미확인이면 physicalQuantity는 null이다.

## 기존 규칙 이관 초안

이관 함수는 기존 API/DB 설정의 필요한 문자열·조건·기간을 투영한 snapshot을 받는다. Cafe24의 여러 별칭은 각각의 OR 규칙으로 만들며 각 옵션 조건은 유지한다. 쿠팡 포함/제외어, Meta 패턴과 지원하지 않는 REGEX/MANUAL 상태, Google 이름별 포함 규칙, 네이버 판매단위 displayName/matchAliases와 판매단위를 보존한다. 네이버의 카프슬리브→쿨토시 하드코딩은 새 기본값에 없다.

01에서 실제 확인한 기준제품 21개의 명칭을 `BASELINE_CANONICAL_PRODUCTS`로 제공한다. 에어스텝퍼의 기존 활성/비활성 ID 두 개가 통합 제품 두 개를 자동 생성하지 않는다. 네이버 `두줄보호대` 정확 별칭의 초안은 호출자가 실제 스토어 범위와 시작일을 넣어 만든다. 다른 플랫폼의 독립 제품은 명시적으로 검토한 canonical 목록에 추가한 후 이관한다.

외부 ID 제한 제거·기존 priority 미이관·과거 공백 제거 정규화의 차이는 `issues`와 `requiresReview`에 남긴다. 이름 조건이 없는 ID/옵션 전용 규칙, 미검토 기준제품, REGEX/MANUAL 규칙은 자동 이관하지 않는다. 미리보기는 데이터를 쓰지 않으며 원본 snapshot도 변경하지 않는다. 초안 저장과 실제 원천 표본 대조는 관리 API 및 후속 어댑터 단계에서 수행한다.

## 기존 01 증거를 사용한 실제 설정 미리보기

`scripts/unified-legacy-name-preview.ts`는 DB·네트워크 연결 없이 기존 `research/01-{inventory,coverage,detail,followup}-result.json`을 읽어 `research/02-name-migration-preview.json`을 생성한다. 입력 증거 파일의 SHA256과 query별 행 개수를 기록한다. `node --import tsx scripts/unified-legacy-name-preview.ts` 실행은 exit 0이었다.

실제 읽은 설정은 기준제품 22행(활성 기준명 21개), Cafe24 규칙 45행, 네이버 판매단위 99행, 쿠팡 제품 119행, Google SALE 설정 1행이다. 직접 관측된 이름 표본은 Google 캠페인 20행이다. 나머지 표본은 설정에 저장된 상품/단위 이름이며 주문 원문 이름을 관측한 것으로 표시하지 않는다. 총 292개 미리보기에서 MATCHED 80, UNMATCHED 212였다.

투영 초안 98행에서 이름 규칙 62개와 판매단위 구성 1개를 제안했다. 이름 조건 없는 기존 Cafe24 규칙 36건은 자동 이관하지 않았다. `GLOBAL_SCOPE_REVIEW` 18건과 과거 공백 제거 정규화의 차이 39건 등을 기록했다. Cafe24 증거에 DB 규칙 ID와 외부 ID 조건이 없으므로 provenance용 `evidence:...` ID를 사용하고 해당 한계를 명시했다. 네이버 구조 그룹과 동등성이 검토되지 않은 이름, 쿠팡 독립 제품/단위는 별도 진단으로 남겼다.

01에 명시된 개별 이름 표본의 동등성만 정확 사전으로 표현했다. 숫자/용량/세트를 일반적으로 제거하거나 부모 ID로 제품 동등성을 추정하지 않았다. 알려지지 않은 플랫폼 전용 제품을 21개 기준제품 중 하나로 강제 병합하지 않는다. Meta 이름 규칙 및 쿠팡 기존 키워드 규칙은 이 증거에 없어 실제 규칙 이관 성공으로 주장하지 않는다.

기존 네이버/쿠팡/Google 이름 초안의 과거 유효일은 증거에 없어서 `2026-10-26`을 명시적 미리보기 날짜로만 사용했다. JSON의 `importReady=false`, `requiresReview=true`를 유지하며 해당 날짜가 실제 운영 규칙의 시작일이라는 뜻이 아니다. 실제 저장 전 날짜·외부 ID 조건·판매단위와 해당 기간의 이름 표본을 검토해야 한다. DB 쓰기 0건이며 새 파일은 로컬 미리보기 산출물뿐이다. 주문키·주문 payload·연락처/주소는 읽거나 출력하지 않았다.

추가 실제 검사: 스크립트를 같은 입력으로 재실행한 전후 JSON SHA256이 동일했다. `node node_modules/typescript/bin/tsc --noEmit --target ES2022 --module CommonJS --moduleResolution Node --esModuleInterop --skipLibCheck --strict scripts/unified-legacy-name-preview.ts`도 exit 0이었다. 공통 어댑터 경계 코드는 독립적으로 읽고 논리키의 recordKind, 원천범위/날짜/중복, JSON 숫자 경계, null/추정값 보존을 확인했으며 `adapter-contract.test.ts` 3개가 통과했다.

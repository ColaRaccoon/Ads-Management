조사일: 2026-10-27 KST. 담당: 서브에이전트 B. 범위: 네이버 참고 저장소의 현재 작업 트리 읽기와 계약 제안. 운영 DB 접속·수정, 네이버 코드 수정, 기능 구현은 수행하지 않았다. 실제 DB 범위·날짜·상품 표본 대조는 주 담당자의 별도 증거를 따른다.

## 사용자 추가 지시 반영

사용자는 네이버 수치의 설계상 정확도가 낮음을 알고 있으며 이를 사용 차단 기준으로 엄격하게 다루기보다, **플랫폼별 체크박스로 포함/제외하여 함께 보거나 빼고 보는 기능**을 요청했다. 따라서 아래 정적 조사에서 발견한 최신성·수수료·그룹 오차는 가능한 금액을 추정치로 표시하고 짧은 상태 설명을 제공하기 위한 근거다. 추가적인 네이버 정밀 원천 조사를 필수 완료 게이트로 확대하지 않는다.

- 선택한 플랫폼의 알려진 매출·광고비·비용을 합산한다. 사용자가 네이버를 끄면 네이버 판매와 네이버 DA 광고 등 네이버 플랫폼에 속한 지표가 모두 선택 합계에서 빠진다. 응답에 선택한 플랫폼 목록과 포함 지표 범위를 남긴다.
- **플랫폼 포함/제외는 집계 범위 변경**이다. 매출을 유지한 채 특정 광고 매체의 변화만 살펴보는 광고 분석 필터와 별도 조건으로 관리한다. 분석 필터는 선택된 플랫폼 범위의 통합 이익을 다시 계산하지 않는다.
- 네이버가 포함된 알려진 수치는 정확도 경고 때문에 전부 숨기지 않는다. 추정 표시와 짧은 안내를 제공한다. 원천 부재·비용 미입력을 실제 0원으로 만들어 합산하지 않으며, 알려진 부분 금액과 계산 불가 구성요소를 구분한다.
- 명확한 이름 충돌은 임의 병합하지 않는다. `카프슬리브`와 `쿨토시` 같은 실제 별도 이름은 유지하고 미확정 연결을 남긴다. 관련 플랫폼을 제외해도 다른 선택 원천의 사용을 막지 않는다.

이 지시는 아래 후속 조사 권고 및 원 계획의 엄격한 네이버 완전성 검토보다 우선한다. 코드에서 확인한 계산식·현재 데이터 사실 자체는 바꾸지 않는다.

`public.canonical_sales_units.payload`의 `storeId`, `displayName`, `matchAliases`, `normalizedMatchAliases`, `parentSalesUnitId`, `isGroup`, `isStoreLevel`, `isActive`, `deactivatedAt`가 이름/구조 계약의 입력이다(`packages/shared/src/types.ts:84`). 네이버 판매단위와 전 플랫폼 통합 제품은 동의어가 아니다. 여러 판매단위를 같은 통합 제품으로 묶되 각 단위 원가를 보존해야 한다. `quantity`는 해당 판매단위 주문수량이므로 명시적인 규칙 없이 1+1·세트 구성개수를 추가로 곱하지 않는다. 실물 개수는 별도 `unitsPerSaleUnit`이 확인되었을 때만 계산한다.

주문명 복원은 `order_items.orderSourceSignatureId`로 `order_source_signatures`의 `rawProductNameSnapshot`, `rawOptionInfoSnapshot`, `normalizedProductName`, `normalizedOptionInfo`를 읽는다. 희소 이력은 옵션의 `]이름:` 또는 `이름:` 추출, `public.products` 상품명, legacy 주문명 순서로 복원한다(`signature-enrichment.ts:98`). `[함께배송]` 상품은 메인상품과 외부 상품번호를 공유할 수 있으므로 옵션명에서 추출한 실제 추가상품명을 우선 판단해야 한다. 현 helper의 의미있는 이름 판정은 길이 2 이하·단순 사이즈·옵션에 그대로 포함된 이름을 배제하므로 원문과 복원 경로를 함께 보존한다.

`normalization.ts:1`의 NFC/공백/소문자 변환은 재사용 가능한 기준이다. 기존 `normalizeMatchAlias`는 문자·숫자 외 기호를 모두 삭제하고 포함 일치를 사용한다. 이는 `1+1`과 `11` 구별을 잃을 수 있으므로 통합의 판매단위 판정 키로 그대로 사용하지 않는다. 원문·보수적인 정규화 키·판매단위 조건을 분리한다.

현 주문 자동매핑은 확인된 시그니처 → 함께배송 관리코드 → 옵션코드 → 일반 상품 ID → 텍스트 폴백 순서이며, ID 결과를 시그니처로 역추론하기도 한다(`sales-unit-auto-mapper.ts:243`). 이 현황은 이관할 통합 제품 분류 기준이 아니다. 외부 ID는 원문 이름을 찾는 참조와 중복 방지에만 쓰고 통합 판정은 이름/옵션/범위/버전으로 다시 한다.

- 광고원천은 `NAVER_DA_XLSX` 업로드. `ad_excel_uploads`가 같은 store이고 `isActive=true`, `state=CONFIRMED`, `weekdayValidationStatus=PASSED`인 ID에 연결된 `ad_campaign_daily_costs.totalCost`만 선택(`helpers.ts:101`). 검색광고 등 다른 상품까지 수집되었다고 하지 않는다.
- 판매는 자식별 수량/매출/비용을 부모로 롤업한다. 자식 ID 광고는 부모로 승격하며 그룹 광고는 부모에 한 번 붙는다(`helpers.ts:829`, `:873`). 출력은 부모와 부모 없는 단위가 최상위이며 선택적으로 `childRows`가 붙는다. 최상위 합과 자식 상세를 더하면 중복이다.
- 통합은 판매·직접비를 원천 주문행/자식 단위에서 한 번만 읽고, 그룹 광고를 별도 한 번 읽는다. 같은 통합 제품 자식이면 제품에 직접 귀속할 수 있으나 여러 통합 제품이 섞이면 명시 배분 규칙 또는 미배분 잔액이다.
- 원천 기존 화면은 미매핑/충돌/의도적 미배분 광고를 `excludedAdCost`로 제외한다(`helpers.ts:1096`). 통합의 선택 계정 총광고비에는 이를 유실시키지 않고 제품배정 합+미배분=유효 원천 총광고비로 보존해야 한다. 기존 네이버 표시 이익보다 차이가 나면 제외광고·공통비 항목으로 설명한다.
- VAT는 기존 부모 그룹 합계에서 반올림되므로 자식 각각을 먼저 반올림하면 원 단위 차이가 날 수 있다. 현 그룹/일 VAT를 보존하고 자식/통합 제품으로 나눌 때 명시적 배분 및 잔여 원 보존이 필요하다. 그룹이 여러 통합 제품이면 일률 재계산으로 기존 대조 성공을 주장하지 않는다.

## 갱신·저장 손익·완전성

`profit-summary.service.ts:21`의 저장 버전은 `profit-v2`. 현재 writer는 `costSnapshotId=null`, `mappingBasisHash=null`을 기록한다(`:375`). 따라서 버전/계산시각이 같아도 현 원가·매핑·주문·광고 업로드와 일치하는지 알 수 없다. 저장 결과는 대조 보조 자료이며 현재 집계의 무조건적인 정본으로 삼지 않는다. 관련 원천 지문과 최신 행수/금액/선택 업로드를 제한된 날짜 범위에서 비교하고 검증 불가 시 재계산한다.

주문 기본 동기화는 `YESTERDAY`이며 `CURRENT` 모드의 변경 워터마크와 별개다(`order-sync-batch.service.ts:34`). `order_sync_states`의 `initialCoverageFrom`, `lastSuccessfulChangedTo`, `lastSuccessfulSyncAt`, `changedCoverageBaselineAt`, `historicalCoverageGap`와 요청 구간/operation 성공 결과를 같이 봐야 한다. 마지막 성공시각만으로 모든 결제일 0건·최신 취소를 보장할 수 없다. CURRENT의 30일 복구 한도는 앱의 검증 정책이며 네이버 원천의 보존기간 보장이 아니다(`order-sync.service.ts:179`). 공백을 acknowledge해도 과거 결손이 복구된 것은 아니다.

날짜는 수집된 `paymentDate`/광고 `reportDate`를 보존한다. 수집기의 날짜 함수와 원 타임존은 후속 대조에서 명시하고 날짜를 임의 이동하지 않는다. 결제일 선택 주문의 이후 취소/반품 갱신 여부는 coverage 근거가 없으면 미확인이다. 삭제·0건 정정·원가 소급·업로드 교체는 `updated_at` 워터마크만으로 검출하지 말고 일별 지문/완전 재대조와 영향일 재발행을 사용한다.

## 전용 읽기 역할과 격리 검증 제안

아래는 코드에서 필요한 테이블/필드 목록이며 **운영 GRANT를 실행한 목록이 아니다**. 모든 테이블은 `public.`을 명시한다. 데이터 컬럼은 `id,payload,payload_hash,updated_at` 구조(`database.service.ts:2654`). reader는 필요한 JSONB 값만 서버에서 추출하고 원 payload/주문 개인정보를 로그/API에 반환하지 않는다.

| --- | --- |
| 범위/배송단가 | `stores`: id,name,platformType,isActive,deactivatedAt,deliveryUnitCost,lastOrderSyncAt,lastOrderSyncStatus. credential 상태·계정 인증정보 제외 |
| 주문 | `order_items`: storeId,orderId,orderSourceSignatureId,canonicalSalesUnitId,externalProductOrderId,quantity,productPaymentAmount,deliveryFeeAmount,수수료 4개,paymentDate,saleStatus,packageNumber,legacy 이름/옵션. 외부키는 추적·복원용이며 외부 공개 금지 |

`commerce_api_credentials`, `audit_logs`, `orders.rawPayload`, `ad_upload_preview_rows`, 인증/토큰 테이블은 불필요하다. 실제 필요 테이블은 후속 reader SQL이 참조하는 목록으로 다시 줄인다. JSONB 컬럼 SELECT를 부여하면 역할 자체는 해당 payload 안의 다른 값도 볼 수 있으므로 SQL projection은 데이터베이스 수준 비공개 보장이 아니다. 더 좁은 접근이 필요하면 명시적인 안전 projection 뷰와 실행 역할/RLS 경계를 별도 검증한다. 권한 실패 회피용 무조건 SECURITY DEFINER는 만들지 않는다.

격리 준비: 운영과 다른 host/database를 확인한 빈 PostgreSQL에 필요한 JSONB 테이블/인덱스를 최소 재현하고, 개인정보 없는 합성 표본 또는 승인된 비식별 발췌만 넣는다. 운영 쓰기 자격증명 없이 네이버 reader 역할과 통합 집계 writer/API 역할을 분리한다. reader에 필요한 스키마 USAGE와 목록 SELECT만, 대상 집계 스키마 쓰기는 별도 역할에만 부여한다. 실제 reader로 SELECT 성공, 원천 INSERT/UPDATE/DELETE 및 인증정보 SELECT 거부, 스토어 범위 제한/민감 필드 비노출을 확인한다. 역할 상속·PUBLIC 기본 GRANT·RLS/BYPASSRLS·뷰 소유자 우회 여부까지 검사한다. 여기서는 연결/역할 생성/GRANT/마이그레이션을 수행하지 않았다.

## 후속 계약에서 반드시 해결할 항목

1. 실제 단품/세트 이름은 위 운영 읽기로 확보했다. 옵션별 적용 원가·효력일을 추가 확인하고 교차 플랫폼 별칭/충돌을 확정한다. `naver_settings`의 `product_cost`, `shipping_cost` null 투영은 잘못된 키다. `naver_cost_keys`가 확인한 실제 `unitCost`, `otherCost`, `feeRate`로 읽어야 하며 해당 null을 비용 누락 증거로 쓰지 않는다.
2. 네이버 상품매출×10% 정책을 이름 있는 업무 추정 VAT 버전으로 보존한다. 그룹→여러 제품 분할의 반올림 잔액 계약을 확정한다.
3. 배송/가구매는 기본 미배분으로 보존한다. 제품 합계를 스토어 총손익이라고 제시하려면 공통비 잔액을 별도로 포함해야 한다.
4. 확보한 최근 하루/7일 원천 금액을 기준선으로 사용한다. 기존 저장 손익·재계산의 정밀 대조나 전 기간 완전성은 확인된 범위만 기록하고 추가 조사 권고로 넘긴다. 사용자 추가 지시에 따라 네이버의 모든 미확인 항목을 해결해야 선택 조회를 진행할 수 있다는 완료 게이트로 삼지 않는다.

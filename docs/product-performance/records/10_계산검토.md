## 계산 성능과 한계

매트릭스의 단일 `summarizeReport` 호출만 측정했다. 독립 기대값 계산·assert는 호출 시간에서 제외했다. 플랫폼/제품/계정 선택별 혼합192표본을 기간마다 사용했다.

| 기간 | 원장 facts / coverage | 계산 p95 / 최대(ms) |
| --- | --- | --- |
| 1일 | 68 / 26 | 1.47 / 5.08 |
| 7일 | 476 / 182 | 6.02 / 9.02 |
| 30일 | 2,040 / 780 | 25.22 / 31.80 |
| 366일 | 24,888 / 9,516 | 364.82 / 502.66 |

전체 매트릭스33.774초에는 원장 생성·독립 기대값·assert가 포함된다. 샘플링한 프로세스 최대 RSS는333,082,624bytes다. 다른 검증이 병행되는 로컬 환경이며 CPU/DB/네트워크 운영 부하를 대표하지 않는다. **읽기 계산 성능이며 어댑터 원천읽기·worker 집계 발행·HTTP p95 측정이 아니다.** C의 PG/HTTP 성능과 구분한다.

366일 성공은 domain 계층 검증이다. 현재/전기 각각 최대366일, 계정×고유날짜20,000 및 facts100,000의 API/repository 경계는 별도이며 이번 매트릭스가 이 경계를 통과했다고 주장하지 않는다. 실데이터의 장기 연속 완결성·운영 권한·운영 화면 최신수치·네이버 정산액의 정확성은 이번 결과로 입증하지 않는다. 네이버의 업무상 추정 오차는 정책대로 배포 차단에서 제외하고 신규 중복/계산/선택 오류는 차단 기준으로 유지한다.

## 다른 담당 영역 교차 검토

- B `unified-stage10-recovery.mjs`: 루프백 새 PG17 확인 후 migration 반복무변경, 비소유자 writer/API와 deny 검증, 기존06의 explicit100/120/0금액·손상999거부·lease/CAS·불변·과거원가/규칙 revision검증, 별도클러스터 physical restore의 table JSON해시 보존을 확인했다. production transform을 입력생성에 사용하지만 고정 기대값과 의도적 손상 검증이 별도여서 동일 함수의 자기비교만으로 통과하지 않는다. 동일PG17 clean-stop physical backup 검증이며 운영 pg_dump/PITR·앱 binary rollback까지 확인한 것으로 확대하면 안 된다.
- C `unified-stage10-performance-http.test.ts`/`-postgres.mjs`: 실제 Nest guard/DTO/repository/PG로 구성되고, 원천쓰기 없이 조회를 측정한다. 기간별 순차10표본의 nearest-rank p95는 최대값이다. 366일 요청의 실제발행밀도는90+14일이므로 full-density366일 HTTP로 설명하면 안 된다. EXPLAIN은 대표 SQL이며 Prisma 실제 SQL전수계획이 아니다. 50ms statement timeout은 수동PG transaction에서 취소/후속조회 회복을 보는 검증으로, API 전체 deadline/Prisma transaction 15초초과 경로를 대체하지 않는다. 이 범위 안에서 차단 결함을 발견하지 않았다.

후속 제한 사항은 주 담당에게 전달했다. Git/index/branch/commit/push는 주 담당만 수행한다.

B와 C는 A의 BigInt 독립계산을 역으로 교차 검토했다. 광고 단품/세트 반복에서 saleUnitName=null 때문에 초기 합성 factKey가 겹칠 수 있다는 같은 지적을 받았다. domain 배열의 금액에는 영향이 없었지만 원장 키에 독립ordinal을 추가하고 전체key 유일성 assert를 추가했다. 최종768사례를 다시 실행해 통과했고 위 표는 수정 후 최종 실행 수치다. production코드 결함으로 보고하지 않는다.

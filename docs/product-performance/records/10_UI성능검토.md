`scripts/unified-stage10-performance-postgres.mjs` → `unified-stage10-performance-http.test.ts`를 실행했다. 첫 실행은 5 pass, fail/skip 0, PG stop exit 0이다. 단일 프로세스 HTTP 요청+JSON 수신까지 측정하며 1/7/30/90/366일 summary/timeseries/diagnostics/relationships 각각 warm-up 1회 제외, 순차 10회다. 366일 summary/relationships 동시 4개씩 5묶음도 측정했다. 최종 실행에는 30일 동시 4개를 추가했다.

실제 저장 표본은 104일(2026-06-17~09-28), 518 publications·928 facts·1,344 coverage다. 두 네이버 일자는 의도적으로 없다. **366일 HTTP 조회는 빈 날짜가 많은 표본이며 366일 모든 날짜가 채워진 DB 부하 결과가 아니다.** A의 366일 24,888 facts domain matrix는 별도 증거다. 순차 10표본의 nearest-rank p95는 최대값이고, 운영 서비스 SLO의 통계적 보장이 아니다. 작업 중 다른 로컬 검증 프로세스도 실행됐다.

수정 전 `10-performance-baseline.json`에서 timeseries 366일 p95 **2,532.43ms**가 2초 목표를 초과했다. 90일 1,221.42ms, 30일 287.56ms였다. 네 개 대표 SELECT의 DB 실행은 0.025~0.490ms여서 JS 구간을 조사했다. `report.service.ts`가 모든 bucket마다 전체 snapshot의 participation을 다시 계산하고, 페이지 밖 bucket도 계산했다. 주 담당이 요청 내부 제품별 scope 캐시와 bucket 페이지 선선택으로 수정했다. 이 캐시는 요청/스냅샷 밖으로 공유되지 않는다. total·cursor hash·offset·기간별 계산식은 유지한다.

수정 전 sampled Node RSS peak 598,900,736 bytes, 해당 DB connection peak 7이다. test runner·fixture·HTTP client도 같은 Node 프로세스에 포함된다. 브라우저/Next/운영 worker RSS나 컨테이너 전체 메모리로 해석하지 않는다. 20ms sampling이 모든 순간의 최고값을 보장하지 않으며 장기 누수 검증은 아니다.

실제 비소유자 viewer로 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`을 실행한 네 query는 publication join/facts/coverage/failure의 **고정 대표 SQL**이다. Prisma가 실제 전송한 SQL을 그대로 캡처한 증거는 아니다. 격리 DB owner의 ANALYZE 외 운영 통계·인덱스 변경은 없다. 별도 tx에 `SET LOCAL statement_timeout='50ms'` 후 pg_sleep(200ms)를 실행해 53.72ms에 취소되고 다음 summary HTTP200으로 복구됨을 확인했다. 이는 **운영 timeout 설정이 완료됐다는 증거가 아니다.** read transaction의 Prisma 기본 timeout 및 운영 역할의 statement/lock timeout 검토는 배포 계획에서 고정해야 한다.

## 추가한 동작

- 기존 요약 바로 아래에 전체 등록·과거 제품을 포함한 상세표를 표시한다. 상단 제품 선택은 요약에만 적용하고 상세표는 전체 제품을 유지한다.
- 제품 / 자사몰 / 쿠팡 / 네이버 / 구글 / 전체 순서의 16열을 사용한다. 각 그룹은 광고비·매출·순이익이며 셀은 금액과 전일 대비 변화 두 줄이다.
- 요약만 인쇄, 상세표만 인쇄, 요약+전체 제품 인쇄/PDF 버튼을 제공한다.
- 요약은 A4 세로, 상세는 A4 가로로 이어 출력한다. 상세 머리글은 페이지마다 반복된다.
- XLSX는 16열 보고용 시트와 숫자·상태·비교 사유가 분리된 데이터 시트를 제공한다. 보고용 시트는 8pt, A4 가로, 가로 1페이지·세로 자동, 반복 머리글과 첫 열 고정을 사용한다.
- XLSX는 Web Worker에서 생성해 많은 제품을 처리하는 동안 화면이 응답할 수 있게 했다. 종료·실패·취소 때 워커를 정리한다.

## 데이터 연결

새 읽기 경로는 `GET /unified-performance/daily-products`다. 기존 권한 `data.read`와 조회 범위 정책을 유지한다. 보고일 D와 D−1의 일 단위 조회만 허용한다.

한 번의 전체 제품 스냅샷에서 선택 제품 요약·시계열과 전체 제품 상세를 제공한다. API 응답의 `products`, `allProducts`, `totalProducts`, `nextCursor:null`, `reportDate`, `previousDate`를 검증한 뒤 화면·인쇄·엑셀이 같은 결과를 사용한다. 조회 조건·버전이 어긋나면 전체 요청을 한 번 재시도하고, 계속 불일치하면 출력하지 않는다.

제품별 fact를 한 번 색인하되 미분류 금액과 채널 구간 문맥은 유지한다. 기존 `summarizeReport`, 참여 정책, storefront overlay를 호출하며 새로운 원가·순이익·광고비 배분 공식을 넣지 않았다. 전체 제품 조회에서는 이미 얻은 시계열의 일별 총계를 재사용한다.

native `CAFE24_META`는 자사몰, `CAFE24_YOUTUBE`는 구글 판매 그룹에 연결한다. 구글 Ads 전환매출을 판매 매출로 새로 합산하지 않는다. 전체 열과 합계 행은 canonical 통합 결과를 사용한다. 이전 Cafe24 통합 결과는 임의로 두 채널에 배분하지 않는다. 이전/신규 기준이 달라지면 해당 증감 비교를 막고, 같은 날 혼합 기준은 경고와 미확인으로 표시한다.

금액은 십진 문자열을 유지하며 표시용 증감액·증감률만 정확한 십진 정수 연산으로 구한다. 0원, 미확인, 부분 금액, 정책상 비참여, 사용자 제외를 구분한다. 엑셀 숫자 정밀도로 원본을 유지하기 어려운 값은 원본 문자열과 사유로 보존한다.

## 성능 확인

운영 수치가 아닌 로컬 단일 합성 측정이다. DB·네트워크 시간과 p95는 포함하지 않는다.

| 제품 수 | API 서비스 처리 | 응답 크기 | XLSX 생성 참고치 |
| --- | ---: | ---: | ---: |
| 100 | 227ms | 0.74MB | 약 0.1초 |
| 1,000 | 1,765ms | 6.74MB | 약 0.8초 |
| 5,000 | 8,949ms | 33.37MB | 약 3.7초 |

API는 크기마다 스냅샷 호출 1회·원천 호출 0회다. 공용 XLSX 스타일 조합 캐시로 중복 XML 생성을 줄였다. 5,000제품에서 생성된 XLSX는 약 56.6MB로 크며 기존 무압축 ZIP 방식의 영향이다. 현재 화면은 모든 행을 렌더링하므로 대규모 환경의 실제 브라우저 메모리·조회시간은 운영 자료로 추가 측정해야 한다. 데이터 누락을 숨기는 임의 행 제한은 없다.

## 통합과 원상복구

1. 다른 세션은 작업 중인 변경을 먼저 기록한다. 이 기능 커밋은 `1186e17` 이후의 추가 기능 변경만 포함하므로 해당 커밋을 통합 대상으로 삼는다.
2. 충돌 검토 대상은 `report.service.ts`, `report.controller.ts`, `daily-report.tsx`, 공용 `xlsx.ts`와 stylesheet 등록이다. 금액 결과 필드나 채널 이름이 바뀌면 어댑터 매핑과 canonical 대조 테스트를 함께 확인한다.
3. 기존 API 타입 오류를 해결한 계산 담당 결과와 함께 웹/API 검사 및 실제 업무일의 플랫폼별 금액 대조를 마친 뒤 배포한다.
4. 아직 통합하지 않았다면 원본 프로그램에는 이 기능의 영향이 없으며 분리 브랜치를 보존하면 된다.
5. 통합 후 되돌릴 때는 **이 기능 커밋만 `git revert <기능 커밋>`**한다. 다른 세션의 계산 커밋은 유지한다. 원본 브랜치를 과거 시점으로 강제 reset하거나 작업 파일을 일괄 덮어쓰지 않는다.
6. DB 변경이 없으므로 이 기능 때문에 되돌릴 schema·데이터 migration은 없다. 배포한 경우 이전 앱 릴리스로 복구하고 기능 커밋을 되돌린 코드를 다음 릴리스 기준으로 삼는다.

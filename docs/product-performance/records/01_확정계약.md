# 01 제품별 통합 성과 데이터 계약

계약 버전: `product-performance-v1.0.0` (2026-10-27 KST). 적용 단계: 02~11. 이 문서는 구현할 필드·산식·선택 정책을 확정하며, 아직 없는 통합 기능의 동작 검증을 주장하지 않는다. 실제 확인 사실은 [현 앱 조사](01_현앱조사.md), [네이버 조사](01_네이버조사.md), [하루·7일 원천 대조](01_원천대조.md) 및 `../research/01-*-result.json`에 구분했다. 작업 도중 별도로 추가된 [플랫폼 선택과 네이버 데이터 정책](../플랫폼선택과네이버데이터정책.md)을 보존하며, 02 이후에는 그 문서의 플랫폼 선택·네이버 처리 정책을 우선 적용한다. 아래 초안의 내부 선택 개념은 같으며 외부 조회 키는 해당 정책의 `platforms`로 통일한다.

## 1 사용자 결정과 적용 범위

- 사용자가 확인한 기존 쿠팡 CSV는 단일 계정의 자료다. 별도 계정 입력 없이 내부 업로드 범위 `LEGACY_COUPANG_SINGLE_UPLOAD`로 취급한다. 원시 조사 JSON의 `UNIDENTIFIED_SCOPE`는 확인 이전의 마커이며 운영 자료 수정이나 계정 추가 설정을 요구하는 값이 아니다.
- 플랫폼별 체크박스로 **데이터를 포함/제외**한다. 포함 범위가 바뀌면 선택 범위의 매출·비용·이익도 바뀐다. 네이버 정확도가 낮다는 이유로 선택이나 추정치 조회를 차단하지 않는다. 정확도 개선을 이번 기능의 선행 조건으로 만들지 않는다.
- 네이버 값은 기존 프로그램 정책에 따른 추정치로 사용하고 간단한 출처/상태를 제공한다. 없는 원천·원가·환율을 0으로 꾸미거나 같은 비용을 중복 반영하는 것은 허용하지 않는다. 정확성 보증과 사용 가능한 추정치를 구분한다.
- 판매 원천 3개(Cafe24/쿠팡/네이버), 광고 4개(Meta/Google/쿠팡/네이버 DA)가 최초 범위다. 다른 네이버 광고상품의 수집을 가정하지 않는다.

## 2 플랫폼 체크박스와 총액의 의미

| 체크박스 키 / 표시 | 포함되는 데이터 | 해제 시 제외 |
| --- | --- | --- |
| `CAFE24` / 자사몰 매출 | Cafe24 판매·직접비·해당 공통비 | 자사몰 판매와 그 비용 |
| `META` / Meta 광고비 | Meta 광고세트 비용 | Meta 광고비 |
| `GOOGLE` / Google 광고비 | Google 캠페인 비용 | Google 광고비 |
| `COUPANG` / 쿠팡 | 쿠팡 판매·직접비·가구매 처리·광고비 | 쿠팡 판매/비용/광고 전체 |
| `NAVER` / 네이버 | 스마트스토어 판매·직접비·DA 광고·배송·가구매 공통비 | 네이버 판매/비용/광고/공통비 전체 |

기본은 최초 연결된 위 항목 모두 선택한다. 기존 저장 선택이 있으면 이를 복원하며 플랫폼 연결 여부와 사용자의 포함 선택을 혼동하지 않는다. 제품의 실제 적용 판매처/매체는 `scopePolicyVersion`으로 별도 관리한다. 체크 해제는 선택 제외(`EXCLUDED_BY_USER`), 실제 미사용은 `NOT_APPLICABLE`, 수집 누락은 `NOT_COLLECTED`다.

`platforms`를 요약·시계열·진단·기간비교·관계분석·내보내기에 동일 적용한다. 선택값은 URL과 사용자별 브라우저 저장에 유지하고 캐시 키에 포함한다. 빈 선택은 허용하되 '선택한 플랫폼 없음'으로 보여주며 매출·광고비·이익 KPI는 null이다. 일부 플랫폼만 선택해도 선택 범위 내 적용 구성요소가 완료된 0건이면 금액 0으로 표시한다.

선택 범위 제목은 '선택 플랫폼 합계', 이익은 **'추정 순이익 · 등록 비용 기준'**이다. 광고만 선택하면 광고비만 표시하고 매출·이익·MER는 해당 없음(null)이다. 판매만 선택하면 광고 전 이익을 표시하고 광고 후 전체 순이익이라고 쓰지 않는다. 이 상태는 `metricAvailability`로 구분한다. 해제된 네이버의 품질은 선택 합계를 불완전하게 만들지 않는다. 해제 비용을 남은 플랫폼에 재배분하지 않는다.

관계분석의 `analysisMedia`는 위 포함 범위 안에서 설명변수/광고비 구성을 고르는 별도 필터다. **`analysisMedia`만 변경하면 선택 플랫폼의 매출·총광고비·총이익은 변하지 않는다.** 기존 설계의 '분석용 매체 필터로 총이익 불변'은 이 경우에 적용하며, 사용자 요청의 포함 체크박스를 제한하는 규칙으로 해석하지 않는다.

## 3 기준 제품명과 판매단위

운영 `meta_ads.products`에는 활성 21개, 비활성 동일명 에어스텝퍼 1개가 있다. 활성명은 노필수면안대, 다이어트양말, 두줄무릎보호대, 러닝양말, 러닝조끼, 바라클라바, 버닝 슬라이드, 버닝웨이브바, 베놈무릎보호대, 뷰티레그보드, 스카이스텝, 아이언볼, 에어스텝퍼, 유쉴드마스크, 자이로볼, 퍼펙트스케이트, 퍼펙트슬라이드, 풀업바, 풀업밴드, 플로우라이트, 한줄보호대다. seed의 '버닝 웨이브바'를 운영명으로 대체하지 않는다.

초기 이름 사전은 위 실제 기준명과 다른 플랫폼의 독립 실제 제품명을 보존한다. 명확히 동일한 이름/기존 별칭은 자동 처리하고, 아직 동등성이 확인되지 않은 이름을 억지로 병합하지 않는다. 다른 플랫폼에만 있는 제품도 자체 기준명으로 집계 가능하다. 이름 검토가 전체 조회를 막지 않는다.

| 실제 표본 | 제품 / 판매단위 해석 |
| --- | --- |
| 쿠팡 버닝웨이브바 1개입 / 2개입 | 기준 버닝웨이브바, 각각 구성수량 1/2인 별도 단위 |
| 쿠팡 플로우라이트_1개입 / _2개입 | 기준 플로우라이트, 각각 별도 단가·원가 |
| 네이버 버닝웨이브바 / 버닝웨이브바 1+1 | 기준 버닝웨이브바, 부모 '버닝웨이브'는 구조·광고 범위이며 별도 매출로 더하지 않음 |
| 네이버 한줄보호대 단품 / 1+1 | 기준 한줄보호대, 단품/세트 별도 |
| Google SALE 두줄무릎보호대 '1+1 세트' | 판매가 34,900 / 원가 9,000 / 배송 0 / 기타 0, 2026-10-24부터. 모두 판매단위 총액 |
| 네이버 카프슬리브 / 쿨토시 | 별개 유지. 기존 코드의 카프슬리브→쿨토시 하드코딩은 이관하지 않음 |
| 네이버 러닝깔창 PORON / 데일리 | 포함 단어만으로 병합하지 않음 |
| 에어스텝퍼 활성/비활성 동일명 | 한 통합 제품의 역사 후보로 취급. 동일 일자 비용 충돌이면 임의 최신 ID 선택 금지 |

정규화 버전 `name-nfc-v1`: NFC, trim, 반복 공백 축약, 영문 소문자만 적용한다. 숫자·용량·모델·1+1·기호·옵션은 제거하지 않는다. 공백 제거 키는 후보 탐색용이며 자동 확정 키가 아니다. '버닝 슬라이드↔버닝슬라이드' 같은 표기는 범위 있는 정확 별칭으로 명시한다. 네이버 '두줄보호대' 등 기존명도 정확 별칭 규칙으로 표현하며 여러 제품이 남으면 `AMBIGUOUS`다.

분류 순서: 범위/유효일 필터 → 정규화 기준명 정확 일치/정확 별칭 → 등록된 포함·제외·옵션 조건의 모든 후보 평가 → 유일 후보 자동 확정. 가장 먼저 나온 후보·유사도 최고점·플랫폼 ID만으로 확정하지 않는다. 상태 `MATCHED | UNMATCHED | AMBIGUOUS | NAME_MISSING | UNIT_REQUIRED`; 원문필드/후보/사유/규칙버전 보존. 이름이 같아도 판매단위 비용은 분리한다. 혼합 제품 세트는 독립 제품 유지.

단위 필드: `saleUnitName`, `optionName`, `orderedQuantity`, `calculationQuantity`, `unitsPerSaleUnit: DecimalString|null`, `physicalQuantity: DecimalString|null`, `quantityBasis`. 원가가 세트 총액이면 `calculationQuantity=orderedQuantity`이며 1+1 때문에 원가를 다시 2배하지 않는다. 실물개수만 `orderedQuantity×unitsPerSaleUnit`. 판매단위 정보가 불확실하면 실물수량 null, 확인된 매출은 보존한다.

## 4 이름·원천 선택·날짜 경로

| 원천 | 이름 취득 / 선택 / 업무일 |
| --- | --- |
| Meta | adset 원문명·기존 제품명·이름규칙. `meta_adset_daily_metrics.is_current`, `selectCurrentSourceRows(META_ADSET)`. 개별 광고 합계 추가 금지. `metric_date`, 광고계정 시간대 |
| Google | campaign_name·활성/역사 기준명. `google_campaign_daily_costs.is_current`와 연결/coverage 검증. `metric_date`, 계정 시간대 |
| Cafe24 | product_name+option_name·Cafe24 이름 별칭/옵션. `is_current`, 비오류, 완료배치/연결/원천정책 및 API parity 경로. `order_date`(API 주문시각 KST 변환) |
| 쿠팡 | sale product_name/option_name, 광고 ad_execution_product_name+campaign/ad name. 비용은 실행상품, 전환상품 ID는 광고비 귀속 기준 아님. current·비오류·완료배치·단일 CSV 범위. sale_date/metric_date |
| 네이버 | canonical displayName/matchAliases + order_source_signatures rawProductNameSnapshot/rawOptionInfoSnapshot, 필요 시 products 이름. ID는 이름 복원 참조에만 사용. 주문 SALE/paymentDate, 광고 reportDate |

현 원천 정책의 효력기간은 `[fromDate,toDate)`이며, 원가 `effectiveTo`는 기존 코드의 당일 포함 의미를 보존한다. 신규 이름/배분 규칙은 날짜 양끝 포함 `[validFrom,validTo]`, 종료 없음 null. 시간은 ISO8601 offset, 업무일은 `YYYY-MM-DD`; UTC Date 저장값을 시각으로 재해석해 일자를 이동하지 않는다. 비KST 일별 광고는 단순 이동하지 않고 `TIME_ZONE_MISMATCH`를 표시한다.

선택된 논리 행은 `sourceSystem + scopeKey + recordKind + sourceRecordKey`로 식별, 현재 원천/버전만 1회 반영한다. 동일 제품명의 서로 다른 주문은 지우지 않는다. Cafe24 API/CSV를 합치지 않고 기존 `source-read-policy.ts`를 그대로 사용한다. 쿠팡 일별 집계는 `sale_line_key` 사실이며 가상의 주문 ID를 만들지 않는다. 네이버 부모+childRows를 합산하지 않는다.

기존 Meta/Cafe24 unbound CSV는 기존 정책이 허용하는 과거 구간만 읽고 `LEGACY_UNBOUND`로 출처를 표시한다. 확인되지 않은 계정에 강제 연결하지 않는다. 현재 연결은 Meta USD/KST 1개, Google KRW/KST 1개, Cafe24 shop1/KRW/KST 1개, 네이버는 인피니티스토어/파티마스토어다. 내부 연결키는 기존 값을 참조하고 사용자가 새 외부 상품 ID를 입력하지 않는다.

## 5 금액과 산식

공통 출력은 기존 최종이익을 입력받아 광고를 다시 빼지 않고 아래 구성요소에서 만든다.

```text
R = 선택 판매처의 업무 상품매출(배송수입 제외)
B = R - productCost - platformFee - directShippingCost - returnCost
      - otherDirectCost - vatExpense - discountNotYetIncluded - manualVendorFee
P = B - assignedSelectedAdSpend + allocatedShippingIncome - allocatedCommonExpense
selectedScopeProfit = sum(P) - unallocatedAdSpend
                      + unallocatedShippingIncome - unallocatedCommonExpense
```

`manualVendorFee`는 쿠팡의 조정된 정상판매 비용에만 별도 1회다. 네이버 가구매는 `commonExpense`다. 각 비용은 `costKind + sourceExpenseKey`로 1회, 직접 귀속·배분·미배분을 분리한다. 상품배분+미배분=원천액이며 알려진 음수 정정도 부호를 보존한다. `unallocatedAdSpend`에는 미분류 광고를 포함하며 범위 전체 이익에서 한 번 차감한다. 미배분이 있으면 제품은 '공통비 배분 전'을 표시하고 범위 합계에서는 잔액을 한 번 반영한다. 제품명 필터에서는 그 제품에 배정된 금액만 이익에 반영하고 범위 잔액은 별도 scopeBalances로 보여준다. 모든 제품 화면에 같은 잔액을 반복 차감하지 않는다.

네이버 원가는 최신 날짜 이하 snapshot과 개별설정을 비교한다. 더 늦은 effectiveFrom 우선, 동률은 개별 `costValuesUpdatedAt ?? updatedAt >= snapshot.updatedAt`이면 개별 우선. 최신 snapshot에 단위가 없거나 우선 개별설정이 만료되면 옛 비용으로 되돌리지 않는다. 필드 null/음수/비유한은 불완전, 명시적 0은 유효. 원가 존재 조사는 이 선택기 전체의 검증과 구분한다.

`revenueBasis = REGISTERED_SALE_PRICE | PRODUCT_PAYMENT_AMOUNT | NET_SALES_REPORTED`를 매출 사실에 기록한다. `discountTreatment`, `refundTreatment`, `taxPolicyVersion`, `feeBasis`, `feePresenceMask`, `costBasisVersion`, `shippingBasis`, `dateBasis`도 필수다. 이름이 같은 매출 필드에 산식 차이를 숨기지 않는다.

실결제는 별도 `collectedPaymentAmount`, `paymentGrain`, `paymentAllocationStatus`다. Cafe24 API의 주문 결제액은 여러 주문행에 반복되므로 주문 단위 1회만 보존한다. 제품별 실결제 배분 규칙이 없으면 제품별 실결제액 null이다. 운영매출을 환불 후 실결제/정산매출이라고 부르지 않는다.

공통비 기본 정책 `UNALLOCATED-v1`: 임의 제품배분 없음. 명시 배분 시 `REVENUE_SHARE | FIXED_WEIGHTS`, 기간·사유·규칙버전 저장. 분모0은 미배분. 중간계산 Decimal, 원단위 배분 잔여는 소수잔여 내림차순→기준명/범위키 오름차순으로 결정하여 보존한다. 네이버 기본 반올림 정책을 바꾼 차이는 보존원장으로 설명한다.

## 6 Decimal·환율 경계

- `DecimalString`: 지수표기 없는 십진 문자열. 금액/수량/비율을 Number로 왕복하지 않는다. 내부 Decimal precision 80, 반올림 기본 HALF_UP. 원천 정책별 원/소수2자리 반올림 위치를 먼저 보존한다. 신규 저장 금액 numeric(30,6), 비율 numeric(18,10), 수량 numeric(24,6); 범위 초과는 거부한다.
- Google micros는 BigInt 또는 정수문자열→Decimal÷1,000,000, KRW rate=1. Meta는 일자별 USD×저장 KRW 환율. 저장 금액은 소수6자리 HALF_UP 양자화하고 원금액·환율·반올림 전 계산 지문과 roundingAdjustment를 보존한다. 원천별 정확 환산 합을6자리로 반올림한 목표액과 개별 저장액 합의 잔액은 결정적 순서로 배정한다. 화면 원단위 표시는 합계 후 반올림한다.
- 환율 필드 `baseCurrency,quoteCurrency,requestedDate,sourceDate,rate,provider,fallbackType,fxVersion`. 없는 환율은 KRW null, 원통화 knownAmount는 보존. 기존 legacy 원가 환율 fallback을 쓰면 출처를 별도 표시한다. 읽기 중 환율 외부 API 호출 없음.
- 10/20~26 저장 USD/KRW 7일 확보. 10/24·25는 10/23 환율 1324.6의 PREVIOUS_AVAILABLE, 10/26은1324.3 EXACT. 모든 과거를 최신 환율로 덮지 않는다.

## 8 품질·추정치·발행·갱신

기존 계획의 상태 `COMPLETE,PARTIAL,NOT_COLLECTED,NOT_APPLICABLE,STALE,MAPPING_REQUIRED`에 선택 표시 `EXCLUDED_BY_USER`를 추가한다. 단일 상태로 정보를 지우지 않고 `issues[]`를 함께 반환한다. `MAPPING_REQUIRED`는 해당 원천의 미분류 진단이며 화면 차단 사유가 아니다.

금액은 `knownAmount: DecimalString|null`, `completeAmount: DecimalString|null`, `isEstimate`, `issues[]`, `knownComponentCount`, `expectedComponentCount`로 표현한다. 부분 합계는 knownAmount이며 모르는 금액을 0으로 바꾸지 않는다. 전체 입력이 없으면 knownAmount도 null. 네이버 선택 시 확인된 매출/비용으로 계산 가능한 추정치를 보여주고 최신 취소·원가 정확성 보증을 요구하지 않는다. 비용 구성요소가 실제로 없으면 해당 제품 이익은 null, 다른 제품과 알려진 부분합은 계속 표시한다.

제품 `knownTotals`에는 확인된 매출/광고비와 계산 가능한 제품 이익을 제공한다. 범위 응답은 `productProfitSubtotal`과 미배분 광고·배송·공통비 잔액을 분리하고, 범위 `knownTotals.estimatedProfit`에는 앞 절 selectedScopeProfit을 사용한다. 미분류 매출/계산 불가 비용이 있으면 부분합 표기를 유지한다. `completeTotals`는 선택 범위 입력의 수치적 계산 가능 여부이며, 네이버 추정치의 실제 정산 정확성 보증이 아니다. 기본 화면은 knownTotals 추정치를 사용하고 일부 항목 누락 시 짧은 표시를 한다. 네이버 stale/unverified만으로 기본 추정 숫자를 숨기거나 rebuild를 요구하지 않는다. 다른 플랫폼도 전체회사 순이익 정확성을 보증하지 않는다.

coverage 필드: `sourceSystem,scopeKey,date,participation,collectionState,rowsPresent,zeroConfirmed,selectedSource,selectedUploadId,sourceVersion,collectedAt,sourceAsOf,calculatedAt,lastSuccessAt,sourceFingerprint,nameRuleVersion,costRuleVersion,mappedRows,unmappedRows,unmatchedAmount,missingCostRows,missingFxAmount,unallocatedAmount,issues`. rows 없음≠0건완료. 네이버 현 order_sync_states=0은 갱신 보장 미확인 표시에만 사용한다.

집계 버전 입력은 주문·광고 업로드/선택 정책·원가·이름·배분·환율의 지문이다. 네이버 stored profit-v2만으로 최신 집계 인정 금지. 원천/계정/날짜 범위 안의 일별 결과+coverage+공통잔액을 동일 run으로 원자 발행한다. 실패하면 이전 발행값과 stale 표시 유지, checkpoint 재개와 멱등 upsert로 중복 금액 방지.

첫 갱신은 수집 성공 후 및 관리자 rebuild, 최근 7일은 일별 재대조, 과거 삭제/소급 변경은 영향기간 rebuild로 처리한다. 실제 운영 주기/스케줄 적용은 10 검증 후 11에서만 한다. watermark만으로 삭제/0건정정/과거원가 변경이 검출됐다고 주장하지 않는다. 조회에서 자동 전체 재집계하지 않는다. 네이버는 읽을 수 있는 저장 추정결과도 버전/시각/한계와 함께 사용할 수 있으며 지문 부재만으로 재계산을 강제하지 않는다. 원천별 완결 버전을 독립 발행해 네이버 실패가 다른 원천 발행을 막지 않도록 하고 조회는 일관된 버전 묶음을 선택한다.

## 9 기간 비교와 관계분석

기본 조회는 어제까지 최근30일, 공통 데이터가 짧으면 보유기간/참고 상태를 표시한다. 직전 동일 일수 비교를 기본으로 직접 지정·요일 비교 허용. 주/월은 선택 범위 내 사실만 합산, 일별 퍼센트를 평균하지 않는다. 오늘/이번달은 잠정 표시.

`change=now-before`, `changePct=change/before×100`, `adShare=mediumSpend/selectedTotalAdSpend×100`, `shareChangePp=shareNow-shareBefore`, `spendChangeContributionPp=(mediumNow-mediumBefore)/selectedTotalBefore×100`, `MER=selectedRevenue/selectedAdSpend`. MER는 매출/광고가 함께 선택되고 광고비>0일 때만 계산한다. 분모0이면 비율 null+`ZERO_BASE`; 이익의 이전값 음수면 증감액만 기본 표시하고 비율은 null+`NON_POSITIVE_PROFIT_BASE`다. 누락은0으로 채워 비교하지 않는다.

매출과 이익의 선택 플랫폼 범위는 현재/비교 기간에 동일해야 한다. 관계분석은 관측 변화/시차만 표현하며 인과효과로 단정하지 않는다. 네이버를 포함/제외한 상태도 분석 메타데이터에 기록한다. 관계 계수의 초기 표시 기준은 유효 일별 쌍60개 이상, 양쪽 분산>0이며 기준/실제 표본수를 응답한다. 이는 통계적 보장이 아니다. 부족하면 관계 계수만 null이며 나머지 조회는 유지한다. 네이버의 추정 신뢰 표시만으로 표본을 제외하지 않는다.

## 10 API 초안

모든 조회는 `data.read` 및 허용 scope 확인. `GET /api/unified-performance/{options,summary,timeseries,diagnostics,relationships}`. 제품/규칙/배분/rebuild 권한은 기존 계획의 products.manage/mappings.manage/operations.run 유지.

## 11 네이버 최소 권한과 격리 준비

현재 카탈로그에서 `meta_ads_app` 및 실제 운영 역할 `meta_ads_prod_runtime` 모두 네이버 조사 대상 SELECT 불가. 관리 연결의 읽기 성공은 런타임 역할 검증이 아니다. 01에서 역할/권한/RLS/DB를 변경하지 않았다.

집계 reader 후보 `unified_naver_reader`: `public` USAGE와 다음 원천의 SELECT만. 기본 목록은 stores,order_items,order_source_signatures,products,canonical_sales_units,ad_campaign_daily_costs,ad_excel_uploads,sales_unit_cost_settings,sales_unit_cost_snapshots,sales_unit_cost_snapshot_entries,daily_fake_purchases,order_sync_states다. source-read 경로가 실제 참조할 때만 order_sync_batches/order_sync_batch_items/operations 및 광고명 규칙 테이블을 추가한다. stored profit 2개 테이블은 선택적 대조 프로파일로 분리한다. reader가 기존 매핑을 이름 복원에만 쓴다는 원칙 유지.

JSONB payload SELECT는 역할 자체에 원문 전체 접근을 주므로 projection만으로 DB 수준의 민감필드 차단을 보장하지 않는다. reader는 서버 전용, 필요한 필드만 추출하고 로그/API에 주문정보·원 payload를 내보내지 않는다. 더 좁은 DB 경계가 필요하면 별도 안전 projection과 RLS/뷰 실행권한을 검증한다. 인증/토큰/credential 테이블·권한회피 SECURITY DEFINER는 사용하지 않는다. 역할은 소유자/SUPERUSER/BYPASSRLS/쓰기 권한 불가.

02의 격리 검증은 운영과 **다른 프로젝트 또는 host/database**인 빈 PG17부터 준비한다. 연결 목적지 allowlist·database/current_user를 확인하고 불일치 시 중단한다. 관리 역할을 런타임 테스트로 대체하지 않는다. 운영 PII 복제 없이 합성 표본으로 필요한 JSONB 테이블/인덱스와 통합 meta_ads 모델을 재현한다. reader SELECT 성공·원천 DML 및 인증정보SELECT 거부, 집계writer만 신규 집계쓰기, API역할만 허용집계읽기를 검증한다.

운영 권한 변경은 10에서 최소 SQL/회수SQL·그랜트 목록·실제역할 접속 검증을 준비하고 11에만 반영한다. 네이버 테이블을 현 Prisma 소유로 편입하거나 파괴적 FK를 만들지 않는다. 플랫폼 체크박스는 서버의 scope 권한을 넓히지 않는다.

## 12 후속 인수 기준과 남은 기술 검증

02는 이 버전의 이름/판매단위/참여선택 타입과 격리 기반만 구현한다. 03~05는 하루/7일 어댑터 결과를 본 원천 기준선과 비교하고, 06은 구성요소·보존·포함선택 불변식을 검증한다. 08은 체크박스·숫자·URL/캐시/새로고침·빈선택·추정표시, 09는 analysisMedia 변경 시 총액불변, 10은 선택범위 전체 회귀를 검증한다.

필수 보존: 이름/ID 변경 후 자동 분류, 같은명 서로 다른 주문 보존, 단품/세트 비용 분리, 광고·쿠폰·VAT·배송·가구매 1회, 원천액=귀속+미분류+미배분, 사용제외 원천은 숫자/품질에서 함께 제외, 미수집 null 유지. 네이버 정확도 개선·완전한 수집 이력 확보는 선행 인수 조건이 아니다.

미실행 기술 검증: 런타임 실제 접속 권한, 실제 비용 선택기 전체 유효일 대조, API/화면/통합집계의 운영금액 일치. 이들은 해당 구현 단계에서 수행한다. 현재 조사 범위와 미확인 항목을 숨기지 않되 01의 업무 결정을 다시 요구하는 조건으로 삼지 않는다.

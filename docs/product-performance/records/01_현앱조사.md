## 2 계정·원천·중복 경계

- **Meta/Cafe24:** `common/source-read-policy.ts:61`의 `selectCurrentSourceRows`를 사용한다. 기능 OFF는 CSV만, ON은 연결·종류·날짜별 유효한 정책 1개를 요구한다. 정책은 `[fromDate,toDate)`이며 API 날짜에는 수집/행수/연결/버전 증거를 검사한다. API 정책 실패를 CSV 자동 fallback으로 숨기지 않는다. 이미 선택한 현재 버전만 어댑터에 전달한다.
- **Meta:** 비용 합계는 `meta_adset_daily_metrics` 한 계층만 사용한다. 개별 광고 비용과 함께 더하지 않는다. 광고의 구매 전환수×설정가로 계산된 기존 Meta 보고서 매출(`domain/margin-calculator.ts:61`)은 Cafe24 실제 판매와 합산하지 않는다.
- **Google:** `google-read.service.ts:52` 이하 읽기는 트랜잭션 안에서 원천·커버리지·link·현재 버전을 대조한다. 통화/계정 시간대도 조회한다. 날짜·캠페인·계정·버전의 유일 키는 `schema.prisma:1957`. 보고서 최대 구간은 92일(`google-read.service.ts:24`).
- **Cafe24:** 주문 행의 외부 키는 `domain/cafe24-csv.ts:282`의 주문번호+품목주문번호+상품번호+옵션. 통합 사실은 연결/원천/버전까지 범위를 보존한다. 같은 이름인 다른 주문은 제거하지 않는다. API/CSV의 이름 문자열이 같다는 이유로 두 원천을 같이 합산하지 않는다.
- **쿠팡:** `CoupangSaleLine`, `CoupangAdMetric`, `CoupangUploadBatch`에는 계정·연결 필드가 없다(`schema.prisma:1188`, `:1218`, `:1263`). 판매는 주문행이 아니라 날짜·옵션·상품명 등으로 된 보고서 집계행(`domain/coupang-sales-xlsx.ts:124`). **이번 대화에서 사용자가 업로드 계정은 하나라고 확인했다.** 기존 전체 자료를 `LEGACY_COUPANG_SINGLE_UPLOAD` 단일 범위로 계약하며 별도 계정 입력을 요구하지 않는다. 실제 계정명이나 Meta/Cafe24 계정 연결을 추정하지 않는다. SQL 조사 당시의 미식별 마커는 조사 시점 한계이며 현재 미해결 업무 결정이 아니다.
- **쿠폰 문맥:** 필터 전에 선택된 주문의 모든 품목과 오류 문맥을 읽어야 한다. Google은 주문을 connection+order로 묶고 line id로 중복을 제거한다(`google-performance.ts:129`). 선택 상품마다 주문 쿠폰 전액을 재차 차감하면 안 된다.

## 3 판매단위·비용·이익 산식

기호: 주문행의 수집 수량 `q`, 실제 제품 개수 `physicalQuantity`, 계산 판매단위 수량 `calculationQuantity`, 등록 판매단위 가격 `P`, VAT 비용 `V`, 상품원가 `C`, 배송 `S`, 기타 `E`, 배분 쿠폰 `K`, 광고비 `A`.

### Cafe24 및 Google 판매 설정

**확인 산식**(`domain/cafe24-sales-calculator.ts:35`, `sales/sales-metrics.service.ts:532`):

```text
V = P × 0.1  // resolveCost가 저장 vatKrw 값 대신 재계산하는 기존 업무 정책
operatingRevenue = P × calculationQuantity
grossDirectCost = (V + C + S + E) × calculationQuantity
profitBeforeAds = operatingRevenue - grossDirectCost - K
profitAfterAds = profitBeforeAds - A
```

1. 판매단위 override가 null이면 상품 원가 규칙 필드로 fallback하며, 모두 없는 상품은 완전 이익을 null 처리한다. 원가 이력은 날짜 유효 규칙을 사용한다.
2. Cafe24의 기존 `1+1` 판정은 규칙 displayName/별칭/옵션 포함어에 `1+1` 또는 포함어 배열에 단독 `+`가 있으면 참(`sales-metrics.service.ts:872`). `physicalQuantity=q×2`지만 **가격과 비용의 calculationQuantity=q**이다. 단품은 두 수량 모두 q다. 세트 가격에 실물수량을 다시 곱하면 안 된다.
3. Google SALE 설정 4개(판매가·원가·배송·기타)가 있으면 4개 전부를 요구하고, `quantity=calculationQuantity=collectedQuantity=q`이며 `saleUnitLabel`을 보존한다. “1+1” 문자열 때문에 다시 두 배 하지 않는다(`google-sale-configuration.ts:6`). 4항목이 없을 때만 기존 Cafe24 bundle 표시 수량을 상속한다.
4. Google의 기존 `[유튜브]` 판매 설정은 원천이 Cafe24다. 상품번호+옵션+기간의 기존 설정을 **기준 제품명+판매단위/옵션 이름+기간** 계약으로 옮겨야 한다(`google-read.service.ts:184`). 이 설정과 Cafe24 규칙이 같은 행에 서로 다른 가격/원가를 주면 두 매출을 더하지 말고 하나의 명시적 판매 설정 선택 정책이 필요하다.
5. 등록 배송비는 주문 배송비 실지급액이 아니라 계산 판매단위당 비용이다. 실제 결제액의 배송 항목과 임의 상계하거나 재차 차감하지 않는다.
6. `totalPaidKrw`/`actualPaymentKrw`는 API 주문의 각 행에 반복 저장된다(`daily-sync/cafe24-order-adapter.ts:170`). **실결제 총액은 주문 범위당 1회만** 읽는다. `aggregateSales`의 행별 totalPaid 합은 통합 실결제 총액으로 재사용하지 않는다. 행별 실결제 배분은 별도 계약이 없는 한 null이다.
7. 현재 Cafe24 API projection은 orderStatus/lineStatus를 수집하지만 cancelled/refunded 금액·시각을 null로 둔다(`cafe24-order-adapter.ts:179`). `Cafe24OrderLine`에는 개별 취소/환불 금액 컬럼이 없고, 기존 판매 조회는 주로 현재·비오류 행이다. 이를 환불 조정까지 끝난 실결제 순매출이라고 표시할 수 없다. 삭제/현재 버전 교체와 수집 현황을 별도로 추적한다.

### 쿠폰

**확인**(`domain/cafe24-coupon-matcher.ts:73`, `:343`): CSV의 쿠폰 결제수단 토큰 또는 API의 providerCouponSignal을 사용한다. API 신호/정책상 금액 기초가 모르면 UNKNOWN이다. 주문 총주문액과 결제액의 차액, 날짜·품목 완전성, 적용기간을 검사해 등록 쿠폰 금액을 결정한다. 배분은 적용 품목의 수집 판매가×수량을 가중치로 0.01원 단위 최대 나머지 방식으로 보존한다. 1원 이내 차이는 EXACT, 큰 잔차는 ESTIMATED와 ignoredResidual로 보존한다.

차액 전체가 항상 쿠폰은 아니다. 확인된 등록 쿠폰만 `K`로 1회 차감하고 잔차를 추가 비용으로 꾸미지 않는다. 미해결 쿠폰은 0원으로 메우지 않는다. 기존 Cafe24 서비스는 특히 unknown을 null로 전파하고, 신규 Google 계산은 미해결 상태도 이익을 막으므로 통합 품질 계약은 더 엄격한 “모르는 쿠폰은 완전 이익 null”을 사용해야 한다.

### 쿠팡 정상판매·취소·가구매

**확인 산식**(`domain/coupang-sales-xlsx.ts:197`):

```text
SALES_IS_NET:       reportedNet = salesKrw
NEGATIVE_ADD:       reportedNet = salesKrw + cancelAmountKrw
POSITIVE_SUBTRACT:  reportedNet = salesKrw - abs(cancelAmountKrw)
normalNetRevenue = reportedNet - manualPurchaseSalesAmount
normalQuantity = reportedQuantity - manualPurchaseQuantity
```

취소는 수집 시 선택한 모드로 `net_sales_krw`에 이미 반영되므로 통합 집계에서 취소액을 다시 차감하지 않는다. 기본 모드는 SALES_IS_NET이며 업로드 배치의 실제 모드가 증거다.

**확인 산식**(`domain/coupang-profit-calculator.ts:98`, `:156`, `coupang-profit-pipeline.ts:353`):

```text
productCost = normalQuantity × unitProductCost
salesFee = normalNetRevenue × globalEffectiveSalesFeeRate
sellerLogistics = sellerNormalQuantity × sellerShippingFee
growthLogistics = growthNormalQuantity × (hanaroShippingFee + growthInboundFee + growthShippingFee)
expectedReturnCost = normalQuantity × returnRate × returnCostPerUnit
otherCost = normalQuantity × extraCostPerUnit
VAT = normalNetRevenue / 11
profitBeforeAds = normalNetRevenue - productCost - salesFee - sellerLogistics
                  - growthLogistics - expectedReturnCost - otherCost - VAT - manualVendorFee
profitAfterAds = profitBeforeAds - coupangAdSpend
```

- 가구매는 매출·수량에서 제외한 정상판매를 먼저 계산한다. 가구매 비용은 현 정책에서 **대행수수료만**이다. 별도 가구매 상품원가·플랫폼수수료·배송·기타·VAT를 다시 더하지 않는다(`calculateCoupangManualPurchaseCost:230`, `aggregateManualPurchasesByProductDate:136`). 저장 스냅샷의 수수료 합계 불일치·중복·누락이면 완전 이익 null.
- 가구매 판매금액은 양수 저장값을 우선, 없으면 기준판매가×수량 fallback과 경고를 사용한다. 판촉가를 임의 적용하지 않는다(`resolveManualPurchaseSalesAmount:184`). 보고서 판매가 없는데 가구매만 있는 경우 경고·계산 불가를 유지한다.
- 가구매 제외는 SELLER 먼저, GROWTH 나중으로 수량을 배정하고 판매금액은 제외 수량 비율로 나누며 나머지를 보존한다(`deductManualPurchaseFromReportedSegments:280`). 이는 실제 가구매 배송 방식의 식별 증거와 다르다.
- 정상판매 비용은 현재 pipeline이 조정 후 세그먼트를 인식/발생 양쪽 기준에 전달한다. 저수준 `calculateCoupangProfitByAccountingBases`가 다른 기준을 지원한다고 기존 서비스가 조정 전 비용을 차감한다고 해석하면 안 된다.
- 판매 수수료는 날짜 유효한 **전역 수수료 규칙**이다. 상품별 원가 테이블의 과거 salesFeeRate/salesFeeKrw를 다시 비용으로 합산하지 않는다.
- 실제 반품 차감액과 `quantity×반품률×단가`의 추정 반품비를 구분한다. 원가/배송/가구매 스냅샷/수수료 미입력은 0원이 아니다.

## 4 광고비·환율·날짜

| 원천 | 확인 산식·기초 | 통합 인계 |
| --- | --- | --- |
| Meta | 선택된 adset 현재 행 `spend_usd × date별 USD/KRW`; `sales-metrics.service.ts:608` | 날짜별 `exchange_rates` 우선, 없으면 상품 원가의 legacy fx를 쓰는 기존 경로가 있다. 적용 rate/provider/sourceDate/fallbackType을 원금액과 함께 기록한다. Fx 없는 유효 지출은 원통화 금액만 알려져 있고 KRW 총액 null. |
| Google | `cost_micros / 1,000,000 × rate`; `google-performance.ts:209` 이후 | BigInt를 number로 먼저 바꾸지 않는다. KRW rate=1, 외화는 일자별 유효 rate 필요. Decimal clone precision=80으로 내부 계산하되 기존 응답에는 number와 exact string이 함께 있다. 신규 계약의 금액 경계는 Decimal string이어야 한다. |
| 쿠팡 | KRW 원천 `ad_spend_krw` | 광고전환매출을 판매 매출에 더하지 않는다. 실행 상품 비용만 1회 귀속하며 미분류 광고비는 별도 잔액으로 보존. |

날짜: Cafe24 API 주문일은 주문 시각을 `Asia/Seoul`로 변환한 일자(`cafe24-order-adapter.ts:87`). Meta/Google 광고는 계정 보고 일자와 시간대를 보존한다. Google 읽기는 Asia/Seoul이 아닌 계정에 TIME_ZONE_MISMATCH를 주고 완전 손익을 막는다(`google-read.service.ts:220`). 쿠팡은 saleDate/metricDate; 날짜 없는 판매행에는 업로드 입력일 또는 파일명 fallback이 있으므로 origin을 추적한다. UTC 자정에 저장된 Date는 업무일자 운반 형식이며 시각이라고 재해석해 9시간 이동하지 않는다(`domain/date-number.ts:8`).

`exchange-rates.service.ts:41`의 환율 수집은 정확일→과거 탐색/저장 fallback→최신값 fallback 경로를 갖는다. 사후 최신 환율을 모든 과거에 곱하지 않는다. 통합 읽기 시 환율 API를 호출하는 대신 저장된 선택값·fallback·버전을 사용하고 소급 수정 시 영향일 재계산한다.

## 5 품질·갱신 계약에 필요한 항목

현재 sourceCoverage는 연결+종류+날짜의 상태/행수/총액/성공 run/시각/경고를 보유한다(`schema.prisma:1914`). 행이 없다는 이유만으로 수집완료 0원을 만들지 않는다. Cafe24/Meta API 일자는 소스 정책과 링크/현재 버전/행수 대조까지 통과해야 한다. Google 읽기도 비용 합계와 coverage를 대조한다. 쿠팡 업로드는 완전 배치·현재·비오류 원천을 쓰지만 계정·일별 수집완료 0건 증거는 별도 준비가 필요하다.

**통합 계약 제안:** 어댑터가 원천/스키마/테이블/원천 키·버전·기초일·수집시각, 계정 식별 상태, 이름 원문·규칙 버전·판정, 판매단위/physicalQuantity/calculationQuantity, 원가 선택/유효일/버전, 각 직접비, 쿠폰 상태/배분, 원통화·환율 증거, 금액별 known/complete를 반환한다. 광고를 뺀 구성요소와 광고비를 분리해서 최종 집계기가 광고를 딱 한 번 차감한다. 전역 원천 합계=제품 귀속+미분류+미배분이 성립해야 한다.

원천 교체/삭제/0건 정정, 이름규칙/가격/원가/환율의 소급 변경은 과거 영향 날짜를 재발행한다. 현재 버전 필드가 있는 것만으로 삭제·소급정정 감지가 완료되는 것은 아니며 주기별 기간 재대조와 명시적 rebuild가 필요하다. 기존 보고서의 최종 이익을 입력받아 광고비를 다시 차감하는 설계는 금지한다.

### 사용자 확정: 플랫폼 포함 선택과 정확도

이번 대화의 추가 지시에 따라 통합 조회는 플랫폼별 체크박스로 데이터 포함/제외를 선택한다. 이 선택은 **계산 대상 범위**이며 선택한 범위의 총매출·광고비·이익을 바꾼다. 이미 정한 계산 범위 안에서 관계 분석의 설명 변수를 고르는 **분석용 광고매체 필터**는 총이익을 바꾸지 않는다. 두 입력을 서로 다른 필드로 관리하고 응답에 계산 대상 선택을 돌려준다.

| 원자 선택 단위 | 포함하는 사실 |
| --- | --- |
| `CAFE24` | Cafe24 판매·관련 직접비·쿠폰. Google 보고서에 노출된 Cafe24 판매도 이 판매 원천에서 한 번만 집계 |
| `META` | Meta 광고비 |
| `GOOGLE` | Google 광고비 |
| `COUPANG` | 쿠팡 판매·관련 직접비·가구매 조정과 쿠팡 광고비를 함께 포함 |
| `NAVER` | 네이버 판매·관련 직접비·DA 광고비·네이버 공통비를 함께 포함 |

쿠팡 판매만/광고만 또는 네이버 판매만/DA만을 고르는 세부 원천 선택은 후속 확장이다. 네이버를 제외하면 네이버 공통비도 범위에서 제외한다. 제외한 플랫폼의 자료를 수집 실패나 금액 0원으로 표시하지 않고 `excluded` 상태와 선택 범위로 구분한다. 최종 [플랫폼 선택과 네이버 데이터 정책](../플랫폼선택과네이버데이터정책.md)에 따라 Meta/Google 광고만 선택하면 광고비만 표시하고 매출·이익·MER는 해당 없음(null)이다. 판매만 선택하면 광고 전 이익을 표시한다. 광고 플랫폼의 전환매출로 판매를 대체하지 않는다. 공개 query는 `platforms` 배열이며 응답 선택범위와 `metricAvailability`로 적용 여부를 구분한다.

네이버 자료의 정확도가 낮아 엄격한 정확도를 요구하지 않는다는 사용자 지시를 반영한다. 네이버 일별 완전 대조 성공을 모든 통합 구현의 중단 조건으로 두지 않고, 확보한 금액·출처·기준시각·잠정/부분 상태를 노출해 사용할 수 있게 한다. 다만 확인하지 못한 비용·누락 매출을 근거 없이 0원으로 만들거나 알려진 부분 합계를 완전한 전체 금액으로 바꾸지는 않는다. 네이버가 선택되지 않은 조회는 네이버 데이터 품질 때문에 완전성 판정을 낮추지 않는다.

## 6 확인되지 않은 업무 선택과 주 담당자 인계

1. 현재 운영 이름·단품/1+1/세트 설정 표본은 위 표에 기록했다. 코드의 합성 예시나 seed를 운영 표본으로 꾸미지 않았다. 해당 일자별 원가/쿠폰의 완전성은 주 담당자의 날짜별 추가 읽기 결과로 확정한다.
2. 동일 Cafe24 행의 설정 선택은 최종 계약에서 `[유튜브]` 행의 유일하고 완전한 Google SALE 설정 우선, 없으면 Cafe24 규칙으로 확정됐다. 이 판매단위 정책은 GOOGLE 광고 체크 상태와 무관하게 유지한다. 일부 입력/복수 설정 충돌은 임의 혼합하지 않고 진단한다.
3. 쿠팡 범위는 사용자 확인으로 단일 업로드 범위에 포함하도록 해소되었다. 복수 계정 입력이나 UI를 이 단계의 선행 조건으로 만들지 않는다.
4. Cafe24 VAT 10%와 쿠팡 VAT 1/11의 차이는 기존 프로그램의 확인된 정책이다. 세무 정확성으로 일반화하지 않는다. 기존 정책 보존이 이번 범위의 기본값이며 신규 공통 VAT 재계산은 하지 않는다.
5. 실제 취소/반품 완전성, 각 날짜 수집 성공, 원가 완전성과 하루/7일 대조 금액은 이 코드 조사만으로 확인하지 않았다.

## 7 실행한 확인

- `rg`와 `Get-Content`로 위 코드·schema·초기 seed를 읽었으며, DB 접속·seed·migration·운영 API를 호출하지 않았다.
- 읽기 전용 calculator 실행: `node --import tsx -e '<Cafe24SalesCalculator/calculateCoupangProfit/calculateCoupangManualPurchaseCost 직접 호출>'` (2026-10-27, exit 0). 입력은 **합성 계산 예시**(판매가 11,000, 원가 3,000, 배송 2,000, 기타 100, 수량 1, 광고비 0; 쿠팡 수수료율 0.1188)이다. Cafe24는 저장 VAT 입력 999를 무시하고 VAT 1,100·이익 4,800, 쿠팡은 VAT 1,000·수수료 1,306.8·이익 3,593.2를 반환했다. 가구매 2개×대행수수료 500은 총비용 1,000이며 나머지 비용은 0이었다. 운영 대조 성공이 아니라 코드 산식 확인이다.
- 코드 변경이 없으므로 별도 회귀 테스트 소스를 추가하지 않았다. 전체 type/schema/build 검증은 주 담당자 결과 기록을 따른다.

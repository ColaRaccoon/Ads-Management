# 11 풀업바 전체 보유 기간 적용

2026-10-30 KST. **DONE**. 사용자 요청에 따라 풀업바의 전체 보유 기간 분류·집계와 네 그래프 표시를 완료했다. 후속 조회 옵션·관계분석 시간 초과도 보완하고 실제 정시 원천→명시 집계 주기까지 확인했다. 12단계는 시작하지 않았다.

## 원인과 적용 기준

기존 플랫폼별 풀업바 설정이 새 통합 설정에 자동으로 등록되는 구조가 아니었다. 초기 운영 검증에서 통합 NAME 규칙을 Cafe24 계정의 10/28부터 적용하고 제한된 날짜만 발행해, 과거 제품명이 있어도 통합 화면에서 분류·발행되지 않았다. 조사 시 계정에 연결된 API 원천만 먼저 확인하고 `LEGACY_UNBOUND` CSV 원천을 빠뜨린 점도 바로잡았다.

기준 제품은 풀업바 한 개다. 기존 NAME `06b05f8c-ea1a-4803-b38c-a4538ac38cfd`를 v2에서 v3으로 갱신했다. 플랫폼·계정 제한 없이 정규화한 이름에 `풀업바`가 포함되면 분류하고, 유효 시작일은 보유 풀업바의 가장 이른 날짜인 **2026-05-13**, 종료일은 미지정이다. 관측한 25개 이름 표본의 이름 단독 분류는 모두 MATCHED였다. 상품 ID는 참조 복원과 중복 방지에 사용하며 분류의 기준으로 삼지 않았다.

SALE_UNIT `7502dd56-c8fb-4d43-894e-d6d2468149ef` v1은 그대로다. 과거 금액은 각 플랫폼의 기존 날짜별 판매단위·원가·환율을 사용한다. 현재 Cafe24의 34,900원/원가 10,000원을 모든 과거·플랫폼에 복사하지 않았다. 관리 미리보기의 통합 판매단위 후보와 실제 어댑터의 과거 플랫폼 판매단위 해석을 구별해 검증했다.

## 조회·집계 시간 초과 보정

네이버 5/21 원천 읽기에서 P2028을 재현했다. 날짜 단위의 읽기 전용 RR 저장점을 공유하고, 이미 투영한 문자열 참조 ID를 바인딩해 이름 복원용 PK 조회에 사용한다. JSON 참조 타입이 잘못됐거나 투영 실패·행 한도·길이 제한을 넘으면 원래 하위 질의로 돌아간다. 내부 타입 확인 플래그는 반환 전에 제거한다. 순수 이름·원가 정규화는 DB 트랜잭션을 반환한 뒤 수행한다.

격리 PG17의 정상 값, SQL 권한 오류 복구, 잘못된 참조 타입, 10,001행 제한에서 이전 투영과 완전히 같음을 확인했다. 정상 읽기 SQL 왕복은 45→17회다. 실제 제한 worker 역할의 5/21 재조회와 최종 발행 해시는 일치하고 확인 가능한 금액 대조 차이는 0이다. 쿠팡 7/26의 한 번의 원천 실행 실패는 읽기 전용 재검증 후 새 작업으로 교체했다. 최초 원인이 특정 SQLSTATE였다고 단정하지 않는다.

새로 늘어난 발행을 읽는 프레임도 수화·누락 날짜 보완을 DB 반환 뒤 수행하도록 바꿨다. 단일 바인딩 SQL의 MVCC 프레임과 READ ONLY/RR은 보존한다. 전체 기간 프레임의 기본 5초 시간 초과를 고려해 **보고서 프레임에만 최대 20초**를 명시한다. 다른 읽기·원천 어댑터의 기본 제한, 연결 수, 격리 수준, 권한, 금액 산식은 바꾸지 않는다. 프레임 실패 로그에는 검증한 Prisma 코드만 기록하며 SQL·파라미터·원문 오류는 남기지 않는다. 100,000 fact/20,000 발행 한도도 유지한다.

추가로 큰 JSON 프레임은 PostgreSQL에서 동일 JSON의 text로 운반하고 트랜잭션 반환 뒤 해석한다. 실제 제한 report 역할로 text→object와 기존 jsonb 반환 값이 정확히 같음을 대조했다. 금액은 문자열을 유지하며 2^53보다 큰 소수 문자열도 회귀 검증했다.

조회 옵션은 선택한 풀업바를 해제하고 다른 모든 제품의 금액까지 읽던 동작을 보정했다. 제품·계정 대안 목록은 같은 MVCC 프레임에서 이름 열만 DISTINCT로 투영해 유지한다. 실제 119개 이름·8개 플랫폼/계정 범위를 확인했다. 옵션을 위해 다른 제품의 재무 payload를 전부 읽지 않으며 사용자 선택·이익 계산은 바꾸지 않는다.

통합·Google API **304개**, 웹 전체 **111개**, API·웹 38페이지 빌드, 원천 설정 guard **10개**를 통과했다. 유지보수 TypeScript 의미 검사도 오류0이다. 성능 프로파일은 제한 report 역할로 SELECT만 실행했고 원천 호출·쓰기 없이 시간과 프레임 크기만 저장했다. 프로파일용 20초 트랜잭션과 실제 source 기본 제한을 구별한다.

복귀는 기존 11단계 순서를 따른다. 새 집계 중지→기능 OFF→검증한 이전 source와 RELEASE_GIT_SHA로 복귀 후 정확 readiness를 확인한다. 배포 브랜치는 고정하고 후속 증거는 개발 브랜치에만 push한다. 데이터/감사/실패 이력을 역삭제하지 않는다. 향후 이름 규칙을 변경할 때도 새 버전과 영향 범위를 남긴다. 12단계는 시작하지 않았다.

# 01 계약 독립 검토

검토일: 2026-10-27 KST. 검토자: `current_sources` (현 앱 조사 담당, 계약 작성자가 아님). 대상: `01_확정계약.md` 초안 `product-performance-v1.0.0`. 검토 당시 181행이며 아래 행 번호는 초안 기준이다. 이 검토 파일만 작성했고 계약·운영 설정을 직접 수정하지 않았다.

## 지적과 수정 제안

### R1 [P1] 미배분 광고비가 범위 총이익 산식에서 누락됨

- 위치: 계약 73~81행, 121행, 133행.
- 근거: 제품 `P`는 제품에 귀속된 selectedAdSpend를 차감한다. `AdSpendFact`는 `UNALLOCATED`도 허용한다. 네이버 현 화면이 제외하던 광고비도 통합 계정 총광고비에서 보존해야 한다(`01_네이버조사.md` 광고 선택 절). 그런데 `selectedScopeProfit=sum(P)+unallocatedShippingIncome-unallocatedCommonExpense`에는 미배분 광고비가 없다.
- 영향: 광고비 원천 총액과 제품별 광고비+미배분액이 맞더라도 계정 총이익이 미배분 광고비만큼 높아진다. 예를 들어 제품 광고 전 이익 100, 제품귀속 광고 10, 미배분 광고 5이면 계정 이익은 85여야 하나 초안 산식은 90이다. 이 수치는 합성 산식 예시다.
- 수정안: 범위 총이익에서 **미배분 광고비를 한 번 더 차감**한다. `selectedScopeProfit = sum(productProfitAfterAllocatedCosts) - unallocatedAdSpend + unallocatedShippingIncome - unallocatedCommonExpense`. 미분류 광고비도 제품배정에 들지 않은 잔액 안에서 서로 겹치지 않게 포함한다. `unallocatedAdSpend`를 API 집계/진단에 명시한다. 제품의 직접 광고비와 잔액을 함께 다시 전액 차감하지 않는다.

### R2 [P2] knownTotals의 이익이 공통잔액을 포함하는지 서로 다름

- 위치: 계약 78~81행, 131~133행, 155~157행.
- 근거: 133행은 knownTotals 이익을 “계산 가능한 제품 이익 합”으로 정의하지만 78행은 배송수입/공통비 미배분 잔액을 범위 이익에 반영한다. summary 최상단과 제품 item이 같은 estimatedProfit 필드를 쓴다.
- 영향: 네이버 가구매/배송 공통비가 기본 미배분이므로 기본 KPI가 이 잔액을 무시하거나 scope와 제품 합계가 설명 없이 달라질 수 있다.
- 수정안: `knownTotals.productProfitSubtotal`과 `knownTotals.estimatedProfit`의 의미를 구분하거나, 최상위 estimatedProfit은 R1의 잔액 반영 산식을 따르고 제품 item은 배분 전 부분이익임을 명시한다. 모르는 제품 이익은 0 대입하지 않고 “계산 가능한 부분합”과 제외 구성 수를 함께 반환한다. 확인된 미배분 비용은 known 범위 이익에서 누락하지 않는다.

### R3 [P2] 제품 필터에 공통잔액 전액을 반복 귀속할 여지가 있음

- 위치: 계약 81행, 99행, 153~157행.
- 근거: API는 productName 필터를 받으나 필터된 이익과 미배분 계정 공통잔액의 관계가 명시되지 않았다. 이름 제품마다 전체 네이버 가구매·배송·미배분 광고 잔액을 전액 붙이면 제품을 각각 조회했을 때 총액이 반복된다.
- 수정안: 제품 필터 이익에는 해당 제품에 직접 귀속/명시 배분된 금액만 사용하고, 미배분액은 별도 **계정 범위 참고 잔액**으로 반환한다. productName이 없는 계정 범위 합계에서만 미배분 잔액을 1회 반영한다. 제품 필터를 바꿔 원래 배분모수를 재계산하거나 잔액을 임의 배분하지 않는다. 범위 표시와 제품 부분합의 차이는 잔액으로 설명한다.

### R4 [P2] 0원 표시 조건이 플랫폼 일부 선택과 충돌

- 위치: 계약 24행과 26행.
- 근거: “전부 선택된 0건 완료 기간만 금액 0”은 체크박스 전부 선택을 요구하는 것으로 읽힌다. 그러나 26행은 Meta만 선택한 경우 매출 0을 표시한다. Cafe24만 선택한 수집완료 0건 기간도 합계 0이어야 한다.
- 수정안: “선택 범위 안의 적용 구성요소가 완료 0임이 확인되면 0, 구조적으로 선택하지 않은 구성요소는 범위 산식에서 0 기여, 누락 구성요소는 null; 빈 선택 KPI는 null”로 구분한다. 적용하지 않는 성분과 수집 실패를 섞지 않는다.

## 확인한 일관성과 보완 권고

- 사용자 확인한 쿠팡 단일 업로드 범위와 5개 원자 플랫폼 토글이 반영됐다. 포함선택이 합계를 바꾸는 것과 analysisMedia만 바꿀 때 총이익이 유지되는 것은 양립한다.
- Cafe24/Google 판매가·VAT·쿠폰·판매단위 경계와 쿠팡 가구매 정상판매 조정은 현재 코드 조사에 부합한다. `[유튜브]` 완전 SALE 설정 우선 정책은 명시됐으며 **GOOGLE 광고비 체크 해제와 관계없이 CAFE24 판매단위 정책을 유지**한다는 설명을 추가하면 구현 오해를 줄일 수 있다. 판매 설정은 광고 포함선택의 부수효과로 바뀌지 않아야 한다.
- 제품명/옵션을 보존하는 NFC 정규화, 유일 후보 확정, ID는 참조·중복방지용이라는 원칙이 일관된다. 단품/세트 수량과 비용 계산수량도 구분됐다.
- Decimal string 경계, micros 정확 환산, 환율 출처/버전, 원천 정책 기간과 원가 기간 차이, 공개 응답의 주문키 비노출이 명시됐다. 원 단위 배분과 신규 저장 소수6자리 사이의 잔액은 ControlTotal.roundingAdjustment로 기록하는 구현 검증이 필요하며 현재 실제 구현 성공을 주장하지 않는다.
- 포함선택은 저장된 원자 구성요소의 읽기 조합이므로 체크 변경이 rebuild/원천 변경을 유발하지 않는 정책이 타당하다. 네이버 추정치 조회를 정확도 미확인 때문에 차단하지 않는 사용자 지시도 반영됐다. 알려진 부분 금액과 완전금액 구분을 유지한다.
- reader 최소 권한은 계획이며 실제 런타임 접속 검증/GRANT 실행 성공으로 오인하지 않는다. 01단계에서 운영 변경이 없다는 기록에 부합한다.

## DONE 적정성

R1~R4의 산식/표시 범위 충돌을 해소하고 결과 기록에 해소 내역을 남기면 01을 DONE으로 표시할 수 있다. 현재 확인된 업무 선택(쿠팡 범위, 플랫폼 선택, 기존 추정 정책 보존, 네이버 정확도 허용) 때문에 별도 사용자 재확인이 필요하지 않다.

이 단계는 기준선과 계약 단계다. 실제 통합 어댑터·API·화면, 비용 선택기 전체 유효일 대조, 실제 런타임 역할 테스트와 완전한 네이버 최신 취소 이력은 아직 구현 검증하지 않았으며 해당 후속 단계의 인수조건으로 남기는 것이 타당하다. 네이버의 모든 미확인 자료를 해결해야 01이 완료된다는 조건을 새로 만들지 않는다.

플랫폼 공개 API는 JSON 배열 query값 `platforms`로 통일됐고 명시 빈 배열과 생략 기본값이 구분된다. 응답의 `selectedPlatforms/excludedPlatforms`, `scopeLabel`, `metricAvailability`, 선택 캐시·URL, 원천별 발행/기준시각도 추가 정책과 맞는다. 네이버는 기존 저장 추정결과를 버전/시각/한계와 함께 사용하도록 허용하며 지문 부재만으로 재계산을 강요하지 않는다. 계산 가능한 추정값과 누락 null을 구별하므로 정확도 허용이 무근거 0원 보충으로 이어지지 않는다.

재검토 중 보완 권고 2개를 주 담당자에게 전달했다. `동일 run 원자발행`의 단위를 원천/계정/날짜 내부로 명시해 독립 발행과 일치시키고, 추가 정책에 있는 선택범위 MER의 API 필드·산식(`선택 매출÷선택 광고비`, 판매/광고 선택·0분모 구분)을 적으면 후속 구현의 해석 차이를 줄일 수 있다. 사용자에게 새로운 업무 결정을 요구하는 사항은 아니다.

**재검토 판단:** R1~R5의 원래 지적은 모두 해소됐다. 실제 구현 검증은 후속 단계에 남기되, 이 단계의 기준선·업무 계약 완료를 막는 미해결 업무 결정은 확인되지 않았다. 01 결과 기록에 실제 검증/미검증 범위를 보존하고 DONE으로 인계할 수 있다.

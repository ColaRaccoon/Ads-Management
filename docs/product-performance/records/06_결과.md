## 계산·품질·스냅샷 결정

선택은 원천별 기존 배분 결과 위에서 적용한다. 제외 비용을 다른 판매처/제품에 다시 배분하지 않는다. Meta/Google에는 Cafe24 매출을 붙이지 않는다. 범위의 추정이익은 확인된 광고 전 이익−선택 광고비−선택 공통비+선택 배송수입이다. 제품이익 소계와 무분류 판매이익/미배분 광고·비용·배송수입을 함께 반환하여 전체 범위와 대조한다.

빈 선택은 KPI null이며 광고만 선택하면 매출·이익·MER는 해당 없음이다. 완전한 0, 미수집 null, 원가·환율 누락, 미분류·미배분을 구별한다. NAVER ESTIMATED와 기존 지문 부재 자체는 수치 완전성을 차단하지 않는다. NAVER의 비용 coverage는 원래 SALE의 비용 진단을 상속하며 없는 원가를 생성하지 않는다. Cafe24/쿠팡의 별도 공통비 사실이 없을 때는 직접비에 포함된 비용을 두 번 차감하지 않도록 COMMON_EXPENSE를 NOT_APPLICABLE로 보강한다.

제품 필터에서는 해당 원천 미분류 사실을 제품 0원으로 확정하지 않는다. 정상 제품의 직접 이익에 다른 제품만의 원가 누락을 전파하지 않는다. 미배분 공통 잔액이 있으면 완전 배분 이익을 주장하지 않는다. 원문·주문키는 공개하지 않는다.

보고서 버전은 현재 설정 버전과 분리한다. 실제 발행 버전이 여러 개면 MIXED와 run별 버전을 반환한다. 참여 정책도 발행 시점의 `participationOverrides`에 고정하여 새 설정이 이전 정상 숫자를 즉시 바꾸지 않게 했다. 현재 설정과 차이가 있으면 경고하고 명시적 rebuild로 반영한다. 기준 제품명 변경 후에도 발행된 역사 이름 행과 옵션을 보존한다.

원천별 포인터·사실·coverage·실패 상태는 한 읽기 스냅샷으로 묶는다. 실패/만료된 실행 이후에도 이전 발행값을 유지하며 STALE을 표시한다. pagination cursor에는 조건/발행/실패/설정/허용 범위를 포함해 다른 선택이나 다른 발행 버전의 페이지 혼합을 거부한다. 캐시는 새로 만들지 않고 HTTP no-store다.

SALE/AD_SPEND 개별 행의 논리키 해시·이름입력 해시·규칙/원천 버전·판정·원금액은 내부 `UnifiedProductMatchResult`에 저장한다. 원문명·옵션·주문키·전체 SourceRef는 보존하지 않는다. 공통비 계보는 종류·범위·날짜별 compact 사실, controlTotals와 원천 지문 수준이며 별도의 주문별 이름 판정을 만들어내지 않는다.

## 병렬 분담과 독립 검토

A `calculation`: 순수 계산·배분·비교, 28개 회귀, 기존 4개 replay hook와 실제 통합 대조 도구를 소유했다. B `publication`: 큐/worker/repository/CLI와 10개 실행 경계 회귀를 소유했다. C `security_review`: 구현 코드 수정과 분리하여 권한·실패 복구를 검토하고 신규 PG17 실제 역할 통합 fixture를 소유했다. 주 담당은 공통 계약·schema/migration·모듈·API·API 9개 회귀·통합·문서·Git을 맡았다. 서브에이전트는 Git index/branch/commit/push를 조작하지 않았다.

주요 지적과 해결:

1. READY를 STAGING으로 되돌려 사실을 바꾸는 우회 → DB trigger는 READY→PUBLISHED 전이만 허용하며 READY 사실 추가/삭제/수정을 거부한다.
2. 불변 trigger와 발행 checkpoint 변경 충돌 → 마지막 발행은 상태·시각·lease 정리만 하고 공개 phase는 status에서 계산한다.
3. 제품 SQL 필터가 null 제품 잔액을 지우는 문제 → 해당 제품 OR productName:null을 유지하고 계산기에서 제품 귀속을 분리한다.
4. coverage×실패 이중 스캔/전 제품 페이지 계산 → 키 Set/Map과 페이지 대상 제품 계산으로 제한한다.
5. compact 변환 뒤 금액 누락/증식이 발행될 가능성 → 발행 경계에서 원천 판매/이익/광고 KRW·원통화/공통비와 직접 보존 대조한다.
6. 현재 참여 정책이 과거 버전에 섞이는 문제 → 발행 run에 정책을 고정하고 실제 역할 fixture에서 설정 변경 후 조회 불변을 검증했다.
7. 웹 역할에 발행 권한을 줄 위험 → API는 제한된 STAGING 큐 INSERT만, writer만 사실/포인터 쓰기라는 실제 역할을 검증했다.
8. NAVER 비용 coverage 부재와 Cafe24/쿠팡 공통비 표현 차이 → 기존 어댑터의 의미를 보존하는 명시적 보강과 회귀를 추가했다.

초기 API 회귀의 괄호 문법 오류, repository null narrowing 타입 오류와 fixture의 SourceConnection 메타데이터 SELECT 정책 누락은 수정 후 재검증했다. 운영 권한이나 관리 역할로 우회하지 않았다.

## 재집계와 다음 단계

1. 격리 환경의 feature flag/전용 집계 역할/허용 범위를 준비한다. 운영 자격증명·GRANT·예약은 이 단계에서 적용하지 않는다.
2. 권한 있는 운영자가 rebuild API에 과거 from/to 또는 최근 7일 from/to를 넣는다. 예시와 반환 jobs는 `06_API계약.md`를 따른다. 이름·원가·환율·원천 교체를 반영할 때 새 멱등 키를 사용한다. productNames는 영향 힌트이며 원천 하루 전체를 발행한다.
3. `$env:TSX_TSCONFIG_PATH='apps/api/tsconfig.json'` 설정 후 `node --import tsx scripts/unified-aggregation-worker.ts --limit=100` 또는 `--job=<jobId>`를 실행한다. 전용 URL은 서버 설정으로만 주입한다. CLI 출력/오류에는 URL·원천 이름·주문키를 쓰지 않는다.
4. 작업 상태와 diagnostics를 조회한다. 중도 중단은 lease 만료 후 재개, 확정 실패는 새 요청으로 재시도한다. 조회 화면이 실행을 대신 시작하지 않는다.

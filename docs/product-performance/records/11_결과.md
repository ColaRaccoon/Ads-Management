설정 변경에 따른 재배포 metadata가 source pin과 달리 개발 브랜치 최신 SHA를 표시한 사례를 확인했다. 당시 앱/배포 소스 diff는0이었으나 정확 SHA 추적을 위해 운영 브랜치를 개발·기록 브랜치와 분리했다. 최초 고정 운영은 codex/product-performance-stage11-frame-release의 e37c6de였고, 후속 그래프 보정 당시에는 codex/product-performance-stage11-chart-release의 d9086a6이었다. 현재 전체 기간 보정은 위 표의 history-options-release/44cd2a5이며 이전 릴리스 브랜치를 이동시키지 않았다. deployment metadata·source·readiness SHA를 일치시켰다. 기록 push로 두 릴리스 브랜치를 갱신하지 않는다.

중단 조건은 금액 보존 차이, 제외 플랫폼 잔존, 권한 누출, 기존 업무 회귀, 반복되는 지연/연결·메모리 한도/수집 지연이다. 새 큐/worker 중지→feature OFF→필요시 검증된 이전 source와 RELEASE_GIT_SHA로 복귀한다. source 연결과 실제 배포 metadata·readiness를 모두 재확인한다. 신규 테이블·발행·audit를 역삭제하지 않으며 공유 DB 전체 복원을 기능 롤백 수단으로 쓰지 않는다. 이번에 실제 OFF 복귀를 수행했으나 운영 DB 전체 복원 성공을 주장하지 않는다.

# 02 저장·분류 후속 계약

계약 `product-performance-v1.1.0`, 2026-10-27 KST. 01 문서는 변경하지 않는다. `01_확정계약.md`를 유지하고 `플랫폼선택과네이버데이터정책.md`의 플랫폼/추정치 정책을 다음 구현 경계에 반영했다.

## 01과의 차이 및 명확화

- 공개 조회 인자는 `platforms`다. JSON 배열 문자열 또는 내부 배열을 정규화한다. 생략은 5개 전체, `[]`는 전체 해제, 중복·순서는 표준 순서로 정리하고 미허용 값은 거부한다. 기본 전체는 연결 활성화나 수집 범위 변경이 아니다.
- 선택은 합계에 영향을 준다. Meta/Google 선택은 광고만, Cafe24는 판매와 해당 비용만, 네이버/쿠팡은 각각 판매·직접비·광고·공통비를 포함한다. `analysisMedia`나 범례 숨김과 구별한다. 제외 비용을 다른 플랫폼에 재배분하지 않는다.
- `selectedPlatforms`, `excludedPlatforms`, `scopeLabel`, `metricAvailability`, 선택 해시를 계산한다. 빈 선택은 모든 KPI N/A, 광고만 선택하면 매출·이익·MER N/A, 판매만 선택하면 광고 전 이익이다. MER 실제 분모 0 처리는 06의 계산기 책임이다.
- `EXCLUDED_BY_USER`는 응답의 선택 메타데이터다. 원천 coverage 저장에는 넣지 않는다. 제외 플랫폼을 읽지 않고 표시를 만들며, 제외 원천의 누락/권한 오류는 선택 합계 품질을 악화시키지 않는다.
- `confidence=ESTIMATED`/`isEstimate`와 수치 계산 가능 여부를 분리한다. 네이버 추정치도 입력이 있으면 `completeAmount`를 제공할 수 있다. 입력이 없으면 null이다. 원천 정확도 증명을 위해 재수집을 강제하지 않는다.
- 원천별 정상 버전과 발행 포인터를 분리한다. 플랫폼·sourceSystem·scopeKey·업무일이 다른 실행을 같은 발행 포인터에 연결할 수 없다. 06은 조회 스냅샷에서 포인터 묶음과 `asOfBySource`를 읽는다.

01에 이미 같은 의미로 반영된 항목도 있지만, 코드의 버전·빈 선택·제외 표시·계산 가능 상태를 02에서 확정했다. 01이나 네이버 원천은 수정하지 않았다.

## 구현 위치와 저장 책임

`apps/api/src/unified-performance/types.ts`가 내부 공통 타입이다. `SourceRef`, `NameEvidence`, 판매/광고/공통비 사실, 수량·환율·비용 적용 근거, coverage, 대조합계, 어댑터 요청/응답, 집계 repository 경계를 제공한다. 원문 이름·원천 주문키·payload는 내부 자료이며 향후 공개 성과 API에 그대로 반환하지 않는다.

`adapter-contract.ts`는 어댑터의 1개 허용 범위·최대 92일·페이지 제한·선택 플랫폼을 확인한다. 원천 논리키는 sourceSystem+scopeKey+recordKind+sourceRecordKey의 해시다. 이름이 같아도 다른 주문은 유지한다. JSON 안 금액도 문자열/정밀도를 검증하며 누락 null을 그대로 둔다. 이 검증은 어댑터의 금액 보존 대조나 전체 업무 산식 검증을 대체하지 않는다.

원천 시각은 유효한 ISO8601 offset을 요구하고 Meta/Google의 공통비 사실은 거부한다. 배치의 논리키 중복 검사는 원천 정규화 직후, 06의 제품별 배분 확장 전에 적용한다. 06이 하나의 원천을 여러 귀속 사실로 나눌 때는 별도 파생 factKey와 원천 근거를 유지하고 배분합을 검산해야 한다.

Prisma 모델은 8개다. 계획상의 모든 모델을 별도 테이블로 만들지 않고 책임을 다음처럼 보존했다.

| 모델 | 책임 |
| --- | --- |
| UnifiedProduct | 기준명·정규화 유일키·활성·버전 |
| UnifiedRule | NAME/SALE_UNIT/ALLOCATION/SCOPE_POLICY별 검증된 JSON payload, 제품/플랫폼/범위/기간·버전 |
| UnifiedMappingAudit | 제품·규칙의 변경 전후 전체 설정, 변경자·사유·행위 |
| UnifiedAggregationRun | 원천·플랫폼·범위·일자별 실행, 입력/계산 버전·체크포인트·대조·상태 |
| UnifiedSourcePublication | 원천별 일자 발행 포인터·revision, 실행 partition 복합 FK |
| UnifiedDailyFact | SALE/AD_SPEND/COMMON_EXPENSE/SHIPPING_INCOME 분리, 금액·수량·귀속·내부 사실 payload |
| UnifiedSourceCoverage | 실행·구성요소별 수집/계산 근거와 추정 표시 |
| UnifiedProductMatchResult | 실행·논리 원천키·이름 해시별 판정과 전체 근거 |

금액 numeric(30,6), 수량 numeric(24,6), 비중 numeric(18,10)에 맞춰 문자열을 검증한다. 비중과 세부 비용은 typed JSON 경계에 보존한다. `domain/decimal.ts`는 독립 Decimal precision80/HALF_UP 생성자를 쓰며 기존 계산기의 전역 설정을 바꾸지 않는다. 원/소수6자리 배분에서 음수 정정과 결정적 잔여 배정을 보존한다.

제품명·제품별 판매단위·배분 정책은 내부 참조키를 쓰지만 플랫폼 상품 ID 입력은 요구하지 않는다. 결과의 제품명 스냅샷에는 카탈로그 FK를 걸지 않아 과거 결과를 현재 이름 변경으로 덮어쓰지 않는다. 네이버 public 테이블과의 FK나 Prisma 모델은 없다.

## 관리 API

기존 `/api` prefix 아래 다음 라우트를 추가했다. `UNIFIED_PERFORMANCE_ENABLED`가 정확히 `true`일 때만 동작한다. 기본 OFF이며 운영 role GRANT가 없으므로 11 이전 운영 활성화 대상이 아니다.

| 경로 | 동작·권한 |
| --- | --- |
| GET /unified-products | 기준제품 목록, data.read |
| POST /unified-products/preview | 정규화/별칭/배분참조/버전 충돌 검토, data.read |
| POST /unified-products | 생성, products.manage |
| PATCH /unified-products/:id | 수정·버전 증가, products.manage |
| DELETE /unified-products/:id | 감사 가능한 비활성화, products.manage |
| GET /unified-rules?kind=NAME | 종류별 목록, data.read |
| POST /unified-rules/preview | 충돌·영향기간·이름/판매단위 표본 진단, data.read |
| POST/PATCH/DELETE /unified-rules[/:id] | 규칙 생성/수정/비활성화, mappings.manage |
| GET /unified-products/:id/audit 및 /unified-rules/:id/audit | 최근 감사 기록, data.read |

규칙 kind는 NAME, SALE_UNIT, ALLOCATION, SCOPE_POLICY다. 별도 종류별 CRUD URL 대신 동일한 수명주기와 버전 검사를 사용하는 공통 경로를 선택했다. 수정/비활성화에는 `expectedVersion`, 모든 쓰기에는 `reason`이 필요하다. 유효일은 양끝 포함이며 wildcard 플랫폼/범위와 날짜의 교집합을 검사한다. 전역 feature advisory lock과 DB exclusion/unique 제약으로 동시 저장을 보호한다. 변경과 audit는 같은 트랜잭션이고 audit 실패 시 변경도 롤백한다.

미리보기는 PostgreSQL READ ONLY + RepeatableRead 트랜잭션이다. 쓰기 권한 없는 사용자도 검토할 수 있으며 저장은 guard와 서비스에서 거부한다. 미리보기는 임의 원천 조회가 아니라 최대 100개 제공 표본과 설정만 읽는다. 영향 금액은 아직 없는 원천 어댑터를 통해 계산했다고 주장하지 않는다. 영향 기간 및 분류·단위 후보를 제공하며 금액 영향 대조는 03~07에서 연결한다.

동일 predicate/겹치는 정확 별칭은 저장 충돌이다. 서로 다른 제품의 독립 포함어 규칙까지 문자열을 임의 결합해 전부 금지하지 않는다. 실제 표본이 여러 제품 조건을 만족하면 `AMBIGUOUS`로 진단한다. 같은 옵션이라도 판매단위명이 명시적으로 다르면 별도 규칙을 허용하되 단위를 지정하지 않아 복수 후보가 남으면 `UNIT_REQUIRED`이며 비용을 자동 선택하지 않는다.

현재 앱 권한은 workspace 전체 접근이다. Meta/Google/Cafe24 범위는 기존 SourceConnection의 provider를 확인하고 쿠팡은 확정 단일 업로드 범위만 허용한다. NAVER 설정 키는 형식만 검사하며 public 원천을 웹 role로 읽지 않는다. 05에서 허용 store 목록과 reader 연결을 검증한다. 이 관리 기반은 후속 조회의 scope 권한을 확대하지 않는다.

## 이름·이관·버전

`domain/product-name-resolver.ts`는 name-nfc-v1과 01의 정확/별칭→포함·제외·옵션/범위/기간→유일 후보 원칙을 구현한다. 비활성 제품도 유효한 명시적 역사 규칙으로 과거 분류가 가능하다. 이름이 없는 행과 복수 제품·단위 후보를 각각 구분한다.

`UnifiedManagementRepository.snapshot()`은 카탈로그와 규칙을 같은 스냅샷에서 읽고 각 payload/조건·범위·유효일·활성·버전을 해시한다. nameRuleVersion에는 카탈로그 변경도 포함한다. 이름 해시는 외부 상품 ID와 무관하며 이름·옵션·범위·일자·단위·규칙 변경으로 무효화한다. 원가/판매단위/배분 버전도 별도로 제공한다.

`legacy-name-migration.ts`의 플랫폼별 projection과 dry-run은 기존 우선순위·공백 제거·ID 제한 차이를 진단한다. 01의 실제 기준명 21개를 사용하며 카프슬리브와 쿨토시를 하드코딩 병합하지 않는다. 실제 저장은 관리 API를 통해 수행할 수 있지만 이번 단계는 운영 규칙을 이관하지 않는다.

## 격리 검증과 다음 구현 경계

`scripts/unified-foundation-postgres.mjs`는 %LOCALAPPDATA%/UnifiedPerformanceStage02 아래 새 PG17 클러스터를 만들고 127.0.0.1:55447/unified_stage02만 사용한다. 실제 host/database/current_user/PG17을 검사한 후 합성 표본을 쓴다. `unified_reader`, `unified_writer`, `unified_api`, `unified_config`의 실제 로그인으로 권한을 검증한다. 이들은 소유자·SUPERUSER·BYPASSRLS·CREATEDB·CREATEROLE가 아니다. 운영 자격증명/PII를 복제하지 않는다. public JSONB 12개 테이블과 필요한 날짜 인덱스는 합성 구조이며 운영 전체 스키마를 복원한 증거가 아니다.

02는 원천 어댑터/통합 집계/조회 화면을 구현하지 않는다. 03은 Cafe24/Meta/Google 어댑터에서 기존 source-read-policy를 재사용하고 본 공통 타입·이름/단위 규칙을 적용한다. 04·05는 같은 경계를 사용한다. 06은 `AggregationRepository`를 구현하며 필수 구성요소 준비, run READY 전환, 발행 후 실행/사실의 불변성, 포인터 CAS, 독립 원천 발행, 스냅샷 조회와 대조합계 보존을 완성해야 한다. 현재 DB trigger는 READY/PUBLISHED 상태와 coverage 존재만 확인하며 전체 집계기의 완결성을 대신하지 않는다.

운영 최소 권한·GRANT·RLS 정책·예약·배포는 10에서 준비하고 11에서만 적용한다. 현재 신규 테이블은 RLS/FORCE RLS 및 기존 공개/런타임 기본 권한 회수만 포함하고 운영 권한을 부여하지 않는다.

참고한 공식 지침: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [확장 버전 지정 변경](https://supabase.com/changelog/extension-version-pinning-ignored), [PG17.11 변경](https://supabase.com/changelog/postgres-15-19-17-11-breaking-changes). 신규 exclusion 인덱스는 문자열/날짜를 사용하며 float/NaN 인덱스가 아니다. 설치된 Prisma6 CLI `--help`를 기준으로 migrate diff/deploy를 사용했다.

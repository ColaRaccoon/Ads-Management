## 화면과 구현

화면 경로는 **`/products/mappings`**, 사이드바의 ‘제품 통합 → 제품명과 배분 설정’이다. 기존 Meta·Google·Cafe24·쿠팡 설정 화면과 계산 정책을 유지한다. 통합 KPI 대시보드는 추가하지 않았다.

- 고정 기준 제품명과 활성·버전을 조회하고, 제품 변경 미리보기 후 추가/수정/비활성 상태를 저장한다. `products.manage`와 `mappings.manage`를 구분한다.
- 저장된 NAME/SALE_UNIT/ALLOCATION/SCOPE_POLICY를 동일 설정 스냅샷으로 불러온다. 이름 원문·옵션 표본, 인식 제품·판매단위·사용 규칙·복수 후보·미분류 사유를 실제 미리보기 API로 확인한다. 외부 상품 ID 등록 필드는 없다.
- 이름 조건은 정확 별칭/전체 포함어/제외어/옵션/원문 필드/판매단위로 편집한다. 날짜 양끝을 포함하고 기간과 원천 범위를 구별한다.
- 단품·세트·옵션별 판매가·원가·배송·기타비·구성수량을 십진 문자열/null로 보존한다. 명시적 0과 미입력은 다르며 세트 전체 금액을 구성수량으로 다시 곱하지 않는다. 저장된 payload 전체도 펼쳐 확인할 수 있다.
- 공통 광고비·배송수입/비용·가구매/기타비의 미배분/고정비중/원천 매출비중을 관리한다. 직접 귀속을 공통비 규칙으로 덮어쓰지 않는 기존 worker 정책을 안내한다. 고정비중은 BigInt 소수 10자리로 정확 합계 1을 검사하고 서버에서 다시 검증한다.
- 규칙 변경 이력의 before/after와 사유를 조회한다. 이전 값을 현재 CAS 버전의 새 수정 초안으로 불러와 미리보기·저장하는 방식으로 복구한다. audit의 ISO 날짜는 date input용 날짜로 정규화한다.

### 기존 규칙과 비용

‘기존 이름 규칙 불러오기’는 원천별 실제 기존 API를 사용한다. 필요한 원천만 사용자가 불러오므로 이 조회 실패가 통합 설정 조회를 막지 않는다. 유일하게 정규화 일치하는 기준 제품명만 자동 선택한다. 이름 조건은 저장 전 검토 초안으로 재사용하며 ID-only·옵션-only·REGEX를 임의 이름 규칙으로 바꾸지 않는다. Cafe24 별칭 OR는 별도 초안으로 분리한다. 기존 우선순위·공백 제거·외부 ID 제한 제거·옵션 결합·불명확한 적용일·범위 확대 차이를 안내한다. 유효일이 없으면 KST 오늘을 초안에 넣고 검토하도록 표시한다.

기존 판매단위/비용의 자동 이관이나 운영 규칙 저장은 수행하지 않았다. 기존 설정 화면 링크에서 원가·비용 이력·적용기간을 손실 없이 확인하도록 유지했다. Google 자동 이름 목록은 전체이며 ID 기반 연결 참고 목록은 첫 100개 제한을 명시하고 자동 복사를 막는다. 네이버는 웹에서 public 원문을 읽지 않는다. 네이버 통합 규칙은 기존 통합 관리 API로 조회·편집한다.

## 금액 영향과 조회 선택 계약

`POST /api/unified-rules/preview`에 선택적 `impactFrom`, `impactTo`(함께, 최대 92일), `previewPlatforms` 배열을 추가했다. 생략 전체/빈 배열 전체 해제/정규화는 기존 플랫폼 계약과 같다. 미리보기 선택은 관리 규칙의 `platform` 필드와 별도이며 저장 payload에 포함하지 않는다. 빠른 선택 변경이나 표본/날짜/규칙 변경 시 전체 입력 키가 달라져 이전 결과로 저장할 수 없다.

미리보기는 설정과 허용된 원천 메타데이터·기존 발행 포인터·compact 사실만 같은 READ ONLY RepeatableRead transaction에서 읽는다. 원천 주문·광고행·JSONB·credential을 읽거나 worker/수집을 시작하지 않는다. 새로 추가한 `impact`는 다음 계약이다.

| 필드 | 의미 |
| --- | --- |
| `basis=PUBLISHED_SCOPE_REVIEW_TOTALS` | 보수적인 기존 발행 범위의 재검토 합계 |
| `from/to`, `selectedPlatforms/excludedPlatforms` | 금액 미리보기의 날짜·플랫폼 선택 |
| `affectedProducts` | 기준 제품과 해당 발행 사실의 역사 제품명을 포함한 재검토 후보 |
| `publishedRevenue/publishedAdSpend` | 선택된 변경 전·후 원천 범위의 기존 발행 금액 문자열/null |
| `publishedRows/unallocatedRows` | compact 사실 수와 제품 미지정 사실 수 |
| `zeroDenominator` | 매출비중 배분의 원천·계정·날짜별 대상 제품 순매출 분모가 없거나 비양수/음수 가중치/필수금액 누락 |
| `warnings` | 보수적 범위 합계·미발행·규칙 기간 밖 조회 안내 |

**이는 변경 전후 매출 증감 예측이나 재분류 확정액이 아니다.** 저장 사실은 원문 이름 대신 해시를 가지므로 정확한 변경 후 금액은 원천 전체 일별 worker 재집계로 확인한다. 화면에 이 한계를 명시한다. 미발행/모르는 금액은 null이며 0으로 채우지 않는다. 빈 선택은 원천 발행 조회 없이 null을 반환한다. 양수 기간합으로 특정 날짜의 0분모를 숨기지 않고, 같은 제품의 다른 판매단위 +100/-100도 순합으로 검사한다.

선택 범위를 꺼도 저장된 원래 비용 배분과 규칙은 변경하지 않는다. 설정 저장 이후 재집계는 변경 전·후 원천 범위 합집합을 사용하며 미리보기 체크박스에 종속되지 않는다. 조회/관리 분리를 검증했고 08의 대시보드 플랫폼 URL·차트·KPI UI는 구현하지 않았다.

RuleInput의 선택적 `expectedConfigurationVersion`은 미리보기 이후 다른 설정이 바뀐 경우 저장을 409로 거부한다. 개별 `expectedVersion` CAS와 동일 transaction audit를 유지한다. preview도 개별·전체 버전 충돌을 `canSave=false`로 반환한다. 저장 응답에는 `affectedScope{platforms,scopeKeys?}`를 추가하여 변경 전·후 범위를 보존한다. 기존 DELETE 경로의 Prisma CAS/동시수정 오류도 안전한 409로 변환했다. 환경에서 허용한 Meta/Cafe24 `LEGACY_UNBOUND` 범위를 관리 규칙에서도 사용할 수 있도록 일치시켰다.

## 중복·충돌·실패 복구

동기 ref 잠금과 disabled 버튼으로 중복 클릭을 막고, 저장은 규칙 CAS 및 미리보기 설정 해시로 보호한다. 403/400/409/503과 네트워크 결과 불명 상태를 구별하며 입력을 보존한다. 결과 불명 시 최신 설정·이력을 확인한 뒤 재저장하도록 안내한다. 충돌 후 최신 설정 조회가 편집 입력을 임의 덮어쓰지 않는다.

재집계는 같은 날짜/키로 재요청 시 동일 작업을 확인한다. 확정 실패/발행 이후 새 키의 실행 준비를 별도 버튼으로 제공하고, 92일을 넘는 영향기간은 날짜를 바꿔 구간별 요청한다. 복수 저장의 이전 영향 범위와 작업을 보존하여 전환할 수 있다. 현재 사용자별 sessionStorage에 요청 메타데이터를 보관하며 사용자 ID가 바뀌면 UI를 remount한다. 이 저장은 작업 자동 실행을 유발하지 않는다. 전체 영향기간 처리 전에는 완료라고 표시하지 않는다. 브라우저 세션 종료 후에는 이력을 다시 확인하고 필요한 기간을 요청하도록 설명한다.

worker는 06의 명시적 실행 계약을 유지한다. UI가 작업을 등록했다고 곧 발행됐다고 표시하지 않으며 QUEUED/READING/FAILED/PUBLISHED를 실제 API 상태로 확인한다. 운영 worker 예약·활성화는 11 범위다.

실제 HTTP로 401/403/400/409, 미리보기 무쓰기, 외부 ID 없는 이름 자동판정·복수/미분류, 동시 수정 1성공/1충돌, 전체 설정 CAS, audit 복구·비활성/재활성, 비용 0/null·비중 검증, 플랫폼 선택별 금액·빈선택, 이전/이후 범위, 재집계 멱등·FAILED 후 새 키 retry·worker PUBLISHED를 확인했다. 합성 데이터이며 운영 인증·운영 DB/화면 검증을 대신하지 않는다. 증거는 [07-management-postgres-result.json](../research/07-management-postgres-result.json)이다.

초기 fixture는 필수 SourceConnection 필드/발행 coverage와 tsx decorator metadata 누락으로 실패했다. 운영 연결로 우회하지 않고 fixture에 실제 필수값과 compiled Nest 동등 metadata를 제공한 뒤 최종 전체 통과했다. SSR 오류 상태 테스트도 React Query의 retryOnMount 때문에 loading으로 보였으며 test QueryClient만 retryOnMount=false로 고쳐 실제 오류 UI를 검증했다. 임시 SSR에서 JSX 설정이 맞지 않았던 실행은 기존 react-jsx test tsconfig로 정리했다.

브라우저의 마우스 클릭 기반 E2E/픽셀 검사는 수행하지 않았다. UI 검증은 실제 React SSR·상태모델 회귀·전체 Next 빌드이며, 실제 관리 흐름은 별도 HTTP+PG 통합 테스트다. 외부 실계정 로그인·운영 원천 이관·운영 권한·운영 재집계·배포는 10~11 검증/반영 범위다. 비밀값·주문 개인정보는 기록하지 않았다.

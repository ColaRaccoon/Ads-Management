# 제품 통합 데일리 보고 전체 제품 상세표와 엑셀 출력 계획

작성일: 2026년 11월 2일 한국시간  
범위: 추가 기능 설계. 구현과 운영 배포는 별도 작업이다.  
코드 확인 기준: 로컬 HEAD `9ccec31`. 다른 세션의 계산 결과 재사용 작업이 끝나면 변경된 계약을 다시 확인한다.

요청한 기능은 구현할 수 있다. 기존 데일리 요약 아래에 모든 제품의 플랫폼별 성과를 배치하고, 같은 데이터를 A4 상세표와 엑셀 파일로 출력한다. 상세표는 **제품 1열과 플랫폼별 3개 지표 15열을 합친 16열**이다. 금액과 전일 대비 증감률을 같은 셀에 두 줄로 표시한다.

권장 인쇄 구성은 **기존 A4 세로 요약 다음에 A4 가로 상세표를 이어 붙이는 방식**이다. 화면에서는 요약 아래에 표시하고, 종이에서는 상세표가 새 페이지에서 시작한다. 제품이 많으면 세로 방향으로 여러 장에 나누며 모든 제품을 한 장에 강제로 축소하지 않는다. 같은 세로 용지의 남은 하단에 16열을 넣는 것도 기술적으로 가능하지만, 기본 출력으로는 가독성이 부족하다.

데이터는 다른 세션이 준비하는 플랫폼별 계산 완료 결과와 통합 합계를 읽는다. 추가 기능은 조회할 때 주문·광고 원천을 다시 계산하거나 원가·수수료·광고비 배분을 재현하지 않는다. 표시용 전일 비교와 정렬·포맷만 맡는다.

## 1 요청 범위와 기본 동작

| 항목 | 설계 기본값 |
| --- | --- |
| 위치 | 제품 통합 성과 → 데일리 보고 → 기존 요약 아래 |
| 상세표 열 | 제품 / 자사몰 / 쿠팡 / 네이버 / 구글 / 전체 순서 |
| 그룹 안 지표 | 광고비, 매출, 순이익 순서. 각 금액 아래 증감률 표시 |
| 비교 | 보고일 D와 달력상 바로 전날 D−1. 한국시간 업무일 기준 |
| 제품 범위 | 전체 등록 제품과 D·D−1 발행 결과에만 남아 있는 과거 제품의 합집합 |
| 제품 숨김 | 광고비·매출 0원, 미수집, 비활성이라는 이유로 자동 제외하지 않음 |
| 제품 필터 | 상단 제품 선택은 기존 요약에 적용. 신규 상세표는 기본적으로 전체 제품 |
| 플랫폼·계정 | 현재 선택 및 사용자 접근 범위를 유지. 제외한 플랫폼의 열도 유지하고 ‘제외’ 표시 |
| 정렬 | 기준 제품명 오름차순으로 고정. 식별자가 같으면 한 행, 이름만 비슷하면 합치지 않음 |
| 출력 버튼 | 기존 요약 인쇄, 요약+전체 제품 인쇄, 전체 제품 엑셀 다운로드 |
| 전체 합계 의미 | 선택 플랫폼·계정 범위의 중복 제거된 통합 실적. 제한된 범위이면 제목에 명시 |

상단에 단일 제품이 선택돼 있어도 상세표 제목은 ‘전체 제품 상세’로 표시한다. 요약 제목은 선택 제품을 유지해 두 범위를 혼동하지 않게 한다. 단일 제품 요약과 전체 제품 상세의 총계가 같아야 한다는 검증은 적용하지 않는다. 전체 제품 요약을 선택한 경우에는 같은 범위·같은 발행 버전의 상세 총계와 대조한다.

한 제품의 단품·세트·옵션을 별도 제품 행으로 늘리지 않고 기존 기준 제품 매핑을 따른다. 판매단위가 별도 기준 제품으로 등록된 경우에만 별도 행이 된다. 제품명 변경을 추적할 내부 키는 제공받되, 플랫폼 상품 ID가 바뀌었다고 수동 재연결을 요구하는 구조를 만들지 않는다.

## 3 플랫폼별 금액과 전체 합계 계약

### 플랫폼 결과를 가져오는 기준

출력의 ‘자사몰·쿠팡·네이버·구글’은 **사용자가 각 플랫폼 화면에서 확인하는 결과 그룹**으로 정의하는 것이 요청 취지에 맞다. 데이터베이스의 `Platform` 열거형과 일대일이라고 가정하지 않는다. 특히 자사몰 그룹은 Cafe24 판매와 Meta 등 광고비의 기존 연결 정책을 함께 확인해야 한다.

| 출력 그룹 | 가져올 값 | 계약 확정 시 확인할 사항 |
| --- | --- | --- |
| 자사몰 | 자사몰 개별 성과 화면과 동일한 제품별 광고비·매출·순이익 | Meta 광고비 포함 범위, Google용 판매 구분이 자사몰에도 포함되는지 |
| 쿠팡 | 쿠팡 개별 계산의 최종 광고비·매출·순이익 | 수수료·배송비·쿠폰·기타 차감이 이미 반영된 최종 필드 |
| 네이버 | 네이버 개별 계산의 최종 광고비·매출·순이익 | 스토어 범위, DA 광고 포함 범위, 추정/미확정 상태 |
| 구글 | Google 개별 계산의 광고비·판매 기반 매출·최종 순마진 | 설정가 매출인지 실결제액인지, `[유튜브]` 판매 범위, 자사몰과 중복 여부 |
| 전체 | 다른 세션이 제공하는 제품별 통합 광고비·매출·순이익 | 판매·광고·공통비가 한 번씩만 반영된 권위 있는 통합 결과 |

계획 기본안은 **구글 그룹에도 개별 화면의 계산 완료 값을 그대로 출력**하는 것이다. Google Ads 전환가치를 판매 매출로 바꾸거나, 광고비에 임의 ROAS를 곱해 매출을 추정하지 않는다. 구글 결과가 아직 제공되지 않으면 해당 금액을 0원으로 채우지 않고 ‘미제공’으로 표시한다.

표 머리글은 요청한 ‘순이익’을 사용할 수 있지만 각 플랫폼의 원래 의미를 바꾸지는 않는다. 보고서 기준 설명에 ‘순이익은 각 플랫폼의 기존 계산 기준이며 추정·잠정 값을 포함할 수 있음’을 명시하고, 지표별 `isEstimate`·기준 설명을 보존한다. 서로 다른 매출 기준을 같은 경제적 금액처럼 합산하지 않는다.

### 전체 열과 합계 행

**제품 행의 전체 3개 값은 앞의 네 그룹을 화면에서 더해서 만들지 않는다.** 다른 세션이 제공하는 중복 제거된 제품별 통합 결과를 읽는다. 네 그룹이 완전히 배타적이라는 계약이 확인된 경우에만 그룹 합과 전체가 같아야 한다고 검증한다.

예를 들어 자사몰 매출 100만원 안에 구글용 판매 20만원이 이미 포함돼 있다면, 자사몰 100만원과 구글 20만원을 나란히 표시할 수는 있어도 통합 매출을 120만원으로 만들면 안 된다. 이 경우 전체 열과 그룹 합이 다른 이유를 ‘구글 판매 포함 관계’로 설명한다. 이는 예시이며 현재 운영 데이터가 반드시 이렇게 중복된다는 뜻은 아니다.

표 마지막에는 전체 제품의 합계 행을 둔다. 금액은 동일 스냅샷에서 제공한 합계를 사용하고, 합계 증감률은 **합계 당일 금액과 합계 전일 금액을 비교**한다. 개별 제품 증감률을 더하거나 평균 내지 않는다.

미분류 매출·미배분 광고비·공통비·배송수입 등 제품에 들어가지 못한 금액은 제품 행에 임의 배분하지 않는다. 제공된 통합 합계와 제품 소계의 차이를 표 아래 ‘제품 미귀속 금액’으로 지표별 표시한다. 금액 부호와 반영 기준을 포함한 대조 자료를 받아 `제품 소계 + 설명 가능한 미귀속 조정 = 통합 총계`가 성립하는지 확인한다. 미확인 금액이 있으면 부분 합계라고 표시한다.

### 다른 세션에 요청할 최소 계약

1. D·D−1 각각의 제품별 4개 출력 그룹 × 광고비·매출·순이익.
2. 같은 제품·기간·권한 범위의 중복 제거된 전체 3개 값과 전체 제품 총계.
3. 내부 제품 키, 기준 제품명, 활성 여부, 과거 제품 여부. 매핑·제품 목록 버전.
4. 지표별 확인 상태, 추정 여부, 원천 시점, 발행 버전, 미확인 사유.
5. 자사몰과 Google 판매·광고·이익의 포함 관계 및 합산 가능한 그룹 여부.
6. 미분류·미배분 금액을 설명하는 대조 정보.
7. 공개 조회가 원천 계산·재집계·쓰기 작업을 호출하지 않는 읽기 인터페이스.

이 계약 확정 전에도 표 컴포넌트, 합성 데이터 기반 인쇄, XLSX 확장은 진행할 수 있다. 실제 금액 연결은 계약을 받은 뒤 진행한다. 이미 새 계층에 같은 형태의 저장 결과가 있으면 재사용하고 별도 집계 테이블을 중복 생성하지 않는다.

## 4 조회 구조와 데이터 모델

권장 흐름은 다음과 같다.

```text
플랫폼별 기존 계산 완료 결과
          ↓ 다른 세션이 저장·발행
제품·업무일·계정별 조회용 결과와 중복 제거된 통합 합계
          ↓ D와 D−1을 같은 읽기 스냅샷으로 조회
전체 제품 상세 조회 응답
          ↓ 공통 표시 모델과 비교 정책
화면 상세표 ─ A4 인쇄 ─ XLSX 보고용 시트와 숫자 데이터 시트
```

조회 응답 예시의 명칭은 제안이며 기존 API에 이미 같은 기능이 있으면 합친다.

```ts
type OutputGroup = 'STOREFRONT' | 'COUPANG' | 'NAVER' | 'GOOGLE' | 'TOTAL';
type MetricKey = 'adSpend' | 'revenue' | 'netProfit';
type AmountState = 'COMPLETE' | 'PARTIAL' | 'UNAVAILABLE'
  | 'NOT_APPLICABLE' | 'EXCLUDED';

type PublishedAmount = {
  value: string | null;           // KRW 십진 문자열
  state: AmountState;
  isEstimate: boolean;
  reasonCodes: string[];
};

type ComparedMetric = {
  current: PublishedAmount;
  previous: PublishedAmount;
  change: string | null;
  changePct: string | null;       // 12.3이면 12.3퍼센트
  comparisonReason: string | null;
};

type ProductDailyRow = {
  productKey: string;
  productName: string;
  active: boolean;
  historical: boolean;
  groups: Record<OutputGroup, Record<MetricKey, ComparedMetric>>;
};
```

응답 전체에는 `contractVersion`, `reportDate`, `previousDate`, 실제 선택 플랫폼·계정, `selectionHash`, `snapshotHash`, 제품 목록 버전, 원천별 발행 버전·시각, `totalProducts`, `items`, `nextCursor`, 그룹별 기준 설명, 총계와 미귀속 조정을 둔다. `snapshotHash`는 D와 D−1의 원천별 발행 버전을 묶은 응답 버전이다. 날짜별 발행 run 자체가 동일해야 한다는 뜻은 아니다.

제안 경로는 `GET /unified-performance/daily-products?date=YYYY-MM-DD&...`다. 상세표 기본 조회에는 단일 `productName` 필터를 전달하지 않는다. 클라이언트가 보낸 계정 조건은 서버 접근 정책과 교차 검증한다. 빈 계정 선택 `[]`를 ‘전체 계정’으로 변환하지 않는다.

소규모 데이터는 한 번의 응답으로 전체 행을 반환하는 것이 단순하다. 큰 데이터에서 페이지 처리가 필요하면 서버가 제품 키 기준으로 제한해서 읽고, 커서에 선택 조건·스냅샷·정렬 기준을 묶는다. 각 페이지 요청마다 전체 원천 fact를 읽고 모든 제품을 계산한 뒤 배열을 자르는 방식은 사용하지 않는다.

인쇄·다운로드 전에는 모든 페이지를 수집하고 제품 키 중복, 수집 행 수와 `totalProducts`, 스냅샷 일치를 확인한다. 버전이 바뀌면 기존 페이지를 섞지 않고 처음부터 한 번 다시 읽는다. 계속 변하면 재조회 안내를 보여주고 불완전한 파일을 생성하지 않는다. 서버는 페이지 전후에도 권한을 확인한다.

기존 요약과 신규 상세를 한 번에 출력할 때는 같은 원천 발행 버전 집합을 사용한다. 하나의 읽기 응답에 요약·상세를 담는 방식을 우선 검토한다. 분리 API를 유지하면 전체 제품용 공통 스냅샷 토큰을 전달해 양쪽을 고정한다. 제품 선택이 다른 두 요청의 기존 `selectionHash`를 그대로 같다고 요구하지 않는다.

### 계산 책임의 경계

저장 전에 수행할 업무 계산은 원가·수수료·환율·쿠폰·배송비·광고비 배분·판매 중복 제거·플랫폼별 순이익 산출이다. 이는 다른 세션이 담당하는 계층에 남긴다.

신규 기능에서 가능한 연산은 이미 발행된 D와 D−1 금액의 차이·증감률, 정렬·표시 변환이다. 이를 공통 순수 함수로 한 번 생성해 화면·인쇄·엑셀이 공유한다. API가 이미 비교값을 제공하면 그대로 사용한다.

필터 조합마다 저장 결과의 합산이 필요하면 기존 조회 계층의 확정된 합계 인터페이스를 사용한다. 모든 플랫폼·계정 조합을 새로 사전 저장하거나, 신규 UI에서 플랫폼 순이익 공식을 다시 만들지 않는다. ‘업무 계산 재실행 금지’와 ‘저장 결과의 비교·선택 합산’은 별도 책임으로 계약에 적는다.

## 5 증감률과 결측값 표시

기본 공식은 `(당일 − 전일) ÷ 전일 × 100`이며 전일이 양수이고 두 금액이 확인됐을 때 사용한다. 금액 원본은 십진 문자열로 보존하고 기존 정확한 십진 연산 도구를 우선 사용한다. 반올림은 마지막 표시 단계에서만 한다.

| 상황 | 셀 표시 정책 |
| --- | --- |
| 전일 100, 당일 120 | `120` 다음 줄에 `(+20.0%)` |
| 전일 100, 당일 100 | `100` 다음 줄에 `(0.0%)` |
| 전일 양수, 당일 0 | `0` 다음 줄에 `(−100.0%)` |
| 전일 0, 당일 양수 | 당일 금액 다음 줄에 `(전일 0)`; 무한대·100%로 바꾸지 않음 |
| 전일·당일 모두 확인된 0 | `0` 다음 줄에 `(전일 0)`; 기존 0분모 정책 유지 |
| 전일 미확인 | 당일 금액 다음 줄에 `(전일 없음)` |
| 당일 미확인 | `—` 다음 줄에 `(자료 없음)` |
| 전일 순이익 음수 | 비율 대신 `(전일 음수)`. 흑자로 바뀌면 `(흑자 전환)` 가능 |
| 양수 이익에서 음수로 전환 | 유효한 증감률과 전환 상태 보존. 상세 기준/숫자 데이터에 ‘적자 전환’ 표시 |
| 일부 수집 | 확인된 금액에 `*`, 비교에도 `*`; ‘부분 금액 기준’ 범례 |
| 해당 없는 플랫폼 | `해당 없음` |
| 사용자 제외 플랫폼 | `제외` |

전일 자료가 없다고 D−2 등 다른 날짜로 대체하지 않는다. 보고일이 오늘이면 잠정 자료 표시를 유지한다. 최신 발행일은 선택 범위의 조회 기준일일 뿐 모든 원천의 수집 완료를 뜻하지 않는다.

증감률 표시는 상세표·엑셀에서 소수점 한 자리로 제안한다. 아주 작은 변화가 반올림되어 0.0%가 되는 것은 허용하되 음수 0.0% 표시는 정규화한다. 원본 비교값은 숫자 데이터 시트에 보존한다. 기존 요약의 정수 퍼센트 표시는 기존 정책을 유지하며, 출력별 반올림 자리 차이를 기준 설명에 적는다.

색만으로 의미를 전달하지 않는다. `+`, `−`, 상태 문구를 함께 사용한다. 광고비 증가를 이익 개선처럼 표현하지 않고, 상승·하락 색은 변화 방향만 뜻한다고 설명한다.

## 6 화면과 A4 인쇄 설계

### 16열 구조

| 열 | 그룹 | 세부 열 |
| --- | --- | --- |
| A | 제품 | 기준 제품명 |
| B–D | 자사몰 | 광고비(증감%), 매출(증감%), 순이익(증감%) |
| E–G | 쿠팡 | 광고비(증감%), 매출(증감%), 순이익(증감%) |
| H–J | 네이버 | 광고비(증감%), 매출(증감%), 순이익(증감%) |
| K–M | 구글 | 광고비(증감%), 매출(증감%), 순이익(증감%) |
| N–P | 전체 | 광고비(증감%), 매출(증감%), 순이익(증감%) |

2단 머리글을 사용한다. 상단은 플랫폼별 3열 병합, 하단은 광고비·매출·순이익이다. 금액 셀은 첫 줄 `1,250,000`, 둘째 줄 `(+12.3%)`처럼 표시하고, 표 상단에 ‘금액 단위: 원’을 한 번 적는다. 전체 그룹은 배경색과 왼쪽 경계선으로 구분한다.

화면은 가로 스크롤을 허용하고 제품명 열과 머리글을 고정한다. 화면까지 인쇄용 7pt 글씨를 강요하지 않고 11~12px 정도부터 확인한다. 로딩 상태, 전체 제품 수, 출력 준비 완료 여부를 표시한다.

### 인쇄 레이아웃 제안

| 항목 | 초기 설정 |
| --- | --- |
| 요약 | 기존 A4 세로 유지 |
| 상세 | A4 가로 297 × 210mm, 별도 새 페이지 |
| 상세 여백 | 좌우 8mm, 상하 10mm부터 검증 |
| 사용 폭 | 281mm. 제품명 32mm, 나머지 15열 약 16.6mm씩 |
| 글자 | 금액 7pt, 증감률 6.5~7pt, 머리글 7~8pt부터 검증 |
| 행 | 금액·증감률 2줄. 제품명 길면 필요한 만큼 행 높이 증가 |
| 반복 | 2단 표 머리글 반복, 제품 행은 페이지 중간에서 나누지 않음 |
| 마지막 | 총계, 미귀속 조정, 단위·기준·상태 범례 |

위 크기는 시제품 시작값이다. 큰 금액·긴 제품명·3자리 이상 증감률로 실제 PDF를 렌더링해 조정한다. 금액 자릿수 때문에 6pt 이하로 계속 축소하지 않는다. 필요하면 모든 금액에 공통 적용되는 ‘천원 단위’ 선택을 추가하고 반올림 단위를 명확히 적는다. 제품마다 단위를 다르게 바꾸지 않는다.

이름 있는 `@page`와 CSS `page` 속성을 사용하면 섹션별 용지 방향을 지정할 수 있다. 요약은 portrait, 상세는 landscape로 분리하고 상세 시작에 명시적 페이지 나눔을 둔다. 대상 브라우저·PDF 출력·프린터 드라이버에서 혼합 방향을 검증한다. [MDN 이름 있는 페이지](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@page#named_pages), [MDN page 속성](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/page).

현재 스타일의 `th:first-child { width:26% }`는 새 표에 적용하지 않고 `colgroup`으로 폭을 정한다. 기존 섹션의 `break-inside:avoid`도 상세표 전체에는 적용하지 않는다. 행 단위 나눔 방지와 머리글 반복만 적용한다. 인쇄 시 스크롤 컨테이너의 `overflow`, 고정 높이, sticky 위치를 해제한다.

현재 요약의 `A4 · 1 page` 문구는 실제 출력 범위를 반영하도록 수정한다. 제품 수와 긴 기준 문구 때문에 페이지 수가 늘어날 수 있으므로 전체 보고서를 1페이지라고 고정하지 않는다.

혼합 방향 인쇄가 특정 환경에서 실패하면 ‘요약 인쇄’와 ‘상세표 인쇄’를 분리 제공한다. 하나의 파일이 반드시 필요하면 후속 단계에서 페이지별 방향을 고정하는 PDF 생성 방식을 검토한다. 첫 구현부터 별도 PDF 서버를 도입할 필요는 없다.

### 인쇄 준비 상태

인쇄 버튼은 전체 행이 준비되고 스냅샷 검증이 끝난 후 활성화한다. `beforeprint`에서 비동기 조회가 끝나기를 기대하지 않는다. 화면에서 가상 스크롤을 쓰더라도 인쇄용 DOM에는 전체 행을 렌더링한다. 숨긴 인쇄 영역은 준비 중이라고 전체 앱을 함께 숨기는 일이 없도록 별도 출력 모드를 사용한다.

## 7 엑셀 파일 설계

다운로드 파일명 예시는 `제품통합_데일리_전체제품_2026-11-02.xlsx`다. 다운로드는 화면에서 확인한 같은 스냅샷을 사용하고, 파일명에 날짜, 시트 상단에 보고일·비교일·조회 범위·작성 시각·발행 기준을 넣는다.

### 보고용 시트

첫 시트 이름은 ‘전체 제품 데일리’로 한다. 요청한 A:P 16열을 그대로 사용하고 플랫폼 머리글을 병합한다. 금액과 증감률을 한 셀의 두 줄 문자열로 넣어 인쇄 표와 같은 모양을 만든다. 정렬·계산용 숫자를 결합 문자열로 오인하지 않도록 둘째 시트를 함께 제공한다.

기본 글꼴은 8pt부터 확인하고 필요하면 7pt로 조정한다. 줄바꿈, 열 폭, 행 높이, 얇은 격자, 전체 그룹 강조를 설정한다. A4 가로, 인쇄 영역 A:P, 가로 1페이지 맞춤, 세로 자동 다중 페이지, 반복 머리글 행, 첫 열·머리글 고정을 지원한다. 세로까지 1페이지에 맞춰 모든 제품을 극단적으로 축소하지 않는다. Open XML은 용지 방향과 가로·세로 페이지 맞춤 속성을 제공한다. [Microsoft PageSetup 문서](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.spreadsheet.pagesetup?view=openxml-3.0.1).

### 숫자 데이터 시트

둘째 시트는 재가공·검산용으로 제품 × 그룹 × 지표별 행을 사용한다. 일반 제품당 15행이며, 인쇄 대상 제품 목록의 모든 그룹·지표를 보존한다.

`제품키 / 제품명 / 그룹 / 지표 / 당일 금액 / 전일 금액 / 증감액 / 증감률 / 당일 상태 / 전일 상태 / 비교 사유 / 추정 여부`를 기본 열로 두고 필터를 적용한다. 합계·미귀속 조정은 제품 데이터와 구별된 별도 영역에 둔다. 전체 원천 개인정보나 주문내역은 넣지 않는다.

일반 범위 금액은 숫자 셀, 증감률은 비율 숫자 셀로 내보낸다. 예를 들어 API의 `12.3`퍼센트는 Excel에 `0.123`을 저장하고 `0.0%` 서식을 준다. 미확인은 빈 숫자 셀과 상태 열로 표현한다. 큰 금액이나 정밀 소수처럼 Excel 숫자 표현에서 원본 정밀도를 지키기 어려운 경우는 텍스트 원본으로 보존하고 정밀도 상태를 함께 표시한다. 무조건 `Number()`로 변환하지 않는다.

### 공용 생성기 변경 범위

현재 `xlsx.ts`에는 다음 기능을 선택 옵션으로 추가해야 한다.

| 확장 | 목적 |
| --- | --- |
| 다중 시트 입력 | 보고용과 숫자 데이터 시트를 같은 파일에 제공 |
| `fontSize` | 11pt 고정 해제. 새 보고서만 작은 글씨 적용 |
| 인쇄 방향·용지·여백 | A4 가로 상세표 |
| 가로·세로 페이지 맞춤 | 가로 1장, 세로 자동 |
| 인쇄 영역·반복 머리글 | A:P 출력 및 페이지별 머리글 |
| `freezeColumn` | 제품 열과 머리글 동시 고정 |

인쇄 영역·반복 행은 workbook의 defined names, 페이지 설정은 worksheet 쪽 등 실제 Open XML 위치와 관계 파일을 함께 처리한다. 기존 단일 시트 호출과 11pt 기본값을 유지하는 호환 입력 형태를 설계한다. `safeExportCellValue` 등 기존 외부 문자열 보호를 유지하며 제품명을 실행 가능한 수식으로 내보내지 않는다.

공용 생성기 확장 때문에 기존 Meta·쿠팡·Google XLSX가 달라지지 않도록 기본 호출 결과와 새 옵션 호출을 함께 검증한다. 작은 인쇄 기능 하나를 위해 새 라이브러리를 바로 추가하기보다 기존 생성기의 확장 난도와 회귀 범위를 먼저 평가한다.

| 영역 | 적용 방법 |
| --- | --- |
| 조회 기간 | 데일리 상세는 D·D−1만 읽음. 화면의 장기 분석 기간을 따라 전체 이력을 읽지 않음 |
| 요청 횟수 | 제품마다 개별 API를 호출하지 않음. 여러 플랫폼 계산 API를 조회 시점에 연쇄 호출하지 않음 |
| DB 읽기 | 발행 완료 결과의 제품·날짜·계정·그룹·3개 금액·상태 중심으로 투영. 원천 주문·대형 checkpoint 제외 |
| 인덱스 | 실제 저장 스키마 확정 후 권한/계정 범위·업무일·발행버전·제품 키 조건에 맞춰 실행계획 확인 |
| 메모리 처리 | 제품 키 Map으로 두 날짜 결합. 매 제품마다 전체 데이터 `filter/find` 반복 금지 |
| 총계 | 발행된 총계·기존 조회 계층의 합계를 읽음. 플랫폼 계산식 재실행 금지 |
| UI | 순수 표시 모델을 메모이제이션. 정렬·단위 변경은 재조회 없이 처리 |
| 출력 | 조회한 공통 결과를 화면·인쇄·XLSX에 재사용. 다운로드를 위해 플랫폼 데이터를 다시 읽지 않음 |
| 동일 요청 | 진행 요청 공유를 재사용. 완료 응답 캐시는 크기·건수·TTL을 제한 |
| 캐시 식별 | 사용자/권한 범위, 실제 계정·플랫폼, D·D−1, 제품 목록·계산·발행 버전, 계약 버전 포함 |
| 무효화 | 발행 갱신, 제품 매핑 변경, 권한 변경, 로그아웃, 수동 새로고침 시 해당 캐시 폐기 |
| 실패 처리 | 이전 성공본을 쓰는 경우 시각·오래된 자료 상태 표시. 조용히 최신 결과처럼 출력하지 않음 |

통신의 중복 제거와 데이터 신선도는 별개다. 짧은 `staleTime`만으로 다른 플랫폼의 발행 버전까지 일치한다고 보지 않는다. 발행 메타데이터 확인 또는 서버 버전 토큰을 사용한다. 출력 중에는 선택 스냅샷을 고정한다.

이미 플랫폼별 결과 저장이 준비되면 초기 기능에 별도 워커·Redis·다운로드 작업 큐를 추가하지 않는다. 1,000제품은 16,000개 표시 셀이므로 이를 기준으로 측정한 후 화면 가상 스크롤·Web Worker XLSX 생성 등을 결정한다. 처리 한도를 넘으면 행을 조용히 잘라 내지 않고 전체 출력 경로 또는 명시적인 안내를 제공한다.

측정용 데이터는 100·1,000·5,000제품으로 준비한다. DB 시간, API 전체 시간, 전송 크기, 브라우저 처리 시간, XLSX 생성 시간, 최대 메모리, 전체 제품 수 일치를 기록한다. 제품 수가 늘어나도 금액 조회 횟수가 제품 수에 비례해 늘지 않아야 한다.

초기 목표는 고정된 검증 환경에서 1,000제품의 상세 API p95 2초 이내, 데이터 수신 후 XLSX 생성 3초 이내로 잡는다. 이는 실측 결과나 보장이 아닌 개발 목표이며, 실제 운영 환경·금액 문자열 길이·다중 시트 크기로 측정해 조정한다. 프린터와 인쇄 대화상자 동작 시간은 API 성능에 포함하지 않는다.

## 9 구현 순서와 파일 소유권

| 단계 | 작업 | 완료 조건 |
| --- | --- | --- |
| 1 | 다른 세션 결과 계약 연결 | 그룹별 금액 필드, Google 포함 관계, 통합 합계, 상태·버전 계약 확보 |
| 2 | 비교·표시 모델과 16열 명세 | 합성 입력으로 행·열·결측·전일 비교 고정 |
| 3 | 전체 제품 읽기 API | 두 날짜·전 제품·권한·버전·완전 수집 검증, 원천 계산 호출 없음 |
| 4 | 화면과 인쇄 상세표 | 기존 요약 아래 표시, A4 가로 다중 페이지, 마지막 제품까지 출력 |
| 5 | XLSX 공용 기능과 내보내기 | 16열 보고용+숫자 데이터, 작은 글씨·인쇄 설정, 기존 내보내기 회귀 없음 |
| 6 | 금액 대조와 성능·시각 검증 | 아래 인수 기준 충족, 변경 파일·검증 결과·남은 제한 기록 |

1단계와 병행 가능한 작업은 합성 데이터로 수행하는 2단계·4단계 시제품·5단계 생성기 확장이다. 플랫폼별 계산 저장이나 통합 총계 정의를 이 기능 구현 세션에서 동시에 다시 설계하지 않는다.

| 파일 영역 | 제안 담당과 변경 원칙 |
| --- | --- |
| 기존 계산·저장·발행·공유 스키마 | 현재 계산 결과 재사용 세션이 담당 |
| `daily-products-contract.ts` 등 신규 전용 계약 | 두 작업의 경계를 먼저 확정한 뒤 단일 담당 |
| `daily-products.repository.ts`, `daily-products.service.ts` 등 | 새 조회 인터페이스가 필요할 때만 추가. 기존 결과 조회 계층을 얇게 감쌈 |
| `daily-products-model.ts`, `daily-products-table.tsx`, `daily-products.css` | 신규 추가 기능 담당 |
| `daily-products-xlsx.ts` | 신규 추가 기능 담당 |
| `daily-report.tsx`, `daily-report.css`, 공통 `types.ts`, 모듈 등록 | 다른 세션 변경 반영 후 연결 부분을 작은 수정으로 통합 |
| `apps/web/src/lib/xlsx.ts` | 담당 한 명이 호환 확장, 기존 export 사용처 대조 |

파일명은 제안이며 작업 시작 시 실제 다른 세션 결과를 확인해 조정한다. 이 문서는 기존 번호 단계의 수행 기록이 아니므로 기존 진행표·완료 상태를 변경하지 않는다. 구현 시점에 관련 AGENTS.md와 현재 작업 규칙을 다시 적용한다.

## 10 검증과 인수 기준

| 구분 | 필수 검증 |
| --- | --- |
| 플랫폼 일치 | 같은 제품·날짜·계정·발행 버전에서 4개 그룹의 3개 금액이 기존 개별 화면의 결과와 일치 |
| 통합 일치 | 전체 열이 제공된 통합 결과와 일치. 중복 판매·광고비·공통비를 다시 합산하지 않음 |
| 제품 누락 | 0원·미수집·비활성·전일에만 존재·과거 제품·첫/마지막 페이지 제품 포함 |
| 매핑 | 동명이지만 다른 키, 이름 변경, 여러 판매단위, 플랫폼 상품 ID 변경 처리 |
| 날짜 | 월·연도 경계, 윤일, 한국시간 자정, D−1 없음. 이전 관측일로 대체하지 않음 |
| 비교 | 0분모·음수 이익·흑자 전환·적자 전환·부분 금액·큰 정밀 금액·반올림 경계 |
| 합계 | 증감률 평균 금지. 제품 소계·미귀속 조정·전체 합계 대조 |
| 스냅샷 | 페이지 중 발행 갱신, 요약/상세 버전 불일치, 요청 취소, 연속 재조회 경쟁 |
| 권한 | 허용 계정만 조회. 권한·계정이 다른 사용자 사이 캐시 공유 금지 |
| 인쇄 | Chrome/Edge의 실제 대상 버전, PDF 저장, 사용하는 프린터. 첫·중간·마지막 페이지 확인 |
| 인쇄 내용 | 16열 유지, 한글·긴 이름·큰 금액 잘림 없음, 반복 머리글, 빈 페이지·행 중간 분리 없음 |
| XLSX | Excel에서 복구 경고 없이 열림. 시트·병합·글꼴·숫자 타입·비율·인쇄 영역·반복 행 검증 |
| 기존 기능 | 기존 요약 단독 인쇄, 제품 필터, 날짜 이동, 부분 자료 경고, Meta·쿠팡·Google XLSX 유지 |
| 성능 | 두 날짜·저장 결과만 읽는 경로, N개 제품에 N개 계산 호출 없음, 목표 규모 측정 |

0·1제품, 페이지 경계 바로 전/후 제품 수, 100·1,000·5,000제품을 사용한다. 단순 함수 테스트로 페이지 잘림을 판정하지 않고 PDF 렌더링과 실제 엑셀 인쇄 미리보기를 확인한다. 모든 제품이 출력됐는지는 마지막 페이지 육안 확인뿐 아니라 제품 키 집합과 총 행 수로 검증한다.

완료는 화면에 표가 보이는 시점이 아니라 **금액 원천 일치, 전체 제품 누락 없음, 전일 비교 정확성, 인쇄 가독성, 엑셀 활용성, 기존 기능 회귀 없음**이 모두 확인된 시점이다.

## 11 구현 시작 시 사용할 합의안

추가 질문 없이 진행 가능한 설계 기본값은 ‘화면 하단에 전체 제품 표, 요약 뒤 A4 가로 부록, 16열, 금액·증감률 두 줄, 보고일 대비 전일, 보고용+숫자 데이터 XLSX’다. 같은 세로 종이의 남은 하단에 반드시 들어가야 한다는 추가 요구가 생기면 레이아웃만 별도 검토한다.

구현 착수 전에 기술적으로 확정할 핵심은 **자사몰·Google의 포함 관계와 기존 계산 결과를 읽는 인터페이스**다. 기존 코드와 다른 세션의 결과에서 확인 가능한 내용부터 확정한다. 서로 다른 업무 정의 중 사용자의 선택이 필요한 경우에만 그 차이를 구체적인 금액 예시로 설명한다.

다음 구현 세션의 시작 지시는 다음과 같이 사용할 수 있다.

```text
이 계획서에 따라 제품 통합 데일리 보고에 전체 제품 16열 상세표와
A4 가로 부록 인쇄, XLSX 다운로드를 구현해줘.
먼저 다른 세션의 플랫폼별 계산 완료 결과 조회 계약을 확인하고 재사용해줘.
조회 시 원천 계산·비용 배분·통합 합계 계산식을 새로 만들지 마.
자사몰과 구글 판매의 중복 관계를 확인하고 전체 열은 제공된 통합 합계를 써줘.
현재 다른 세션 변경을 보존하고 신규 모델·표·출력 파일부터 구현한 뒤 연결해줘.
모든 제품 수집, 전일 비교, 발행 버전, A4 페이지, XLSX 숫자·인쇄 설정을 검증해줘.
```
